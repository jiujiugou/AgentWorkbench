# 底座与 MAF 功能对照

- **适用侧**：公共 ｜ **寿命**：长期（MAF 大版本或方向变时才改）｜ **最后校准**：2026-11-19
- **回答**：Agents 领域逐项功能取什么、放弃什么、为什么
- **不回答**：MAF 原文（查官方页，地址在文末）；哪个类在哪（查 `docs/core/`）；逐格判据（查 `Sxx` 测试）

一句话：MAF Agents 是一张能力目录，不是必选项清单。本项目只取「能让一次受控 run 跑起来」的最小子集，其余显式放弃——**放弃的理由比取用的理由更重要**。

> 怎么读：一回答为什么底座选 Agents；二是主体，按官方页面原顺序逐项对照；三把放弃理由归成四类；四是边界与一处待核。
> 本文只做解释，不是事实源、不驱动门禁。行为判据在测试里。

## 一、为什么底座选 Agents

三个理由，一个是官方的，两个是本项目的：

1. **四个领域里只有 Agents 同时提供三样东西**：统一 run 接口、会话状态载体、三层可拦截管道。Harness 是拼出来的、Workflows 是显式图、Integrations 是目录——它们都不提供"模型请求进来时能拦一道"的通用入口。
2. **方向句要求唯一入口**。*"拿掉模型还能安全拒绝"* 的前提是：所有请求都经过同一个能挂判定的点。代码里的这个点就是 `agent.RunAsync` / `agent.RunStreamingAsync` 两行，其余判定挂在它们下游。
3. **依赖范围可核对**。`Microsoft.Agents.AI` 只进 Context / Session / Harness 三个 Core 项目；其余用 `Microsoft.Extensions.AI`。agent 抽象没有扩散到工具、领域、实现层——这就是"底座"在编译期能指出来的位置。

结论：**Agents 是四个领域里唯一原样用的，但只取它的对象和接口，不取它的 middleware 管道。**

## 二、逐项对照（按官方 `concepts/agents/` 页面顺序）

### 1. 开场定义：七个部件

> 官方原句：*"将代理抽象、模型或远程代理连接、指令、工具、中间件、上下文提供程序和会话状态组合在一致的运行接口后面"*

| 官方部件 | 取 / 舍 | 为什么 |
|---|---|---|
| 代理抽象 | **取** | 编排层只认这一个接口，换模型/provider 不动业务代码 |
| 模型连接 | **取**（仅模型） | 远程代理连接不取：身份与权限若由外部 agent 定义，就破坏"身份只当不透明字符串 + 对象级权限" |
| 指令 | **取** | 走 `ChatOptions.Instructions`，每轮下发、不进会话历史；只设一次（两级都设会拼接重复） |
| 工具 | **取**（仅函数工具形态） | 清单先过白名单裁剪；调用必须走 `FunctionInvoker` 的判定序列，不是框架直调 |
| 中间件 | **取一层**（chat client 层） | agent middleware 层与 context provider 层都不取，理由见第 6 小节 |
| 上下文提供程序 | **舍** | 它在工具环之外注入，拆掉守卫与轨迹；指令改用框架原生的 `Instructions`（见 [请求装配](core/请求装配.md)） |
| 会话状态 | **取** | `AgentSession` 的建 / 序列化 / 反序列化全用；本仓只负责给 session 贴 id |

### 2. 运行时和执行

| 官方项 | 取 / 舍 | 为什么 |
|---|---|---|
| `RunAsync` / `RunStreamingAsync` | **取** | 两条出口各调一个，但准备、预算、守卫、归类、落库、写回合并成一份 `RunCoreAsync`——差别只在产出形态 |
| 运行选项（`AgentRunOptions`） | **几乎不取** | 官方自己说"自定义抽象级别的运行能力相当有限，代理差异太大，没有真正通用的自定义选项"。本项目 agent 级一次装配，run 级只带模型参数，不带指令 |
| 响应 / 消息 / 内容类型 | **取三类** | `FunctionCallContent`、`FunctionResultContent`、`UsageContent`——工具调用、回填、计量，正是要落轨迹的三种。图片、代码解释器、shell、OAuth 同意等类型与本格无关，不解析 |
| 代理管道（三层） | **取一层** | 只把工具环挂在 `IChatClient` 层；执行流的其余步骤用框架默认 |
| 运行时模型路由 | **舍** | 一次 run 中途换模型会改变"模型看到什么"的口径，轨迹无法重建；当前无此需求 |

### 3. 代理类型

| 官方项 | 取 / 舍 | 为什么 |
|---|---|---|
| 自定义代理 | **舍** | 没有自写 `AIAgent` 的必要，统一抽象已够；自写等于另开一条不受统一 run 接口约束的路 |
| 模型提供程序 | **取** | 把应用自有的 agent 接到推理服务，就是本项目的模型解析层 |
| 代理服务（远程）/ 直接代理类型 | **舍** | 外部 agent 不替我们定义身份、权限、数据模型；碰真系统靠 MCP + 适配器，不靠远程 agent |

### 4. 聊天客户端代理

| 官方能力 | 取 / 舍 | 为什么 |
|---|---|---|
| 函数工具 | **取形态，换执行** | 模型能看见工具 ≠ 模型能执行工具；调用一律过四道闸后再执行 |
| 多轮对话 | **取** | session + history provider 支撑，跨 run 的历史由本仓 provider 落库 |
| provider 托管工具 | **舍** | 执行发生在 provider 侧，本地守卫与轨迹看不到，等于把判定权外包 |
| 结构化输出 | **舍** | 唯一结构化出口是 `propose_action`——动作必须经闸，不能被"模型返回结构化对象"绕过 |
| 流式 | **取** | 实时通道需要增量；与一次性出口共用同一套判定 |
| 本地 / 服务管理的历史 | **取本地** | 落库版由本项目 provider 实现，服务托管历史不属受控面 |
| `open()` / `close()` 管 MCP 资源 | **舍**（形态不同） | C# 侧由 hosted service 管 MCP 连接生命周期，不随单次 run 开关 |

### 5. 对话和内存

| 官方项 | 取 / 舍 | 为什么 |
|---|---|---|
| 会话 `AgentSession` | **取** | 建、序列化、反序列化；`JsonSerializerOptions` 必须传 null（本仓实测，官方未写） |
| 上下文提供程序 | **舍** | 同第 1 小节：会拆掉执行控制 |
| 存储 | **取自己的** | 自建会话存储 + 落库 history provider，不用官方抽象——多一层同构接口，改一次要动两处 |
| 压缩（compaction） | **舍** | 撞①红线；代价是模型可见历史全量、无 token 上限，如实登记在 [状态与记忆](core/状态与记忆.md) |
| 内置聊天历史内存提供程序 | **只取默认** | 无存储环境用内存版；落库版由实现层 `Replace` 覆盖 |

### 6. Middleware（官方八项）

| 官方项 | 取 / 舍 | 为什么 |
|---|---|---|
| 定义 / 范围 / 排序 / 共享状态 / 运行时上下文 | **用默认** | 不自加 agent middleware 层——那是官方的展开点，不是本项目的判定点 |
| 终止 | **取语义，换层** | 守卫命中设 `Terminate`，实现在 chat client 层的 `FunctionInvoker`，不在 agent middleware |
| 错误 | **取语义，换层** | 异常归类写进轨迹，不靠框架默认错误路径 |
| 结果替代（result overrides） | **取语义，换层** | 拒绝时回填结构化载荷给模型，属于工具调用的配套动作，不属于 agent 级中间件 |

> 前一轮图里写"Middleware 借三项"容易读成"官方只有三项"。准确说法是：**八项里只用三项的语义，且换了一层实现。**

### 7. Safety

| 官方项 | 取 / 舍 | 为什么 |
|---|---|---|
| 验证函数输入 | **取为模式** | 白名单 + 类型/范围/长度约束；判定由本仓做，不交给模型 |
| 高风险工具审批 | **取模式，换实现** | 官方默认工具直调；本项目四道闸 + fail-closed，判定来自规则与外部审批人 |
| 系统消息可控 / 扩展审查 / 输出清理 / 日志脱敏 / 会话保护 | **取为模式** | 这些是边界纪律，不产生新的机制 |
| 资源限制 | **自己做** | 官方明说框架不施加长度与速率约束——它不知道你的场景合理值 |
| FIDES（标签化信息流控制） | **舍** | 确定性防御很好，但判定来源是标签，不是四道闸 + 业务规则 + 外部审批人；不是等价物 |

## 三、放弃的理由归成四类

1. **会拆掉执行控制**：context provider、agent middleware 层。注入发生在工具环之外，守卫与轨迹都失效。
2. **扩大副作用面**：压缩、自动记忆注入、文件访问、后台代理、shell、web search、skills。官方 Harness 的目标是"让 agent 更能干"，本项目方向相反。
3. **判定权不能外包**：官方默认 tool approval、provider 托管工具、远程 agent、FIDES。它们都能"安全"，但安全的依据不在我们手里。
4. **官方明确不管**：外部服务的认证 / 加密 / 连接细节、输入与输出长度、速率限制。官方安全页原话：*"代理框架不管理这些服务的身份验证、加密或连接详细信息"*、*"代理框架不会对输入/输出长度或请求速率施加约束"*。这不是缺口，是分工。

## 四、边界与一处待核

- 本文不替代 [三条主线落地概念](三条主线落地概念.md)（三种决定权）、`docs/core/*.md`（机制与验收）、`Sxx`（行为判据）。
- 官方能力名与页面结构会随版本变，核对以官方页为准；本表不写行号，定位用名字搜。
- **待核**：官方管道页提到一种可选的 agent hooks，说它能跨 agent / chat / function 层装一个中间件捆绑包，并让"输出在相关裁决允许前不被发布或存储"。这与本项目"未审批零外部调用"形状很近，本轮只读到概述、未读完能力细节，先登记不判定。读完后若它能覆盖业务规则与外部审批人，才谈得上替换；否则只是又一个官方形态。
