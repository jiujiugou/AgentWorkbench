## 0. 一句话结论

> 底座六能力域的正确性**几乎全是布尔可判定**的——超时是不是超时、白名单外的工具可不可见、跑满迭代与答完能不能区分、取消与失败会不会混。
>
> 因此：**判据自建（确定性），MAF 只承担三件事**——批量场景驱动（`LocalEvaluator` + `EvalChecks`）、断言容器（`AssertAllPassed`）、指标留存与趋势（`Reporting`）。
>
> MAF 的 12 个 Quality 裁判（全部需要 `ChatConfiguration` = LLM judge）**在底座里没有位置**：它们属于《标准》§1.1 的第 3 档（无金标开放文本质量），而底座六域全部落在第 1、2 档。**档位不同，不可互换。**

## 3. 六能力域评测矩阵（本文主体）

每域三张表：**A 判定型不变量**（正例绿 / 负控红）、**B 工程度量指标**（阈值 + 趋势）、**C MAF 用得上什么**。

判据证据列一律指向 `文件:方法/行`（源码检查）或可执行测试名。**无证据不得判 PASS**（《标准》§1.2）。

### 域 1｜模型交互 Model Runtime

目标：`src/AgentWorkbench.ModelRuntime/ModelRuntimeChatClient.cs`、`Providers/`

#### A 判定型不变量

| # | 不变量（可证伪） | 正例（绿） | 负控（红） |
|---|---|---|---|
| 1.1 | 单次请求超时 → `TimeoutException`，**不是** `OperationCanceledException` | `RequestTimeoutSeconds>0` + 慢响应 | 去掉 `catch (...when !cancellationToken.IsCancellationRequested)` 分支 |
| 1.2 | 调用方取消 → 保持 `OperationCanceledException`（不被误判为超时） | 传入已取消令牌 | 把 1.1 的判据放宽成无条件转超时 |
| 1.3 | 瞬时错误（`HttpRequestException`/`IOException`/`SocketException`/408/429/5xx）重试**恰好** `MaxRetries` 次 | `MockHttp` 连续 500 | 改成 `<= MaxRetries`（多一次）或 `IsTransient` 恒真 |
| 1.4 | 非瞬时错误（400/401）**一次都不重试** | `MockHttp` 返回 400 | 让 `IsTransient` 恒真 |
| 1.5 | 退避 = `Base × 2^attempt`，且**用调用方原始令牌**取消等待 | 断言等待间隔 | 用本次尝试的超时令牌替代 |
| 1.6 | 流式：**已吐出增量后不再重试**（防重复半截回答） | 中途失败 | 去掉 `yielded` 判据 |
| 1.7 | 流式：闸门覆盖从建流到吐完的**整段** | 慢流 + 并发请求 | 在首个增量后提前 `Release` |
| 1.8 | 闸门许可在所有退出路径归还（成功/超时/重试/其它异常） | 见 `finally` | 移到成功分支内 |
| 1.9 | `Wrap` 幂等——不叠两层超时/重试 | `Wrap(Wrap(c))` | 去掉 `is ModelRuntimeChatClient` 早退 |
| 1.10 | 用量计量：每次**实际发出**各计一次；未上报时跳过而非记 0 污染 | `ModelUsageMeter.Snapshot` | 重试时只在成功时计数 |

> 1.1 与 1.2 **互斥**，是本域的核心不变量对：把两者混为一个，超时与取消在账本里就无法区分（进而污染域 3 的 `Status` 分类）。

#### B 工程度量指标

| 指标 | 定义 | 阈值 | 趋势 |
|---|---|---|---|
| 重试率 | 重试次数 / 总请求 | 基线不劣化 | ↓ 优 |
| 重试成功率 | 重试后成功 / 重试次数 | ≥ 基线 | ↑ 优 |
| 超时率 | `TimeoutException` / 总请求 | 基线不劣化 | ↓ 优 |
| P95 单次请求延迟 | 含重试的墙钟 | ≤ 预算 | ↓ 优 |
| P95 首字延迟（TTFB） | 流式首个增量 | ≤ 预算 | ↓ 优 |
| 闸门排队时长 | 取许可等待 / 执行时长 | 基线不劣化 | ↓ 优 |
| token / run、成本 / run | `ModelUsageMeter` + 计价 | ≤ 预算 | ↓ 优 |

#### C 已知偏差 → 必须是负控或必修

**`_gate` 是实例级信号量，而 `Wrap` 每次调用都 `new`**（`ModelRuntimeService.Wrap`），因此当前装配下**不跨请求限流**——代码注释自陈「详见 README『现状与偏差』」。

→ 处置二选一：**修**（闸门改单例）或**建负控**（并发 N 请求断言实际并发 > `MaxConcurrentRequests`，测试**必须变红**）。禁止沉默。

#### C MAF 用得上什么

### 域 3｜执行控制 Agent Loop / Harness

目标：`src/AgentWorkbench.AgentLoop/`、`src/AgentWorkbench.AgentHarness/`

#### A 判定型不变量

| # | 不变量 | 正例（绿） | 负控（红） |
|---|---|---|---|
| 3.1 | 同工具 + 同参数连续 `MaxRepeatedToolCalls` 次 → `LoopDetected` 且 `Terminate=true`（干净收口，不入 MEA 失败路径） | `harness-loop` 场景 | 去掉 `context.Terminate = true` |
| 3.2 | token 预算：`当前用量 − 构造时基线 > MaxTokensPerRun` → `BudgetExceeded` | 小预算 + 多轮 | 基线改在每次判定时取（永远不超） |
| 3.3 | `InspectCompletion`：最后工具轮次顶到 `MaxIterations - 1` → `IterationLimit`，**与"模型答完了"必须可区分** | 跑满轮次 | 恒 `return null` |
| 3.4 | run 级超时 → `AgentRunTimeoutException`（**≠** `TimeoutException`） | `TimeoutSeconds` 极小 | 抛出通用 `TimeoutException` |
| 3.5 | 调用方取消 → `Status=Cancelled`（**≠** `Failed`） | `CallerCancellation_PersistsCancelled_NotFailed`（已有，`Harness/AgentHarnessExecutionControlTests.cs:138`） | 归入 `Failed` |
| 3.6 | 失败 / 取消 / 超时**都必须落账本** | 三路径断言 `agent_runs` 有行 | 只在成功分支落库 |
| 3.7 | 会话写回 best-effort，但**绝不因调用方取消而丢写**（`CancellationToken.None`） | 取消后断言会话已写 | 传原令牌 |
| 3.8 | 空答复**不落** assistant 步（否则"没有答复"被写成"答复为空"） | 提前终止 | 无条件落步 |
| 3.9 | 失败分类：工具异常 → `ToolError`，其余 → `Unhandled`（按实例引用优先，退化为类型+消息） | 工具抛异常 | 恒返回 `Unhandled` |
| 3.10 | 落库/会话写回自身出错**不得掩盖**原始异常 | 仓储抛异常 | 让落库异常外泄 |

#### B 工程度量指标（本域是"Harness 有没有变好"的主战场）

| 指标 | 定义 | 阈值 | 趋势 |
|---|---|---|---|
| **`IterationLimit` 占比** | 被强制收口的 run / 总 run | ≤ 基线 | **↓ 优（核心）** |
| **`LoopDetected` 率** | 检出循环 / 总 run | ≤ 基线 | ↓ 优 |
| 成功率 | `Status=completed` / 总 run | ≥ 基线 | ↑ 优 |
| 失败原因分布 | 按 `AgentRunCode` 分组计数 | 记录 | 观察 |
| 轮次分布 | `iterations` 直方图 | 记录 | ↓ 优 |
| P95 run 延迟 | `latency_ms` | ≤ 预算 | ↓ 优 |

#### C 已知偏差 → 必须是负控或必修

**`ModelUsageMeter` 是进程级单例**，`AgentRunGuard` 用「当前读数 − 构造时基线」凑本轮用量。→ **并发两个 run，A 烧的 token 会算进 B 的预算**（`RuntimeUsageSource` 注释自陈）。

→ 处置：**修**（改用 `LoopAgent.BuildResult` 的逐轮 `UsageDetails`，见 §8）或**建负控**（并发双 run 断言用量串扰，测试**必须变红**）。

#### D 现有覆盖

`Loop/AgentRunGuardTests.cs`(10)、`Loop/AgentLoopTests.cs`(3)、`Harness/`(15)。3.1–3.3 已有基座，缺的是**负控**（正例齐了，故意做坏的对照不齐）。

|---|---|---|---|
| 6.1 | 每次 run 必有 `agent_runs` 行（成功/失败/取消/超时四条路径） | 四条路径各跑一次 | 只在成功路径落库 |
| 6.2 | `agent_steps.Iteration` 单调不减 | 多轮 run | 乱序插入 |
| 6.3 | 轨迹可回放：`GetRunAsync(runId)` 复原 `HarnessRunResult` | 落库后取回比对 | 丢掉 `ErrorCode` |
| 6.4 | 失败时 `ErrorCode` 非空 | `ToolError` 场景 | 置 `null` |
| 6.5 | assistant 步截断到 `MaxAssistantChars` | 长答复 | 不截断 |
| 6.6 | 落库失败不得掩盖原始异常 | 仓储抛异常（同 3.10） | 让落库异常外泄 |
| 6.7 | 用量统计有消费者且数值正确 | `RuntimeUsageSource` → `AgentRunGuard` | 断开装配 |

> 6.7 背景：曾有文档断言"用量统计无消费者"，实为**错误**——`RuntimeUsageSource.cs:16` 经 `AgentHarnessService.cs:116` 接入 `AgentRunGuard`。此条正是把该断言固化为不变量，防止回归。

#### B 工程度量指标（MAF `Reporting` 的落点）

| 指标 | 定义 | 阈值 | 趋势 |
|---|---|---|---|
| 轨迹完整率 | 有 `agent_steps` 的 run / 有 `agent_runs` 的 run | = 100% | — |
| 成功率 | `Status=completed` / 总 run | ≥ 基线 | ↑ 优 |
| 失败原因分布 | 按 `AgentRunCode` 计数 | 记录 | 观察 |
| token / 成本 / run | 账本 + 计价 | ≤ 预算 | ↓ 优 |
| P95 延迟 | `latency_ms` | ≤ 预算 | ↓ 优 |
| 基线对比 | 本次 vs 上次同类运行 | 不劣化 | — |

#### C MAF 用得上什么

`Reporting`（`ReportingConfiguration` → `ScenarioRun` → `DiskBasedResultStore` / `ResponseCacheProvider` → `HtmlReportWriter` / `JsonReportWriter`）是六域里**唯一真正需要 MAF 的重活**：指标留存 + 报告产物 + 基线对比的物理基础。

**归属**：MAF 负责**存与画**；**基线选哪次、劣化多少算 P1、是否阻断，是我**（《标准》§6/§7）。

## 4. 判定型实现（门禁轨）

```
EvalCheck[]                              ← 我（§3 各域 A 列）
   └→ new LocalEvaluator(EvalCheck[])    → IAgentEvaluator（无 API 调用）
        └→ EvaluateAsync(agent, queries, evaluator, evalName,
                         expectedOutput, expectedToolCalls, splitter, numRepetitions, ct)
             └→ AgentEvaluationResults
                  └→ AssertAllPassed(msg) / AssertNoFailedItems(msg)   ← 失败即抛 → CI 红
```

- `EvalCheck` 是**同步逐条**委派，返回 `EvalCheckResult(Passed, Reason, CheckName)`；形如 `EvalCheckResult(EvalItem)`（精确签名以程序集为准）。
- 需要**数值**指标时才用 `IEvaluator`（`NumericMetric` + `EvaluationMetricInterpretation`，`Failed` 是**我传进去的 bool**）。
- `EvaluationRating` 取值：`Exceptional` / `Good` / `Average` / `Poor` / `Unacceptable` / `Inconclusive` / `Unknown`。

### 回放：不重跑 agent

四个 `EvaluateAsync` 重载中有两个接收 `IReadOnlyList<AgentResponse>`（"without re-running the agent"）。本项目已有配对物：

- 账本 `agent_runs` + `agent_steps`（域 6）
- `tests/AgentWorkbench.MockLlm`：`POST /control/scenario?name=`、`/control/reset`、`GET /control/stats`（`{scenario, calls}`）

→ 从账本造 `AgentResponse`，实现**零真实模型、逐次可重放**（《标准》§5）。

### 与 `MockLlm` 场景的对应

| 场景 | 用途 | 断言 |
|---|---|---|
| `normal` | 正例绿 | `EvalChecks.NonEmpty(n)` |
| `harness-tool` | 工具环被触发 | `EvalChecks.ToolCalledCheck(["calculator"])` |
| `harness-loop` | 死循环被终止 | `agent_runs.status == loop_detected`（域 3.1） |
| `reject-tools` | 工具降级路径 | `EvalChecks.ToolCallsPresent` **取反** |

## 8. 环内那半边（`LoopAgent` / `LoopEvaluator`）—— 待实验

`LoopAgent(AIAgent, LoopEvaluator, LoopAgentOptions, ILoggerFactory)`，每轮后调 `LoopEvaluator.EvaluateAsync(LoopContext)` → `LoopEvaluation{ShouldReinvoke, Feedback, Messages}`。

`LoopContext`：`Agent` / `Session` / `InitialMessages` / `RunOptions` / `Iteration` / `LastResponse` / `Feedback` / `AdditionalProperties`。
`LoopAgentOptions`：`MaxIterations` / `FreshContextPerIteration` / `NonStreamingReturnsLastResponseOnly` / `OnBehalfOfAuthorName` / `ExcludeOnBehalfOfMessages` / `SessionCreatedCallback`。

**可能带来的三件当前做不到的事**：

1. `LoopEvaluation.Messages` → **能构造下一轮输入（要求重做）**；`AgentRunGuard` 现只能 `Terminate = true`（只能停）。
2. `LoopAgent.BuildResult` 的 `UsageDetails` **逐轮累加** → 修掉 P2（域 3C）。
3. 终止判定从硬编码变为可插拔 evaluator（对应域 3 的 A 列整体外移）。

**两个必须先解决的冲突（未实测禁止替换）**：

| 冲突 | 说明 |
|---|---|
| **三个 `MaxIterations`** | `AgentLoopOptions.MaxIterations`（工具轮次预算）↔ `FunctionInvokingChatClient.MaximumIterationsPerRequest`（工具环）↔ `LoopAgentOptions.MaxIterations`（loop 安全上限）。名义近似、语义不同，叠加会互相遮蔽 |
| **`LoopEvaluation` 不承载「为什么停」** | 只有 `ShouldReinvoke`/`Feedback`/`Messages`。`AgentRunStatus` / `AgentRunCode`（含 `InspectCompletion` 对"跑满被强制收口"的识别）是资产 → 必须写映射层，否则域 3/6 的回放语义退化 |

**实验设计**：同一 `MockLlm` 场景（`harness-tool` / `harness-loop`）分别跑「现网」与「叠加 `LoopAgent`」，比较终止原因、轮次、`agent_runs` 完整性、用量归属、延迟。
