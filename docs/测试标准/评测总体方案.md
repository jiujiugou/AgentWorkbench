# 评测总体方案（AgentWorkbench）

> 版本：v0.1 ｜ 2026-10-13
> 上游：`Agent-测试与验收标准.md`（判据铁律）/ `评测实现指南.md`（六域矩阵与分工边界）
> 本文回答三件事：**测什么**、**从哪开始**、**为什么这么排**。
> 上游两份文档回答的是"每条不变量是什么"，本文把它们编排成一条可执行的路径。

## 0. 一句话

> 引入 MAF Evaluation 和 τ²-bench，不是为了"跑出一个分数"，是为了**让两类失败各自有对应的捕获工具**：
> MAF 抓"管道行为退化"（确定性、能进门禁），τ² 抓"任务办不成"（外部判分、治自循环）。
> 两者评的不是同一件事，也不能互相替代。

---

## 1. 三条轨道：各自回答什么问题

| | **轨 A：MAF 判定轨** | **轨 B：τ² 认证轨** | 轨 C：质量轨（Ragas 等） |
|---|---|---|---|
| **回答的问题** | 管道行为退化了吗？（白名单、循环终止、预算、超时≠取消、落账） | Agent 真能把事办成吗？（多轮交互后环境状态对了没） | 系统哪方面质量不好？（检索召回、回答依据） |
| **判据来源** | **全部自建**，布尔可判定 | τ² 自带（环境状态比对 + NL 断言） | LLM-as-judge 为主 |
| **谁判分** | 我（xunit 断言，零 LLM） | **τ² 的 Python 侧**（外部） | 模型 |
| **能否进门禁** | ✅ **能**，是唯一能进的 | ❌ 不能（外部依赖 + 无 key） | ❌ 不能（撞 §1.1 与 §6） |
| **驱动** | 进程内 `ScriptedChatClient` / MockLlm | MockLlm（无 API key） | 需真模型 |
| **现状** | **6/6 绿，可继续铺** | 三张账单未付 | **暂不引入**（见 §7） |
| **绿了代表** | 管道没退化 | 管道能把事办成 | —— |

> **轨道之间的分工是判据性质决定的，不是工作量排序。** 能脚本判定的必须自己判（§1.1），
> 有外部基准的必须让外部判（治自循环）——这两条是硬约束，不是偏好。

## 2. 为什么 MAF 先于 τ²（顺序不是随便排的）

### 2.1 MAF 评"失败路径是红的"，τ² 评"成功路径是绿的"

顺序反了的后果是具体的：给一条**没测过失败路径**的 harness 发能力认证，
`reward = 1.0` 无法归因——你分不清是"真办成了"还是"恰好没踩到坑"。

当前状态正好印证：P2 负控（并发 run 用量串扰）**首版假绿过**——
因为预算检查挂在 `AgentRunGuard.InspectToolCall`（只在模型发工具调用时才判），
我的场景第二轮返回文本，根本不触发检查。修正场景后它才真红。
**这条经验比那 6 个测试本身值钱**：它说明"看起来对"和"测到了"是两回事。

### 2.2 成本：MAF 现在就能跑，τ² 要付三张账单

| 轨 | 现在能不能跑 | 前置 |
|---|---|---|
| MAF | ✅ 能（`dotnet test tests/AgentWorkbench.EvaluationTests`） | 无 |
| τ² | ❌ 不能 | V8 MockLlm fixture 回放、BenchmarkHost 补 Program.cs、每任务全新环境实例 |

### 2.3 τ² 的判分必须留在 Python 侧——这是它唯一不可替代的价值

他自己发现过的问题（记忆 2026-10-08）：`fault-cases.json` 同一条里同时写 `query` 和 `rootCause`，
即**我出题、我作答、再测我的检索**——Recall@5 0.90 含金量极低。

τ² 治的正是这个：出题、执行、判分全在外部。
**失败没法靠改判据消掉**，这才是"外部独立裁判"的意义。
如果把 τ² 的判分搬进 .NET 侧自己实现，等于把自循环又造了一遍——那就白引入了。

## 5. 每阶段的"完成判据"怎么写

不是"跑通了"，是**可证伪的判据**：

| 阶段 | 判据 |
|---|---|
| 1 | 每个正例都有配对的负控；逐个关掉检测器，对应测试**必须变红**（抽样验证即可） |
| 2 | P1/P2 各有明确结论（修了 → 负控转绿并有提交；保持红 → 负控常驻且有注释说明为何不修） |
| 3 | 能产出 `report.json` 且与上次可比；明确写"不进门禁" |
| 4 | 74 个无 NL 断言任务批量跑完；负控（错 order_id）reward=0.0 |

**当前已完成 2 项验证**（可以作为后续阶段的模板）：
① `AssertAllPassed` 本身有牙（负控里直接验证它会抛）；
② 3.1 的负控真红（关掉检测 → 结局从 `loop_detected` 变 `iteration_limit`）。

## 6. 诚实边界：绿了代表什么、不代表什么

**这一节不能省。** 绿灯很容易被误读成"系统很好"。

| 绿灯 | 代表 | **不代表** |
|---|---|---|
| MAF 判定轨全绿 | 管道行为没退化（工具白名单、循环终止、预算、超时≠取消、落账都对） | ❌ Agent 聪明、❌ 回答质量好、❌ 场景做对了 |
| τ² reward 1.0（MockLlm 驱动） | .NET 侧管道能把事办成（**能力认证**） | ❌ 模型决策质量（那要真 key） |
| —— | fixture 是我们自己写的轮次脚本 | 所以 τ² 是 **harness 认证**，不是场景质量评测 |

**客观约束**：全仓库无可用 API key。因此任何"模型决策质量"的结论现在都拿不到——
这不是方案缺陷，是环境事实，写清楚比含糊过去好。

## 7. 为什么暂不引入 Ragas

1. **撞铁律**：核心指标（faithfulness、goal accuracy）几乎全是 LLM-as-judge，
   违反《标准》§1.1（能脚本判定的禁止用 AI）与 §6（AI 不得作为门禁判据）。
2. **没有测量对象**：知识库小、负控误命中 1.0 未修，现在引入是给空气称重。
3. **自己算更准**：场景层要的是字段级 P/R/F1，两百行自算比 Ragas 准且零依赖。
   它唯一的确定性指标 ToolCallAccuracy 现在也没有轨迹数据可测。

→ 等 P1 检索优化真开始时再评估，且 judge 类指标只能当趋势、不能当门禁。
