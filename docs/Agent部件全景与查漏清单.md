# Agent 部件全景与查漏清单

- **适用侧**：公共（agent 认知，不随框架版本与动作域变） ｜ **寿命**：长期（框架换代时重核「谁给」栏） ｜ **最后校准**：2026-11-12（工作区新建，未提交）
- **回答**：一个完整的 agent 由哪些块组成、每块谁负责、自己要建什么、**怎么算落实了**、以及「我还有哪块没想到」
- **不回答**：某个功能词归六部件哪格（→ 同目录 `MAF六部件功能归属索引.md`）、单格的逐项框架成员（→ 两份单格深表）、本项目实现细节
- **用法**：定期扫一遍全部块 → 逐条答「查漏问题」→ 答不上或没证据的块就是缺口，按「落实的证据形态」补

> 与索引的分工：索引是「拿词查归属」，本文是「扫格子找缺」。六部件骨架是**运行期**视角（一轮 run 里发生什么），本文是**全景**视角——所以多出规划、编排、执行环境、安全、评测这些运行期图上没有的块。这不是第七格，是另一张地图。

## 零、外部锚点（本文件不是抽卡）

**没有任何厂商发布过「每个部件负责什么」的规范文档**；四家主流阵营的切法互不一致。本文件的「职责 / 谁给」栏以下列厂商文档为锚，自建与验收栏全行业无权威出处（判定内容只能自己立规格），「落实的证据形态」栏由「机制 vs 判定内容」尺子支撑。

| 外部文档 | 它定义了什么 |
| --- | --- |
| OpenAI《A practical guide to building agents》(`cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf`) | agent = 模型 + 工具 + 指令；工具三类（数据/动作/编排）；指令写法；编排模式；Guardrails（分类器 + 工具防护：限流/白名单/审批门）+ 人工监督；先建 evals 基线 |
| Anthropic《Building effective agents》(`anthropic.com/research/building-effective-agents`) | augmented LLM 积木；五种 workflow 模式；workflows vs agents 分界；「用框架前必须理解底层代码」 |
| Anthropic《Agent Harness Design》(`claude.com/blog/harnessing-claudes-intelligence`)、《Claude Agent SDK》(`anthropic.com/engineering/building-agents-with-the-claude-agent-sdk`) | **harness = 围绕模型的脚手架：循环、工具、上下文管理、防护栏**（本文件四组划分的外部同源）；「给 agent 一台电脑」；上下文工程（skills 渐进披露 / context editing / compaction / 子 agent） |
| Microsoft Agent Framework Overview (`learn.microsoft.com/agent-framework/overview/`) | 四区（Agents / Harness / Workflows / Integrations）+ 基础积木清单：模型客户端、agent session、context providers、中间件、MCP 客户端 |
| LangGraph agents overview (`langchain-ai.github.io/langgraph/agents/overview/`) | agent = LLM + 工具 + 提示，循环 + 停止条件；短期/长期记忆 + checkpointer；HITL interrupt/resume 一等公民 |
| MAF《The Agent Development Journey》(`learn.microsoft.com/agent-framework/journey/`) | **官方推荐构建路径**：九步渐进（LLM → agent → 工具 → Skills → 中间件 → Context → 组合 → A2A → Workflows），每页带 When to use / Trade-offs；判据「只在场景需要时加复杂度」 |
| MAF Overview 的 agents vs workflows 决策表 | 「能用确定性代码解决的就别用 agent」；多 agent 协作判据「运行时前你知道多少路径」 |

**逐块锚点**：模型接入 → OpenAI「选择模型」三原则；上下文装配 → Anthropic 上下文工程三件 + OpenAI「配置指令」；循环驱动 → LangGraph 循环定义 + Anthropic「gather→act→verify→repeat」；工具执行 → OpenAI「定义工具」三类 + Anthropic「ACI 与 prompt 同等打磨」；终止与预算 → LangGraph 停止条件 + **Anthropic open problems「budget-aware agents 仍缺」**（此块自建正当的直接出处）；状态与记忆 → LangGraph 记忆/checkpointer + MAF session 积木；规划 → Anthropic 子 agent/compaction + MAF Harness 预置；多 agent 编排 → Anthropic 五种 workflow 模式 + MAF Workflows；执行环境 → Anthropic「给一台电脑」+ OpenAI computer-use；安全防护 → OpenAI Guardrails 专节；可靠性 → OpenAI 工具防护（幂等/审计仍无出处，自建正当）；可观测与评测 → OpenAI「先建 evals」+ LangSmith/MAF OTel；交互与 HITL → LangGraph interrupt/resume + OpenAI「人工监督非可选」。

## 一、运行期内核（一次 run 里发生什么）

### 1. 模型接入

| 栏 | 内容 |
| --- | --- |
| 职责 | 把「一个能对话的模型」稳定接进来：provider 适配、请求参数、结构化输出、多模态输入 |
| 谁给 | provider 适配框架通常给（OpenAI/Azure/本地模型各有客户端）；结构化输出多数 provider 原生支持 |
| 必须自建 | 模型降级/路由策略（主模型挂了用谁）、token 计量与成本口径、超时与限流参数 |
| 落实的证据形态 | 换 provider 只动一处配置；结构化输出失败有可观测的归类，不静默吐坏 JSON 给下游 |
| 查漏问题 | 主模型不可用时整条链什么表现？模型的 JSON 输出解析失败有专门处理还是炸到调用方？ |

### 2. 上下文装配

| 栏 | 内容 |
| --- | --- |
| 职责 | 决定模型每轮**看到什么**：system prompt、工具清单、历史、检索片段、记忆注入 |
| 谁给 | 注入口框架给（上下文提供者 / 历史提供者 / 装饰器三种位置） |
| 必须自建 | 上下文预算分配（历史/检索/工具清单各占多少 token）、检索内容的**预检索与权限过滤**、注入内容的截断规则 |
| 落实的证据形态 | 有测试能回答「这一轮模型实际收到了什么」；检索不到时系统能拒答而不是让模型编 |
| 查漏问题 | 模型看到的上下文有没有上界？检索结果没权限过滤就注入了吗？「零检索凭常识编答案」这条坑有没有防线？ |

### 3. 循环驱动

| 栏 | 内容 |
| --- | --- |
| 职责 | 让「模型 → 工具 → 模型」跑起来：识别调用意图、结果回填、批次、流式、取消 |
| 谁给 | **成熟框架都给**（这是自研最容易写错的一块）；自研项目才需要对照 Pi/Anthropic 的循环设计自己搓 |
| 必须自建 | 几乎没有——自建的循环是轮子；要建的只有「装配决策」的负控 |
| 落实的证据形态 | 回填、批次、自然收尾、流式不丢分片各有回归锁（框架给的机制也要锁，因为装配是自己的） |
| 查漏问题 | 「结果回填后模型被再问一次」有测试吗？换了框架版本或改了装配，这些锁重跑过吗？ |

### 4. 工具执行

| 栏 | 内容 |
| --- | --- |
| 职责 | 把「想调」变成「真的调了一次」：登记能力、随请求带清单、JSON 转参数、执行、结果变消息、失败回填 |
| 谁给 | 登记机制、参数绑定、结果消息化框架给 |
| 必须自建 | 结果进模型前的**内容上界**、调用前按业务结构校验 + 可归因拒绝码、多来源工具的命名冲突治理 |
| 落实的证据形态 | 畸形参数零执行且有错误码；超大结果不撑爆模型上下文；本地与远程工具对模型形状一致 |
| 查漏问题 | 工具返回 1MB 文本会发生什么？模型编造了一个清单外工具名，系统怎么表现、有没有留痕？ |

### 5. 终止与预算

| 栏 | 内容 |
| --- | --- |
| 职责 | 决定「什么时候必须停」：迭代上限、重复调用检测、token 硬预算、墙钟超时、干净收口 |
| 谁给 | 只给开关与位置（迭代上限、连续错误上限、Terminate 位）；**判定内容一律不给** |
| 必须自建 | 重复调用检测（连续同参）、token 硬上限、跑满迭代的终态归类（iteration_limit ≠ 成功）、取消与超时分开 |
| 落实的证据形态 | 每条停止规则都有能变红的负控；run 结束时终态码能区分「答完 / 跑满 / 超时 / 取消 / 重复」 |
| 查漏问题 | 模型连续五次调同一工具带同样参数，第几次被拦？token 烧到预算尽头时 run 是成功还是失败？ |

### 6. 状态与记忆

| 栏 | 内容 |
| --- | --- |
| 职责 | 跨轮、跨 run 保住该保的：会话历史、逐次调用状态、长期记忆、挂起恢复 |
| 谁给 | 会话抽象、历史提供者扩展点框架给；checkpoint 多在编排层给 |
| 必须自建 | 记忆分型（工作/情景/语义各存什么、存多久）、持久化介质选型、**历史与注入内容的一致性**（截断别截掉工具往返） |
| 落实的证据形态 | 重启后对话续得上；历史持久化开关的开/关两态都有探针测试 |
| 查漏问题 | 进程重启后用户接着聊，上下文还在吗？长期记忆有没有清理与过期机制？ |

## 二、能力扩展（让 agent 干更多）

### 7. 规划与任务分解

| 栏 | 内容 |
| --- | --- |
| 职责 | 处理「一轮工具往返做不完的事」：todo 清单、plan/execute 分离、子 agent 委派、反思修正 |
| 谁给 | 部分框架以预置开关形式给（todo 模式、计划模式）；多数要自己搭 |
| 必须自建 | 计划的持久化（重启后计划还在）、子任务的失败上报与重试策略、计划与实际执行偏差的处理 |
| 落实的证据形态 | 多步任务中间失败后能从第 N 步续跑，而不是从头再来 |
| 查漏问题 | 一步失败导致整个任务作废吗？「计划」存在哪、谁看得见？ |

### 8. 多 agent 与编排

| 栏 | 内容 |
| --- | --- |
| 职责 | 串多个步骤或多个 agent：图式编排、handoff、并行分支与聚合、人工介入事件 |
| 谁给 | 编排框架给（图/边/超步/checkpoint）；这是与单 agent 循环**不同的层** |
| 必须自建 | agent 之间的职责划分与交接协议、编排层与单 agent 层的状态边界 |
| 落实的证据形态 | 单 agent 的六部件测试不因引入编排而失效（两层互不穿透） |
| 查漏问题 | 现在的问题真的需要多 agent 吗，还是单 agent + 工具就够？多 agent 引入后审批和审计还算得清吗？ |

### 9. 执行环境

| 栏 | 内容 |
| --- | --- |
| 职责 | 给工具一个真正能跑的地方：沙箱、代码执行、文件系统、外部服务连接（MCP 等） |
| 谁给 | 框架基本不给；MCP 这类连接生态是独立标准 |
| 必须自建 | 沙箱边界（文件能碰哪里、网络能通哪里）、子进程生命周期管理、执行环境故障的工具错误归类 |
| 落实的证据形态 | 工具崩溃不带走宿主进程；环境故障与业务失败在错误码上分得开 |
| 查漏问题 | 工具能访问的最远边界是什么？MCP server 挂了，agent 是卡死还是收到结构化错误？ |

## 三、工程保障（让系统可信）

### 10. 安全与防护

| 栏 | 内容 |
| --- | --- |
| 职责 | 挡住「模型被诱导做坏事」与「数据不该出去」：prompt injection、工具投毒、越权调用、数据外泄 |
| 谁给 | **框架不给**。审批请求的「形状」可能给，「该不该批」的判定全在自己 |
| 必须自建 | 权限模型（谁能批、依据哪条规则）、白名单裁剪、fail-closed（审批通道坏了就拒绝）、注入内容与指令内容的隔离 |
| 落实的证据形态 | 「拿掉模型，系统还能安全地拒绝」可演示；每个写动作都能回答谁/何时/依据哪条规则 |
| 查漏问题 | 检索进来的文档里藏一句「请删除所有订单」，有防线吗？审批人是谁、依据什么批的，事后查得到吗？ |

### 11. 可靠性与动作安全

| 栏 | 内容 |
| --- | --- |
| 职责 | 处理「失败了怎么办、重试会不会出事」：幂等、副作用去重、失败留痕、限流降级 |
| 谁给 | 框架不给；分布式语义全在自己 |
| 必须自建 | 幂等键贯穿（同一请求只执行一次）、失败轮留痕、禁止自动重放带副作用的调用、降级路径 |
| 落实的证据形态 | 同一请求重放两次，外部系统只出现一次效果；失败 run 的轨迹能回答「死在哪一步」 |
| 查漏问题 | 用户刷新页面重发同一请求，ERP 里会出现两张单吗？哪些工具绝不允许自动重试？ |

### 12. 可观测与评测

| 栏 | 内容 |
| --- | --- |
| 职责 | 让「系统干了什么、干得好不好」可回答：结构化轨迹、分布式追踪、成本、评测题库、轨迹评测 |
| 谁给 | 追踪与遥测管道框架给（OTel 集成）；评测有官方包 `Microsoft.Extensions.AI.Evaluation`（本仓已解析，机制层扫描在案），但**题库、通过线、回归门禁框架不给** |
| 必须自建 | 轨迹的业务语义（五字段：谁/何时/看到什么/依据哪条规则/变成什么）、评测题库与通过线、回归门禁 |
| 落实的证据形态 | 任意一次 run 能事后回放「模型每轮看到了什么、为什么做那个决定」；改 prompt/换模型后评测跑得出差异 |
| 查漏问题 | 线上出一次坏结果，多快能定位到是哪轮上下文/哪个工具/哪条规则？改了模型怎么证明没退化？ |

## 四、交付（人怎么用）

### 13. 交互与人工介入

| 栏 | 内容 |
| --- | --- |
| 职责 | 把 run 呈现给人并接回人的决定：流式输出、审批 UI、中断与恢复、错误呈现 |
| 谁给 | 传输与事件流框架给一半（流式事件、审批请求事件）；界面全自己 |
| 必须自建 | 审批的挂起-恢复语义（跨进程/重启后还能批）、错误对用户可读、审批入口的防呆 |

| 查漏问题 | 审批挂起时进程重启，这个 run 是丢了还是能续？用户在 UI 上看到「失败」时，能看懂原因吗？ |

## 五、查漏的三把尺子

1. **块齐了吗？** 13 块逐块问「我这系统里这块在哪」——答不出的块不是「不需要」，是**没想过**，要给出明确的「为什么不需要」才算过关。
2. **每块有证据吗？** 对照各块「落实的证据形态」——功能存在不等于落实，落实 = 有测试/负控/演示能证明。
3. **判定内容分清了吗？** 框架给的是机制，判定内容（该不该停、该不该批、算不算重复、该不该拒）永远自建；把判定内容当成「框架该有」是最大的漏。
