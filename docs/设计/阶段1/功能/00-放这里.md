# 功能文档：一条信息该放哪

这个目录只放一件事：**一个功能域"应该是什么样、做到没有、为什么这么定"。**

放东西之前先过下面的抽屉问句。**按顺序问，第一个答"是"的就是它的家。** 不需要读懂四份文档，只需要回答是或否。

## 抽屉

| 序 | 问句 | 答"是" → 去哪 |
|---|---|---|
| 1 | 这条在说这个功能**应该是什么样**吗（有什么子问题、由哪几段构成、不做什么） | **功能文档**（`F3-知识问答.md`） |
| 2 | 这条在说它**现在做到没有**吗 | **验证文档**（`F3-功能验证.md`） |
| 3 | 这是某个动作跑出来的**数**吗 | **验证文档**（第六节，指标定义） |
| 4 | 这是**下一步做什么**、或它要用的临时值（如 0.08）吗 | **验证文档**末尾"先补什么" |
| 5 | 这是"我们**这么定、但还没验证**"的信念吗（选了 A 不选 B / 假设 X 成立） | **决策记录**（`F3-决策记录.md`） |
| — | 全否 | **不进文档**：代码注释、测试、或直接丢 |

第 1 与第 2 问的界线是「应该」和「实际」，不需要懂内容就能分。第 4 与第 5 问的界线是「要去做」和「已经定了」。

**最后一个出口最重要。** 用例表、函数签名、代码片段、调参过程，全部落在「全否」——它们真正的家是代码和测试，抄进文档的那一份只会过期。没有这个出口，这个目录就只是个分拣器，文件只会变厚。

## 三条减法规则

文档只增不减就一定会腐烂。三条规矩各管一边：

- **功能文档**：一条子问题如果**说不出"用户看到什么"**，删掉它，不要拆它。（拆是无限的，删是有限的）
- **验证文档**：一条如果**说不出"红了算什么"**，状态降为"未验"，不要写"通"。
- **决策记录**：一条如果**能在代码里读出来**，不写；写进去的只留"为什么"，不留"怎么做"。

## 目录

| 文件 | 只回答 | 不回答 |
|---|---|---|
| `F3-知识问答.md` | 这个功能由什么构成，每个子问题落在哪一步 | 现在做到没有、为什么这么定 |
| `F3-功能验证.md` | 21 项各自验到哪、用什么验、红了算什么；指标怎么定义 | 应该是什么样（那是功能文档） |
| `F3-决策记录.md` | 选了 A 不选 B 因为 X；哪些是赌的 | 规则本身怎么实现（指针回代码） |

## 只有一种时刻需要判断

日常维护只有一个动作：**改状态、改数字**。上表那五个问句是给"新出现的东西"用的，不是每次都要跑一遍。

需要停下来想一下的，只有两个信号：

- **说不出"这算不算本功能的"** → 这是定义边界要动，改功能文档
- **发现"用户会看到一个我没列过的坏结果"** → 功能文档加一条子问题，验证文档同一 commit 加一行

反过来的信号也很清楚：**如果你改的是"怎么实现"或"数字是多少"，功能文档一个字都不用碰。**
