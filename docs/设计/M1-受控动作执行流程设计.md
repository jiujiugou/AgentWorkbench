# M1 受控动作执行流程设计

- **版本**：v0.1-draft ｜ **状态**：待确认 ｜ **日期**：2026-11-08
- **定位**：**派生设计**。把 `docs/需求/产品目标与范围.md` v3.0（已确认）§4.1 / §5.1 / §7，与 Py 仓 ADR 0013–0017 的既有判据，投影成一条可执行链路和一组契约形状。
- **不是什么**：不是第三份事实源，不新增判据，不定义完成标准，不替代 `运行时底座完成定义.md` 的测试规格。冲突时一律以正本 + ADR 为准。
- **生效条件**：正本已于 2026-11-08 转「已确认」；本文仍是 v0.1-draft，因 M1 契约尚未评审，**不挂进 `AGENTS.md` 事实源表**，草稿不进每会话注入地图。
- **范围**：M1 契约 + 假 ERP。目标是让「一次提问 → 出结果」整条链以**最假的实现**跑通，并让 AC-01 第一次可验。

## 0 设计对象

设计对象是**一次动作 run**，不是聊天、不是问答、不是平台。

一句话：把「模型想做什么」变成「系统真的做了什么」，并保证**不越权、不重复执行、办错了能追回**。模型只负责把人的自然语言翻成结构化请求；其余判断权全部在代码与人手里。

## 1 边界与明确不做

### 1.1 本设计做

| 项 | 内容 |
|---|---|
| 契约 | `ActionSpec` / `ActionRequest` / `ActionResult` 三类型、三个注入口、`TraceEvent` 结构 |
| 网关 | 四道校验接口 + **默认全部拒绝**的 fail-closed 骨架 |
| 动作域 | 假 ERP（内存四原语）、假 PDP、假业务规则、第二套假动作集 |
| 运行时 | run 状态机（挂起 / 恢复 / 幂等 / 超时查证）、审计五字段落点 |
| 验收 | 六句成功判据、RR-1~RR-5、AC-01/02 各自挂到具体步骤与测试 |

### 1.2 本设计不做（每条都有依据）

| 不做 | 依据 |
|---|---|
| 技能注入、MCP / 通用连接器、子智能体 | 正本 §2.3「不做通用连接器」「不做平台」；ADR 0016 **B1 多 agent / 自主规划 / 任务分解**已放弃，重开条件「第二个 ERP、第二类动作跑通且需角色协作」未触发；能力矩阵附录 C「MCP / PLC 第一版不做」 |
| 真 ERPNext 接入、真实权限四维 | 属 M2；M1 一律用假实现 |
| 最小审批页之外的前端、管理后台 | 正本 §5.1 B「审批最小闭环：待办 + 详情 + 同意/拒绝两个按钮」 |
| 知识层检索（RAG / 制度文档预检索） | 正本 §7「M1~M3 不碰 Python 仓」「Python 侧深度接入 M3 端到端跑通后决定」；**且 ADR 0016 A1 明写 `harness 暗做检索` 已放弃**（R5 不自作主张）。见 §10 待确认 |
| 加严 prompt、换模型、自研循环 | ADR 0016 A4「不重开」；正本 §2「模型输出一律当不可信数据」 |
| 功能数、覆盖率、绿灯数当完成标准 | 正本 §4.2 明令 |

**关于「系统预检索」**：Py 仓 F3 v1 因 run 18 模型零检索改用系统预检索；C# 底座 ADR 0016 A1 却把「暗做检索」列为放弃项，重开条件写「若出现判定与模型必须拿同一份证据的强约束，由 **C# 侧显式工具调用**实现，不是恢复 ContextBuilder」。两条证据冲突，**本设计不预设答案**：M1 流程不含检索步骤，「依据哪条规则」由动作域注入的 `BusinessRule` 快照提供。该分歧留到 M3 之后裁决，不进 M1 范围。

## 2 完整流程规格

### 2.1 验收用问题（保持单据模型，不用设备现场）

> 「按公司《备件采购审批制度》，PO-2026-1108 这张 4.8 万的备件单能批吗？能的话帮我提交，并告诉我依据。」

这一句同时逼出：身份判定、意图结构化、四道校验、挂起审批、四个原语、审计五字段、带出处的回执。

### 2.2 逐步规格

| # | 步骤 | 触发者 → 输入 | 输出 / 动作 | 落痕 | 对应判据 |
|---|---|---|---|---|---|
| 1 | **收请求** | `Host` 接 HTTP/SignalR | 企业应用层验身份、算 `subject` 与可见范围；生成 `request_id` 贯穿全程；`Runtime.Session` 取会话，`Runtime.Context.Assemble` 固定窗口组装 | `TraceEvent(Stage=Received)` | §4.1 第 5 句（审计）、RR-5 |
| 2 | **意图结构化** | 模型，唯一必用点 | 自然语言 → `ActionRequest`（`ActionKey` + 不透明 `JsonElement Arguments` + `RequestId` + `IdempotencyKey`）。**输出一律当不可信数据，自由文本不进执行路径** | `TraceEvent(Stage=Intent)` | §2 第 3 条、方向判据 3 |
| 3 | **四道校验** | `IActionGateway`，fail-closed | 按序：`Schema` → `PermissionQuery`（唯一 PDP）→ `BusinessRule`（动作域注入）→ `Audit`。任一不过即 `Rejected`，**零外部调用**；默认实现全部拒绝 | 拒绝码写进 `ActionResult.Code` + `TraceEvent(Stage=Validated)` | §4.1 第 2 句、RR-2 |
| 4 | **挂起审批** | 仅 `SideEffecting = true` 的 `Submit` | `Suspend` → 人批 → `Resume`；`Checkpoint` 只存**执行进度字节**，不存「采购单待审批」这类业务状态；审批人 / 层级 / 时长为注入策略 | `TraceEvent(Stage=Approved, Approver=…)` | §4.1 第 2 句、ADR 0017 §四 |
| 5 | **执行四原语** | `IActionExecutor`（动作域适配器半边） | `Query` 查真实状态 → `Draft`（可重复、无副作用）→ `Submit`（幂等，同 `request_id` 只一张单）→ `Cancel`（可选）。**超时 → 状态未知 → 只发起 `Query` 查证，不重放** | `ExternalId` 回写、`TraceEvent(Stage=Executed)` | §4.1 第 1、3、4 句、RR-3 / RR-4 |
| 6 | **收口出结果** | Runtime 收终态 | 审计五字段齐全（意图 / 参数 / 审批人 / 结果 / 外部单号）；证据快照可复核；`ActionResult` 写回会话；回执由模型组织语言（**可选**），单号 / 条款 / 审批人必须来自结构化字段 | `TraceEvent(Stage=Completed)`、审计事件表 | §4.1 第 5 句、RR-5 |

### 2.3 每步经过的层

| 层 | 参与步骤与职责 |
|---|---|
| 企业应用层 | 1 验身份 / 3 唯一 PDP / 4 审批人 / 5 权限四维 / 6 审计查询 |
| Runtime / Harness | 1 收请求 / 2 执行环看守 / 3 抽参数 / 4 挂起 / 5 执行环 / 6 收终态 |
| 编排层 | 4 挂起→人批→恢复、5 步骤状态 |
| 工具层 | 3 白名单 + 四道校验 + 审批闸、5 执行体、5 幂等键与去重表、6 审计落库 |
| 知识层 | **M1 不参与**（见 §1.2）；M3 后决定是否接入 |
| 记忆与状态层 | 1 会话历史、4 Checkpoint、5 任务状态、6 快照可查 |
| 工程保障层 | 1 `request_id`、3 拦截留痕、5 查证不重放、6 审计事件表与 `TraceEvent` 结构 |

> 层归属只用于核对覆盖，**不代表工程组织**：Py 仓能力矩阵结论原话是「这张七层图只能当体检表，查不出这些能力归谁、状态在哪、边界在哪」。真正指导落地的是 §3 的端口契约与 §7 的依赖规则。

### 2.4 run 状态机

```
Received → Intent → Validated → (Rejected 终态)
                        ↓
                   PendingApproval → (Rejected 终态)
                        ↓ Approved
                   Executing → Completed
                        ↓ Timeout
                   Unknown → Query(查证) → Completed | Failed
```

- `Rejected` / `PendingApproval` / `Unknown` 三个状态下**不得产生外部副作用**。
- 终态码复用 `AgentWorkbench.Shared.AgentRunStatus` / `AgentRunCode`；拒绝原因用独立拒绝码，不与 `unhandled_error` 混。
- 每个终态必须能归因到**唯一一个 RunCode**（RR-1），「跑满被逼收口」与「模型自己收口」可区分。

## 3 契约设计：`src/Core/Ports`

**性质**：只有接口与 record，**零实现、零业务词、零 NuGet 包依赖**。`Domains/*` 唯一允许 import 的项目。形状示意，不是最终签名。

### 3.1 动作契约三类型

```csharp
namespace AgentWorkbench.Ports;

public sealed record ActionSpec(
    string ActionKey,
    string SchemaId,        // 指向动作域提供的 JSON Schema
    bool SideEffecting,     // Draft=false 可重复 / Submit=true 必登记
    string Primitive);      // Query | Draft | Submit | Cancel

public sealed record ActionRequest(
    string RequestId,
    string Subject,
    string ActionKey,
    JsonElement Arguments,  // 对底座不透明，底座不理解字段含义
    string? IdempotencyKey);

public sealed record ActionResult(
    string RequestId,
    string Status,          // 复用 AgentRunStatus
    string Code,            // 复用 AgentRunCode / 独立拒绝码
    string? ExternalId,     // 外部单号
    string? ErrorCode,
    JsonElement Data);
```

`ActionSpec` 的**类型**定义在底座，**实例声明**在动作域（ADR 0017 §三「由适配器声明」）。参数值对底座是不透明 JSON，这是「底座问，但不理解」的落点。

### 3.2 三个注入口

```csharp
public sealed record PermissionQuery(string Subject, string ActionKey, string Scope);
public sealed record PermissionDecision(bool Allow, string Reason);

public interface IPermissionQuery          // 注入口 1：权限，底座只问 allow/deny
{
    ValueTask<PermissionDecision> QueryAsync(PermissionQuery query, CancellationToken ct);
}

public interface IBusinessRule            // 注入口 2：判据，由动作域实现并注入
{
    ValueTask<RuleDecision> EvaluateAsync(ActionRequest request, CancellationToken ct);
}

public interface ITraceSink               // 注入口 3：轨迹结构，判据/题库/通过线由动作域注入
{
    ValueTask WriteAsync(TraceEvent trace, CancellationToken ct);
}

public interface IActionGateway           // 底座侧，四道校验
{
    ValueTask<ActionResult> SubmitAsync(ActionRequest request, CancellationToken ct);
}

public interface IActionExecutor          // 适配器半边，动作域实现，拿已校验参数
{
    ValueTask<ActionResult> ExecuteAsync(ActionRequest request, CancellationToken ct);
}
```

### 3.3 轨迹与错误信封

```csharp
public sealed record TraceEvent(
    string RequestId, string Stage, string Outcome,
    string Intent, string Arguments, string? Approver,
    string? Result, string? ExternalId, DateTimeOffset At);
```

`TraceEvent` 是**结构**，不是判据。「这张单有没有下错」的判据、题库内容、通过线由动作集自带并注入（ADR 0017 §三）。

**五字段错误信封**：ADR 0017 §二 提到该信封，但 §三 未列出具体字段构成。**本文不臆造**，实现前须先在 ADR 补齐定义，再落 `ErrorEnvelope` 类型；当前只保留类型名占位。见 §10。

### 3.4 命名绑定（实现时不得改名）

现有 `ApplicationTests` 的 F5 / X 组 21 条预期红测试，是通过 `src/Core/Ports/` 与 `src/Domains/Erp/` 下的**源码标记扫描 + 反射类型名**断言契约存在。以下名字同时是判据与扫描词：

```
ActionSpec  ActionRequest  ActionResult  SideEffecting
PermissionQuery  Permission  Schema  JsonSchema  BusinessRule  Audit
Query  Draft  Submit  Cancel
Checkpoint  Suspend  Resume
Idempot  RequestId  request_id  Timeout  InProgress  Pending
Intent  Arguments  Approver  Result  ExternalId
InMemory  Fake
```

命名一旦改动，那批预期红不会转绿。若确需改名，必须同步改测试，并把理由写进 ADR。

## 4 网关设计：四道校验

| 道 | 接口 | 拒绝条件 | 默认行为 |
|---|---|---|---|
| 1 Schema | `ISchemaValidator` | 参数不符合 `ActionSpec.SchemaId` 指向的 Schema | 拒绝 |
| 2 权限 | `IPermissionQuery` | PDP 返回 `Allow=false` | 拒绝 |
| 3 业务规则 | `IBusinessRule` | 动作域注入的判据不过 | 拒绝 |
| 4 审计留痕 | `ITraceSink` | 轨迹写不进去 | 拒绝（fail-closed） |

**骨架的默认实现全部返回拒绝**，不提供任何「放行」默认。这样「拿掉模型、或让模型吐畸形 JSON，系统仍然拒绝且留痕」在设计上成立，而不是靠提示词保证。

四道必须**按序**、每道独立可测（M1 退出条件「四道校验各有单测」）。任何一道不过，`IActionExecutor` 一次都不能被调用。

## 5 动作域设计：`src/Domains/Erp`

### 5.1 组成

| 文件 / 类型 | 职责 | 业务语义 |
|---|---|---|
| `ErpActionSpecs` | 注册 4 个 `ActionSpec` 实例 + 对应 JSON Schema | 有 |
| `InMemoryFakeErp : IActionExecutor` | 内存实现四原语，是网关单测装置也是 AC-01 载体 | 有 |
| `ErpPermissionPdp : IPermissionQuery` | 假 PDP，返回 allow/deny + reason | 有 |
| `ErpBusinessRule : IBusinessRule` | 假判据（金额档位、制度条款快照） | 有 |
| `FakeActionSet`（第二套） | 字段、策略、判据、题库全不同 | 有，**AC-01 验收装置** |

业务语义**全部**集中在 `Domains/Erp`。`Core` 下任何项目不得 import `Domains`。

### 5.2 假 ERP 状态机与幂等

- 内存状态：`Draft` / `Submitted` / `Cancelled`，按 `ExternalId` 索引。
- `Draft` 可重复调用、不产生副作用；`Submit` 必须带 `IdempotencyKey`，去重表按 `request_id` 判定，**同 `request_id` 只生成一张单**。
- 超时模拟：把 `Submit` 置为 `InProgress` 后不返回；恢复路径只发 `Query` 查状态，**永远不自动重放写动作**。
- `Cancel` 只作用于未提交状态的单据。
- 提供 `Reset()` 供测试隔离，不依赖真实数据库或网络。

### 5.3 AC-01 换域演练

`FakeActionSet` 与 `Erp` 的字段、策略、判据、题库**全部不同**，但实现同一组 `Core.Ports` 接口。验收动作：把组合根从 `Erp` 换成 `FakeActionSet`，`git diff src/Core` 必须为空。这不是功能，是**唯一能证明底座业务无关的判据**。

## 6 运行时状态机与审计

- `request_id` 从步骤 1 贯穿到 `ExternalId` 回写与所有 `TraceEvent`。
- 幂等键与 `request_id` 同源（ADR 0013 §三·附）；去重表在底座侧，不在动作域。
- `Checkpoint` 用已实施的 MAF `CheckpointManager`，只恢复**框架内部执行进度**；业务状态在业务库，两者不混写（ADR 0017 §四）。
- **证据快照**：本次判定与模型/回执必须出自同一份证据（ADR 0015 D-03）。M1 里由 `BusinessRule` 返回的条款快照充任，落在 C# 侧，不复制正文但保留片段 id、文件名、序号、页码；原文删除后仍可复核。
- 审计五字段（意图、参数、审批人、结果、外部单号）分散在步骤 2/3/4/5/6 产生，工程保障层只提供**事件结构与落库通道**，不产生业务内容。

## 7 分层与依赖规则

```
src/Core/Ports        ← 唯一允许 Domains import 的项目（零依赖、零业务词）
src/Core/...          ← 底座五层 + 工具管辖半边；禁止 import src/Domains
src/Domains/Erp       → 只允许 import Core.Ports；承载全部业务语义
src/Host/Webapi       ← 组合根：把 Domains.Erp 的实现注入 Core.Ports 的接口
```

门禁（新增架构测试，且须先自证能变红）：

1. `Core` 下任何项目不得出现对 `Domains` 的 `ProjectReference` 或 `using`。
2. `Domains` 下任何项目只允许引用 `Core.Ports`。
3. `Core.Ports` 源码不得出现 AC-02 禁词（按 ADR 0017 §六 词表，只扫代码行，注释不算违规）。
4. `Core.Ports` 的 `ProjectReference` 数量恒为 0。

`AgentWorkbench.Shared` 保留现状、**不往里加东西**；新增类型一律进 `Core.Ports`。

## 8 验收设计：怎么证明这个设计做完了

### 8.1 判据挂到步骤

| 判据 | 挂在 | 最小验证 |
|---|---|---|
| §4.1 第 1 句 真实 API 查状态 | 步骤 5 `Query` | 假 ERP 返回状态，断言 `Query` 被调用且状态被读取 |
| §4.1 第 2 句 未审批零外部调用 | 步骤 3/4 | 审批未通过时 `IActionExecutor` 调用次数 = 0 |
| §4.1 第 3 句 同 `request_id` 只一张单 | 步骤 5 | 连打两次 `Submit`，假 ERP 单据数 = 1 |
| §4.1 第 4 句 超时只查证不重放 | 步骤 5 `Unknown` | 写调用次数 = 1，且发起了 `Query`，无第二次 `Submit` |
| §4.1 第 5 句 审计五字段齐全 | 步骤 6 | 抽一笔执行，五字段均非空且可反查 |
| §4.1 第 6 句 假第二动作集跑通 | §5.3 | 换 `FakeActionSet`，整条六步链仍跑通 |
| RR-1 唯一 RunCode | §2.4 | 每个终态有唯一归类码，跑满截断 ≠ 模型收口 |
| RR-2 拒绝无外部调用 | 步骤 3 | 四类拒绝各一条，ERP 侧无新单据、轨迹有拒绝码 |
| RR-3 幂等 | 步骤 5 | 同 `request_id` 重复提交副作用一次 |
| RR-4 恢复不重放 | 步骤 5 | 中断恢复后不产生第二张单 |
| RR-5 六项可查 | 步骤 6 | 谁发起 / 调了什么 / 参数原文 / 谁批的 / 外部单号 / 终态 |
| AC-01 换域 diff 为空 | §5.3 | `git diff src/Core` 为空 |
| AC-02 禁词 | §7 门禁 3 | 类型名 / 字段名 / 方法名扫零命中 |

### 8.2 让现有 21 条预期红转绿

按 §3.4 命名实现契约与假 ERP 后，`ActionContractExistenceTests` / `ActionExecutionContractTests` / `CrossModuleVerificationTests` 三组会由红转绿。**这些红是验收装置，不是失败**；转绿的前提是命名对齐，不是放宽断言。

其余预期红（F2.8 参数校验、F2.9 结果上界、F2.10 幂等键、F3.5 能力位、F4.7 长期记忆默认值）分属工具层与既有模块，不在 M1 契约范围，按 `运行时底座完成定义.md` 逐条处理。

### 8.3 负控要求（沿用 11-08 已验证的做法）

每条新测试必须写明「改坏哪一行会红」，并**实跑一次变异自证**：备份 → 精确改坏一处 → 跑全量 → 看到该条变红 → 还原 → 校验源码哈希一致。只断言「不为空 / 没抛异常」的不算测试。
