# 功能域怎么写

下一个功能域（F4 及以后）从这一页开始。**本文不超过一页**，只允许替换，不允许追加——它一旦变长，就变成了它要防的那种东西。

## 一、写第一行代码前必须回答四个问题

答不上任何一个，说明还没到能动手的程度。

**判据是什么。** 一句话，一次操作就能验证，不依赖"我觉得"。
反例"答案质量好"；正例"问 X 得到 Y，Y 来自资料不是常识"。

**这个数谁提供。** 只有三种答案：本件自给、借另一个功能、无人。
"无人"不是问题，**不写下来才是问题**。F3 的"模型读没读"就是借第三件的引用台账，但当时没写，几个月后才发现"子功能 1 的问题由子功能 3 验证"，看起来像分层错了。

**什么能推翻它。** 哪条实验结论会让这个设计作废，作废之后交付什么。
没有这一条，每个设计都显得零成本、一定成立；等实验发现不成立，就变成"方向错了"而不是"走到了岔路口"。

**现在哪些是猜的。** 列成清单，每条配一个能把它变成已知的实验。
猜的部分不许写进硬逻辑——见下一条。

## 二、一条铁律：赌注不是设计

**凡是依赖"模型会遵守"或"数据会这样分布"的地方，必须留一条退路。**

检验方法：把那条假设拿掉，系统还能不能跑、会不会**静默失效**。会静默失效的，就是赌注。

F3 的三个对照：

| 依赖 | 留没留退路 | 结果 |
|---|---|---|
| 两个拒答阈值 | 留了（可空，空则不生效） | 假设不成立时闸只是不开，不会崩 |
| 引用覆盖率阈值 | 留了（可空，只记不判） | 同上 |
| 六条模型指令（先检索、写 `[n]`、承认未提及…） | **没留** | 模型不遵守时，链路照常成功、照常出答案，全部指标好看 |

第三条是 F3 最脆弱的地方，也是唯一没有退路的地方。**同一个功能域里，代码逻辑都留了开关，最依赖外部行为的那部分反而裸奔。**

## 三、验收期发现的问题往哪流

**按"这条发现动摇了什么"分流，不按"它什么时候被发现"分流。** 验收会一直发现问题，这是正常路径，不是文档失败。

| 发现的性质 | 改哪份 | 判据 |
|---|---|---|
| 用户能看到的坏结果清单变了（多一条、少一条、某条含义变了） | 功能文档增删一条，**验证文档同一 commit 增删对应行** | 能说出"用户看到一个以前没列过的坏结果" |
| 坏结果没变，是实现没做到 | 只改验证文档状态 + 它末尾的"先补什么"；功能文档一个字不动 | 子问题在，代码不在 |
| 坏结果没变，当初选的做法被证伪 | **决策记录写一条**（够格的再按 ADR 模板拆）+ 补什么表；功能文档不动 | 换一种做法就能满足同一子问题 |
| 只是实现坑（浮点、并列、输入顺序） | 代码注释与测试，三份文档都不进 | 换个人写同一规格也会踩 |
| 只是数字变了 | 只改验证文档 | 功能文档不写数 |

三条边界：

- **功能文档只因为"用户能看到的东西变了"而改。** 任何"这样更优雅/更好维护"都不进。
- **决策记录只记"选 A 不选 B，因为 X"**，一条一段，只追加、不修改，不装过程、不装问题清单。跑了几次试了哪几个值不是决定，除非它排除了一个方向。
- **两份文档不许单方面改。** 功能文档加一条，验证文档必须同时加一行，否则一周内就会出现"清单 22 条、对账 21 行"。

四种内容的寿命不同：**定义**活到功能被推翻，**做法**活到被证伪，**数字**活一次实验，**进度**活一轮。混在一节里，读者分不清哪句还作数。

F3 的正确样例：可核三的二级校验判别力为零——那条子问题（误挂）没变，变的是抓它的手段，所以只动验证文档（状态改"不通过"、补什么表加一行），功能文档不动。备选做法（IDF 加权 / 关键值命中）还没选，所以先留结论里，等选定那一刻才进决策记录。

## 四、先分清是几个功能，再分节

一个功能域里通常有几条**不变量**，它们不是几个功能。判据只有一条：

> 去掉其中一条，另外几条的判据会不会失效。会 → 是不变量；不会 → 是独立功能，应该拆成两个功能域。

F3 是前者：去掉"可核"，"可用"的后半段就没有任何观测点；去掉"不编"，前两条不算完成。所以 F3 是一个功能、三条不变量，文档里三节并列，但不许说成"三个功能"——那会让人以为可以做一个、放两个。

**一个功能、N 条不变量、N 份独立判据。** 判据必须分开写、分开验收；功能不许拆。

## 五、一个功能域产出哪四份

| 文件 | 只写 | 判据 |
|---|---|---|
| **功能文档** | 应该是什么样：N 条不变量、链路分解、每条不变量的子问题、边界 | 每条子问题都能说出"用户看到什么"；说不出的删掉，不要拆 |
| **验证文档** | 每一项验到哪、用什么验、红了算什么；指标怎么定义；下一步补什么 | 每一项都能说出"红了算什么"；说不出的状态只能是"未验" |
| **决策记录** | 选 A 不选 B 因为 X；哪些还是赌的 | 能在代码里读出来的不写 |
| **入口页** | 新信息该放哪（抽屉问句 + 三份文件的分工） | 不问人就能确定去处 |

**设计正文里不再写"怎么做"和"怎么验"。** F3 的教训：把做法、验收、评测、假设塞进同一份设计文档，结果是 615 行里一半会过期，而读者分不清哪句还作数。拆开之后四份加起来 620 行，但没有一行是"当时对、现在已经不对"。

假设不再单独成节，它进决策记录第二部分——**因为一条假设就是一条"我们这么定、还没验证"的决定**，两者的寿命一样，配的也都是"什么条件下推翻"。

## 六、F3 为什么长成那样（反例，只记三条）

1. **开工时没有假设清单。** 于是每走一步撞见一个新未知，就开一个新方向：题集是补的、负控三档是后拆的、阈值是后发现的。
2. **假设和结论混写。** "没有任何阈值能判这一档"这种话被写成了结论，实际是一次观察加推理。读者（包括作者）分不清哪句站得住。
3. **执行顺序和生产顺序塞进同一份文档。** 七步落地顺序是排期，做完就过期，却留在主文正中间，读者以为还没开始。

三条都不是纪律问题，是**没有把"已知"和"待验"分开存放**。分开之后，纪律就不需要了。
