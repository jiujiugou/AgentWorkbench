# 状态与记忆持久化方案（跨模块记录 / ADR 草案）

> 状态：**阶段 1 / 2 已实现**，阶段 3 未做｜ 已转：[ADR-0003](../adr/0003-memory-persistence-boundary.md) ｜ 关联：缺口清单 P1-3、`src/AgentWorkbench.Memory/README.md` 二 ｜ 日期：2026-10-12

一句话：**会话与长期记忆各落一张表；`Memory` 契约模块继续只依赖 `Shared`，SQLite 实现放进新模块 `AgentWorkbench.Memory.Persistence`，由组合根注入替换；会话用 MAF 官方序列化 JSON 续存，并给内存缓存加 TTL + 上限。**

本方案要解决 `src/AgentWorkbench.Memory/README.md` 第二节列出的四个问题：会话重启即丢、字典无限增长、长期记忆没有载体、依赖方向挡住持久化。

---

## 一、现状与证据

| 事实 | 证据 |
| --- | --- |
| 会话存进程内 `ConcurrentDictionary`，无 TTL、无上限 | `src/AgentWorkbench.Memory/SessionStore.cs`（`_sessions`，仅一个建会话闸门） |
| 配置只有「开关」，没有任何容量/时效项 | `src/AgentWorkbench.Memory/MemoryOptions.cs`（仅 `SessionEnabled`） |
| 唯一消费者是 Harness，会话历史由 `InMemoryChatHistoryProvider` 持有 | `src/AgentWorkbench.AgentHarness/AgentHarnessService.cs:122`、`BuildAgent` |
| `Memory` 只引用 `Shared` | `src/AgentWorkbench.Memory/AgentWorkbench.Memory.csproj` |
| 有 `agent_runs` 等先例，迁移编号已排到 M022 | `src/AgentWorkbench.Persistence/Migrations/` |

### 关键技术验证（已用 spike 跑通，非推测）

`Microsoft.Agents.AI` 1.23.0 提供会话序列化/反序列化，且**会把 `InMemoryChatHistoryProvider` 的历史一起带上**：

- `AIAgent.SerializeSessionAsync(session, JsonSerializerOptions?, CancellationToken)` → `ValueTask<JsonElement>`
- `AIAgent.DeserializeSessionAsync(JsonElement, JsonSerializerOptions?, CancellationToken)` → `ValueTask<AgentSession>`
- 序列化结果形如 `{"stateBag":{"InMemoryChatHistoryProvider":{"messages":[...]}}}`。

Spike 结果：跑两轮 → 序列化 → 用**新建的 agent** 反序列化 → 再跑一轮，模型看到 `hello | ack-1 | again | ack-2 | third`（历史完整续上）。

> ⚠️ 坑：**必须传 `null` 作为 `JsonSerializerOptions`**。传自定义 `new JsonSerializerOptions(...)` 会抛 `NotSupportedException`，因为 MAF 的 source-generated `JsonSerializerContext` 在内部且不可访问。这一点要写进实现注释与测试，避免后人"顺手传个 Options"把续存打断。

## 二、根因

四个问题其实是两个根因：

1. **会话没有"数据面"**：会话状态只活在对象内存里，既没序列化出口，也没落库载体；顺带没有淘汰策略 → 前两个问题。
2. **契约与实现耦合在一个模块里**：`Memory` 既定义 `ISessionStore` 又直接实现内存版，而它被约束为「仅依赖 Shared」，于是任何基础设施（SQLite/Dapper）都无处安放 → 后两个问题。

---

## 三、目标 / 非目标

**目标**
- 重启进程后，同一 `sessionId` 仍能接上上文（判据：序列化往返历史不丢）。
- 进程内与会话表都有界：TTL 过期 + 条数上限，长跑不涨内存、表不长垃圾。
- 长期记忆有载体、有写入/召回/遗忘口径，且按 scope 隔离。
- 全程不违反模块依赖方向；`Memory` 项目继续只依赖 `Shared`。

**非目标（本方案不碰）**
- 历史裁剪 / 压缩 / token 预算 → 归 `Context`（红线 #1）。
- **prompt 组装 / 注入条数与长度 / 预算分配 → 归 `Context`；`Memory` 只出结构化数据，不出文本**（详见 §4.8）。
- **历史策略（裁剪 / 压缩 / 模型可见视图）→ 归 `Context`**；`Memory` 只持久化完整会话，不裁剪。
- run 断点恢复、工具幂等 → 归 P2-2 / Harness。
- 多实例一致性：SQLite 单文件不是分布式会话存储，多副本部署仍需外置存储（记为已知限制）。
- 长期记忆的向量语义召回：MVP 先关键词，向量化留到 phase 3。

## 四、决策

### 4.1 模块拆分（解决"依赖方向挡住持久化"）

新增项目 `src/AgentWorkbench.Memory.Persistence`，与 `Knowledge.Local` / `Knowledge.Abstractions` 的既有模式一致：

```
Memory（契约 + 内存实现 + Options）            → Shared
Memory.Persistence（SQLite 实现）              → Memory, Persistence, Shared, (ToolExecution)
Context（组装面，本方案不改其依赖）             → Knowledge.Abstractions, Shared
Webapi（组合根）                                → Memory, Memory.Persistence, Context
AgentHarness                                    → Memory, Context（均不变）
```

- **契约留在 `Memory`**：`ISessionStore`、`ISessionFactory`、`ILongTermMemoryStore` + 记录类型。
- **实现在 `Memory.Persistence`**：读 `Persistence` 的连接/迁移，写 SQLite。
- **由组合根注入**：`Program.cs` 先 `AddNitroMemory(...)`（注册内存默认实现），再 `AddNitroMemoryPersistence(...)` 用 `services.Replace(...)` 覆盖 `ISessionStore` 并注册 `ILongTermMemoryStore`。这样未配置数据库的单元测试/精简环境依旧零依赖可跑。
- **不新增 `Context → Memory` 依赖**：Context 继续只依赖 `Knowledge.Abstractions`，记忆数据由编排层映射成中性片段后传入（见 §4.8）。

**为什么不这样做**
- ❌ 让 `Memory → Persistence`：把基础设施塞进契约模块，违反文档依赖方向，且 `Memory` 会被 Dapper/SQLite 污染。
- ❌ 把实现塞进 `Persistence`：通用基础设施反向依赖 `Memory`（进而依赖 MAF 会话类型），底层被上层语义污染。
- ❌ 依赖 MAF 自带的 `AgentSessionStore`：其控制反转点在框架内部（`IServiceProvider` 查找），装配不透明；我们保留 `ISessionStore` 作为唯一会话契约，后续可加一个 MAF 适配器而不改契约。

> 注：架构切片按顶层命名空间分组，`AgentWorkbench.Memory.Persistence` 仍落在 `Memory` 切片内（与 `AgentWorkbench.Knowledge.Local` 落在 `Knowledge` 切片同理）。因此依赖表按**项目**列明，并在 `AGENTS.md` 补一行。

### 4.2 会话契约（解决"序列化出口"）

把 `ISessionStore` 从「只会在内存里建会话」升级为「会加载/落库会话」，序列化细节通过 `ISessionFactory` 抽象（由 Harness 用当前 `agent` 实现）：

```csharp
// src/AgentWorkbench.Memory/SessionStore.cs
public interface ISessionStore
{
    Task<AgentSession> GetOrCreateAsync(
        string sessionId, ISessionFactory factory, CancellationToken cancellationToken = default);

    Task SaveAsync(
        string sessionId, ISessionFactory factory, AgentSession session, CancellationToken cancellationToken = default);
}

/// <summary>会话材料化：建新会话 / 序列化 / 反序列化。由 AgentHarness 用当前 agent 实现。</summary>
public interface ISessionFactory
{
    ValueTask<AgentSession> CreateAsync(CancellationToken cancellationToken);
    ValueTask<JsonElement> SerializeAsync(AgentSession session, CancellationToken cancellationToken);
    ValueTask<AgentSession> DeserializeAsync(JsonElement state, CancellationToken cancellationToken);
}
```

- 内存版 `SessionStore`：`CreateAsync` 建新会话；`SaveAsync` 是 no-op（对象还在内存里）。
- 落库版 `SqliteSessionStore`（在 `Memory.Persistence`）：命中且未过期 → `factory.DeserializeAsync(state)`；否则 `factory.CreateAsync()`；`SaveAsync` → `factory.SerializeAsync` 后写表。
- Harness 侧只多一个内部适配器：

```csharp
private sealed class AgentSessionFactory(AIAgent agent) : ISessionFactory
{
    // 注意：options 必须为 null（见 §1 spike），否则 MAF 抛 NotSupportedException
    public ValueTask<AgentSession> CreateAsync(CancellationToken ct) => agent.CreateSessionAsync(ct);
    public ValueTask<JsonElement> SerializeAsync(AgentSession s, CancellationToken ct)
        => agent.SerializeSessionAsync(s, null, ct);
    public ValueTask<AgentSession> DeserializeAsync(JsonElement e, CancellationToken ct)
        => agent.DeserializeSessionAsync(e, null, ct);
}
```

契约变更会影响三处 Harness 测试里的 `new SessionStore()`（签名参数变了，但调用点只在 `AgentHarnessService`），改动可控。

### 4.3 会话表（解决"重启即丢"）

`M023_CreateAgentSessions`（`[Migration(202601010023)]`）：

```sql
agent_sessions (
  session_id    TEXT PRIMARY KEY,          -- 64，对齐 agent_runs.session_id
  state_json    TEXT NOT NULL,             -- MAF 序列化结果，含 InMemoryChatHistoryProvider 历史
  created_at    TEXT NOT NULL,             -- ISO-8601
  updated_at    TEXT NOT NULL,
  expires_at    TEXT NULL                  -- NULL = 不过期
)
CREATE INDEX ix_agent_sessions_expires ON agent_sessions(expires_at)
```

- 只增表、不破坏既有迁移，符合「DB 变更必须 FluentMigrator」。
- 不存 `message_count`：当前没有消费者（保留策略还没做），先不写永远为 0 的列。

### 4.4 TTL 与上限（解决"字典无限增长"）

`MemoryOptions` 扩展（沿用 `Harness:Memory` 配置节）：

| 键 | 默认 | 含义 |
| --- | --- | --- |
| `SessionEnabled` | `true` | 不变 |
| `SessionTtlMinutes` | `1440`（24h） | `0` = 不过期 |
| `MaxCachedSessions` | `1000` | 内存缓存条数上限，`0` = 不限 |
| `EvictionSweepSeconds` | `60` | 后台清理周期（落库版） |

- **内存版**：`ConcurrentDictionary<string, Entry>`，`Entry` 记 `LastAccess`；命中时按 `TimeProvider` 判过期并顺带淘汰，超过 `MaxCachedSessions` 时按 LRU 淘汰，保证读路径 O(1) 且不依赖后台线程。
- **落库版**：读时判 `expires_at`（过期即删并当未命中）；`Memory.Persistence` 里加一个 `SessionRetentionService : BackgroundService`（`PeriodicTimer`）定期 `PurgeExpired()`，让 Webapi 保持只做组合。
- 注入 `TimeProvider` 而不是直接读 `DateTimeOffset.UtcNow`，TTL / 淘汰用例才能真正做到确定性（红绿可复现）。

### 4.5 长期记忆载体（解决"没有载体"）

新增 `M024_CreateMemoryItems`（`[Migration(202601010024)]`）：

```sql
memory_items (
  id                TEXT PRIMARY KEY,       -- guid N
  scope_type        TEXT NOT NULL,          -- global | agent | user | session
  scope_id          TEXT NOT NULL DEFAULT '',
  kind              TEXT NOT NULL DEFAULT 'fact',  -- fact | preference | decision | note
  mem_key           TEXT NULL,              -- 同 (scope_type, scope_id, mem_key) 覆盖（upsert 键）
  content           TEXT NOT NULL,
  importance        REAL NOT NULL DEFAULT 0.5,
  source_session_id TEXT NULL,
  source_run_id     INTEGER NULL,
  created_at        TEXT NOT NULL,
  updated_at        TEXT NOT NULL,
  last_used_at      TEXT NULL,
  use_count         INTEGER NOT NULL DEFAULT 0,
  expires_at        TEXT NULL               -- 隐私保留期
)
CREATE UNIQUE INDEX ux_memory_items_key ON memory_items(scope_type, scope_id, mem_key)
CREATE INDEX ix_memory_items_scope ON memory_items(scope_type, scope_id)
CREATE INDEX ix_memory_items_expires ON memory_items(expires_at)
```

> SQLite 的唯一索引允许多个 `NULL`，所以"没有 mem_key 的记忆"不会被去重键误伤。

契约（`Memory` 内，不依赖 MAF）：

```csharp
public interface ILongTermMemoryStore
{
    Task<MemoryItem> RememberAsync(MemoryWrite write, CancellationToken ct = default);
    Task<IReadOnlyList<MemoryItem>> RecallAsync(MemoryQuery query, CancellationToken ct = default);
    Task<bool> ForgetAsync(string id, CancellationToken ct = default);
    Task<int> PurgeExpiredAsync(CancellationToken ct = default);
}
```

- **写入口径**：`RememberAsync` 同 `(scope_type, scope_id, mem_key)` 覆盖，没有 key 则新增。
- **召回口径（MVP）**：按 scope 过滤（`scope_id` 匹配 或 `IncludeGlobal` 且 `scope_type='global'`），`content` / `mem_key` 走 `LIKE`，按 `importance DESC, updated_at DESC` 取**候选 K**（`MemoryQuery.CandidateK`），命中后回写 `last_used_at` / `use_count`。
  - ⚠️ `CandidateK` 只是**取库候选上限**；最终注入几条、多长、占多少预算由 `Context` 决定（见 §4.8）。Memory 不产出 prompt 文本。
- **隐私口径**：scope 隔离 + `expires_at` + 显式 `ForgetAsync`；召回默认不含 `global` 之外的 scope。
- **落库实现**：`SqliteLongTermMemoryStore`（`Memory.Persistence`）。

**两个入口（分阶段）**
1. **MVP（phase 2）**：记忆工具。`Memory.Persistence` 注册 `IAgentToolProvider`（`remember` / `recall`），与 `Knowledge.Local` 的 `SearchKnowledgeTool` 同构——依赖方向允许 `Memory.Persistence → ToolExecution`，工具平台不反向依赖记忆。
   - 这是 **agent 主动** 的 IO 通道，工具返回**原始记忆数据**，不是系统拼好的 prompt；它不与 Context 的「系统注入」职责冲突。
2. **自动召回（phase 3）**：与知识检索保持同形——`Memory` 的 `RecallAsync` 只返回结构化候选，**注入格式与预算由 `Context` 唯一负责**：
   - `AgentHarness` 调 `RecallAsync(input)`（IO，在 Memory）→ 把 `MemoryItem` 映射成 Context 的中性片段 → 调 `IContextBuilder.Compose(...)`（纯逻辑，在 Context）。
   - `Context` **不引用 `Memory`**：新增一个中性片段类型（如 `ContextFragment { Kind, Title, Lines }`），知识命中与记忆项在编排层各自映射到它；这也顺带解掉 Context 对 `RetrievalHit` 的硬绑定（可选，phase 3 落地时定）。
   - 结论：**召回（IO）= Memory，注入（纯逻辑/预算）= Context，串联 = Harness**，三者不重叠。

### 4.6 编排层改动（`AgentHarness`）

- 构造 `AgentSessionFactory(agent)`，`GetOrCreateAsync(sessionId, factory)`。
- run 结束（成功 / 失败 / 取消 / 超时）后 best-effort `SaveAsync`，沿用 `PersistQuietlyAsync` 的思路：**落库失败不能掩盖原始结局**，用 `CancellationToken.None` 写。
- 长期记忆注入（phase 3）时，Harness 是唯一把 `MemoryItem` 映射成 Context 中性片段的地方；Memory 与 Context 互不认识。
- `HarnessCapabilities.Memory` 语义不变；如需暴露长期记忆，另加 `LongTermMemory` 能力位（可选）。

### 4.7 组合根与配置

```csharp
// Program.cs
builder.Services.AddNitroMemory(builder.Configuration);            // 契约 + 内存默认实现
```

### 4.8 与 Context 的职责边界（防重叠）

`src/AgentWorkbench.Context` 的红线是「禁止 IO、只看传进来的东西、不新建第二个历史存储」。据此把职责切成三面，任何一边都不越界：

| 面 | 模块 | 职责 | IO | 拥有的契约 |
| --- | --- | --- | --- | --- |
| 数据面 | `Memory` / `Memory.Persistence` | 会话存取；长期记忆的存 / 查 / 忘；返回**结构化数据** | ✅（查库） | `ISessionStore` / `ISessionFactory` / `ILongTermMemoryStore` |
| 组装面 | `Context` | 把传入材料拼成最终 user 文本；注入条数 / 长度 / token 预算；**历史裁剪与压缩** | ❌（纯逻辑） | `IContextBuilder`（+ 中性片段 DTO） |
| 编排面 | `AgentHarness` | Memory 取数据 → Context 组装 → 调模型 | ✅（编排） | — |

四条硬规则：

1. **Memory 不拼 prompt**：`RecallAsync` 只回 `MemoryItem[]`，绝不回「拼好的 user 文本」或带 【记忆】 标题的字符串。
2. **Memory 不管注入策略**：注入几条、每条多长、和知识/历史怎么分预算，全在 `Context`；`MemoryQuery.CandidateK` 只是取库候选上限。
3. **Context 不查库**：它永远只处理调用方递进来的材料；记忆与知识对它都是「中性片段」，因此它的 `csproj` 不新增对 `Memory` / `Persistence` 的引用。
4. **历史只有一个策略点**：`Memory` 持久化**完整**会话（source of truth），`Context` 决定**模型可见视图**（裁剪 / 压缩 / 预算）；Memory 绝不裁剪历史，Context 绝不落库历史。

> 与现状的一致性：知识检索已经是这个形状（`IKnowledgeEngine.RetrieveAsync` 取候选 → `ContextBuilder.Compose` 注入）。长期记忆只是**第二个检索来源、共用同一个注入点**，而不是在 Memory 里再造一条注入管线。

### 实施时的两处补充决定（阶段 1 / 2 落定时确认）

1. **去掉 `message_count` 列**：当时无消费者，不写永远为 0 的列。
2. **记忆工具的作用域来自 ambient（`IMemoryScopeAccessor`）而不是模型参数**：
   方案原文只写了「召回按 scope 过滤」，没写工具怎么拿到 scope。最终由 `AgentHarness` 在每次 run 开始时
   设置 `MemoryScope.Session(sessionId)`，工具读 ambient；模型只能选「本作用域 / 全局」（`global=true`）。
   否则等于把隐私边界（scope_id）交给模型。默认作用域可用 `Harness:Memory:LongTermScope` 改成 `global`。
   写入内容为空 / 超长时工具回一句话而不抛异常（否则会把整轮 run 打挂）。

## 六、验收（判定型：正例绿 + 负控红；能脚本判定的禁止用 AI）

新增 `tests/AgentWorkbench.UnitTests/Memory/`：

| 判据 | 正例 | 负控（必须能红） |
| --- | --- | --- |
| 同 id 复用 | 同 `sessionId` 取两次 → 同一实例 | 换一个 `sessionId` → 必须新建、不得复用 |
| 会话续存 | 序列化→落库→**重建 store 与 agent**（模拟重启）→ 历史续上 | 不写 `state_json`（或写别家 session）→ 重启后历史为空 / 不得读到别人会话 |
| 开关 | `SessionEnabled=true` 多轮共享 | `SessionEnabled=false` → 两轮不共享（历史必须丢） |
| 上限 | `MaxCachedSessions=2` 插 3 条 → 最久未用被淘汰 | 上限设为 `0`（不限）→ 不淘汰 |
| TTL | 用假 `TimeProvider` 越过 TTL → 视为未命中 | TTL 设为极大 / `0` → 仍命中 |
| 长期记忆隔离 | 同 scope 写入后可召回 | 换 scope 查询 → 必须为空 |
| 去重 | 同 `(scope,key)` 二次写入 → 覆盖不新增 | 去掉 key → 两条 |
| 隐私 | 过 `expires_at` 后不召回 | — |
| **职责不重叠** | Memory 只回结构化候选（`RecallAsync` 的返回不含 prompt 文本） | 架构测试：`Context` 不得依赖 `Memory` / `Persistence`；把一行 `using AgentWorkbench.Memory;` 加进 Context → 必须变红 |
| **预算归 Context** | 候选多、预算大 → 注入多；注入条数由 Context 决定 | 候选 `CandidateK` 调大但 Context 预算调小 → 注入条数**跟着预算变**，证明预算不在 Memory |

架构层（`tests/AgentWorkbench.ArchitectureTests`）：
- 新增用例：`Memory` 类型不得依赖 `Persistence`；**负控**：把一行 `using AgentWorkbench.Persistence;` 加进 `Memory` → 必须变红。
- 现有 `Domain_should_not_depend_on_infrastructure` / `Modules_should_not_depend_on_webapi` / 无环测试保持全绿。

> 端到端「真的重启进程」超出当前能力：`scripts/` 未落地（见缺口清单），阶段 1 用"销毁连接 + 重建 store/agent"的进程内等价物判定；真重启场景待验收脚本落地后补。

## 九、备选方案（为何不选）

1. **只持久化历史消息（复用 `messages` 表），不持久化整个会话**：丢失 MAF 会话里除历史外的状态（routing / provider state），且把"历史怎么进会话"塞进 `Memory`，踩红线 #1；序列化整会话更完整、更少猜测。
2. **让 `Memory` 直接引用 `Persistence`**：最省事，但破坏依赖方向、把契约模块污染成基础设施模块，架构测试与文档都不允许。
3. **用 MAF 自带 `AgentSessionStore` 接管**：控制反转不透明、与现有 `ISessionStore` 契约重叠；保留自有契约、后续加适配器更可控。
4. **只做 TTL 不做落库**：治不了"重启即丢"这个核心缺口（P1-3）。
