# 记忆作用域与身份策略（跨模块记录）

> 状态：**已决定「暂不实现」，待权限管理落地后重启** ｜ 日期：2026-10-12
> 关联：[ADR-0003](../adr/0003-memory-persistence-boundary.md)、[状态与记忆持久化方案](状态与记忆持久化方案.md)、`docs/底座建设清单.md`

**收纳范围**：本文件收两类东西 ——

1. 「记忆作用域 / 跨会话记忆」这个决策（本文主体）；
2. 凡是**必须在权限系统建立之后才能解决**的跨模块问题（第五节那两条 + 将来新发现的，见第七节）。

不属于第 2 类的跨模块问题**不要放在这里**，留在各自模块的 README。

## 一、为什么记这一笔

阶段 1 / 2 落地后，暴露出一个需求：

> 记下来的东西，**换一个会话就找不到**。

分析后发现，这个需求的**前提是「这是谁」**，而本仓库目前没有任何身份概念。所以结论是
**先不做**，等权限管理落地后再重启 —— 本文记录这个决定、依据，以及将来接手时改哪里。

---

## 二、现状事实（只列与本决策相关的）

| 位置 | 身份字段 | 现状 |
| --- | --- | --- |
| `HarnessRunRequest` | 无 | `(SessionId, Input, UseKnowledge)` |
| `conversations` 表（M016） | 无 owner | 只有 `id` / `title` / 时间 |
| `agent_runs`（M014）、`agent_sessions`（M023） | 只有 `session_id` | 无 `user_id` |
| `memory_items`（M024） | 有 `scope_type` / `scope_id` | 但**没有任何代码能填入 user 作用域** |
| 鉴权 | **零** | 无 `Authorize` / `ClaimsPrincipal` / 鉴权中间件 |
| `MemoryScope.User(userId)` | 契约已存在 | **零调用点（空壳）** |
| `MemoryScope.Agent(agentId)` | 契约已存在 | **零调用点（空壳）** |

唯一的身份锚点是 `sessionId`，而它由客户端提供（`HarnessController` 从请求体读，为空时服务端生成 Guid）。

**因此：当前「记忆」的真实语义是「同一次会话内的记忆」，而不是「长期记忆」。**
`MemoryOptions.LongTermScope` 默认 `session`，`remember` 默认写进当前会话的 scope。

---

## 三、决策

**现在不做，等权限管理（鉴权 / 用户身份）落地后再做。**

理由：

1. 这个需求的前提就是「这是谁」。权限管理没做，就得先临时编一个身份锚点，等权限管理上来再返工一遍。
2. 权限管理做完后，这个问题会**自己变简单**：有了 `userId`，`MemoryScope.User(userId)`（现成的空壳）直接可用。
3. 现在停下来的收益是零损失 —— 阶段 2 交付的记忆已经能用（模型调 `remember` / `recall`），
   缺的只是「跨会话」这一个便利。

## 四、将来怎么接（接缝已经留好，不会返工）

| 到时候要改 | 改动量 |
| --- | --- |
| `HarnessRunRequest` 加 `UserId` | 1 处（做权限管理时本来就会改） |
| `AgentHarness` 里设置作用域那一行（`_memoryScope.Begin(...)`） | 1 行 |
| 作用域解析策略（`LongTermScope` 支持 `user`） | 1 处（`MemoryToolScope.Resolve` + Harness，共 2 个小地方） |
| `MemoryScope.User` / `MemoryScope.Agent` 契约 | **不用改**，已存在 |
| `memory_items` 表结构 | **不用改**，`scope_type` / `scope_id` 已经够用 |
| 已有数据 | **不用迁移**，老的 `scope_type='session'` 行留着即可，只是不再被召回 |

身份来源建议按部署形态选（内网单机 → 请求体带 `userId`；对外 → 走鉴权 Claims）。
**两者的落点是同一个位置**，所以先做哪一种都不会白做。

## 五、做权限管理时必须一起收口的两件事

这两件**本身不是本次决策的内容**，但都在「权限管理」这一步里变成真问题，别漏。

### 1. `global` 写入门槛（现在是敞开的）

`remember` 工具暴露了 `global` 参数，**由模型自主决定**要不要写全局，而全局记忆**任何会话都能召回**：

```csharp
var scope = MemoryToolScope.Resolve(_scopeAccessor, _options, global == true);
```

- 单人单机部署：`global` 就是「我的全局」，没问题。
- 库变成多用户后：同一个 `global` 变成「所有人共享」。模型可以根据对话内容自主把 A 说的话写进去，B 就召回到了，
  而且**不可控**。

将来要加 `MemoryOptions.AllowGlobalWrite`（默认 `false`），让 `global=true` 受配置放行。
判据：正例放行时能写全局；负控关闭时工具返回拒绝**且库里查不到 global 行**。

### 2. `sessionId` 的归属校验

有了用户身份之后，`sessionId` 也必须校验归属，否则拿到别人的 `sessionId` 就能续别人的会话。

## 六、明确不做 / 已排除

| 项 | 结论 |
| --- | --- |
| 记忆提升（写入时把 session 记忆提升到 user 层） | **不做**。现在只有读时叠加（`MemoryQuery.IncludeGlobal`），没有写时提升；独立于身份，暂不需要 |
| `MemoryScope.Agent` | **建议删除**。没有任何「agent 身份」来源，且底座里连 agent 实体都还不存在；留着是「看起来支持」的误导。将来真需要再加一个常量，比删已公开契约便宜 |
| 记忆的语义召回（FTS5 / 向量） | **另立**。属「检索/生成类改动」，按测试标准必须先定度量指标（命中率@k / MRR）；且要先在「Memory 自带检索」与「复用 `IKnowledgeEngine`」之间做架构决策 |
| 长期记忆自动注入（阶段 3a） | **另立**。与身份无关，但收益有限（每轮塞记忆费 token、可能塞不相关），且会引入注入预算策略 |

## 七、附：已评估、不需要权限系统的问题

按「跨模块问题的解决时点是否依赖权限系统」逐模块筛过一遍，已评估的结论如下：

| 模块 | 跨模块问题 | 依赖权限系统？ | 记在哪 |
| --- | --- | --- | --- |
| `Context` | 历史消息裁剪 / 历史压缩 / 片段与历史共用预算 / 按 token 精确截断 / 拿不到用量 / 记忆片段注入 | **否** | `src/AgentWorkbench.Context/README.md` §2.2 |

`Context` 那几项依赖的是「编排层把材料与预算传进来」和「`ModelRuntime` 暴露只读计量」，
与「这是谁」无关，因此不进本文件。

其中两项与身份**相邻**，但耦合点不在 `Context`，所以只在本文登记：

| 相邻项 | 真正的耦合点 | 本文位置 |
| --- | --- | --- |
| 会话历史必须按用户隔离（否则拿到别人 `sessionId` 就能续别人会话） | `AgentHarness` / `Memory`（`agent_sessions` 无 `user_id`） | 第五节第 2 条 |
| 记忆片段注入中按 user / global 作用域召回的那一半 | `AgentHarness` 的召回作用域（`Context` 只负责拼文本） | 第三节、第五节第 1 条 |

## 八、什么情况下应该回来做

满足**任一**条件即可重启本决策：

1. 权限管理（鉴权 / 用户身份）已落地 —— 这是主要触发条件；
2. 出现真实的「新会话记不住我」的使用反馈；
3. 部署形态从「单人单机」变为「多人共用」—— 此时第五节第 1 条（`global` 门槛）**必须**先做。
