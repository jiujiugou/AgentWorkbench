# 文档工程研究依据与证据等级

- **适用侧**：公共 ｜ **寿命**：常驻 ｜ **最后校准**：2026-11-22

## 一、这份文件解决什么

本次文档工程改造引用了八份外部资料。它们**证据强度不同**：有的是正式标准，有的只是某家公司的经验自述，有的只是社区方法框架。把它们并列成"最佳实践"会误导后续读者，也会让 Coding Agent 把建议当成强制要求。

本文记录：每份资料的实际内容、访问状态、证据等级、可借鉴之处、以及**不适用于本项目的地方**。规范正文只引用本文的编号，不重复这些结论。

## 二、证据等级定义

| 等级 | 含义 | 在规范中的效力 |
|---|---|---|
| **S** Standard | 正式发布的标准，有明确规范性条款 | 可引用为要求，但需核对全文；只有摘要时降级使用 |
| **H** Handbook | 工程手册的系统性建议，有完整论证 | 可引用为应然做法，须标明"建议" |
| **P** Practice | 某个组织公开的实际做法 | 只能作为可选实践，不得包装成行业标准 |
| **M** Method | 社区方法/框架，无固定权威 | 只借用概念区分，不借用其流程仪式 |

## 三、逐份资料

### R1 · Diátaxis（M）

- 来源：https://diataxis.fr/ ；辅以 `/map/` 页。
- 访问状态：全文可读。
- 核心：文档按两轴分为四类——**tutorials**（学，教学）、**how-to guides**（做事，目标导向）、**reference**（陈述机制，信息导向）、**explanation**（阐明理解）。原文表格给四类的答问分别对应 "Can you teach me to...?" / "How do I...?" / "What is...?" / "Why...?"，形态分别是 a lesson / a series of steps / dry description / discursive explanation。
- 关键警告：原文 "Blur" 一节指出相邻类型会互相渗透（guide action / serve application of skill 等），一旦模糊，"Writing style and content make their way into inappropriate places"。
- 可借鉴：作为规范 §1 文档分类的主结构；作为"一份文档混多种类型"这一病态的判据来源。
- **不借用**：它的完整四象限流程仪式。本项目是单人项目，不会为 tutorial 单独建目录。

### R2 · Google Documentation Best Practices（H，部分受限）

- 来源：题目给的 best_practices.html **两次抓取失败（fetch failed）**。改用 Google Developer Documentation Style Guide 与 Google Technical Writing Course 的公开页面补证：
  - https://developers.google.cn/style （"About this guide"，2025-12-09 更新）
  - https://developers.google.com/tech-writing/one/documents
- 访问状态：原始指定页**不可达**；替代页可读。这是证据限制，不假称读到了原文。
- 核心（来自可读页面）：
  - 文档开头要写 scope 和 **non-scope**：原文 "A better document additionally defines its non-scope—the topics not covered that the target audience might reasonably expect your document to cover."
  - 要明确 audience，含前置知识：原文 "State your audience"、"What do your readers already know before they read this document?"
  - 开头给要点：原文 "ensure that the start of your document answers your readers' essential questions."
  - 参考层级：项目自身风格 → 本指南 → 第三方参考（Merriam-Webster / Chicago Manual / Microsoft Writing Style Guide）。
  - "Break the rules"：原文 "This guide contains guidelines, not rules. Depart from it when doing so improves your content."——**这直接支持"不把建议写成强制标准"**。
- 可借鉴：scope/non-scope、audience、要点前置，写进规范 §2 和 §4。
- **不借用**：英文字母拼写、串行逗号等纯英文规则；中文文档不适用。

### R3 · OpenAI Harness Engineering（P）

- 来源：https://openai.com/index/harness-engineering/
- 访问状态：全文可读。
- 核心主张与**证据强度自评**（原文没有分级，以下是本次阅读时的判定）：
  - "Humans steer. Agents execute." —— 定性主张。
  - "We made repository knowledge the system of record."、`AGENTS.md` 约 100 行，定位成 "the table of contents"，`docs/` 才是 source of record —— 结构性事实 + 设计主张。
  - 反对 "one big AGENTS.md"，四条理由：context 稀缺、too much guidance becomes non-guidance、rots instantly、hard to verify —— 轶事/定性，无对照实验。
  - progressive disclosure、专用 linters 与 CI 校验知识库、recurring "doc-gardening" agent 自动开修补 PR —— 结构性事实。
  - "Agent legibility is the goal." / "anything it can't access in-context while running effectively doesn't exist." —— 设计主张。
  - "enforcing invariants, not micromanaging implementations"、"enforce boundaries centrally, allow autonomy locally" —— 设计主张，且有 custom linters + structural tests 作为执行手段。
  - 数字：约百万行、1500 PR、3.5 PR/人/日、开发时间约 1/10、每周 20% 时间清 AI slop —— **量化自述，无外部审计、无口径细节**。
- 可借鉴：AGENTS.md 做目录不做百科；docs/ 做 system of record；linters 校验文档结构；doc-gardening 扫描；**把约束写进可执行的 linter 而非只写进 prose**——这与本项目"架构门禁"已有做法一致。
- **不借用**：它的仓库布局（design-docs/exec-plans/product-specs 等一整套目录）。本项目规模不同，照搬就是过度文档化。它的数字不可当行业基准。

### R4 · ISO/IEC/IEEE 42010:2022（S，摘要级）

- 来源：https://www.iso.org/standard/74393.html
- 访问状态：**全文付费（CHF 204），仅公开摘要可读**。
- 摘要原文要点：规定 architecture description (AD) 的结构与表达要求；明确区分 "the architecture of an entity of interest" 与 "an AD expressing that architecture"；规定 AD framework (ADF)、ADL、architecture viewpoints、model kinds 的使用要求与符合性；**明确不规定**创建/使用/管理 AD 的过程、方法、记号、技术或工具，也不规定记录格式或媒介。
- 证据限制：**不能声称本文符合 ISO 42010 的规范性条款**——没有全文，无法逐条核对。只能借用其公开摘要中的概念区分（架构本身 vs 架构描述；viewpoint vs view）。
- 可借鉴：架构文档要显式声明利益相关方与关注点、视图与视角；架构描述不等于架构本身。
- **不借用**："完整符合 ISO 42010" 的说法。

### R5 · ISO/IEC/IEEE 29148:2018（S，摘要级）

- 来源：https://www.iso.org/standard/72089.html
- 访问状态：**全文付费（CHF 227），仅公开摘要可读**。状态标注 "International Standard to be revised"。
- 摘要原文要点：规定贯穿生命周期的需求工程过程、必须产出的 information items 及其内容要求，并给出格式指南；适用于 15288/12207/15289 的使用场景。
- 证据限制：同 R4，**不能声称符合其规范性条款**。
- 可借鉴：需求与实现分离、需求产出物要有规定内容、需求过程要有验证环节。
- **不借用**：完整 SRS 模板。本项目正本已经承担需求职责，再建一套 SRS 就是重复定义。

### R6 · NASA Systems Engineering Handbook §4.2（H）

- 来源：https://www.nasa.gov/reference/4-2-technical-requirements-definition/
- 访问状态：全文可读。
- 核心：需求写成 "shall" statements，**每条一句、每条一个 shall**；好的需求是 clear / correct / complete / achievable / verifiable / unique / necessary；六步验证包括 "Are the Requirements Verifiable?" 与 "Are the Requirements Redundant or Over-specified?"；强调 **bidirectional traceability to the baselined stakeholder expectations**；Rationale 要记录 reason、assumptions、relationships、design constraints，并 "kept up to date"；需求经 customer 与 key stakeholders 同意后 baseline 并纳入 configuration control。
- 可借鉴：作为规范 §5 知识状态与 §6 证据追溯中"可验证性、双向追溯、理由必须记录且保持更新"的手册依据。
- **不借用**：SRR、PBS、MOE/MOP/TPM 等完整系统工程流程；本项目的六句判据已经承担可验证性角色。

### R7 · GDS ADR（P/H 之间：政府工程实践）

- 来源：https://gds-way.digital.cabinet-office.gov.uk/standards/architecture-decisions.html ；框架页 https://www.gov.uk/government/publications/architectural-decision-record-framework
- 访问状态：GDS Way 全文可读；题目给的 gov.uk 子页 404，已从检索结果取得等价内容。
- 核心：ADR 五段——Title（描述决定而非问题）/ Status / Context / Decision / Consequences（正反两面都要）；生命周期 Proposed → Accepted → Superseded；已被取代的 ADR **必须明确标 superseded 并链接到新 ADR**；若原决策已有部分实现，写新 ADR 而不是改写旧 ADR；澄清性补充可更新现有 ADR 的 Consequences。原文明确 "An ADR isn't a complete description of a software system or architecture."
- 可借鉴：作为规范 §7 生命周期与"ADR 不静默改写历史决策"的依据。
- **不借用**：它的跨部门升级矩阵（team / cross-team / department-wide / cross-government）。单人项目没有治理层级。

### R8 · C4 Model（M）

- 来源：https://c4model.com/ 与 https://c4model.com/abstractions
- 访问状态：全文可读。
- 核心：四层抽象 software system → container → component → code，人使用系统；四层图 system context / container / component / code，另有 system landscape / dynamic / deployment 辅助图；"abstraction-first" approach；notation independent、tooling independent。
- 可借鉴：架构文档按抽象层次组织，读者按层次进入；动态图可表达交互顺序。
- **不借用**：图形符号与绘图工具。本项目已有自己的六部件划分，不另建一套图集。

## 四、综合推导（不属于任何单一来源）

以下是本次从多份资料交叉推导出的建议，**不是任何标准的要求**，规范里按推导结论标注：

1. **"内容类型"与"生命周期状态"必须分列**。Diátaxis 给类型，GDS 给生命周期，两者叠加才完整；任一单独使用都会把"这是一份 reference"和"这份 reference 还有效吗"混成一个问题。（推导自 R1 + R7）
2. **不能用修改日期判断文档过期**。NASA 要求 rationale kept up to date，OpenAI 指出 monolithic manual "rots instantly"——两者都指向内容事实的变化，而非时间戳。（推导自 R6 + R3）
3. **文档不得充当门禁或判据源**。本项目既有纪律"文档不做功能，文档只做解释"，与 OpenAI "enforce invariants... with linters/structural tests" 一致：约束要落在机器可执行处，文档只解释它。（推导自项目纪律 + R3；这是本项目自有约束，不是外部标准要求）
4. **AI 生成的文档最典型的失真形态是把意图写成事实**。本次改造发现 `docs/core/工具执行.md` 描述了代码中不存在的 gateway 分支——这不是任何资料里的结论，是本次对真实代码核对后的实证。规范据此增加"实现声明必须定位到代码行"的检查项。

## 五、证据限制汇总

- ISO 42010、ISO 29148 **只有公开摘要，全文付费未获取**。规范中凡涉及这两份标准处，一律写"参考其公开摘要的概念区分"，不写"符合要求"。
- Google 指定页 best_practices.html **两次抓取失败**，用同组织公开的 style guide 与 technical writing course 补证，已在 R2 标明。
- OpenAI 文章的数字为**作者自述**，未见外部审计或方法说明；规范不引用其数字作为目标。
- 其余资料全文可读。
