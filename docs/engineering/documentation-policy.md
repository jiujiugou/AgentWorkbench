# 项目文档编写与维护规范

- **适用侧**：公共 ｜ **寿命**：常驻 ｜ **最后校准**：2026-11-22

## 0. 效力与边界

本规范是**文档表达的规范**，不是架构约束，也不是行为判据。依据见 [研究依据与证据等级.md](研究依据与证据等级.md)。

三条不可越界的效力线：

1. **文档不做功能，文档只做解释。** 结构约束归 `csproj` 引用与架构门禁，行为判据归测试输出。文档不得成为事实源、不得驱动门禁、不得反向生成模块结构。
2. **建议不等于要求。** 本规范中标注「应」的条款是本仓自定规则；引用外部资料时区分 S/H/P/M 四级（见研究依据 §2），**不得把某家公司的做法或标准摘要包装成强制标准**。
3. **不新增门禁。** 文档卫生由 `DocsHygieneTests` 既有四条 Checker 承担（D1 状态位 / D2 相对链接 / D3 局部不重定义 / D4 纯文本路径）。本规范只解释它们的语义，不另建一套。要新增机器检查，先问现有 Checker 能否扩展。

适用范围：`docs/` 全部 Markdown、`src/**/README.md`。不适用：`.workbuddy/`（本地笔记，不提交）、`docs/机制层/`（机械生成快照）。

## 1. 文档分类

### 1.1 内容类型（八类）

内容是**类型**与**生命周期状态**两个正交维度。一份文档的类型不随它过期而改变。类型划分参照 Diátaxis 四类（R1/M），并按本仓实际补齐四类。

| 类型 | 解决什么 | 面向谁 | 应包含 | 不应包含 | 本仓实例 |
|---|---|---|---|---|---|
| **Requirements 需求** | 系统要满足什么、什么不算成功 | 人类（需求方）+ Agent | 目标、边界、判据、判定权 | 当前实现、类与方法、测试结果 | `docs/产品目标与范围.md` |
| **Architecture 架构** | 边界、职责、状态所有权、交互与恢复语义 | 改代码的人 + Agent | 部件边界、依赖契约、决策权归属、失败/恢复语义 | 类清单、行号流水账、进度 | `docs/core/工具执行.md`（六部件解释） |
| **ADR 决策记录** | 当初为什么这么定、否掉了什么 | 后来的人 + Agent | 一条决策、背景、后果正反、重开条件 | 完整架构、实现细节、进度 | `docs/adr/` |
| **Tutorial 教程** | 带新手走通一次 | 新接手的人 | 一条可走通的路径、预期结果 | 边界讨论、设计理由 | 本仓暂无独立教程 |
| **How-to 操作指南** | 完成一个具体任务 | 要动手的人 | 前提、步骤、怎么确认做成了 | 为什么这么设计 | `scripts/dev.sh` 用法散见 AGENTS.md |
| **Reference 参考** | 查参数、查契约 | 所有人 | 机器可生成的清单、配置键、端点 | 推测、未验证行为 | 优先指向命令或生成脚本，不手抄 |
| **Verification 验证** | 怎么判定真假、证据在哪 | 验收者 + Agent | 可证伪判据、观察点、证据状态 | 绿灯数当结论、测试文件清单（会漂） | `docs/验收映射.md`、`docs/host/运行期流程.md` |
| **Execution Plan 执行计划** | 本阶段做什么、卡在哪 | 人类 | 现状、卡点、下一步、判定权 | 已完成事项的美化、无主体的待办 | `docs/plans/P01`–`P15`（一问题一文件） |

说明：

- `AGENTS.md` **不属于以上任何类型**。它是给 Agent 的入口指令（目录/约束），定位见其自身第 0 节。不得把它当事实源。
- 一份文档原则上只属于一种类型。若发现自己在同一篇里既讲"为什么"又讲"怎么查"，拆开或明确分节并标注各自类型。
- `docs/core/` 下六份是 **Architecture 类中的 explanation 子型**（解释型架构文档）；它们不是 Reference，故允许带设计理由，但**不得引入第二种写法定义**（D3 门禁）。

### 1.2 生命周期状态（五种）

| 状态 | 含义 | 进入条件 | 退出条件 |
|---|---|---|---|
| **Draft** | 尚未生效，可被推翻 | 开始写 | 人类确认后转 Current |
| **Current** | 当前有效 | Draft 经确认 | 事实过期 / 被取代 / 主动废弃 |
| **Deprecated** | 仍可读但不再推荐 | 存在替代做法但未完全取代 | 归档 |
| **Superseded** | 被另一份明确取代 | 新文档生效并**双向链接** | 归档 |
| **Archived** | 只读历史 | 已无现行读者 | 不退出 |

规则：

- ADR **不得静默改写历史决策**：内容变化走 Superseded + 新 ADR，正/负后果可随理解深化在原文补注并留痕（GDS/R7）。
- 非 ADR 文档同样适用状态流转；Superseded 必须双向链接，禁止只改正文不标状态。
- 状态位三要素（**适用侧 / 寿命 / 最后校准或建立**）由 D1 门禁检查，写在前 15 行。`docs/adr/` 与 `docs/plans/` 自带生命周期，不套此格式。

### 1.3 类型与状态的区分例

- 「`docs/验收映射.md` 是 Verification 类型」——说的是它解决什么问题。
- 「`docs/验收映射.md` 最后校准 2026-11-22、寿命 Current」——说的是它现在是否有效。
- 把这两件事写在一个字段里（例如「状态：现状型参考」）是常见错误，禁止。

## 2. 文档内容边界

### 2.1 通用开场要求

每份正式文档前 15 行必须包含（D1 机械检查）：

```
- **适用侧**：底座 / 应用 / 公共 ｜ **寿命**：常驻 / 现状（就近维护）/ 阶段 ｜ **最后校准**：YYYY-MM-DD
```

并应给出**范围与非范围**（Google/R2）：明确"本文回答什么、不回答什么"。非范围只写读者合理预期会问的内容，不写明显无关的东西。

### 2.2 按类型的边界细则

**Requirements 需求**

- 回答"是什么、做到哪、什么不算成功"，不回答"怎么实现"。
- 判据必须可证伪，并写明**判定权在谁**（我方测试 / 对方系统 / 人类）。
- 禁止把当前实现状态写进需求正文；现状单独放状态节并标日期。

**Architecture 架构**

- 必须解释：设计目的、系统或组件边界、职责分配、外部依赖、接口与交互关系、状态所有权、执行过程、错误与恢复语义、架构约束、验证依据。
- **不得只用正常流程的时间顺序定义组件边界**。正常流程说明"先做 A 再做 B"，不说明"A 和 B 谁有权决定、谁持有状态、谁对外负责"。边界必须按控制权、决策权、执行责任、状态所有权、外部接口五维分别写清。
- 依赖不能只列名字，必须写**依赖契约**：依赖什么能力、什么形状的数据、失败时谁能继续、失败时归谁。
- 类清单、方法行号不是架构文档的主体；需要时作为定位辅助，且必须核对真实代码（见 §3.3）。

**ADR**

- 一条决策一篇，编号不复用，写完不改（Superseded 除外）。
- 后果**正反成对**；只写好处的 ADR 是宣传不是记录。
- 必须给**可观测的重开条件**：什么事实出现时这条决策应被重新审视。

**Verification 验证**

- 写"去哪里查、什么算过、什么算失败、现在有没有证据"，不写"测试有多少条"。
- 判定型用例要求**正例能绿、负控能红**；能脚本判定的禁止用 AI 判。
- 绿灯只证明被断言的那件事，不能推广成整体正确性。

**Execution Plan 执行计划**

- 一问题一文件，文件名带编号；每个文件四件事：现状 / 卡在哪 / 下一步 / 判定权。
- 索引只做导航，不写正文（避免同一件事两处写、改一处漏一处）。

**Reference 参考**

- 优先指向命令或生成脚本，不手抄会漂的清单（默认值、版本号、入口名）。
- 未验证的 API 行为必须标 `未验证`，不得写成"实际行为"。

## 3. 架构文档的设计要求

### 3.1 必须回答的十问

架构文档（六部件解释属于此类）应能回答：

1. 为什么有这个部件（设计目的）？
2. 边界在哪——它管什么、不管什么（判据一句话）？
3. 与相邻部件的职责如何分配（谁拥有哪块）？
4. 外部依赖是什么，依赖契约是什么（不是只列名字）？
5. 接口形态是什么（谁调谁、传什么、失败怎么回）？
6. 状态归谁所有（谁写、谁读、谁能改）？
7. 正常执行过程是什么（顺序，但**不能以此代替边界**）？
8. 异常、失败、恢复语义是什么（谁归类、谁收口、会不会重放）？
9. 并发与重复场景怎么处理（同一请求两次、同时两次）？
10. 架构约束是什么，如何验证（对应哪条门禁/判据）？

### 3.2 决策权与控制权分离

正常流程里"先校验、再审批、再执行"只说明调用顺序，**不说明谁决策**。架构文档必须分别回答：

- **控制权**：谁触发下一步（框架循环 / 我方钩子 / 调用方）？
- **决策权**：结果由谁判定（规则代码 / 模型 / 对方系统）？
- **执行责任**：副作用由谁产生（工具实现 / 网关 / 外部系统）？
- **状态所有权**：证据记在哪、谁能改（轨迹 / 账本 / 对方单据）？
- **外部接口**：跨边界传的是不透明数据还是共享业务类型？

### 3.3 实现事实必须核对代码

- 文档中的每条实现声明（类名、方法名、行号、调用链、配置默认值、依赖版本）**必须定位到真实代码**，且在当前工作区可读到。
- 写行号是高风险动作：代码一改就漂。优先写"方法名 + 文件"，行号只在必要时给出并同步校准。
- **禁止描述代码中不存在的分支**。本次改造实证：`docs/core/工具执行.md` 旧版写了 `gateway.Handles / gateway.ExecuteAsync` 分支，而真实 `FunctionInvoker` 中零命中——这是把设计意图写成实现事实的典型失真（见 [文档改造报告](文档改造报告.md)）。
- 找不到对应代码时，按 §4 标 `Assumption` 或进 `Open Question`，不得补全。

## 4. 事实与决策分类（六种知识状态）

每个重要主张都要显式或隐式归入以下一种。**禁止把 Assumption / Open Question 写成已确定的系统行为。**

| 状态 | 定义 | 允许怎么写 | 禁止 |
|---|---|---|---|
| **Requirement** | 已确认的需求 | 引正本、标第几句 | 混入当前实现 |
| **Decision** | 已批准的设计决策 | 引 ADR 编号与状态 | 把 Draft 决策写成 Accepted |
| **Implementation Fact** | 已从代码确认的实现事实 | 给文件与位置，必要时给行号 | 凭记忆写；描述不存在的分支 |
| **Verified Behavior** | 已通过验证的行为 | 给测试或真跑证据（见 §6） | 用绿灯数代替具体断言 |
| **Assumption** | 临时假设 | 明写"假设…"，给验证条件 | 当成事实使用；隐藏在句子里 |
| **Open Question** | 尚未解决的问题 | 进 `docs/plans/` 一问题一文件，本文留指针 | 擅自决定答案；写成"待办"混入正文 |

建议在长文档里用显式标签（例如 `实现事实：` / `假设：` / `未验证：`）。短文档至少在关键句上标注。

## 5. 文档质量要求

八项要求，每项给出**可执行的检查方法**，避免抽象口号：

| 要求 | 检查方法 |
|---|---|
| **清晰性** | 开头有 scope + non-scope + audience；一段只讲一件事；术语首次出现有定义。人工读一遍开场三句能否回答"这篇给谁、讲什么、不讲什么"。 |
| **完整性** | 按类型清单逐项对照（§2.2）；架构文档按十问逐项核对（§3.1）；缺项写"未覆盖"而不是省略。 |
| **一致性** | 同一事实全仓只在一处定义（单一事实源）；跨文档引用同一数字/路径/口径时，用脚本比对（见检查脚本）。 |
| **单一性** | 一条事实一个落点；发现两处定义时，选事实源，另一处改成指针。D3 门禁防 `docs/core/` 内重复定义写法。 |
| **可追溯性** | 每个重要主张有 §6 的 ID；能沿 需求 → 决策 → 职责 → 实现 → 用例 → 证据 走通；断链标 `UNKNOWN`。 |
| **可验证性** | 判定型主张问"改哪里会红"；没有负控的能力声明标 `未验证`。机器可判的不得用 AI 判。 |
| **边界明确性** | 每份文档有"不归本格/非范围"节；跨部件必写决策权与状态所有权归属。 |
| **依赖明确性** | 依赖列名字之外必须写契约（能力、数据形状、失败归属）；NuGet 依赖标准确版本与其保证的能力，不臆测框架行为。 |

## 6. 证据追溯机制

### 6.1 ID 规则

沿用项目现有稳定 ID，**不破坏、不重编号**：

- 六句：沿用「第 1 句 … 第 6 句」，不另编号。
- 架构约束：`AC-01`、`AC-02`。
- 架构门禁：`F38` 等既有编号。
- 流程验收：`S01`–`S10`，格内序号沿用 `S04_08` 形式。
- ADR：沿用 `ADR 00NN`（本仓 0001–0007；正本声明的其他编号见正本，本规范不改其归属）。
- 问题：`P01`–`P15`，新增顺延，不复用。

本次新增**证据类前缀**（只用于追溯，不改变上述 ID）：

| 前缀 | 指代 | 例 |
|---|---|---|
| `REQ-` | 已确认需求条款 | `REQ-3` = 六句第 3 句 |
| `ARCH-` | 架构约束 | `ARCH-01` = `AC-01` |
| `IMPL-` | 实现定位 | `IMPL-T01` = 工具执行管线的调用点 |
| `TEST-` | 测试用例 | `TEST-S04_08` |
| `EVID-` | 验证证据 | `EVID-R1` = 一次真跑证据 |
| `UNKNOWN-` | 未取得证据 | `UNKNOWN-4` = 第 4 句外部闭环 |

### 6.2 每项证据的五要素

每条追溯记录必须写清：来源、具体位置、能证明什么、**不能证明什么**、当前状态。没有证据写 `UNKNOWN`，**禁止为了让文档看起来完整而伪造追溯关系**。

追溯链：

```
需求或约束 → 架构决策 → 组件职责和接口 → 具体实现 → 验证用例 → 实际验证报告
```

实际记录见 [证据追溯索引](证据追溯索引.md)。

## 7. 维护规则

### 7.1 代码变更触发文档影响检查

以下变化**必须**做文档影响检查（在提交信息里写明"文档已校准"或"未涉及文档"）：

- 公共接口变更
- 组件职责变化
- 依赖关系变化
- 状态模型变化
- 执行流程变化
- 安全约束变化
- 配置语义变化
- 部署与恢复方式变化

不影响外部行为、架构或使用方式的内部重构，可声明"无文档影响"。

检查动作：定位受影响的文档 → 逐条核对实现事实 → 更新状态位日期 → 跑文档门禁 + 相关测试 → 记录证据缺口。

### 7.2 文档生命周期

按 §1.2 的五种状态流转。要点：

- ADR 不静默改写历史决策（GDS/R7）。
- 交付文档的"最后校准"写实际核对日期；`AGENTS.md` 现用 commit hash 定位基线，两种口径并存时**以能独立复核者为准**，不做形式统一（见 [文档改造报告](文档改造报告.md) 的未决项）。
- 完成的问题文件**留在原地**，状态改 `已解决` 并补证据与日期，不删除、不复用编号。

### 7.3 防止过期

**禁止用修改日期判断文档是否过期。** 必须区分三种过期：

| 过期类型 | 判据 | 处理 |
|---|---|---|
| **事实过期** | 文档描述的路径/默认值/版本/行为与代码或配置不一致 | 改文档或改成"跑命令现取"；同一次提交完成 |
| **决策过期** | 决策被新决策取代或重开条件已触发 | 写新 ADR，旧文标 Superseded |
| **时间陈旧** | 纯粹久未更新但事实仍成立 | 不改；不必为刷新日期而动文档 |

机制：

1. **事实映射**：§7.1 的八类代码变化 ↔ 受影响的文档清单，见 [文档改造报告](文档改造报告.md) 的影响映射表。
2. **自动链接检查**：`DocsHygieneTests` D2/D4，检查相对链接与纯文本路径。
3. **代码示例检查**：本仓文档不内嵌编译型代码示例；若将来加入，必须可被编译或脚本验证，不得是伪代码冒充可运行代码。
4. **配置与 API 参考检查**：默认值、版本、端点一律指向生成脚本或命令；手抄前先核对真实配置。
5. **一致性检查**：跨文档同一事实（正本路径、章节号、ADR 范围、终态词表、状态位格式）用脚本比对，见 `scripts/doc_consistency_check.py`。
6. **Doc-gardening 定期扫描**：每次阶段收口跑一次检查脚本；发现事实过期生成问题文件，不静默改文档。参照 OpenAI 的定期扫描实践（R3/P），但**不引入自动改写 PR**——单人项目由人确认。

## 8. AI 写作特别约束

本项目以 AI 原生方式开发，以下失真形态为高危，写作时逐条自查：

1. **把设计意图写成实现事实**（本次实证发现，见 §3.3）。
2. **把"测试全绿"写成"能力完备"**：绿灯只覆盖被断言项。
