# AgentWorkbench 底座建设清单

> **定位**：基于 MAF 的通用 Agent 运行底座。不绑定任何行业业务。
> **目标形态**：一个可独立启动、可测试、可观测、可扩展的 .NET Web 服务——
> 建任务 → 指定模型与工具 → 执行并实时观察 → 查看每步输入输出耗时异常 →
> 主动取消 → 限制步数与时间 → 查询历史 → 支持恢复 → 跑自动化验收。
> **这不是产品，是运行时。**

---

## 零、三条铁律

违反任何一条，这份清单就作废。

1. **不重做 MAF 已有的。** Agent Loop、工具调用协议、Workflow 引擎、Checkpoint 机制，
   MAF 已经提供。底座只补它没直接满足的：**执行策略、持久化、统一接口、可靠性保证**。
   判断标准：动手前先问"MAF 能不能配置出来"，能就别写。
2. **每项能力必须配一个能变红的负控。** 只有正例绿的测试 = 假绿。
   仓库目前**没有任何验收脚本**（`scripts/` 目录从未进入版本库），历史上跑过的 P2/P3
   是 1 个样本跑出的 100%、industrial 是 FAIL——**这就是没有负控的后果**。
   新写的每一条都必须先写"什么情况下它必须失败"。
3. **不引入任何垂直业务语义。** 底座代码里不得出现合同 / 工业 / 仓储 / 单证等词。
   业务模块未来以独立模块接入，只依赖底座契约。

## 二、缺口清单（按优先级）

图例：`做什么` / `为什么` / `完成判据` / **负控（必须能红）** / `规模`

### P0 — 试验装置与真实验证

这一级的目标是**把 mock 绿变成真绿**。不新增业务，只新增"能让底座出错"的试验工具。

#### P0-1 失败工具 FailingTool
- **做什么**：内置 `fault_injector`，参数 `mode=throw|timeout|hang`、`failTimes=N`。
- **为什么**：工具执行失败的错误分类、重试策略、降级规则——**当前零覆盖**。
  `PersistFailureAsync` 那条分支从来没被真正触发过。
- **判据**：连续失败达到上限后**必须降级返回**（不再重试），且轨迹里记录失败原因，`Status=failed`。
- **负控**：把重试上限设为 0 后，同一用例必须 FAIL。
- **规模**：`ToolExecution/Builtin` 加 1 个工具类 + 1 个测试。

#### P0-2 慢工具 SlowTool
- **做什么**：内置 `slow_op`，参数 `delayMs`。
- **为什么**：现在的取消只有外层 `CancelAfter`，**取消信号是否真穿透进工具内部，未验证**。
- **判据**：`delayMs > TimeoutSeconds` 时，工具内部必须收到 `OperationCanceledException`，
  而不是等它跑完再由外层判超时。
- **负控**：把 `delayMs` 调到超时窗口以内，同一用例必须从"超时"变成"正常返回"。
- **规模**：1 个工具 + 1 个测试。

#### P0-3 计数工具 CounterTool
- **做什么**：内置 `counter`，参数 `key`，返回并自增。
- **为什么**：并发执行、重复调用去重——**零覆盖**。
- **判据**：并发 10 次调用同一 key，最终计数必须**恰好等于 10**（不多不少）。
- **负控**：去掉幂等键后重跑，计数必须 > 10（证明去重真的在起作用）。
- **规模**：1 个工具 + 1 个测试。

#### P0-4 真实模型冒烟
- **做什么**：用真实模型（SiliconFlow / Qwen3-8B）跑通 3 条：单轮问答、工具调用、多轮会话。
- **为什么**：现有 13 个断言全是 mock。**没跑过真模型 = 没验证过。**
- **判据**：三条全部成功，轨迹完整落库。
- **负控**：抽掉 API key → 必须返回明确的"未配置模型"错误，而不是空结果或 500。
- **规模**：1 个 Python 脚本（不依赖 PowerShell）。
- **阻塞**：需要可用的 API key。

> **P0 做完，底座才算"跑通过"。在此之前新增任何功能都是叠沙堡。**

### P1 — 执行控制的硬保证

#### P1-1 循环检测
- **做什么**：检测模型重复调用同一工具且参数相同，达到阈值则终止并标记 `loop_detected`。
- **为什么**：`MaxIterations` 只限制总数，不识别"卡住了"。
- **判据**：构造重复调用场景，必须在第 N 次终止而不是跑满 `MaxIterations`。
- **负控**：关闭检测后，同一场景必须跑满 `MaxIterations` 才结束（证明检测真的生效）。
- **规模**：`AgentLoop` 内加一段判重逻辑。

#### P1-2 调用预算（token / 次数 / 时长三选二）
- **做什么**：单次 run 的预算上限，超限即终止并返回已得部分。
- **为什么**：超时只管墙钟时间，管不住"钱"。
- **判据**：预算耗尽必须终止，且 `Status` 标记 `budget_exceeded` 而非 `succeeded`。
- **负控**：预算设为极大值，同一用例不得提前终止。
- **规模**：`AgentLoopOptions` 加字段（用量侧读 `IModelRuntime.GetUsage()`）+ 一处检查。

#### P1-3 会话记忆持久化
- **做什么**：会话从进程内 `ConcurrentDictionary` 迁到仓储（SQLite）。
- **为什么**：重启即丢，且多实例部署时根本不可用。
- **判据**：重启服务后，同一 `sessionId` 仍能接着聊。
- **负控**：用一个不存在的 `sessionId` → 必须新建而不是报错或复用他人会话。
- **规模**：新增一张表（FluentMigrator M0xx）+ 仓储方法。
- **状态**：✅ 已实现（M023 + `Memory.Persistence`）。判据用「销毁 store/agent、复用同一 SQLite 库」做进程内等价验证；
  真·跨进程重启仍待验收脚本落地。方案见 `docs/跨模块记录/状态与记忆持久化方案.md`。

#### P1-4 长期记忆 + 记忆跨会话
- **做什么**：长期记忆载体（`memory_items` + `remember` / `recall` 工具）；以及让记忆跨会话。
- **状态**：
  - 载体 ✅ 已实现（M024 + `ILongTermMemoryStore` + 两个工具 + 保留服务）。
  - **跨会话 ⏸ 已决定暂缓**：默认按会话隔离（`LongTermScope=session`），换会话召回为空。
    前提是「这是谁」，而仓库目前零身份 —— **等权限管理落地后重启**。
    决策、依据、接缝与「做权限管理时必须一起收口的两件事」见
    `docs/跨模块记录/记忆作用域与身份策略.md`。

### P2 — 可靠性

#### P2-1 错误分类
- **做什么**：把失败分成 `模型不可用 / 工具异常 / 超时 / 预算耗尽 / 取消 / 内容违规` 六类，
  每类有独立错误码。
- **为什么**：现在只有一个 `ex.Message` 字符串，无法据此决定重试还是降级。
- **判据**：六类错误各自能被 `P0-1` 的 FailingTool 稳定触发，且错误码正确。
- **负控**：故意把超时错误归类成工具异常 → 测试必须 FAIL。
- **规模**：一个枚举 + 映射函数。

#### P2-2 副作用去重（幂等）
- **做什么**：给工具调用加幂等键，重复执行同一键不产生二次副作用。
- **为什么**：MAF 明确说明 Checkpoint **不等于**自动解决外部工具的重复执行问题。
  恢复后重跑，写操作会执行两遍。
- **判据**：恢复一个中断的 run，写类工具的副作用只发生一次（用 `P0-3` 的 CounterTool 验）。
- **负控**：去掉幂等键后恢复，计数必须变成 2。
- **规模**：工具调用包装层加幂等键。

#### P2-3 降级策略
- **做什么**：工具失败后，依次尝试「重试 → 换等价工具 → 返回占位结果 → 终止」，可配置。
- **为什么**：现在失败只能整条 run 失败。
- **判据**：`P0-1` 的 FailingTool 在 `failTimes=1` 时，重试后必须成功；`failTimes=99` 时必须降级终止。
- **负控**：把降级关掉 → `failTimes=99` 时整个 run 必须 failed 而不是 degraded。
- **规模**：重试策略类。

### P3 — 可观测性

#### P3-1 OpenTelemetry 追踪
- **做什么**：接 OTel，每次模型调用 / 工具调用出一个 span，带 runId、iteration、耗时、错误码。
- **为什么**：现在只有 `ILogger` + 落库，**没有调用链**。长任务里没法定位"卡在哪一步"。
- **判据**：一次含 3 次工具调用的 run，导出 ≥ 5 个 span，且父子关系正确。
- **负控**：注入一次工具异常，对应 span 必须带错误标记且状态为 Error。
- **规模**：一个 `ActivitySource` + 导出配置。

#### P3-2 指标
- **做什么**：四个计数器——run 总数 / 成功率 / P95 延迟 / 工具失败率。
- **为什么**：没有指标就谈不上"可观测"，只有日志。
- **判据**：跑 10 次后指标非零且与落库统计一致。
- **负控**：全部失败时成功率必须为 0（不能因为没上报而显示 100%）。
- **规模**：`Meter` + 4 个计数器。

#### P3-3 失败原因可检索
- **做什么**：按 `Status` / 错误码 / 时间范围 / sessionId 查询失败 run。
- **为什么**："故障诊断"这一条验收目标，现在只能翻数据库。
- **判据**：造 3 种错误类型各 1 条，能按错误码精确筛出。
- **负控**：查一个不存在的错误码必须返回空，而不是全量。
- **规模**：仓储加查询方法 + 一个接口。

### P4 — 并发与资源预算

#### P4-1 并发隔离
- **做什么**：两个 run 并发执行，轨迹、会话、计数器互不串扰。
- **为什么**：`_sessions` 是共享字典，工具状态若共享会串。
- **判据**：并发 10 个 run，各自的 `steps` 只含自己的步骤。
- **负控**：故意让工具共享一个静态计数器 → 测试必须 FAIL（证明测得出串扰）。
- **规模**：测试为主。

#### P4-2 并发上限与排队
- **做什么**：同时运行的 run 数上限，超出排队或拒绝。
- **为什么**：无限制并发会打爆模型配额。
- **判据**：上限设为 2，并发发 5 个，最多 2 个在跑，其余排队或 429。
- **负控**：上限设为 0 → 所有请求必须被拒，而不是全部放行。
- **规模**：`SemaphoreSlim` + 配置。

#### P4-3 取消的传播与清理
- **做什么**：取消时释放占用、落 `cancelled` 状态、工具侧收到 token。
- **为什么**：现在取消了但资源可能还占着。
- **判据**：取消 `P0-2` 的 SlowTool 后，并发名额必须立即释放。
- **负控**：取消一个不存在的 runId → 必须返回明确错误而不是静默成功。
- **规模**：取消路径补清理。

---

### P5 — 审批与权限边界

#### P5-1 危险工具审批
- **做什么**：标记 `requiresApproval` 的工具，执行前暂停，等外部批准后继续。
- **为什么**：长文明确——MAF 提供审批**机制**，但"权限边界、审批规则、服务端授权"是自己负责的。
- **判据**：未批准时工具不执行，run 停在 `awaiting_approval`；批准后继续执行。
- **负控**：伪造批准信号 → 必须被拒绝。
- **规模**：状态机加一个状态 + 一个接口。

#### P5-2 工具级权限
- **做什么**：白名单从"全局配置"升级为"每次 run 可指定可用工具子集"。
- **为什么**：现在白名单写死在配置里，不同任务不能有不同的权限。
- **判据**：run 指定只允许 `calculator` 时，模型调用 `list_documents` 必须被拒。
- **负控**：不传子集时，行为必须与现在一致（向后兼容，不能全禁）。
- **规模**：`HarnessRunRequest` 加字段。

## 三、验收任务（夹具业务，不是产品）

底座需要一个**可重复执行的标准任务**来验证，但又不能绑定行业业务。方案：

**用一个确定性的、对错 100% 客观的核对任务做夹具**（例如仓储收货-上架核对之类的
合成任务）。⚠️ **该夹具尚未建立**——下面描述的是目标形态，不是现有资产。

它的角色定位必须清楚：

| 项 | 说明 |
|---|---|
| 在底座里扮演什么 | **验收夹具 / 测试装置**，和 `P0-1` 的 FailingTool 同级 |
| 为什么合适 | 对错 100% 客观可判定，不需要 LLM-as-judge，负控能稳定变红 |
| 对外怎么说 | **不提**。它不是产品、不是业务，不进简历、不进 README 卖点 |
| 什么时候用 | 验证 P2-2 幂等、P3-1 追踪、P4-1 并发隔离这类"需要真实任务"的能力 |

> 如果不想要这个夹具，替代方案是一组纯合成任务（斐波那契 / 排序 / 计数）。
> 但那样验证不了"真实数据脏"的情况，P2 的可靠性测试会失真。**建议保留。**

## 四、总验收表（判定型 + 度量型双轨）

判定型——每项绿/红，且正例绿时负控必须红：

| 编号 | 能力 | 正例 | 负控 |
|---|---|---|---|
| B1 | 正常执行 | 模型调工具并返回 | 工具抛异常 → 必须 failed |
| B2 | 循环终止 | 重复调用在第 N 次终止 | 关检测 → 跑满 MaxIterations |
| B3 | 超时 | SlowTool 超时被取消 | 延迟调小 → 正常返回 |
| B4 | 预算 | 超预算终止 | 预算极大 → 不提前终止 |
| B5 | 工具失败降级 | failTimes=99 时降级 | 关降级 → 整条 failed |
| B6 | 取消 | 取消信号进到工具内部 | 取消不存在的 run → 报错 |
| B7 | 并发隔离 | 10 并发轨迹不串 | 共享计数器 → 必须 FAIL |
| B8 | 并发上限 | 上限 2 时最多 2 个在跑 | 上限 0 → 全拒 |
| B9 | 幂等 | 恢复后副作用只一次 | 去幂等键 → 两次 |
| B10 | 审批 | 未批准不执行 | 伪造批准 → 拒绝 |
| B11 | 权限 | 子集外工具被拒 | 不传子集 → 行为不变 |
| B12 | 追踪 | 3 次工具调用 ≥5 span | 注入异常 → span 标 Error |
| B13 | 失败检索 | 按错误码精确筛出 | 不存在 → 返回空 |

度量型——给出数字与趋势（不是阈值判定）：

| 指标 | 口径 |
|---|---|
| run 成功率 | 成功 run 数 / 总 run 数 |
| P95 延迟 | 全部 run 的 95 分位耗时 |
| 工具失败率 | 失败工具调用 / 总工具调用 |
| 平均迭代数 | 反映循环检测是否误伤 |
| 降级率 | degraded 结束的 run 占比 |

## 六、明确不做

避免范围膨胀，以下一律不做：

- ❌ 不做任何垂直业务模块（维持 10-08 终裁）

## 七、环境前置（开工前先解决）

| 项 | 现状 | 动作 |
|---|---|---|
| PowerShell | **本机只有 5.1，没有 pwsh** | 装 PS7，或新脚本一律用 Python（推荐） |
| API key | `appsettings.json` 的 Key 长度为 0 | 需要一个可用的 key，否则 P0-4 做不了 |
| 后端进程 | 容易被回收，会锁 `bin/**/*.dll` | 验证前先确认 8080 端口存活 |
| 数据库 | 生效的是 `src/AgentWorkbench.Webapi/data/agentworkbench.db` | 根目录 `data/` 那个是旧的，别看错 |
| 向量模型 | 配的 ollama/bge-m3，但 Ollama 默认不启动 | 需要时先 `ollama serve` |
