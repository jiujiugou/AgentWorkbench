## 一、外部验证缺口（结果层，判定权在对方系统）

### 1. 第4句「超时只查证不重放」— 机制已修，真站点闭环未跑 `未验`
- **现状**：三层缺口全修（错误归类 → `Unknown`、调用超时 → `ToolCallTimeout`、查证分支可达），20 条判据绿，
  两处负控变异自证。端到端判据证明：写 1 次 / 查证 1 次 / `verified_by_query` / 明确拒绝零查证。
- **卡在哪**：真站点上没法制造「对方写成功、但 C# 超时」这一次。注入 sleep 的实验暴露 frappe_mcp 用同步
  `httpx.Client` + 同步 `time.sleep` 会堵死 asyncio 事件循环，查证被排队饿死——那是造出来的故障，不是产品链路。
- **下一步**：换一个支持并发工具调用的 MCP server，或找别的故障注入点；不要在同步 server 上继续造。
- **判定权**：超时后对方系统里有没有第二次写。

### 2. 第6句「换第二体系，底座 diff 为空」— 结构成立，结果层缺 token `未验`
- **现状**：切 `Actions:ActionSet=GiteaActionSet` 只改环境变量，`git diff src/Core/` 切前切后都为 0；
  能力目录真换了（`erp.query` → `spec_not_found`，`repo.query` → 识别并打到 GiteaAdapter）。
  gitea.com 公开实例可达（版本/仓库匿名读 200）。
- **卡在哪**：`GiteaOptions.IsConfigured` 要 Token 非空；当前环境没有 gitea.com 只读 token，
  真查证返回对方 `401 not_authenticated`。
- **下一步**：拿到一个 gitea.com 只读 token（走环境变量，不进 git），真跑一遍 `repo.query`。
- **判定权**：第二体系自己的记录 + `git diff src/Core/` 为空。

### 3. 第3句剩余边界 `未验`
- **现状**：ERP 侧同 request_id 只一条已实证（`f1da53e8...`，重放返回 `replayed_from_idempotency`，execute 段 1 个）。
- **卡在哪**：Gitea 侧按业务键的读取口仍缺失。
- **下一步**：随第 6 句 token 到位后一并补。
- **判定权**：对方按业务键查到的记录条数。

## 二、能力缺口（产品边界，判定权在业务语义）

### 4. `erp.draft` 真建单缺必填字段 `未验`
- **现状**：MCP 绑定已补（`frappe_create_doc`，`amount → data.remarks`），离网判据绿。
  真跑被 Frappe 以 `417 + MandatoryError: supplier, items` 明确拒绝——绑定只写备注，建不了真单。
- **卡在哪**：一张真采购单需要 supplier / items 等必填字段，那是业务语义重量，不是传输绑定。
- **下一步**：要么把 Draft 的 InputSchema 扩成能收 supplier/items（改业务契约），要么承认草稿只在本地登记。
- **判定权**：对方系统里有没有真的多出一张草稿单。

### 5. 审批人是操作者本人，非独立真人 `未验`
- **现状**：cancel 的审批是真闸（挂起→approve→执行），但审批人取登录用户（`wang` → 王工），提交与批准同一人。
- **卡在哪**：没有第二个真人账号参与，「未审批零外部调用」的「未审批」成立，但「真人拒绝」那一半没验。
- **下一步**：用一个独立审批人账号，真跑一次拒绝路径。
- **判定权**：对方记录数在拒绝后不变。

  最小修法是让 C# 直接读 `FRAPPE_URL`，但会改变现有启动方式，待定。
