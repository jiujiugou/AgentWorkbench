# 终止与预算（Runtime.Loop · 六部件之③）

- **适用侧**：底座 ｜ **寿命**：现状（就近维护） ｜ **最后校准**：2026-11-18（当日按统一骨架重写，技术判断未变）

一句话：**管住一次 Agent 运行的「停」**——允许循环几次、跑多久、什么时候必须提前停、停下来以什么状态收尾。
拿掉它，预算用光被框架当成功返回，从返回值和异常里都看不出来——「跑满了」和「答完了」在账本上长得一模一样。

> 怎么读：第一节划边界，第二节给判定点的位置，第三节给要判断「这条规则归谁」的人（六个决定），
> 第四到六节是配置、排障、红线，第七节是验收；附录给要评估框架的人。
> 本文只做解释，不是事实源。决定与证据的机器可读登记在仓根 `agent-parts.toml`，本文不复制。

## 一、负责什么 / 不负责什么

判据只有一条：**「该不该停」和「停了算什么」是不是本模块决定的？**

| 事 | 只存在于哪 | 能重建吗 | 归属 |
|---|---|---|---|
| 跑满迭代 vs 主动收尾的区分 | `InspectCompletion()` 看私有 `_lastIteration` | 否 | **本模块** |
| 连续重复调用的计数 | `AgentRunGuard` 私有指纹与计数 | 否 | **本模块** |
| run 级墙钟是否到点 | linked CTS + `CancelAfter` | 否 | **本模块** |
| token 是否超预算 | 本次 run 起点取基线、读增量 | 否 | **本模块** |
| 终态与归类词表 | 停时现算 | 否 | **本模块** |
| 循环本体、回填、批次 | MEA `FunctionInvokingChatClient` | 是（框架） | ② |
| 单次工具调用怎么执行 | ④ 的 `FunctionInvoker` | 是 | ④ 工具执行 |
| 单个工具自己的超时 | 工具侧 / `Runtime.Model` | 是 | ④ / 模型层 |
| 审批、白名单、幂等 | 动作域 | 否 | 边界外（「该不该做」不是「该不该停」） |
| 归类写进哪张表 | 编排层 | 是 | Harness / 应用层 |
| 暂停 / 人工确认 | — | — | 没有，本模块只有「继续」和「停」 |

**本模块管（6 条）**：迭代上限的透传与「跑满算不算答完」的判定；run 级墙钟真取消；重复调用检测；token 硬预算；终态与归类词表；「停下来不记成成功」。

**不归本格**：循环本体、单次执行、业务判定、落库、暂停恢复。详见上表。

## 二、判定在哪发生：三处分工

```
配置 Harness:Loop
  │
  ├── MaxIterations ──→ ToolExecutionLimits ──→ ④ FICC.MaximumIterationsPerRequest
  │                                                    （框架管轮数，但不告诉你是「跑满」还是「答完」）
  ├── TimeoutSeconds ──→ AgentLoopService.ExecuteAsync 的 linked CTS + CancelAfter（圈整轮）
  ├── MaxRepeatedToolCalls ─┐
  └── MaxTokensPerRun ─────┴──→ CreateGuard(usage) ──→ IAgentRunGuard
                                                            │
                                             ④ FunctionInvoker 调用前问一次
                                             guard.InspectToolCall(observation)
                                             命中 → context.Terminate（不抛异常）
  ─────────────────────────────────────────────────────────────
  收尾时 Harness 再问一次 guard.InspectCompletion() → 区分 iteration_limit / succeeded
```

三处的职责：**阈值与判定**在本模块（纯类，零 AI 依赖，只引 `Shared/Execution` 词表）；**装配与传递**在 `AgentHarness`（读配置、`CreateGuard` 接用量读数）；**环内执行点**在 `Runtime.Tools/FunctionInvoker`（每次工具调用前问 guard）。

`IAgentLoop` 只四个成员：`MaxIterations` / `TimeoutSeconds` / `CreateGuard(usage)` / `ExecuteAsync<T>`——**它不驱动循环**，循环本体是框架的。

## 三、六个决定

**1. 迭代上限透传，但「跑满」必须自己判。**
为什么：MEA 跑满 `MaximumIterationsPerRequest` 不报错，而是清空工具逼模型用文本收口、正常返回——不问就是 `succeeded`。本模块的 `InspectCompletion` 看最后一次工具调用是否顶到 `MaxIterations - 1`，是则标 `iteration_limit`。
改它：删掉收尾那一问，预算耗尽与主动答完在轨迹里无法区分——这是本模块存在的意义本身。

**2. 墙钟超时必须是真取消。**
为什么：linked CTS + `CancelAfter` 把令牌链进正在跑的动作；外层「等个时间就放弃」不算。取消（调用方意愿）转成 `Cancelled`，本模块超时转成 `AgentRunTimeoutException`，后者先于泛 `TimeoutException` 被捕获——两者归类码不同。
改它：把令牌换成外层 `Task.WhenAny`，正在跑的工具不会被中止；把两个 catch 合并，`run_timeout` 退化成 `model_timeout`。

**3. 重复调用只统计「连续」，指纹按名排序。**
为什么：模型卡在同一调用上反复打转是白烧钱；中间夹了别的调用就重新计数。指纹 = 工具名 + 参数文本，参数序列化按键名排序，键序稳定才可比。命中即停标 `loop_detected`，`0` = 关闭检测。
改它：把「连续」改成「累计」，正常的反复查不同单会被误判；参数不排序，同一个调用换个键序就漏判。

**4. token 预算取本 run 起点，读增量。**
为什么：框架没有任何等价物（六部件图 ③ 标「缺」的那格）。取基线后读 `IAgentUsageSource` 的增量，超限标 `budget_exceeded`；用进程累计会把别的 run 的花费算进来。
改它：换成进程级累计，并发 run 的口径全错；`MaxTokensPerRun=0` 表示不限，不是「零预算」。

**5. 环内判定要「干净收口」，不抛异常。**
为什么：重复与 token 的信息只有到工具调用真正发出之前才有，事后追认等于钱已经烧了。命中后跳过执行、记轨迹、`context.Terminate = true`——抛异常会被框架当「工具失败」喂回模型，模型可能换个写法再试一次。
改它：改成抛异常，本意是省钱却多烧一轮模型请求。

**6. 终态与归类码必须是结构化的。**
为什么：状态回答「以什么结束」（`succeeded` / `iteration_limit` / `loop_detected` / `budget_exceeded` / `timeout` / `cancelled` / `failed`），归类码回答「为什么」。一串人话的失败没法决定重试还是降级。
改它：把归类码塞进消息文本，回放时只能解析中文——这正是 ⑥ 拒绝做的事。

## 四、配置（`Harness:Loop`）

| 键 | 默认 | 含义 |
|---|---|---|
| `MaxIterations` | 6 | 最多几轮「模型→工具→模型」；不配真模型必 504（Loop 那一轮耗在等模型） |
| `TimeoutSeconds` | 30 | 整轮墙钟，包住整段流式 drain（不是单次请求） |
| `MaxRepeatedToolCalls` | 3 | 连续同参重复阈值，`0` = 关闭 |
| `MaxTokensPerRun` | 0 | run 级 token 上限，`0` = 不限 |

四个值由 `Runtime.Harness/LoopAssembly` 显式给出，不靠框架隐式默认——升级 MEA 改了默认值，本仓行为不该跟着变。

## 五、出问题先看哪

| 现象 | 先看 |
|---|---|
| 跑满迭代却记成成功 | 收尾有没有调 `InspectCompletion()`；私有 `_lastIteration` 是否真的在每次工具调用时更新 |
| 超时了但工具还在跑 | 令牌有没有链进正在跑的动作；是不是用外层等待代替了 `CancelAfter` |
| `run_timeout` 被记成 `model_timeout` | catch 顺序——`AgentRunTimeoutException` 继承 `TimeoutException`，必须先接子类 |
| `loop_detected` 该触发没触发 | 中间是否夹了别的调用（只统计连续）；参数序列化有没有按键排序；阈值是不是 `0` |
| `budget_exceeded` 不触发 | `MaxTokensPerRun` 是不是 0；基线是不是取的本 run 起点，而不是进程累计 |
| 停了却看着像答完 | 终态词表里 `iteration_limit` / `loop_detected` / `budget_exceeded` 有没有各自独立的值 |

## 六、红线

1. **不重写框架已有的东西**：循环本体、工具协议、最后一轮收口都是框架的，动手前先问能不能配出来。
2. **零垂直业务语义**：不出现合同、工业、仓储、单证这类词。
3. **职责单向**：只依赖 `Shared/Execution` 契约词表，不认识 Harness 流水线与工具/模型实现；`IAgentLoop` 契约不得取消。
4. **超时必须是真取消**：令牌传进正在跑的动作里。
5. **停了就不能记成成功**：预算 / 截断 / 取消各有独立状态。
6. **加一项执行控制要做三件事**：配置项 → 判定（能拦在 `ExecuteAsync` 的就在这儿拦，要环内信息的让下游递信号到 `FunctionInvoker`）→ 能落进 `ExecutionTrace.Status`。缺第三步，前两步等于没做。

## 七、怎么算验收通过

判定型用例必须**正例能绿、负控能红**；能脚本判定的禁止用 AI 判。验收以 `dotnet test` 实测为准，本文不列测试文件名与条数（会漂）。

**已有覆盖**：四个选项落到框架实例属性、跑满迭代与主动收尾分得开、重复调用与 token 预算命中后干净收口、取消与超时归类码分开。装配侧 `LoopAssembly` 的五个决定值有结构与行为判据，负控实测过（把 `MaxConsecutiveErrorsPerRequest` 从 3 改成 5，两条判据红）。

**证据打折的地方**：迭代预算「预算 2 → 恰好 2 轮」只有间接对账，没有直接数轮数的用例。

**还没建立的**：单个工具「收到取消也不理」时怎么强制隔离未做；并发 run 的 token 口径依赖进程级用量计数器，串行跑才准。

**明确不在本文范围的**：审批、白名单、幂等（边界外）；归类落库（Harness / 应用层）。

# 附录（要评估框架与选型的人看，改代码不必读）

## A. 框架给了什么，没给什么

| 需求 | MEA / MAF 有等价物吗 | 本仓怎么做 |
|---|---|---|
| 循环轮数 | `FunctionInvokingChatClient.MaximumIterationsPerRequest` | 透传，不自研 |
| 连续错误上限 | `MaximumConsecutiveErrorsPerRequest` | 显式赋值，不靠默认 |
| 单次请求超时 | `HttpClient.Timeout` | 在 `Runtime.Model`，管单次不管整轮 |
| **整轮墙钟** | 无 | `AgentLoopService` linked CTS + `CancelAfter` |
| **重复调用检测** | 无 | `AgentRunGuard.InspectToolCall` |
| **run 级 token 预算** | 无（context window compaction 是压缩，不是预算） | `AgentRunGuard` 读用量增量 |
| **跑满迭代的判定** | 无（框架清空工具逼收口，不报错） | `InspectCompletion` 主动问 |

## B. 与其它五份的边界

② 讲「怎么从一轮走到下一轮」；④ 讲「一轮里的工具怎么执行」——本格把判定点借在 ④ 的 `FunctionInvoker` 里，但阈值与归类归本格；⑥ 讲「走过之后留下什么」——本格产出停因，⑥ 把它写进账本。

`MaxIterations` 是 ② 与 ③ 唯一共用的数字：② 负责把它交给框架，③ 负责定义它。
