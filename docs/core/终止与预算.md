# 终止与预算（Runtime.ExecutionControl · 六部件之③）

- **适用侧**：底座 ｜ **寿命**：现状（就近维护） ｜ **最后校准**：2026-11-23

> **类型**：Architecture（解释型）。本文解释"一次 Agent 运行凭什么停、停在哪一步、停下来以什么状态收尾"，不是事实源、不是参考手册。
> **范围**：边界归属、判定点的分工、阈值语义、设计理由、失败语义、验收判断、未决问题。
> **非范围**：循环本体、单次工具执行、业务判定、停因落库与呈现。
> **可枚举部分不写在这里**：文件/符号定位、配置实际值与代码默认、测试规模、终态词表都在 `docs/kb/documents/budget.toml` 的 `evidence` / `fact` 段，由 `scripts/kb_check.py` 对账；本文只写机器判不了的判断。

一句话：**管住一次 Agent 运行的「停」**——允许循环几次、跑多久、什么时候必须提前停、停下来以什么状态收尾。
拿掉它，预算用光被框架当成功返回，从返回值和异常里都看不出来——「跑满了」和「答完了」在账本上长得一模一样。

## 一、负责什么 / 不负责什么

判据只有一条：**「该不该停」和「停了算什么」是不是本格决定的？**

| 事 | 归属 |
|---|---|
| 跑满迭代 vs 主动收尾的区分 | **本格** |
| 连续重复调用的计数 | **本格** |
| run 级墙钟是否到点（到点真取消） | **本格** |
| token 是否超预算 | **本格** |
| 终态与归类词表 | **本格** |
| 循环本体、回填、批次 | ② |
| 单次工具调用怎么执行 | ④ |
| 单个工具自己的超时 | ④ / 模型层 |
| 审批、白名单、幂等 | 领域（边界外：那是「该不该做」，不是「该不该停」） |
| 归类写进哪张表 | 应用层 |

本格管六件事：迭代上限的透传与「跑满算不算答完」的判定；run 级墙钟真取消；重复调用检测；token 硬预算；终态与归类词表；「停下来不记成成功」。**没有「暂停 / 人工确认」这一格**——本格只有「继续」和「停」。

依赖断了谁兜着：

| 依赖 | 提供什么 | 断了谁兜着 |
|---|---|---|
| ④ 的环内回调 | 每次工具调用前问一次守卫的执行点 | 守卫只剩收尾判定，重复与 token 无法提前拦，钱已经烧了 |
| ② 的预算透传 | 把迭代上限交给框架 | 本格没有对照物，「跑满」只能退化成猜 |
| 配置节 | 四个阈值的取值 | 缺节时取代码默认；行为不丢，意图丢了 |
| 模型层的用量读数 | 本格起点之后花了多少 | 读不到增量，token 预算只能关掉，回到不设防 |

## 二、机制形状

判定发生在三处，各自管一段：

```
配置节（四个旋钮）
  │
  ├── 迭代上限 ──→ ④ 的限额 ──→ 框架的每请求迭代上限
  │                              （框架管轮数，但不告诉你是「跑满」还是「答完」）
  ├── 墙钟秒数 ──→ 包住整轮的链接取消令牌（到点真取消）
  ├── 连续重复阈值 ─┐
  └── token 上限 ──┴──→ 每次 run 新建守卫 ──→ 交给 ④
                                                │
                                  ④ 的环内回调在工具执行前问一次
                                  命中 → 置终止标志（不抛异常）
  ─────────────────────────────────────────────
  收尾时编排层再问一次「是不是跑满」→ 区分 iteration_limit / succeeded
```

三处分工：**阈值与判定**在本格（纯类，零 AI 依赖，只引共享词表）；**装配与传递**在装配层（读配置、接用量读数）；**环内执行点**在 ④ 的工具执行回调（每次工具调用前问守卫）。

接口只给三件事：两个预算读数、一个守卫工厂、一个「带超时执行」的包装——**它不驱动循环**，循环本体是框架的。

## 三、为什么这么定

只有这几条测试答不了的取舍；判据与负控在测试里，本文不复述。

**迭代上限透传，但「跑满」必须自己判。** 框架跑满每请求上限不报错，而是清空工具逼模型用文本收口、正常返回——不问就是 `succeeded`。本格在收尾时看最后一次工具调用是否已顶到预算允许的最后一轮，是则标 `iteration_limit`。

**墙钟超时必须是真取消。** 把超时令牌链进正在跑的动作；外层「等个时间就放弃」不算。取消（调用方意愿）转成 `cancelled`，本格超时转成专门的 run 超时异常（继承 `TimeoutException`），后者先于泛超时被捕获——两者归类码不同。

**重复调用只统计「连续」，指纹按名排序。** 模型卡在同一调用上反复打转是白烧钱；中间夹了别的调用就重新计数。指纹 = 工具名 + 参数文本，参数序列化按键名排序，键序稳定才可比。命中即停标 `loop_detected`，阈值取关闭值 = 关闭检测。

**token 预算取本 run 起点，读增量。** 框架没有任何等价物（六部件图 ③ 标「缺」的那格）。构造守卫时取一次基线，之后读用量增量，超限标 `budget_exceeded`；用进程累计会把别的 run 的花费算进来。

**环内判定要「干净收口」，不抛异常。** 重复与 token 的信息只有到工具调用真正发出之前才有，事后追认等于钱已经烧了。命中后跳过执行、记轨迹、置终止标志——抛异常会被框架当「工具失败」喂回模型，模型可能换个写法再试一次。

**终态与归类码必须是结构化的。** 状态回答「以什么结束」，归类码回答「为什么」。一串人话的失败没法决定重试还是降级；词表本身受落库列宽约束，取值见 TOML 证据，本文不抄。

**框架给了一半，另一半只能自补。** 迭代轮数与连续错误上限框架有等价物，本格透传、显式赋值，不自研；单次请求超时框架也有，但归模型层，管单次不管整轮。整轮墙钟、重复调用检测、run 级 token 预算、跑满迭代的判定，框架都没有——context window compaction 是压缩上下文，不是预算，替代不了。这四项就是本格存在的理由。

## 四、配置口径

实际键名与取值不抄在这里——值以配置节与代码默认之间的对账为准，登记在 `docs/kb/documents/budget.toml` 的 `fact` 段。本次校准发现启动配置的墙钟覆盖了代码默认，旧表照抄的是代码默认，已删。

三条判断：

1. **可关闭的阈值用零表示关闭 / 不限**，不是「立刻停」；调用方不必为每个旋钮记一套例外。
2. **迭代上限是 ② 与 ③ 的唯一接口**：数字只有一个来源，② 负责交给框架，③ 负责定义它的含义。
3. **不靠框架隐式默认。** 循环侧的四项装配由装配层显式给值，本格阈值来自配置节、代码给默认——升级框架改了默认值，本仓行为不该跟着变。

## 五、失败与恢复语义

停下之后是重试、降级还是结束，本格不决定，只把归类码交出去。

| 形态 | 记在哪 | 回填什么 | 谁能继续 |
|---|---|---|---|
| 迭代预算跑满 | 收尾分类（本格现算） | 模型用文本收口，run 正常返回 | 收口，不重试 |
| 墙钟到点 | 专门的 run 超时异常 | 不抛给模型，向上传播 | 调用方决定重试或放弃 |
| 连续重复命中 | 终止标志 + 轨迹 | 跳过执行，本轮不再回问模型 | 收口，模型换路 |
| token 超预算 | 终止标志 + 归类码 | 同上 | 收口 |
| 调用方取消 | 归类码（与超时分开） | 无 | 调用方 |
| 单个工具不理会取消 | —（没有强制出口） | — | 未建立：只能等它自己返回 |
| 并发 run 的 token 计数 | 进程级用量计数器 | — | 串行才准，并发下口径失真 |

## 六、怎么算验收通过

判定型用例必须**正例能绿、负控能红**；能脚本判定的禁止用 AI 判。验收以实测为准，本文不列测试文件名与条数（会漂）。

| 主张 | 守它的那一组 | 强度 |
|---|---|---|
| 四个循环选项真的落到框架实例属性 | 装配判据 | 当前版本实测，可信 |
| 循环侧装配常量不漂移（结构与行为两路判据） | 装配判据 + 结构门禁 | 负控实测：改任一常量，对应判据红 |
| 跑满迭代与主动收尾分得开 | 运行结局合同 | 可信 |
| 重复调用与 token 命中后干净收口 | 守卫判定组 | 可信 |
| 取消与超时的归类码分开 | 运行结局合同 | 可信 |
| 超时是真取消（动作内部能观察到令牌被取消） | 超时与取消组 | 可信 |

**证据强度打折的地方：**

- 迭代预算「预算 N → 恰好 N 轮」只有间接对账，没有直接数轮数的用例。
- 「真取消」的观察点在动作内部，不是真工具；工具自己吞掉取消时，本格拦不住。

## 七、未决问题

1. **单个工具「收到取消也不理」时怎么强制隔离？** 现在只能等它返回，没有强制出口。
2. **并发 run 的 token 口径要不要按 run 隔离？** 现在依赖进程级用量计数器，串行跑才准；并发下会把别的 run 的花费算进来。

## 八、与其他五个部件

② 讲「怎么从一轮走到下一轮」；④ 讲「一轮里的工具怎么执行」——本格把判定点借在 ④ 的环内回调里，但阈值与归类归本格；⑥ 讲「走过之后留下什么」——本格产出停因，⑥ 把它写进账本；① 讲「模型每轮看到什么」；⑤ 讲「跨轮保住什么」。

共用数值：迭代上限由本格定义、② 消费（交给框架）；墙钟由本格定义，装配层把它包在整轮外层；重复阈值与 token 上限由本格定义、④ 的环内回调执行。
