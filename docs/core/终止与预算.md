# 执行控制模块（Runtime.Loop · 六部件之③ 终止与预算）

- **适用侧**：底座 ｜ **寿命**：现状（就近维护） ｜ **最后校准**：2026-11-12（当日曾并入 Harness，已按决定还原为独立项目）

这个模块只干一件事：**管住一次 Agent 运行的「停」**——允许循环几次、允许跑多久、什么时候必须提前停、停下来以什么状态收尾。
它不做循环本体：模型说要调工具、结果回填、再问模型，循环往复直到给出答案——这套在框架里（MEA 的 `FunctionInvokingChatClient`），底座不重写。

## 一、职责七项

| # | 职责 | 说明 |
|---|---|---|
| 1 | **允许循环几次** | 迭代上限。本仓不自己数，把配置透传给框架的 `MaximumIterationsPerRequest`；但「跑满算不算答完」必须它判——收尾时问一句（`InspectCompletion`），最后一次工具调用顶到 `MaxIterations - 1` 就标 `iteration_limit`，模型主动文本收尾标 `succeeded`。不问，两者在轨迹里长得一模一样 |
| 2 | **允许跑多久** | run 级墙钟超时（linked CTS + `CancelAfter`）。要点是**真取消**：令牌要链进正在跑的动作里，不是外层等个时间就放弃；「调用方取消」（`OperationCanceledException` 原样冒泡）和「本模块超时」（转 `AgentRunTimeoutException`，先于泛 `TimeoutException` 捕获）必须分得开 |
| 3 | **重复调用检测** | 模型卡在同一个调用上反复打转 = 白烧钱。指纹 = 工具名 + 参数文本（参数序列化按名排序，键序稳定才可比）；只统计**连续**重复，中间夹别的调用就重新计数；到阈值即停，标 `loop_detected`，`0` = 关闭检测 |
| 4 | **token 硬预算** | 按「本 run 起点」取用量基线，读增量（`IAgentUsageSource`）；超限即停标 `budget_exceeded`。框架没有任何等价物——六部件图 ③ 标「缺」的那格 |
| 5 | **判定时机：环内、执行前** | 重复和 token 的信息只有到环内、工具调用**真正发出之前**才有——事后追认等于钱已经烧了。判定点在 `Runtime.Tools` 的 `FunctionInvoker`：每次调用前问 `guard.InspectToolCall`，返回非空就跳过、记轨迹、干净收口（不是抛异常——抛了会被框架当「工具失败」喂回模型） |
| 6 | **终态与归类词表** | 状态（`agent_runs.status`）回答「以什么结束」：`succeeded` / `iteration_limit` / `loop_detected` / `budget_exceeded` / `timeout` / `cancelled` / `failed`；归类码（`error_code`）回答「为什么」。一串人话的失败没法决定重试还是降级，必须有结构化码 |
| 7 | **停下来就不能记成成功** | 「预算用光」和「答完了」是两件事，轨迹状态必须分得开——这是本模块存在的意义本身 |

## 二、不归本格

- 循环本体、回填、批次 → **② 框架**（装配在 `Runtime.Harness`，内核在 `Runtime.Tools` 被 new 出来）
- 单次调用怎么执行 → **④ 工具执行**；单个工具自己的超时也归工具模块，本模块只圈整轮
- 审批、白名单、幂等 → 边界外的判定内容（「该不该做」，不是「该不该停」）
- 归类落库 → 本模块只「判」，写 `agent_runs.status` 由编排层做
- 暂停 / 人工确认 → 没有，本模块只有「继续跑」和「停」两种结果

## 三、三处分工（判定 / 装配 / 执行点）

| 处 | 位置 | 干什么 |
|---|---|---|
| 阈值与判定 | 本模块（纯类，零 AI 依赖，只引 `Shared/Execution` 词表） | `AgentLoopService`、`AgentRunGuard`；契约 `IAgentLoop` 四成员：`MaxIterations` / `TimeoutSeconds` / `CreateGuard(usage)` / `ExecuteAsync<T>` |
| 装配与传递 | `AgentHarness` | 读 `Harness:Loop` 配置，`MaxIterations` 交工具环当预算，`TimeoutSeconds` 圈整轮，开跑前 `CreateGuard` 接用量读数 |
| 环内执行点 | `Runtime.Tools/FunctionInvoker` | 每次工具调用前问 guard，该停就置 `context.Terminate`，停的理由一路带到 `ExecutionTrace` |

## 四、配置（`Harness:Loop`）

| 键 | 默认 | 含义 |
|---|---|---|
| `MaxIterations` | 6 | 最多几轮「模型→工具→模型」；不配真模型必 504 |
| `TimeoutSeconds` | 30 | 整轮墙钟 |
| `MaxRepeatedToolCalls` | 3 | 连续同参重复阈值，`0` = 关闭 |
| `MaxTokensPerRun` | 0 | run 级 token 上限，`0` = 不限 |

## 五、红线

1. **不重写框架已有的东西**：循环本体、工具协议、最后一轮收口都是框架的，动手前先问能不能配出来。
2. **零垂直业务语义**：不出现合同、工业、仓储、单证这类词。
3. **职责单向**：只依赖 `Shared/Execution` 契约词表，不认识 Harness 流水线与工具/模型实现；`IAgentLoop` 契约不得取消。
4. **超时必须是真取消**：令牌传进正在跑的动作里。
5. **停了就不能记成成功**：预算 / 截断 / 取消各有独立状态。
6. **加一项执行控制要做三件事**：配置项 → 判定（能拦在 `ExecuteAsync` 的就在这儿拦，要环内信息的让下游递信号或回 `FunctionInvoker` 拦）→ 能落进 `ExecutionTrace.Status`。缺第三步，前两步等于没做。

## 六、怎么算验收通过

判定型用例必须**正例能绿、负控能红**；能脚本判定的禁止用 AI 判。验收以 `dotnet test` 实测为准，本文不列测试文件名与条数（会漂）。

还没覆盖的（对应总验收表 B2 / B6）：迭代预算轮数对账（预算 2 → 恰好 2 轮）只有间接覆盖；单个工具「收到取消也不理」时怎么强制隔离未做；并发 run 的 token 口径依赖进程级用量计数器，串行跑才准。
