# 终止与预算（Runtime.ExecutionControl · 六部件之③）

- **适用侧**：底座
- **寿命**：现状（就近维护）
- **最后校准**：2026-11-23
- **类型**：Architecture（解释型）

> 本文解释「一次 Agent 运行凭什么停、停在哪一步、停下来以什么状态收尾」，不是事实源、不是参考手册。
>
> **范围**：边界归属、判定点的分工、阈值语义、设计理由、失败语义、验收判断、未决问题。
>
> **非范围**：循环本体、单次工具执行、业务判定、停因落库与呈现。
>
> **事实来源**：文件与符号定位、配置实际值与代码默认、测试规模、终态词表、用例名与预设变异点，都在 `docs/kb/documents/budget.toml` 与 `docs/kb/contracts/budget.toml`，由 `scripts/kb_check.py` 对账。本文只解释这些事实背后的判断。

> **本文为什么存在**：服务于交接边界（改这段代码的人哪里不能碰）和局部验收标准（这一格做到什么算完成）。§7 的每条验收都从前面的边界推导；测试与契约是执行形式，不反过来定义边界。本文不与正本六句比大小——六句回答项目成没成，这里回答这一格做完没做完。

## 1. 这一格要解决什么问题

框架跑满一次请求的上限时不会报错。它清空工具，逼模型用文本收口，然后正常返回。从返回值看，「跑满了」和「答完了」一模一样；从账本看，钱花光了却没有任何一条记录说「是被迫停的」。

这就是本格存在的理由：**让「停」变成一件能被判定、能被归类、能被追溯的事。** 具体管四件事——允许循环几次、跑多久、什么时候必须提前停、停下来以什么状态收尾。

边界先划清楚：本格判「该不该停」「停了算什么」，不判「该不该做」。后者是业务的审批、白名单和幂等，属于领域。循环本体归 ②，单次工具调用归 ④，停因写进哪张表归应用层。本格只有「继续」和「停」两态，**没有「暂停 / 人工确认」这一格**。

但要知道停该在哪一步发生，得先看一次 run 从开始到结束经过哪些判定点。

## 2. 整体模型：一次 run 经过哪些判定点

四个阈值在 run 开始前装配；重复与 token 在每次工具调用发出前检查；墙钟包住整轮；是否跑满在收尾时分类。顺序不能挪——重复和 token 的信息只有到工具即将发出时才有，事后追认等于钱已经烧了。

```text
配置节（四个旋钮）
  │
  ├── 迭代上限 ──→ ④ 的限额 ──→ 框架的每请求迭代上限
  │                              （框架管轮数，不告诉你是「跑满」还是「答完」）
  ├── 墙钟秒数 ──→ 包住整轮的链接取消令牌（到点真取消）
  ├── 连续重复阈值 ─┐
  └── token 上限 ──┴──→ 每次 run 新建守卫 ──→ 交给 ④
                                                │
                                  ④ 的环内回调在工具执行前问一次
                                  命中 → 置终止标志（不抛异常）
  ─────────────────────────────────────────────
  收尾时编排层再问一次「是不是跑满」→ 区分 iteration_limit / succeeded
```

三处分工：**阈值与判定**在本格（纯类，零 AI 依赖，只引共享词表）；**装配与传递**在装配层（读配置、接用量读数）；**环内执行点**在 ④ 的工具执行回调。本格对外只给三件事——两个预算读数、一个守卫工厂、一个「带超时执行」的包装；**它不驱动循环**，循环本体是框架的。

这些判定要成立，依赖别的部件把东西送到手上：

| 依赖 | 提供什么 | 断了谁兜着 |
|---|---|---|
| ④ 的环内回调 | 每次工具调用前问一次守卫的执行点 | 守卫只剩收尾判定，重复与 token 无法提前拦，钱已经烧了 |
| ② 的预算透传 | 把迭代上限交给框架 | 本格没有对照物，「跑满」只能退化成猜 |
| 配置节 | 四个阈值的取值 | 缺节时取代码默认；行为不丢，意图丢了 |
| 模型层的用量读数 | 本 run 起点之后花了多少 | 读不到增量，token 预算只能关掉，回到不设防 |

判定的依据都来自阈值。下一节先看阈值怎么装配、又有哪些语义是配置值本身表达不了的。

## 3. 阈值装配：四个旋钮怎么生效

四个旋钮是迭代上限、墙钟秒数、连续重复阈值、token 上限。本格只读它们的语义，实际键名与取值由配置节和代码默认对账，登记在 `documents/budget.toml` 的 `fact` 段——上次校准发现启动配置的墙钟覆盖了代码默认，照抄默认值的旧表已经删掉。

这里有三条配置值本身说不出的判断。

**其一，可关闭的阈值用零表示关闭 / 不限，不是「立刻停」。** 调用方不必为每个旋钮记一套例外。

**其二，迭代上限是 ② 与 ③ 的唯一接口。** 数字只有一个来源：② 负责交给框架，③ 负责定义它的含义。两边各存一份，跑满的判定就没了对照物。

**其三，不靠框架隐式默认。** 循环侧四项装配由装配层显式给值，本格阈值来自配置节、代码给默认。框架升级改了默认值，本仓行为不该跟着变。

阈值装好之后，真正决定停的是两类判定：一类在工具发出前拦，一类包住整轮。先看前者。

## 4. 环内判定：工具发出前拦下

### 4.1 重复调用：只数连续

模型卡在同一调用上反复打转是白烧钱；中间夹了别的调用就说明它在推进，计数重新来过。指纹是工具名加参数文本，参数序列化按键名排序——键序稳定，同样的参数才能比出一样。命中即停，标 `loop_detected`。阈值为零表示关掉检测，不是「零次就停」。

### 4.2 token 预算：按本 run 起点读增量

框架没有任何等价物（六部件图 ③ 标「缺」的那格）；context window compaction 是压缩上下文，不是预算，替代不了。构造守卫时取一次用量基线，之后读增量，超限标 `budget_exceeded`。用进程累计会把别的 run 的花费算进来——那是在替别人关自己的闸。

### 4.3 命中之后：干净收口，不抛异常

两道判定命中后跳过执行、记轨迹、置终止标志。不能抛异常：框架会把异常当「工具失败」喂回模型，模型可能换个写法再试一次——本想省钱，反而多烧一轮。零为关闭的语义在这里同样成立。

这两道拦的是工具调用。还有两种停不经过工具调用：整轮跑钟到点，以及收尾时发现迭代已跑满。

## 5. 整轮约束与收尾分类

### 5.1 墙钟：令牌必须链进正在跑的动作

把超时令牌链进正在跑的动作，到点真取消。外层「等个时间就放弃」不算——动作还在跑，钱还在烧。调用方主动取消转成 `cancelled`；本格墙钟超时转成专门的 run 超时异常（继承 `TimeoutException`），后者先于泛超时被捕获。两者的归类码不同，因为「用户改主意了」和「跑太久了」该走不同的恢复路径。

### 5.2 跑满：框架不告诉你的，自己判

框架跑满上限时不报错，所以收尾时得自己看最后一次工具调用是否已顶到预算允许的最后一轮。是，就标 `iteration_limit`；不是，才是 `succeeded`。不问这一句，所有被迫收口都会被记成模型主动答完。

### 5.3 停因必须结构化

状态回答「以什么结束」，归类码回答「为什么」。一串人话的失败没法让调用方决定重试还是降级。词表本身受落库列宽约束，取值见 TOML 证据，本文不抄。

停被判定、被归类之后，还要把它交出去——交的时候哪些能恢复、哪些只能结束，是下一节的事。

## 6. 失败与恢复语义

停下之后是重试、降级还是结束，本格不决定，只把归类码交出去。不同停法交出去的东西不一样：

| 形态 | 记在哪 | 回填什么 | 谁能继续 |
|---|---|---|---|
| 迭代预算跑满 | 收尾分类（本格现算） | 模型用文本收口，run 正常返回 | 收口，不重试 |
| 墙钟到点 | 专门的 run 超时异常 | 不抛给模型，向上传播 | 调用方决定重试或放弃 |
| 连续重复命中 | 终止标志 + 轨迹 | 跳过执行，本轮不再回问模型 | 收口，模型换路 |
| token 超预算 | 终止标志 + 归类码 | 同上 | 收口 |
| 调用方取消 | 归类码（与超时分开） | 无 | 调用方 |

### 6.1 两处没有强制出口的地方

还有两种情形不在这张表里，因为本格根本没有相应机制：工具吞掉取消时只能等它自己返回；token 读数来自进程级计数器，并发 run 会互相污染——构造时取基线只在串行下成立。两处都没有隔离实现，也就没有判据；分别登记为 `STOP-ISOLATION-001` 与 `STOP-USAGE-001` 的 gap。写在这里不是留待办，是让改这段代码的人知道边界到此为止。

上面这些边界凭什么算成立？下一节把每一条变成可验的契约。

## 7. 契约验收：从边界推导

本节不是测试清单，是 §1–§6 每条边界的验收推导。判定型用例必须正例能绿、负控能红；能脚本判定的禁止用 AI 判。用例名、变异点与强度细节在 `contracts/budget.toml`；不设 ID 的装配约束用例在 `documents/budget.toml` 的 `test-count` 事实里。本文只留结论。

| 契约 / 小节 | 从哪条边界推导 | 结论 |
|---|---|---|
| `STOP-ITERATION-001`（§5.2） | 跑满必须自己判，不能当主动收尾 | 有判据：流程层 + 纯判定层 + 状态对照三路 |
| `STOP-TIMEOUT-001`（§5.1） | 真取消；取消与超时归类分开 | 有判据：动作内部观察到令牌取消（非真工具） |
| `STOP-REPEAT-001`（第 4.1 节） | 只数连续；指纹按名排序；零为关闭 | 有判据：流程层 + 纯判定层，含绿对照与关闭态 |
| `STOP-BUDGET-001`（§4.2） | 取本 run 起点读增量；零为关闭 | 有判据：替身读数，非真实模型计量 |
| `STOP-CLEAN-001`（§4.3） | 命中后跳过执行、置标志，不抛异常 | 跳过执行与轨迹收口有判据；「不抛异常」只有间接断言（`thrown == null`），契约里另留 gap |
| 装配约束（§3，无 ID） | 不靠框架隐式默认 | 有判据：结构与行为两路；用例在循环驱动装配，不进契约层 |
| `STOP-ISOLATION-001`（§6.1） | 工具不理取消时没有强制出口 | **无判据**：本格没有隔离机制，只有等待 |
| `STOP-USAGE-001`（§6.1） | 并发 run 的 token 口径 | **无判据**：进程级计数器，串行才准 |

证据强度有四处打折，别把「有判据」读成「完全证明」：

- 迭代预算「预算 N → 恰好 N 轮」只有间接对账，没有直接数轮数的用例。
- 「真取消」的观察点在动作内部，不是真工具；工具自己吞掉取消时，本格拦不住。
- token 读数是本地替身，不是真实模型计量；「读数确实来自模型」不在这里验。
- `AgentHarness` 如何把守卫停因接到最终 run 状态与轨迹，流程验收一条都没验（与 S03 登记的缺口同一处）。

验得出的部分已经验了，剩下的是还没定的决定和未关闭的缺口。

## 8. 未决问题

1. **单个工具「收到取消也不理」时怎么强制隔离？** 现在只能等它返回，没有强制出口——`STOP-ISOLATION-001` 的 gap 尚未关闭。
2. **并发 run 的 token 口径要不要按 run 隔离？** 现在依赖进程级用量计数器，串行跑才准——`STOP-USAGE-001` 的 gap 尚未关闭。
3. **守卫停因到最终 run 状态的装配谁验？** 流程验收止于「守卫给出停因」，之后的接线是另一段装配，目前无判据。

## 9. 与其他五个部件

本格把判定点借在 ④ 的环内回调里，但阈值与归类归本格；产出的停因由 ⑥ 写进账本。② 拥有循环本体，① 决定模型每轮看到什么，⑤ 维持跨轮状态。

共用数值的归属必须单调：迭代上限由本格定义、② 消费（交给框架）；墙钟由本格定义，装配层把它包在整轮外层；重复阈值与 token 上限由本格定义、④ 的环内回调执行。一个数字若有两处定义，§5.2 的「跑满判定」就没有对照物。
