# 轨迹与观测（内核侧 · 六部件之⑥）

- **适用侧**：底座 ｜ **寿命**：现状（就近维护） ｜ **最后校准**：2026-11-24

> **类型**：Architecture（解释型）。本文解释「内核为什么必须自己产出这条记录、它长什么样、哪一步会丢」，不是事实源、不是参考手册。
> **范围**：边界归属、一条轨迹的生命周期形状、设计取舍、失败语义、验收判断、未决问题。
> **非范围**：表结构与迁移、落库实现、回放界面、保留期与报表——全属应用层。
> **可枚举部分不写在这里**：文件与符号定位、结局与归类码词表、表名列名、依赖版本、测试规模都在 `docs/kb/documents/trace.toml` 的 `evidence` / `fact` 段，由 `scripts/kb_check.py` 对账；本文只写机器判不了的判断。

> **本文为什么存在**：服务于两件事——**交接边界**（告诉要改这段代码的人哪里不能碰）和**局部验收标准**（这一格做到什么算完成）。§6 的每条验收都从前面各节推导；测试是它的执行形式，不反过来定义边界。

**内核产出「事后无法从别处重建」的事实**——一次执行是什么结局、为什么、做了哪些动作、花了多少。拿掉它，内核就说不清自己为什么停：提前终止被框架正常返回，从返回值和异常里都看不出来。

## 1. 整体模型

判据只有一条：**事后能不能从别处重建？重建不了的，内核必须产出；重建得了的，应用层自己算。**

这条判据决定了本格的全部内容。工具调用次数、平均耗时、成功率都能从记录里算出来，所以一个都不进记录——它们属于报表。终态怎么判、什么算停，由外部判定，本格只搬结论。

### 1.1 一条轨迹的四段

内核不产生终态，终态是判完交给它的。一条轨迹从产生到写入是四段：

```
判定（终态 / 归类码 / 停因依据）
  → 组装（步骤序列 + 最终答复步 + 时长 + 用量 + 完整性）
  → 出口（唯一一次写，返回 run 标识）
  → 消费（应用层回放 / 检索；内核不再碰）
```

四段的控制权分散在四处，这是本格最容易被误解的地方：

```
② / ③   判定：结局与归类码
   ↓
④       采集：工具步（截断版 + 截断标志）
   ↓
⑥       组装：拼成一条记录 + 时长 + 用量 + 完整性    ← 本格
   ↓
出口     写口                                       ← 本格唯一持有的存储引用
   ↓
应用层   读口：回放 / 检索 / 报表 / 保留期
```

### 1.2 各段由谁负责

| 事 | 归属 |
|---|---|
| 一次 run 的终态 + 归类码（枚举值，不是人话） | 本格 |
| 停因的结构化依据：哪一类 / 观测到的值 / 阈值 / 对象 | 本格（判定归 ③，本格只搬） |
| 本次执行的用量：输入与输出两侧 token 数（不是进程累计） | 本格 |
| 步骤序列：迭代号 / 工具 / 参数 / 结果 / 异常 / 是否被截断 | 本格（采集归 ④，本格只存） |
| 每条结局都产出，并能声明「这条记录写没写全」 | 本格 |
| 终态怎么判、什么算停 | 外部（② / ③） |
| 每一步怎么采集 | 外部（④） |
| 模型这一轮看到了什么（指令 / 片段） | 外部（①，现为未闭合缺口） |
| 界面上的对话 | 应用层 |
| 落库：表结构、迁移、仓储实现 | 应用层 |
| 按 run 标识回放、按会话 / 终态检索 | 应用层 |
| 展示：执行过程面板、回放界面 | 应用层 |
| 保留期、归档、配额 | 应用层 |
| 报表：成功率、P95、工具失败率 | 应用层 |
| 业务审计：谁批的、外部系统里变成什么 | 应用层（动作域另记一套账） |

一个容易混的点：**内核「产出」记录，应用层「保存」记录。** 这两件事的边界不是文件位置，而是「谁定义字段」。

依赖断了谁兜着：② / ③ 不交终态，本格只能按异常兜底归类，「为什么」退化成猜；④ 不交采集结果，步骤序列整段缺失，只剩一条没有过程的结局；① 不交「模型看到了什么」，记录里有动作、没有依据；落库端口不在或写失败，记录根本不会进库，只留下一条 Warning。

### 1.3 为什么这件事只能由内核做

框架没有「一次 run 的记录」这个实体。它给的是管道上的横切层（agent 级 / chat 级 / 工具级各有插入点）、span，以及挂在响应对象上的用量 / 结束原因 / 响应标识；导出走遥测或结构化日志。它的 "trace" 指分布式追踪，不是「一次执行的历史」——**两个词在中文里都叫「轨迹」，这是混淆源头。**

于是分工断成两截：事实产生在响应对象上，观测导出在 span 与日志里，中间那截「把事实变成一条可重建的记录」没人管。这正是本格存在的理由。

同理，遥测替代不了账本。span 回答「系统健康吗、哪一步慢、钱花在哪」，读者是运维；记录回答「这一次执行是什么结局、为什么、做过哪些动作」，读者是排障、验收、追责。**span 是树不是实体**，按标识取不回一次完整执行，也没有「终态」这个概念，生命周期还是采样且短期。

反过来它有一件账本补不上的事：单次工具调用耗时——记录里只有整条 run 的墙钟。接入遥测是加法而不是替代，但有两条前提：它是装饰器形态，不触发 ① 那条「工具环外再包一层」的红线；本仓**未接入、未实测**，真接时要补「接入后循环判定与工具失败归类仍照常成立」的负控。没验过就接，等于拿形态推断当结论。

四段里第 2、3 段是本格自己要做的。下面按顺序展开。

## 2. 机制展开

### 2.1 判定：终态从哪来

内核不判。它拿到的是一个已经判好的结论：循环与预算由守卫判，异常归类由编排层判。

**成功路径不等于成功结局。** 模型正常返回时，终态取自停因；只有停因为空才记成功。提前终止（连续重复调用、预算耗尽、跑满迭代、依据不足而拒答）走的都是同一条正常返回路径——框架跑满迭代时不报错，而是清空工具逼模型用文本收口再正常返回，不主动问守卫就与「答完了」无法区分。

结局与归类码是两列，分工不能合并：**结局说「以什么状态结束」，归类码说「为什么」。** 同为超时，整轮超预算与单次模型请求超时的处理方式不同；同为失败，工具异常与模型不可用的重试价值也不同。只有一串人话时，调用方无法据此决定「重试、降级还是提示用户」。

停因依据必须带结构化的三样：类别、观测到的值、阈值（以及对象）。**不能靠解析中文消息**——同一个「检测到循环」，「连续 3 次」里的 3 是观测值还是阈值，从人话里读不出来；能读出来的也只能靠正则抠数字，那等于没有。

### 2.2 组装：步骤序列怎么拼

组装做的是把三处的产物拼成一条记录：

```
④ 的采集结果                ⑥ 的记录
  工具调用 ──────────────→ 工具步（参数、结果、异常、截断标志原样搬）
  最终文本 ──┬─ 空 ──────→ 不落步
             └─ 非空 ────→ 答复步（截断 + 标志，迭代号 = 最后一步 + 1）
```

三条规则各有理由。**工具步原样搬，不再截一次。** 参数与结果的上界由 ④ 的工具执行配置给，截断动作也在那里发生。本格把截断版和「是否截断」标志一起搬进记录——回放看到的应该是 ④ 的口径，在这里再截一次，就会出现「记录说的截断长度和工具实际返回的长度对不上」。

**空答复不落成最终答复步。** 提前终止（循环 / 预算 / 拒答）时模型往往没有最终文本，落一条空的就分不清「答了个空」和「根本没答」。将来真要记「模型确实产出空串」，得另加字段，不能复用空值。

**答复步的上界是内核常量，不是配置项。** 它随写轨迹的代码走，改它是代码改动，不是部署改动——也就不会有某次部署悄悄去掉截断。

**为什么必须有截断标志。** 没有它，回放时「模型只看到截断后的那部分」与「结果本来就这么短」无法区分。这是「写了一半比没写更危险」在单个字段上的版本。

### 2.3 出口：唯一一次写

出口只有一个动作：写一条记录，返回 run 标识。内核从不读自己的记录做决策。成功与失败走同一个出口，但带的东西不同：

```
模型循环结束
   ├── 正常返回（含提前终止）
   │      ↓
   │   终态取自停因，缺省成功
   │   用量取自响应对象
   │   完整性 = 真
   │   停因依据原样转存
   │
   └── 抛异常
          ↓
      ├─ 调用方取消 → cancelled（给用户看的是「已停止生成」）
      ├─ 轮级超时   → timeout
      ├─ 单次超时   → timeout
      └─ 其余       → failed（工具异常 / 未归类）
      用量 = 空；完整性 = 假
```

两条硬要求在这个分支上：

**失败 / 取消 / 超时也留痕，且落库不跟随调用方的取消令牌。** 只在成功时留记录的系统，出事时恰恰什么都没有——最需要回放的那次正好是失败那次。取消是「按用户意愿停下」，不是「这件事没发生」，丢掉它就丢掉了用户主动停止的证据。所以写记录用的是独立令牌：调用方取消了，不代表这次 run 可以不记账。

**写库失败只记 Warning，不掩盖原始异常，也不重试。** 出口不能把「记不下来」变成「这次执行失败」。

还有一处答不全：失败路径没有响应对象，取不到用量，记空值而不是 0——0 会被读成「这次真的没花钱」。想补只能在函数调用环外再包一层只读装饰器，那会绕过守卫与轨迹采集，所以宁可空着，也不拿进程累计冒充。

### 2.4 消费：内核不碰

回放、检索、报表、保留期，全在出口外面。这不是「暂时没做」，是边界：内核一旦能读自己的记录，判定就与存储耦成一个环——换存储要改判定，改判定会动存储。这条边界靠什么保证住，在 §3.2。

### 2.5 这一段必须成立的

- 每条结局都产出记录，并能声明完整或不完整；
- 停因能被机器读，不解析中文；
- 用量等于本次调用上报的值，不是进程累计；
- 内核不在决策路径上读轨迹。

具体主张、判据与证据强度在 §6。除了这条链上的四件事，还有几条不在链上、破了却会出事的约束，下一节说。

## 3. 特殊约束

这一节是几条不在主链上、但破了就会出事的约束。它们的共同点是：违反时不会立刻报错，会慢慢变成一个说不清的状态。

### 3.1 只存不算

内核不参与判定，也不在记录里存可算出来的东西。工具调用次数、平均耗时、成功率，全都能从步骤序列算出来。把它们放进记录，同一件事就有两个来源，改一处忘了另一处，报表和记录对不上，而没人知道该信哪个。真要让本格参与判定，先把判定收成一份（现在在 ②）。

### 3.2 只拿写口

写口与读口拆成两个接口，内核的构造只拿得到写口：

```
内核 ──注入──→ 写口
                  ↑
存储实现 ──同时实现── 写口 + 读口
                  ↓
宿主只读端点 ──注入──→ 读口
```

这样「内核不读」不是靠代码审查保证，是编译期就拿不到。反过来，只靠一句注释约定「不要读」，第一次有人为了图方便加一个读取调用、审查没拦住，环就成立了——而它不会立刻报错，只会在某次换存储时暴露。

读到哪、怎么查、留多久，全在出口外面。

### 3.3 不依赖存储与领域

观测模块只许引共享词表。引存储、领域、持久化框架一律不允许——否则内核为写一条记录，就把整个存储栈拖进编译期依赖。

方向是持久化层实现本模块的契约，反过来就错了。这条同时是一条架构门禁：给这个模块加一条存储或领域引用，编译期就会先报错。

### 3.4 加字段必须三处同改

记录结构、数据库迁移、出口映射，三处要在同一次提交里改完。只加结构不交出，等于内核产出了应用层收不到的事实；只加结构不改迁移，写的时候报错；改了迁移不改映射，读回来是空——**「字段有了、读回来是空」比没有这个字段更糟，因为它看起来是完整的。**

### 3.5 截断的上界有三个归属

三个上界分别属于三处，不能合并：

| 上界 | 归属 | 改了算什么 |
|---|---|---|
| 工具参数与结果 | ④ 的工具执行配置 | 部署改动，本格只搬结果 |
| 最终答复 | 内核常量 | 代码改动 |
| 记录条数 / 保留期 | 应用层 | 不在本格 |

在记录里再加一项上限，同一件事就有两个口径。

### 3.6 不把「模型看到了什么」塞进来

一轮 run 可能有多次模型调用，把指令与片段塞进轨迹或会话历史，会把两个口径搅在一起。那是 ① 的字段，要加就得动记录形状与出口（见 §7 第 1 条）。

约束都摆完了。但有一条没法用约束表达：**这些规则在出事那一次还成立吗。** 下一节讲。

## 4. 故障处理

本格的失败不在「判错」——本格不判；只在「没记」「记了半截」「记了但读不回」。

| 形态 | 记在哪 | 回填什么 | 谁能继续 |
|---|---|---|---|
| 没抢到会话票 | 这一次根本没有 run，没有记录 | 明说「未开始执行」 | 调用方；回放查不到是预期，不是丢账 |
| 准备阶段抛异常 | 已收进 try，落一条失败记录 | 归类码跟着分 | 调用方 |
| 中断（取消 / 超时） | 正在执行的那次调用没进步骤，标「不完整」 | 不假装全 | 应用层按「不完整」处理 |
| 落库本身失败 | 只有一条 Warning 日志，没有记录 | — | 没人；这条轨迹彻底没有 |
| 先写 run 再写步骤、两步不同事务 | 有 run 没步骤，看起来还正常 | 「完整」标志（还没接） | **未兜住**，见 §6 |

两条硬要求写在表外，因为它们是纪律不是形态：

- 失败 / 取消 / 超时这几条路径**落库不跟随调用方的取消令牌**——调用方取消了，不代表这次 run 可以不记账。
- 写库失败**只记 Warning，不掩盖原始异常**，也不重试。

准备阶段曾经在 `try` 之外：只有「模型未配置」自己落了轨迹，其余路径直接冒泡、库里什么都没有——「无论成败都留一条轨迹」这句话，在准备阶段失败时曾经不成立。已修，并有用例钉住；配套代价是原来那段「自己落轨迹」必须删掉，否则准备失败会写两条。

**一个诚实的边界**：这张表说的是本格这一侧。落库实现先插 run 再插步骤、两步不在一个事务，步骤写失败会留下「有 run 没步骤」且看起来正常——那是应用层的缺口，但「完整」这个字段真正的用武之地在这里，所以必须记在本格（见 §6）。

失败都长什么样，上面列完了。奇怪的是本格几乎没有可调参数——这本身也是一条判断，下一节说为什么。

## 5. 配置

本格没有独立配置节：轨迹的形状是代码里的约定，不是可调参数。实际值也不抄在这里——元数据登记依赖与规模，检查脚本对账，仓库是权威。

三条判断：

1. **步骤文本的上界不归本格。** 参数与结果的上界由 ④ 的工具执行配置给，本格把 ④ 的截断版和「是否截断」标志原样搬进记录——回放看到的是截断版，那是 ④ 的口径，不在这里再截一次。
2. **最终答复的上界是内核常量，不是配置项。** 它随写轨迹的代码走，改它是代码改动，不是部署改动——也就不会有某次部署悄悄去掉截断。
3. **不新增旋钮。** 留多久、归档到哪、一次查多少条，都在出口外面（应用层）；在这里再加一项，同一件事就有两个口径。

配置到这里就完了。下一个问题是：凭什么说这些规则真在生效。

## 6. 验收

判定型用例必须**正例能绿、负控能红**；能脚本判定的禁止用 AI 判。测试文件名与条数会漂，本文不列，由元数据对账。

本格该验的四件事：

| 主张 | 判据形态 | 强度 |
|---|---|---|
| 停因能被机器读：同一个「判循环」能分别读出观测值与阈值，不靠解析中文 | 正例 + 负控 | 负控实测：把观测值写死成常量、或让观测值恰好等于阈值，必须红 |
| 用量能进记录：等于该次调用上报的用量，不是进程累计 | 正例 + 负控 | 负控实测：换成进程累计值，必须红 |
| 完整性可声明：中断能被识别为「不完整」 | 正例 + 负控 | 负控实测：把中断态报成完整，必须红 |
| 内核只拿写口、只引共享词表 | 结构断言 | 读源码与工程文件：出现读轨迹的调用、或加一条存储引用，必须红 |

**三处证据要打折，别当完整证明：**

- **有一条单独看恒真。** 「供应商没报用量记空值」——不实现读取路径时字段本来就是空值。它必须与相邻那条「用量等于本次上报」一起读，单独读证明不了任何事。
- **两条边界用例读的是源码字符串。** 「决策路径上没有出现读轨迹的调用」「观测模块只引了共享词表」，证明的是「没写出来」，不是运行期行为。
- **落库往返有一条闭环，但只到形状。** 它用真迁移、真存储，验的是「同一条记录写得进去、读得回来、值不变」，证明形状、列、映射三者一致；它**不证明**事务原子性——先插 run 再插步骤两步分开，步骤写失败仍会留下「有 run 没步骤」。

**落库侧的缺口（不在内核，但必须记）**：两步不在一个事务；步骤写失败会留下看起来正常的不完整记录。「完整」字段真正的用武之地在这里，还没接。

**明确不在本文范围的**（属应用层）：检索面有没有消费者、保留期、报表、表结构怎么设计。

### 6.1 本部件算通过的标准

不能用「记录能写进去」判断完成。至少要能回答：

1. 这次 run 是什么结局、为什么——结局与归类码分开，停因带结构化依据；
2. 它做了哪些动作、分别结果如何——步骤序列完整，且「失败」与「返回空」分得开；
3. 花了多少——本次 run 的输入与输出 token，供应商没报时是空值不是 0；
4. 每条结局都产出，中断能声明不完整；
5. 内核拿不到读口，决策路径上不读轨迹；
6. 未验证的行为明确登记，不因为别的用例通过就宣称整个部件完成。

最终以实际执行结果为准，不以测试数量或测试名称为准。

验到这一步，剩下的都不是「能不能验」，而是「还没定怎么算」。下一节三条。

## 7. 未决问题

1. **「模型当时看到了什么」怎么进记录？** 一轮 run 可能有多模型调用；是每次调用一条，还是只留一份合成后的指令与片段快照？这是 ① 的字段，加进来要动记录形状与出口。
2. **「完整」标志在应用层怎么用？** 回放遇到不完整的记录，是拒绝展示、还是展示并标注？落库还不是原子的，这个标志的用法得与事务一起定。
3. **接入遥测后，判定还准吗？** 循环 / 工具失败的判定必须补负控，且遥测要落在工具环内侧，才拿得到单步耗时。

三条都指向同一件事：记录的形状还会变。形状一变，最要紧的是知道该谁跟着改——最后一张表。

## 8. 与其他五个部件

① 讲「模型每轮看到什么」——本格缺的正是这一维度，一轮 run 可能有多模型调用，那是 ① 的字段；② 讲「怎么从一轮走到下一轮」；③ 讲「允许走几轮、什么时候停」，并把终态与归类交给本格；④ 讲「一轮里的工具怎么执行」，采集在那里、落成步骤在这里；⑤ 讲「跨轮保住什么」，界面会话历史也在它那边，本格不重复存。

| 部件 | 负责的问题 | 与本部件的关系 |
|---|---|---|
| ① 请求装配 | 模型每轮看到什么 | 本格缺这一维度；补进来要动记录形状 |
| ② 框架层（MEA） | 如何从一轮走到下一轮 | 它返回，本格据此判结局 |
| ③ 终止与预算 | 允许走几轮、什么时候停 | 判定与依据由它给，本格只搬不判 |
| ④ 工具执行 | 一轮里的工具怎么执行 | 采集在它那里，落成步骤在这里 |
| ⑤ 状态与记忆 | 跨轮保住什么 | 界面会话历史在它那边，本格不重复存 |
| ⑥ 轨迹与观测（本部件） | 运行过程留下什么 | 产出那条不可重建的记录 |

一句话划界：**判定在 ② / ③，采集在 ④，装配在 ①，保存、检索、呈现、保留期都在应用层，本格只做「产出那条不可重建的记录」。**

回到开篇那句：内核必须产出「事后无法从别处重建」的事实。四段里它只做中间两段——把判好的结论和采到的步骤，拼成一条带终态、带依据、带完整性声明的记录，然后交出去，不再回头读。
