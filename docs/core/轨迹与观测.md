# 轨迹与观测（内核侧 · 六部件之⑥）

- **适用侧**：底座 ｜ **寿命**：现状（就近维护） ｜ **最后校准**：2026-11-23

> **类型**：Architecture（解释型）。本文解释「内核为什么必须自己产出这条记录、它长什么样、哪一步会丢」，不是事实源、不是参考手册。
> **范围**：边界归属、一条轨迹的生命周期形状、设计取舍、失败语义、验收判断、未验项。
> **非范围**：表结构与迁移、落库实现、回放界面、保留期与报表——全属应用层。
> **可枚举部分不写在这里**：文件与符号定位、结局与归类码词表、表名列名、依赖版本、测试规模都在 `docs/kb/documents/trace.toml` 的 `evidence` / `fact` 段，由 `scripts/kb_check.py` 对账——对不上就红。本文只写机器判不了的判断。

一句话：**内核产出「事后无法从别处重建」的事实**——一次执行是什么结局、为什么、做了哪些动作、花了多少。
拿掉它，内核就说不清自己为什么停：提前终止被框架正常返回，从返回值和异常里都看不出来。

## 一、内核负责什么 / 不负责什么

判据只有一条：**事后能不能从别处重建？重建不了的，内核必须产出；重建得了的，应用层自己算。**

| 事实 | 只在什么时候、什么地方存在 | 能重建吗 | 归属 |
|---|---|---|---|
| 终态 + 归类码 | 失败分支或正常收尾的那一刻才算得出 | 否 | **内核** |
| 停因的结构化依据（类别 / 观测值 / 阈值 / 对象） | 判定（③ 的守卫）发生时才拿得到，事后从结局和人话里抠不出来 | 否 | **内核**（③ 判、这里搬） |
| 本次调用的 token 用量 | 模型响应对象上；响应本身不落库 | 否 | **内核** |
| 每一步的工具名 / 参数 / 结果 / 异常 / 是否截断 | ④ 采集的内存轨迹，进程一退即失 | 否 | **内核**（④ 采、这里存） |
| 模型这一轮看到了什么（指令 / 片段） | ① 的请求计划，内存 | 否 | ①，不是本格 |
| 界面上的对话 | 应用层的会话历史 | 是 | 应用层 |
| 成功率 / P95 / 工具失败率 | 可从 run 记录聚合 | 是 | 应用层 |
| 保留多久、归档到哪 | 纯策略 | 是 | 应用层 |
| 回放面板长什么样 | 纯展示 | 是 | 应用层 |

按这条判据切开，分三块：

**内核管（5 条）**

- 一次 run 的**结论**：终态 + 归类码，枚举值，不是人话
- **停因的结构化依据**：哪一类、观测到的值、阈值、对象
- **本次执行的用量**：输入与输出两侧的 token 数（不是进程累计）
- **步骤序列**：迭代号、工具、参数、结果、异常、是否被截断
- **完整性**：每条结局都产出，且能声明「这条记录是否写全」

**应用层管（6 条，内核不碰）**

- 落库：表结构、迁移、仓储实现（住在持久化层）
- 按 run 标识回放、按会话 / 终态检索
- 展示：执行过程面板、回放界面
- 保留期、归档、配额
- 报表：成功率、P95、工具失败率
- 业务审计：谁批的、外部系统里变成什么（动作域另一套表）

**谁都不管（归别的格）**

- 终态**怎么判** → ② 循环驱动（守卫判环与预算，编排层归类异常）
- 每一步**怎么采集** → ④ 工具执行
- 模型**看到了什么** → ① 请求装配（现为未闭合缺口）

一个容易混的点：**内核「产出」记录，应用层「保存」记录。** 这两件事的边界不是文件位置，而是「谁定义字段」。

## 二、内核的观测该做到什么

### 三条要求

**1. 一个数据形状，且每个字段都必须是「重建不了」的。**
能算出来的（工具调用次数、平均耗时、成功率）一个都不许进来——它们属于报表，进来就是双写。

**2. 完整性：每条结局都产出，并且能声明「完整 / 不完整」。**
「写了一半」比「没写」更危险：run 有了、步骤丢了，回放看到的是一半的真相却以为是全部。

**3. 内核只拿写口。**
```
写(记录) → 返回标识
```
内核从不读自己的记录做决策，所以出口只有写。写口与读口已拆成两个接口：内核的构造只拿得到写口，读口只出现在宿主的只读端点——「内核不读」因此是编译期事实，不是注释约定。读到哪、怎么查、留多久，全在出口外面。

### 三个验收问题

内核这一格做完没做完，不看功能列表，只问三句：

| 问题 | 现在能答吗 |
|---|---|
| 这次 run 是什么结局，**为什么**？ | **能** —— 结局 + 归类码；「为什么」带结构化依据（类别 / 观测值 / 阈值 / 对象），不解析中文 |
| 它做了哪些动作，分别结果如何？ | **能** —— 步骤序列有迭代号 / 工具 / 参数 / 结果 / 异常 / 是否被截断，且「失败」与「返回空」分得开 |
| **花了多少**？ | **能** —— 本次 run 的输入 / 输出 token 数进记录；供应商没上报记 null（不是 0） |

三问都答得了。只剩一处**答不全**：失败路径没有响应对象，取不到用量，记 null。
想补只能在函数调用环外再包一层只读装饰器——那会绕过守卫与轨迹采集，所以宁可空着，也不拿进程累计冒充。

## 三、一条轨迹的生命周期

内核不产生终态，终态是 ② 判完交给它的——循环与预算由守卫判，异常归类由编排层判。形状是四段：

```
判定（终态 / 归类码 / 停因依据）
  → 组装（步骤序列 + 最终答复步 + 时长 + 用量 + 完整性）
  → 出口（唯一一次写，返回 run 标识）
  → 消费（应用层回放 / 检索；内核不再碰）
```

结局与归类码是两列，分工不能合并：**结局说「以什么状态结束」，归类码说「为什么」。**
同为超时，整轮超预算与单次模型请求超时的处理方式不同；同为失败，工具异常与模型不可用的重试价值也不同。稳定标识与词表见元数据，本文只列形状：

| 结局 | 归类 |
|---|---|
| 成功收尾 | 无归类码 |
| 环内提前终止 | 判循环 / 预算耗尽 |
| 跑满迭代 | 跑满迭代（不是「答完了」） |
| 否决式收口 | 依据不足（拒答是按设计，不是故障） |
| 调用方取消 | 取消（不是失败） |
| run 级墙钟超时 | 超时 / 整轮超预算 |
| 单次请求超时 | 超时 / 单次模型请求 |
| 其他异常 | 按异常归类（工具异常 / 模型不可用 / 未归类 …） |

两条硬要求：

- 失败 / 取消 / 超时这几条路径**落库不跟随调用方的取消令牌**——调用方取消了，不代表这次 run 可以不记账。
- 写库失败**只记 Warning，不掩盖原始异常**，也不重试。

准备阶段（装配 / 取会话 / 解析模型）也在 `try` 内：抛异常同样落一条失败记录，归类码跟着分。
它曾经在 `try` 之外，只有「模型未配置」自己落了轨迹，其余路径直接冒泡、库里什么都没有——「无论成败都留一条轨迹」这句话，在准备阶段失败时曾经不成立。已修，并有用例钉住。
配套代价：准备阶段原来那段「自己落轨迹」必须删掉，否则准备失败会写两条。

**哪一步会丢：**

| 位置 | 丢什么 | 现在怎么兜 |
|---|---|---|
| 没抢到会话票 | 这一次根本没有 run | 明说「未开始执行」，回放查不到是预期，不是丢账 |
| 准备阶段抛异常 | 整条 run 没有记录 | 已收进 `try`，落一条失败记录 |
| 中断（取消 / 超时） | 正在执行的那次调用没进步骤 | 标「不完整」，不假装全 |
| 落库本身失败 | 这条轨迹彻底没有 | 只记 Warning，不掩盖原始异常 |
| 先写 run 再写步骤、两步不同事务 | 有 run 没步骤，看起来还正常 | **未兜住**，见 §六 |

## 四、为什么这么定（六条）

只有这里几条是测试答不了的取舍；判据与负控在测试里，本文不复述。

**只存不算。**
判定分散到两处，同一件事会有两个结论；而且判定要读守卫与环的内部状态，本格拿不到。真要让本格参与判定，先把判定收成一份（现在在 ②）。

**失败 / 取消 / 超时也留痕，且不跟随调用方的取消。**
只在成功时留记录的系统，出事时恰恰什么都没有——最需要回放的那次正好是失败那次。取消是「按用户意愿停下」，不是「这件事没发生」，丢掉它就丢掉了用户主动停止的证据。

**超长必须截断：记录是回放用的，不是全文归档。**
参数与结果都是外部输入，长度不可控；不截断会把表撑爆，也把无关文本拖进排障视野。完整答复另有出处（应用层的会话历史）。调上限可以，别去掉截断。

**空答复不落成最终答复步。**
提前终止（循环 / 预算 / 拒答）时模型往往没有最终文本；落一条空的，就分不清「答了个空」和「根本没答」。唯一的正当理由是将来要记「模型确实产出空串」，那得另加字段，不能复用空值。

**不依赖存储与领域记录**（硬约束）：观测模块只许引共享词表；引存储 / 领域 / EF Core 一律不允许——否则内核为写一条记录，就把整个存储栈拖进编译期依赖。方向是持久化层实现本模块的契约，反过来就错了。

**两个边界**（别处没写，记在这里）：一是**加字段必须同时进记录结构、迁移与出口**——只加结构不交出，等于内核产出了应用层收不到的事实；这几处要在同一次提交里改完，就是为了不出现「字段有了、读回来是空」。二是**不把「模型看到了什么」塞进轨迹或会话历史**——一轮 run 可能有多模型调用，塞进历史会把两个口径搅在一起，那是 ① 的字段。

## 五、怎么算验收通过（内核级）

判定型用例必须**正例能绿、负控能红**；能脚本判定的禁止用 AI 判。测试文件名与条数会漂，本文不列，元数据里对账。

**内核该验的三件事，按重要性排**：

1. **停因能被机器读**：同一个「判循环」，必须能分别读出「观测到几次」和「阈值几次」，不靠解析中文。
   负控：把观测值写死成常量，或用例里让观测值恰好等于阈值，用例必须红。
2. **用量能进记录**：一次 run 结束后，记录里的 token 数等于该次调用上报的用量，不是进程累计。
   负控：换成进程级累计值，用例必须红。
3. **完整性可声明**：run 被中断时，记录必须能被识别为「不完整」，而不是看起来正常。
   负控：把中断态也报成完整，用例必须红。步骤写失败的同类情形还没兜住，见本节末尾的落库缺口。

**本格现在的强度**：判据落成了一组用例，验的是「交给存储的那条记录字段对不对」，
**不是**「存储写对了」——落库往返属应用层，别读成「轨迹已端到端验证」。

**证据打折的地方，别当完整证明：**

- 有几条用例单独看恒真（例如「供应商没报用量记 null」——不实现读取路径时字段本来就是 null），必须与相邻那条一起读。
- 两条边界用例读的是源码字符串（「决策路径上没有出现读轨迹的调用」「观测模块只引了共享词表」），证明的是「没写出来」，不是运行期行为。
- 落库往返只有一条：它验的正是第四节那条「加字段必须同时进记录结构与出口」，属例外，不是存储实现的证明。

**落库侧的缺口（不在内核，但必须记）**：落库实现先插 run 再插步骤，两步不在一个事务；
步骤写失败会留下「有 run 没步骤」且看起来正常。「完整」字段真正的用武之地在这里，还没接。

**明确不在本文范围的**（属应用层）：检索面有没有消费者、保留期、报表、表结构怎么设计。

## 六、Open Questions（不擅自决定）

1. **「模型当时看到了什么」怎么进记录？** 一轮 run 可能有多模型调用；是每次调用一条，还是只留一份合成后的指令与片段快照？这是 ① 的字段，加进来要动记录形状与出口。
2. **「完整」标志在应用层怎么用？** 回放遇到不完整的记录，是拒绝展示、还是展示并标注？落库还不是原子的，这个标志的用法得与事务一起定。
3. **接入遥测后，判定还准吗？** 循环 / 工具失败的判定必须补负控，且遥测要落在工具环内侧，才拿得到单步耗时。

# 附录（要评估框架与选型的人看，改代码不必读）

## A. 框架给了什么

**可观测性不是轨迹。** 框架给的是管道上的横切层（agent 级、chat 级、工具级各有插入点）与 GenAI 语义约定的 span，以及把用量 / 结束原因 / 响应标识挂在**响应对象**上；导出走 OTel 或结构化日志。

**它没有「一次 run 的记录」这个实体。** 在它的词汇里 "trace" 指分布式追踪，不是「一次执行的历史」——这两个词在中文里都叫「轨迹」，是混淆源头。

所以分工是两段，中间断了一截：

```
事实产生  ── 用量 / 结束原因 / 响应标识（在响应对象上）
                 ↓ 没有谁负责接住
观测导出  ── span / 日志 → OTLP / 文件
```

**中间那截「把事实变成一条可重建的记录」没人管**——这正是 ⑥ 存在的理由。
基线版本以各工程文件的包引用为准，升级后需重核（语义约定仍标 experimental，会变）。

## B. 成熟库能补吗

结论先给：**没有一个库能直接提供这个部件，因为它不是通用设施，是领域模型。**

**① 直接可用：没有。**
「什么算一次 run」「什么算停」「步骤怎么归属」「哪些字段必须留」——这些是领域判断，任何库都不会替你定义。库能提供的是**管道和零件**，不是语义。

**② 已经在手边的零件**：持久化、结构化日志、重试、遥测。四个都解决「怎么传、怎么写」，没有一个定义「记录里该有什么」。
最关键的错配是形态：**一次 run 是个实体，日志是条流。** 流表达不了终态，也答不了「这个 run 现在什么状态」——那在账本里是一列。

**③ 可参照结构、但不建议引入的**：后台任务调度器、工作流引擎、事件溯源库、消息 saga 各有「一次执行」的账，但它们的账是给调度器 / 编排器自己用的：schema 固定，没有会话、工具步骤、停因枚举这些本仓需要的维度。最接近的那一类（工作流历史）要额外跑一个服务、并把整个编排换成它的 workflow / activity 模型——那不是补一个部件，是换掉运行时；事件库那条则要先换数据库。

**④ 一个反例：不要用日志库当账本。**
日志库写进数据库技术上可行，但日志是**追加的流**，账本是**可查询的实体**：「这个 run 现在是什么状态」在日志里要扫全表才能答，在账本里是一列。两者不能互相替代。

所以这一格的归属很清楚：**结构参照 job run 的表形状，实现用自己的表，不引依赖。**

## C. 遥测为什么替代不了账本

| | OTel span | 内核产出的记录 |
|---|---|---|
| 回答 | 系统健康吗、哪一步慢、token 花在哪 | 这一次执行是什么结局、为什么、做了哪些动作 |
| 读者 | APM / 运维 | 排障的人、验收、追责 |
| 生命周期 | 采样、短期 | 随库保留 |
| 能否按标识取回一次完整执行 | 不能（span 是树，不是实体） | 能 |
| 有没有「终态」这个概念 | 没有 | 有 |

它有一件账本补不上的事：**单次工具调用耗时**。记录里只有整条 run 的墙钟，没有单步耗时；
要排「哪个工具慢」，只能上工具级 span。

接入遥测是**加法**，但要认清两点：

- 它是装饰器形态（agent 级 / chat 级各一层），不是请求装配的扩展点，不触发 ① 那条「工具环外再包一层」的红线。
- 本仓**未接入、未实测**。真接时必须补「接入后循环判定与工具失败归类仍照常成立」的负控，
  并且遥测要落在工具环**内侧**，才既能发 chat span、又能拿到单步耗时。
  没验过就接，等于拿形态推断当结论——那正是 ① 当初付代价学到的教训。
