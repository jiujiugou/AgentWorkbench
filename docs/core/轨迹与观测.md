# 轨迹与观测（内核侧 · 六部件之⑥）

- **适用侧**：底座 ｜ **寿命**：现状（就近维护） ｜ **最后校准**：2026-11-13

一句话：**内核产出「事后无法从别处重建」的事实**——一次执行是什么结局、为什么、做了哪些动作、花了多少。
拿掉它，内核就说不清自己为什么停：提前终止被框架正常返回，从返回值和异常里都看不出来。

> 怎么读：第一节定边界，第二节给判据，第三到五节给改代码的人，附录给要评估框架与选型的人。
> 本文只写**内核**。落库、回放、报表、审计一律不在内核，第一节已划出去。
> 决定与证据的机器可读登记在仓根 `agent-parts.toml`（`trace-observability`）：
> 10 条能力全部 wired，16 条用例全绿。红过的每一条都对应过一处真实缺口，不是补测试凑出来的。

## 一、内核负责什么 / 不负责什么

判据只有一条：**事后能不能从别处重建？重建不了的，内核必须产出；重建得了的，应用层自己算。**

| 事实 | 只存在于哪 | 能重建吗 | 归属 |
|---|---|---|---|
| 终态 + 归类码 | `catch` 块里临时算出来 | 否 | **内核** |
| 停因的计数（「连续 **3** 次」的 3） | `AgentRunGuard._repeats` 私有字段 | 否 | **内核** |
| 本次调用的 token 用量 | `AgentResponse.Usage`（响应对象不落库） | 否 | **内核** |
| 每一步的工具名 / 参数 / 结果 / 异常 | ④ 的 `ToolCallTrace`，内存 | 否 | **内核** |
| 模型这一轮看到了什么（指令 / 片段） | `ContextPlan`，内存 | 否 | ①，不是本格 |
| 界面上的对话 | `messages` 表 | 是 | 应用层 |
| 成功率 / P95 / 工具失败率 | 可从 run 表聚合 | 是 | 应用层 |
| 保留多久、归档到哪 | 纯策略 | 是 | 应用层 |
| 回放面板长什么样 | 纯展示 | 是 | 应用层 |

按这条判据切开，分三块：

**内核管（5 条）**

- 一次 run 的**结论**：终态 + 归类码，枚举值，不是人话
- **停因的结构化依据**：哪一类、观测到的值、阈值
- **本次执行的用量**：input / output tokens（不是进程累计）
- **步骤序列**：迭代号、工具、参数、结果、异常、是否被截断
- **完整性**：五条出口都产出，且能声明「这条记录是否写全」

**应用层管（6 条，内核不碰）**

- 落库：表结构、迁移、仓储实现（现住 `Foundation/Persistence/Traces/`）
- 按 runId 回放、按会话 / 终态检索
- 展示：执行过程面板、回放界面
- 保留期、归档、配额
- 报表：成功率、P95、工具失败率
- 业务审计：谁批的、ERP 里变成什么（动作域另一套表）

**谁都不管（归别的格）**

- 终态**怎么判** → ② 循环驱动判、Harness 归类
- 每一步**怎么采集** → ④ 工具执行
- 模型**看到了什么** → ① 请求装配（现为未闭合缺口）

一个容易混的点：**内核「产出」记录，应用层「保存」记录。** 这两件事的边界不是文件位置，而是「谁定义字段」。

## 二、内核的观测该做到什么

### 三条要求

**1. 一个数据形状，且每个字段都必须是「重建不了」的。**
能算出来的（工具调用次数、平均耗时、成功率）一个都不许进来——它们属于报表，进来就是双写。

**2. 完整性：五条出口都产出，并且能声明「完整 / 不完整」。**
「写了一半」比「没写」更危险：run 有了、步骤丢了，回放看到的是一半的真相却以为是全部。

**3. 一个只写出口。**
```
写(记录) → 返回标识
```
内核从不读自己的记录做决策，所以出口只有写。读到哪、怎么查、留多久，全在出口外面。
（已拆成 `IExecutionTraceWriter` / `IExecutionTraceReader` 两个口：Harness 构造函数里只有 Writer，
读口只出现在 Host 的只读端点。所以「内核不读」是编译期事实，不是注释约定。）

### 三个验收问题

内核这一格做完没做完，不看功能列表，只问三句：

| 问题 | 现在能答吗 |
|---|---|
| 这次 run 是什么结局，**为什么**？ | **能** —— 结局 + 归类码；「为什么」带结构化依据（类别 / 观测值 / 阈值 / 对象），不解析中文 |
| 它做了哪些动作，分别结果如何？ | **能** —— `agent_steps` 有迭代号 / 工具 / 参数 / 结果 / 异常 / 是否被截断，且「失败」与「返回空」分得开 |
| **花了多少**？ | **能** —— 本次 run 的 input / output token 进记录；供应商没上报记 null（不是 0） |

三问都答得了。只剩一处**答不全**：失败路径没有 `AgentResponse`，取不到用量，记 null。
想补只能在函数调用环外再包一层只读装饰器——那会绕过守卫与轨迹采集，所以宁可空着，也不拿进程累计冒充。

## 三、五条出口（内核与 Harness 的交界）

内核不产生终态，终态是 Harness 判完交给它的。五条出口对应五组结论：

```
成功收尾        → succeeded        / 无归类码
环内提前终止    → loop_detected    / loop_detected
                 budget_exceeded  / budget_exceeded
跑满迭代        → iteration_limit / iteration_limit
否决式收口      → refused         / knowledge_insufficient
调用方取消      → cancelled       / cancelled
run 级墙钟超时  → timeout         / run_timeout
单次请求超时    → timeout         / model_timeout
其他异常        → failed          / 按异常归类（tool_error / unhandled_error …）
```

两条硬要求：

- 失败 / 取消 / 超时这几条路径**用 `CancellationToken.None` 落库**——调用方取消了，不代表这次 run 可以不记账。
- 写库失败**只记 Warning，不掩盖原始异常**（`PersistQuietlyAsync`）。

准备阶段（装配 / 取会话 / 解析模型）也在 `try` 内：抛异常同样落一条 `failed`，归类码跟着分。
它曾经在 `try` 之外，只有「模型未配置」自己落了轨迹，其余路径直接冒泡、库里什么都没有——
`IAgentHarness` 注释里那句「无论成败都留一条轨迹」，对任何非 Hub 调用方都不成立。已修，并有用例钉住。
配套代价：`PrepareRunAsync` 里原来那段「自己落轨迹」必须删掉，否则准备失败会写两条。

## 四、四个决定

**1. 只存不算。**
为什么：判定分散到两处，同一件事会有两个结论；而且判定要读守卫与 loop 的内部状态，本格拿不到。
改它：真要让本格参与判定，先把判定收成一份（现在在 Harness），否则就是第三份口径。

**2. 失败 / 取消 / 超时也留痕，且不跟随调用方的取消。**
为什么：只在成功时留记录的系统，出事时恰恰什么都没有——最需要回放的那次正好是失败那次。
取消是「按用户意愿停下」，不是「这件事没发生」，丢掉它就丢掉了用户主动停止的证据。
改它：要改先想清楚「出事时靠什么还原现场」，现在没有第二份。

**3. 超长必须截断：记录是回放用的，不是全文归档。**
为什么：参数与结果都是外部输入，长度不可控；不截断会把表撑爆，也把无关文本拖进排障视野。
完整答复另有出处（`messages` 表）。改它：调上限可以，别去掉截断。

**4. 空答复不落成 assistant 步。**
为什么：提前终止（循环 / 预算 / 拒答）时模型往往没有最终文本；落一条空的，就分不清「答了个空」和「根本没答」。
改它：只有一种正当理由——将来要记「模型确实产出空串」，那得另加字段，不能复用空值。

## 五、红线

1. **只存不算**。终态与归类码的判定在 ② 与 Harness；本格改了判定，等于两处逻辑打架。
2. **五条出口都必须留痕**，且写库失败不能掩盖原始异常。
3. **超长必须截断**。任何来自模型或工具的文本，进记录前都要有上界。
4. **加字段必须同时进记录结构与出口**。只加结构不交出，等于内核产出了应用层收不到的事实；
   出口包含落库那一步——`M033` 与记录形状同一次提交，就是为了不出现「字段有了、读回来是空」。
5. **不把「模型看到了什么」塞进 `chat_messages` 或 `agent_steps`**。一轮 run 可能有多模型调用，塞进历史会把两个口径搅在一起；那是 ① 的字段。
6. **内核不依赖存储与领域记录**。`Observability.csproj` 只许引 `Shared`；引 `Persistence` / `Domain` / EF Core 一律不允许——
   否则内核为写一条记录，就把整个存储栈拖进编译期依赖。

## 六、怎么算验收通过（内核级）

判定型用例必须**正例能绿、负控能红**；能脚本判定的禁止用 AI 判。本文不列测试文件名与条数（会漂）。

**内核该验的三件事，按重要性排**：

1. **停因能被机器读**：同一个 `loop_detected`，必须能分别读出「观测到几次」和「阈值几次」，不靠解析中文。
   负控：把观测值写死成常量，用例必须红。
2. **用量能进记录**：一次 run 结束后，记录里的 token 数等于该次调用上报的用量，不是进程累计。
   负控：换成进程级累计值，用例必须红。
3. **完整性可声明**：步骤写失败时，记录必须能被识别为「不完整」，而不是看起来正常。

**本格现在的强度**：判据落成了一组用例，验的是「Harness 交给存储的那条记录字段对不对」，
**不是**「存储写对了」——落库往返属应用层，别读成「轨迹已端到端验证」。

**落库侧的缺口（不在内核，但必须记）**：`SaveAsync` 先插 run 再插 steps，两步不在一个事务；
步骤写失败会留下「有 run 没步骤」且看起来正常。`complete` 字段真正的用武之地在这里，还没接。

**明确不在本文范围的**（属应用层）：检索面有没有消费者、保留期、报表、表结构怎么设计。

唯一一条例外是「记录字段能原样落库读回」——它验的不是存储实现，而是红线 4：
内核加的字段，应用层真的收得到。没有它，前面所有断言都只到「交出去了」这一步。

# 附录（要评估框架与选型的人看，改代码不必读）

## A. MAF 给了什么

基线版本以各 csproj 的 `PackageReference` 为准，升级后需重核（语义约定仍标 experimental，会变）。

| 层 | 来源 | 类型 | 给到的能力 |
|---|---|---|---|
| 挂载机制 | MAF | `AIAgentBuilder.Use` 四重载、`UseAIContextProviders` | 任意横切逻辑的插入点：装饰器 / 带 DI 装饰器 / 替换式 run / 环绕式中间件 |
| agent 级追踪 | MAF | `OpenTelemetryAgent`、`OpenTelemetryConsts`、`UseOpenTelemetry` | GenAI 语义约定（v1.37）span；`DefaultSourceName` 供 `AddSource` 订阅；`UpdateCurrentActivity` 挂标签；`EnableSensitiveData` 默认 false |
| chat 级追踪 | **MEA** | `OpenTelemetryChatClient`、`UseOpenTelemetry`（本仓已引的 10.10.0 里就有） | GenAI 语义约定（v1.41）chat span + token 用量；无需新增依赖 |
| 工具级追踪 | MAF + MEA | `TryActivateInnerChatClientTelemetry` | 自动把 OTel 插到 `FunctionInvokingChatClient` **下方**，让 FICC 发 `execute_tool` span |
| 结构化日志 | MAF / MEA | `LoggingAgent`、`LoggingChatClient` | 装饰器形态，写 `ILogger`，敏感内容需显式开启 |
| 事实字段 | MAF | `AgentResponse.Usage` / `FinishReason` / `ResponseId` / `AgentId` | **框架把事实放在响应对象上**，不放在观测层 |

**MAF 没有「轨迹」这个部件。** 它只定义「可观测性」：管道上的横切层 + 语义约定 span。
在它的词汇里 "trace" 指 OpenTelemetry 的分布式追踪，不是「一次 run 的历史记录」。这两个词在中文里都叫「轨迹」，是混淆源头。

所以框架的分工是两段，中间断了一截：

```
事实产生  ── AgentResponse.Usage / FinishReason
                 ↓ 没有谁负责接住
观测导出  ── OpenTelemetryAgent / LoggingAgent → OTLP / ILogger
```

**中间那截「把事实变成一条可重建的记录」没人管**——这正是内核 ⑥ 存在的理由。

## B. MAF 不给的，C# 成熟库能补吗

结论先给：**没有一个库能直接提供这个部件，因为它不是通用设施，是领域模型。**

拆三层看：

**① 直接可用：没有。**
「什么算一次 run」「什么算停」「步骤怎么归属」「哪些字段必须留」——这些是你的领域判断，任何库都不会替你定义。
库能提供的是**管道和零件**，不是语义。

**② 已经在手边的零件**（本仓已引，不用新增依赖）：

| 零件 | 本仓用什么 | 它解决什么 | 它不解决什么 |
|---|---|---|---|
| 持久化 | EF Core + Dapper + FluentMigrator | 写表、迁移 | 记录里该有什么字段 |
| 结构化日志 | Serilog（Console / File sink） | 传输、格式化、落文件 | 一次 run 是个**实体**，日志是**流**，流表达不了终态 |
| 重试 | Polly | 重试策略 | **不记重试历史**——做过几次、上次为什么失败，它不管 |
| 遥测 | OTel（经 MEA 已在） | span / 指标 | 树不是账本，见附录 C |

**③ 可参照结构、但**不建议**引入的**：

| 库 | 它的模型 | 为什么只参照不引入 |
|---|---|---|
| Hangfire | `Job` / `State` / `Set` 表：状态机 + 重试计数 | 表是给调度器自己用的，schema 固定，没有 session / 工具步骤 / 停因枚举；只为一张表引一整套后台任务栈不划算 |
| Quartz.NET | `QRTZ_JOB_DETAILS` / `QRTZ_FIRED_TRIGGERS`：一次触发一条记录 | 同上，且模型是「触发器→作业」，不是「会话→一次执行」 |
| Temporal | workflow history：事件溯源式的执行账本，**最接近** | 引入等于把整个编排换成 workflow/activity 模型，还要跑 Temporal Server——这不是补一个部件，是换掉运行时 |
| Marten | event store + projection | 要 PostgreSQL；本仓是 SQLite 单文件 |
| MassTransit | saga 状态机 + 消息追踪 | 面向消息流，不是「一次执行」 |

**④ 一个反例：不要用日志库当账本。**
Serilog 写进数据库技术上可行，但日志是**追加的流**，账本是**可查询的实体**：
「这个 run 现在是什么状态」在日志里要扫全表才能答，在账本里是一列。两者不能互相替代。

所以这一格的归属很清楚：**结构参照 job run（Hangfire / Quartz / Temporal 的表形状），实现用自己的表，不引依赖。**

## C. 遥测为什么替代不了账本

| | OTel span（`OpenTelemetryAgent` 等） | 内核产出的记录 |
|---|---|---|
| 回答 | 系统健康吗、哪一步慢、token 花在哪 | 这一次执行是什么结局、为什么、做了哪些动作 |
| 读者 | APM / 运维 | 排障的人、验收、追责 |
| 生命周期 | 采样、短期 | 随库保留 |
| 能否按标识取回一次完整执行 | 不能（span 是树，不是实体） | 能 |
| 有没有「终态」这个概念 | 没有 | 有 |

它有一件账本补不上的事：**单次工具调用耗时**。记录里只有整条 run 的墙钟，没有单步耗时；
要排「哪个工具慢」，只能上 `execute_tool` span。

接入遥测是**加法**，但要认清两点：

- `OpenTelemetryAgent` 是 `AIAgent` 装饰器、`OpenTelemetryChatClient` 是 `IChatClient` 装饰器，
  都不是 `AIContextProvider`，不触发 ① 那条「工具环外再包一层」的红线。
- 本仓**未接入、未实测**。真接时必须补「接入后 `loop_detected` 与 `tool_error` 仍照常判定」的负控，
  并且 OTel 要落在 `FunctionInvokingChatClient` **内侧**，才既能发 chat span、又能让 FICC 发 `execute_tool` span。
  没验过就接，等于拿形态推断当结论——那正是 ① 当初付代价学到的教训。
