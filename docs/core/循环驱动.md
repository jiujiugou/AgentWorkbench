# 循环驱动（Runtime.Harness · 六部件之②）

- **适用侧**：底座
- **寿命**：现状（就近维护）
- **最后校准**：2026-11-23
- **类型**：Architecture（解释型）

> 本文解释「怎么从一轮走到下一轮、这一格能决定什么、决定不了什么」，不是事实源、不是参考手册。
>
> **范围**：边界归属、循环装配形状、设计取舍、失败语义、验收判断、未决问题。
>
> **非范围**：允许跑几轮 / 多久 / 何时停的规则（③）、单轮工具执行（④）、终态落库（⑥）、请求内容组装（①）、业务审计与「成功」的整体判据（正本六句）。
>
> **事实来源**：文件与符号定位、配置实际值与依赖版本、测试规模、用例名与预设变异点，都在 `docs/kb/documents/loop.toml` 与 `docs/kb/contracts/loop.toml`，由 `scripts/kb_check.py` 对账。本文只解释这些事实背后的判断。

> **本文为什么存在**：服务于交接边界（改这段代码的人哪里不能碰）和局部验收标准（这一格做到什么算完成）。§6 的每条验收都从前面的边界推导；测试与契约是执行形式，不反过来定义边界。本文不与正本六句比大小——六句回答项目成没成，这里回答这一格做完没做完。

## 1. 这一格要解决什么问题

一次问答不需要循环：用户问一句，模型答一句。但只要模型说「我查一下」，事情就变了——工具结果得回到模型，模型才能基于它继续判断；如果这一步回不去，模型就永远只能凭空答。

框架其实已经提供了这圈：识别工具调用、回填结果、再问模型一次，都在它的函数调用环里。所以本格要做的不是**造一个循环**，而是**把已经装好的那圈正确接进一次 run**：让循环跑起来、把预算交给它、在它停下来时多问一句「是答完了还是跑满了」。

判据是：**「怎么从一轮走到下一轮」是不是本格决定的？** 注意这句话问的不是「跑几轮」——那是 ③ 的规则；本格只决定这圈怎么接、预算怎么传、收尾怎么分类。

这也是六部件里最特殊的一格：② 在代码里没有自己的模块，决定散在 Harness（怎么装）与 Tools（环怎么配）两处。它长期没写文档、至今没有独立门禁，根源就在这里。要从一轮走到下一轮，得先看清谁装、谁跑、谁判。

## 2. 整体模型：谁装、谁跑、谁判

③ 定义迭代预算，本格把它翻译成框架能懂的限额；④ 在工具执行管道里建好函数调用环；本格的 `BuildAgent` 把这条已装好的 client 原样交给 Agent；之后 MEA 驱动整圈，直到模型自己停或预算拦下。

```text
③ 的迭代预算 ──→ CreateLimits ──→ ④ 的工具执行管道
                                        │
                     new FunctionInvokingChatClient(guard, …)
                     { MaximumIterationsPerRequest = 预算,
                       其余三项：连续错误上限 / 允许并发 / 未知工具是否终止
                                 （全部显式给出） }
                                        │
① 装配产物 → 消息 / 指令              │
                                        ▼
② BuildAgent(client, instructions)
   装配选项 { 原样使用已装好的 client, 请求选项 = … }
                                        │
              RunAsync / RunStreamingAsync ──→ MEA 驱动整圈
```

三处职责不能混：**循环本体**由 ④ 装配、MEA 实现——本仓不写 `while`；**装配**归本格——`BuildAgent` 把 client 原样交给 Agent；**预算与判定**归 ③——环内 `InspectToolCall`，收尾 `InspectCompletion`，本格只负责把预算装到环上、收尾时主动问一次分类。

这些判定要成立，靠别的部件把东西送到手上：

| 依赖 | 提供什么 | 断了谁兜着 |
|---|---|---|
| ④ 装的函数调用环 | 循环本体、结果回填、批次 | 环不在就没有循环，本格只剩装配 |
| ③ 的迭代预算 | 「跑到几轮 / 何时停」的含义 | 本格只翻译，不自己定阈值 |
| 框架的响应对象 | 中间轮次与正文 | 中间轮次被丢，收尾判定只能靠计数猜（缺口 A） |

图上每一处都已经写成了"应该怎么做"，但为什么不能换一种做法，得逐条说清。

## 3. 为什么这么定

### 3.1 不自研循环

识别工具调用、结果回填、批次、自然收尾全在框架的函数调用环里。本仓不写 `while`，也不手写「再问模型一次」——框架有等价物就用它的，这是项目一贯的纪律。自己造一圈，就要自己负责它的并发、取消、分片和终止语义，而这些恰好是框架已经处理过的部分。

### 3.2 原样使用装好的 client

`UseProvidedChatClientAsIs` 表达「让框架原样使用 ④ 装好的函数调用环，不在外面再包一层」。但措辞要说准：在当前版本、client 已经是函数调用环的条件下，删掉这个开关**没有可观测差异**——实测是「装配约定，因果未证实」，不是「硬要求」。保留它是为了表达意图，不能拿它当「防绕过守卫」的证据；后者没有实验支持。

### 3.3 两条出口共用一个循环

普通与流式都走同一个执行核心；流式把整段 drain 包进同一个墙钟预算。流式不是第二条执行路径，差别只在产出形态——如果给流式另建一条环，两条路径会各自演化，终态和循环次数迟早对不上。

### 3.4 预算经限额对象传递

迭代预算是 ② 与 ③ 共用的数字：③ 定义含义，本格只负责翻译，经装配常量交给框架，不由 Harness 直接设。在这里再加一个上限，同一件事就有两个口径——收尾判定拿哪个数去比，就没有唯一答案。

### 3.5 环上四个选项全部显式赋值

最大迭代数之外的三项——连续错误上限、允许并发、未知工具是否终止——框架都有默认值，本仓全部显式给出，取值仍等于当前默认。这是有意的：不改变现有行为，只把隐式默认变成显式决定。否则框架升级改了默认值，代码一行没动，行为变了，没有测试会红。

### 3.6 跑满迭代时主动问一次收尾分类

框架跑满迭代不报错，而是清空工具逼模型用文本收口、正常返回。不问就与「模型主动答完」无法区分。判定归属 ③，但**问这个动作**是本格收尾流程的一部分——这是本格在循环上唯一主动做的事。

### 3.7 框架没给循环状态快照，本仓也不造

响应只暴露正文与用量，中间轮次留在消息列表里；「跑满迭代」不是框架给的信号，是 ③ 靠计数猜出来的。这是设计缺口，不是加测试能补的——补它需要框架暴露中间轮次，本仓自己造一份只会和框架的版本对不上。

这些取舍都落在装配上，但装配值本身不是本格定的：预算的「多少」归 ③，本格只决定「怎么交」。

## 4. 配置：本格只参与一项

实际键名与取值不抄在这里——`loop.toml` 的 fact 段登记生产取值，`scripts/kb_check.py` 读宿主配置与 csproj 对账，仓库是权威。

四组参数分属两格：**迭代预算归 ② / ③ 交界**——③ 定义含义，本格经装配常量交给框架；**run 级墙钟、重复调用上限、token 上限归 ③**，本格不碰。上次校准发现墙钟的启动配置覆盖了代码默认，旧表照抄默认值的写法已经删掉。

两条判断：**显式胜过默认**——环上其余三项就算取值等于当前默认也要写出来，这是防升级漂移的安全边界；**本格不新增旋钮**——在这里再加一个上限，同一件事就有两个口径。

配置定了，但环里出错时怎么处理还没说——本格没有独立的失败出口。

## 5. 失败与恢复语义

环内的失败由框架归类，终止语义归 ③；本格只负责把预算装到环上、在收尾时多问一次：

| 形态 | 记在哪 | 回填什么 | 谁能继续 |
|---|---|---|---|
| 跑满迭代 | ③ 的收尾分类（本格主动问） | 清空工具后模型用文本收口 | 模型收口，run 正常返回 |
| 连续错误到上限 | 框架终止 | 框架给的错误结果 | 框架；本格只显式给值 |
| 未知工具名 | 框架默认回填 | 「工具找不到」 | 视终止开关，本仓显式关 |
| 中途取消 | 循环停下，记录不完整 | 无 | 调用方 |
| 流式分片 | 同一执行核心、同一墙钟预算 | 产出形态不同 | 与普通出口一致 |

这也是 ② 在六部件里最特殊的地方：没有独立模块、没有独立判据登记、没有门禁会红——它是唯一一格。上面这些边界凭什么算成立？下一节把每条变成可验的契约。

## 6. 契约验收：从边界推导

本节不是测试清单，是 §1–§5 每条边界的验收推导。判定型用例必须正例能绿、负控能红；能脚本判定的禁止用 AI 判。用例名、变异点与强度细节在 `contracts/loop.toml`，本文只留结论。

| 契约 / 小节 | 从哪条边界推导 | 结论 |
|---|---|---|
| `LOOP-FRAME-001`（第 3.1 节） | 不自研循环；回填、批次、自然收尾都在框架里 | 有判据：真 run 回归锁 |
| `LOOP-SHAPE-001`（第 3.3 节） | 两出口共用一环；循环次数与终态一致、分片不丢 | 有判据：真 run 回归锁 |
| `LOOP-BUDGET-001`（第 3.4 节） | 迭代预算经限额落到环上，不超上限 | 有判据：回归锁 + 装配判据两路 |
| `LOOP-OPTIONS-001`（第 3.5 节） | 四项显式落到框架实例属性，默认值不漂移 | 有判据：装配判据 + 结构门禁，负控实测过 |
| `LOOP-FINISH-001`（第 3.6 节） | 跑满时主动问一次收尾分类 | 有判据：③ 的判定层 + 本格收尾调用 |
| `LOOP-SNAPSHOT-001`（第 3.7 节） | 中间轮次可观察，收尾不靠计数猜 | **无判据**：框架不给快照，缺口 A |

证据强度有四处打折，别把「有判据」读成「完全证明」：

- 回归锁没有改动 Harness 实现，只是把「现在的行为」钉住；锁只在当前版本下证明过，换版本或改装配必须重跑，升级流程里没有强制入口。
- 有一次结构门禁假绿：扫的是含注释全文，删掉代码行、注释还在，断言照样绿。已改成只扫代码行，实测删行会红。别过度解读反向结论——去掉开关在当前装配下没有可观测差异，不等于开关没用，它可能防的是别的框架版本或别的 client 形态。
- 不二次包裹的行为必要性仍无证据，只有装配约定的实测记录。
- 缺口 A 是设计缺口，不是加测试能补的；本格也没有独立门禁会红。

验得出的部分已经验了，剩下的是未定的决定和未关闭的缺口。

## 7. 未决问题

1. **换了框架版本或改了装配，这些锁重跑过吗？** 目前只在当前版本下证明过；升级流程里没有强制重跑的入口。
2. **要不要补一份 run 内循环状态快照？** 现在 Harness 看不到中间轮次，收尾判定只能靠执行控制层私有的迭代计数猜（缺口 A）——`LOOP-SNAPSHOT-001` 的 gap 尚未关闭。

## 8. 与其他五个部件

③ 的模块名容易误认成本格——它原名 `Runtime.Loop`，正名是因为它不驱动循环；接口只做两件事：加 run 级墙钟超时、造判定器。本格只回答「怎么从一轮走到下一轮」：① 决定每轮看到什么，③ 决定何时停，④ 决定工具怎么执行，⑤ 维持跨轮状态，⑥ 保存运行证据。

迭代预算是 ② 与 ③ 唯一共用的数值：③ 定义它，本格消费它（交给框架、落到环上）。一个数字若有两处定义，收尾分类就没有对照物。
