# 循环驱动（六部件之②）

- **适用侧**：底座 ｜ **寿命**：现状（就近维护） ｜ **最后校准**：2026-11-13

一句话：**让「模型 → 工具 → 结果回填 → 再问模型」这圈跑起来，直到模型自己停、或被预算拦下。**
循环本体由 MEA 的 `FunctionInvokingChatClient` 承担，本仓不自研循环——这是判据，不是省事。

> 怎么读：第一、二节划边界，第三节说清「框架给的」与「本仓决定的」，第四节列配置，
> 第五节红线，**第六节是本文的重点：`Runtime.Harness` 这一侧没做完整的地方**。
> 本文只做解释，不是事实源。决定与证据的机器可读登记在仓根 `agent-parts.toml`；
> **② 是六部件里唯一既没有部件文档、也没有进表的一格**——本文补齐前者，后者仍空，
> 所以第六节列的缺口目前**没有机器可读登记，也没有门禁会变红**。

## 一、职责

按「这段机制 MAF / MEA 有等价物吗」分两栏。有等价物的用框架的，没有的才是本仓要写的。

**框架给（不写、不包、不重排）**

1. 识别模型响应里的工具调用意图，把结果回填成消息，再问模型一次
2. 一轮里多个工具调用的批次与并发
3. 模型不再调工具时的自然收尾
4. 流式分片与增量产出
5. 未知工具名的回填（`TerminateOnUnknownCalls` 默认 false，本仓依赖这个默认）

**本仓决定（只有这四件）**

1. **用哪条链跑循环**：`UseProvidedChatClientAsIs = true`，让 MAF 原样使用 `ToolExecutionPipeline` 装好的函数调用环，而不是在工具环外再包一层
2. **两条出口同一个 loop**：`RunAsync` 与 `StreamAsync` 都走 `_loop.ExecuteAsync`，流式把整段 drain 包进同一个墙钟预算；差别只在产出形态
3. **循环允许跑几轮**：`_loop.MaxIterations` 经 `ToolExecutionLimits` 落到 `MaximumIterationsPerRequest`
4. **循环外的收尾分类**：跑满迭代时框架不报错、而是清空工具逼模型用文本收口，Harness 必须主动问一次 `InspectCompletion()`

## 二、不归本格

| 事 | 归谁 | 为什么 |
|---|---|---|
| 允许跑多久、重复调用几次、烧多少 token | ③ 终止与预算（`Runtime.Loop` / `AgentRunGuard`） | 阈值与判定，不是「让循环转起来」 |
| 每轮工具怎么执行、参数校验、异常回填、未知工具留痕 | ④ 工具执行（`Runtime.Tools`） | 环内执行点 |
| 模型这一轮看到什么（指令 / 历史 / 片段） | ① 请求装配（`Runtime.Context`） | 注入内容 |
| 一次 run 的终态、停因、用量、步骤、完整性 | ⑥ 轨迹与观测 | 记录，不参与驱动 |
| 界面要不要增量、要不要 Stop | 应用层 | 展示与交互 |

一个容易混的点：**`Runtime.Loop` 这个模块名对应的是 ③，不是 ②**。`IAgentLoop` 只做两件事——`ExecuteAsync`（加 run 级墙钟超时）与 `CreateGuard`（造一个判定器），它**不驱动循环**。② 在代码里没有独立模块，跨的是 `Runtime.Harness`（装配决定）与 `Runtime.Tools`（FICC 配置）。这是本格长期没写文档的一个原因：它没有一个「自己的家」。

## 三、三处分工

```
③ AgentLoop.MaxIterations ──→ ToolExecutionLimits ──→ ④ ToolExecutionPipeline
                                                          │
                                    new FunctionInvokingChatClient(guard, …)
                                    { MaximumIterationsPerRequest = N }
                                                          │
① Context.Compose ──→ run.Messages / Instructions          │
                                                          ▼
② Harness.BuildAgent(execution.Client, instructions)
   ChatClientAgentOptions { UseProvidedChatClientAsIs = true, ChatOptions = … }
                                                          │
                    RunAsync / RunStreamingAsync ──→ MEA 驱动整圈循环
```

- **循环本体**（④ 装配、MEA 实现）：`FunctionInvokingChatClient` 在 `ToolExecutionPipeline.Create` 里建，工具清单一同挂在 `ChatOptions.Tools`。
- **装配**（② 归 Harness）：`BuildAgent` 把它原样交给 `ChatClientAgent`；`UseProvidedChatClientAsIs` 是这里唯一的硬开关。
- **预算与判定**（③）：`ToolCallGuardChatClient` 在环内调 `InspectToolCall`，Harness 收尾调 `InspectCompletion`。

为什么 `UseProvidedChatClientAsIs` 是这个装配的关键开关：本仓的意图是让 MAF 原样使用已装好的函数调用环，不另包一层。
**但「不设就会绕过守卫与轨迹采集」这个因果，在 MEA 10.10.0 下尚未得到行为证据**——删掉它，① 与 ② 的装配判据全部仍绿，详见第六节 F。

## 四、配置

`Harness:Loop`（`AgentLoopOptions`，默认值以源码为准）：

| 键 | 默认 | 落到哪 | 归哪格 |
|---|---|---|---|
| `MaxIterations` | 6 | `FICC.MaximumIterationsPerRequest` | **② / ③ 交界** |
| `TimeoutSeconds` | 30 | `AgentLoopService.ExecuteAsync` 的 `CancelAfter` | ③ |
| `MaxRepeatedToolCalls` | 3 | `AgentRunGuard.DetectLoop` | ③ |
| `MaxTokensPerRun` | 0（不限制） | `AgentRunGuard.DetectBudgetOverage` | ③ |

**只有 `MaxIterations` 是本格参与的配置**，而且它也不由 Harness 直接设，是经 `ToolExecutionLimits` 传给 ④。

FICC 的其余选项全部用 MEA 默认值，本仓没有任何显式决策：

| 语义 | 现状 | 风险 |
|---|---|---|
| 连续错误上限（`MaximumConsecutiveErrors`） | 隐式默认 | 升级 MEA 改了默认值，本仓没有回归锁会发现 |
| 一轮多工具调用的并发 / 批次 | 隐式默认 | 同上；且没有测试证明批次在本装配下正确 |
| 未知工具名行为（`TerminateOnUnknownCalls`） | 注释明写「默认 false，本仓依赖它」 | 依赖一个未钉住的默认值——框架一改，④ 的未知工具留痕逻辑语义就变 |
| 工具调用失败后的重试 / 结果裁剪 | 隐式默认 | 同上 |

这张表是**第六节缺口 B 的来源**：不是「框架没给」，而是「框架给了、本仓没做决定、也没锁住」。

## 五、红线

1. **不自研循环**。`IAgentLoop` 不写 `while`，Harness 不手写「再问模型一次」。判据：这段机制 MEA 有等价物吗？有 → 用它的。
2. **不在工具环外再包一层**。`UseProvidedChatClientAsIs = true` 与「不挂 `AIContextProviders`」是本仓的装配约定；
   「包第二层会绕过守卫与轨迹采集」在 MEA 10.10.0 下尚未被行为断言证实（见第六节 F）。
3. **② 不判终止**。跑满迭代的归类在 ③ 的 guard 与 Harness 收尾，循环层只负责转。
4. **两条出口必须同一个 loop、同一道 guard、同一套轨迹**。流式不是第二条执行路径。
5. **默认值的改变必须能被发现**。依赖框架默认值可以，但要有回归锁证明「换版本后这些锁重跑过」——现在没有（见第六节）。

## 六、怎么算验收通过：Harness 这一侧没做完整

**结论先给（2026-11-14 更新）：② 的装配已完整落实，循环行为有回归锁，但 A 与 F 仍未闭合。** 装配决定现集中在 `Runtime.Harness/LoopAssembly.cs`；FICC 四个选项全部显式赋值（B 已闭）；F1.7 的假绿已修（F 拿到结构证据，仍缺行为必要性证据）。下表保留 11-13 的原始核对结果，标「已闭」的行是本轮处置后的状态。

按全景清单给的四条回归锁（回填 / 批次 / 自然收尾 / 流式不丢分片）逐条核对：

| 判据 | 现有覆盖 | 判定 |
|---|---|---|
| 结果回填后模型被再问一次 | ① 的 `两轮模型请求` 验的是「没包第二层」；④ 的 `工具异常仍被转成结果消息回填且不炸整轮` 在工具层 | **半** —— 没有 Harness 层「两次不同工具 → 两轮回填 → 收口」的用例 |
| 批次（一轮多工具并行） | 无 | **缺** |
| 自然收尾（模型不再调工具就停） | 无显式锁 | **缺** |
| 流式不丢分片 | `ScriptedChatClient.ToolCallFragmented` 有装置，但验的是 `ToolCallGuardChatClient` 的「整轮结束再判」 | **半** —— Harness 的 `StreamRunAsync` 没有分片用例 |
| `MaxIterations` 真的落到 FICC | `循环驱动.cs` 的行为断言 + `循环驱动装配.cs` 读 FICC 实例属性 | **已闭**（11-14）—— 四个选项全部显式赋值并真触达 |
| 不二次包裹 | ① 的 `两轮模型请求` + F1.7（已改只扫代码行） | **结构已证、行为未证** —— 删掉代码行现在会红；删掉开关本身仍无可观测差异，详见缺口 F |

### 六处具体缺口

**A. Harness 看不到循环状态。**
`RunAsync` 拿到 `AgentResponse` 后只读 `.Text` 与 `.Usage`（⑥ 加的），中间轮次全在 `response.Messages` 里、被丢掉。
「跑满迭代被强制收口」不是框架给的信号，而是 `AgentRunGuard.InspectCompletion()` 拿私有 `_lastIteration` **猜**出来的。
后果：循环转了几轮、每一轮模型请求了什么，Harness 只能靠 ④ 内存里的 `ToolExecutionRun.Traces` 侧面知道；一旦轨迹采集被绕过，收尾分类也跟着错。

**B. FICC 只决策了一个选项，其余靠隐式默认。（2026-11-14 已闭）**
原来最容易被「框架升级」静默击穿：默认值变了，代码一行没改，行为变了，没有测试会红。
现在四项（`MaximumIterationsPerRequest` / `MaximumConsecutiveErrorsPerRequest` / `AllowConcurrentInvocation` /
`TerminateOnUnknownCalls`）的值全部由 `Runtime.Harness/LoopAssembly.cs` 显式给出，`ToolExecutionPipeline.Create`
照单赋值；`循环驱动装配.cs` 读框架实例的属性做真触达判据，期望值硬编码，改决定必须连判据一起改。
值仍取 MEA 10.10 的当前默认，是刻意的：落实 ② 不改变现有行为，只把隐式默认变成显式决定。

**C. 循环行为没有 Harness 级回归锁。**
现有与循环有关的测试，全部是①的装配形状断言或④的工具层断言。缺的是「一次真 run 里循环到底怎么转」——两轮不同工具、批次、自然收尾、跑满迭代时框架真的不再给工具、取消时循环真的停下来。

**D. 两条出口的循环语义没有对齐验证。**
代码注释写着「同一 loop / 同一 guard / 同一轨迹」，但没有一条测试同时跑 `RunAsync` 与 `StreamAsync`、断言「工具调用次数 / 步骤序列 / 终态一致」。流式与同步目前是**靠代码长得像**来保证一致，不是靠判据。

**E. `CancellationToken` 传到 FICC 之后的行为未验。**
Harness 把 token 交给 `_loop.ExecuteAsync` → `run.Agent.RunAsync(..., token)`。中途取消时，正在执行的工具调用会不会被中止、轨迹会不会落在「不完整」上，⑥ 只验了「超时后 `Complete=false`」，没验取消传导。

**F. 「不二次包裹」的防护是恒真的，开关的必要性没有行为证据。**
2026-11-13 实测：把 `AgentHarnessService.BuildAgent` 里 `UseProvidedChatClientAsIs = true` 整行删掉，重跑——

| 检查 | 结果 |
|---|---|
| ② 的 `两轮不同工具的回填_模型被再问一次且两轮都进轨迹` | **仍绿**（模型 3 次请求、工具恰好执行 2 次） |
| ① 的六条装配判据 | **6/6 仍绿** |
| `LoopStructureTests.Harness_不得二次包裹函数调用环`（F1.7） | **仍绿** |

F1.7 恒真的原因很具体：它 `Assert.Contains("UseProvidedChatClientAsIs", source)` 扫的是**含注释的全文**，而 `BuildAgent` 的 `<remarks>` 注释里本来就写着这个词。删掉代码行，注释还在，断言照样绿——它证明的是「注释里有个词」，不是「代码里有这一行」，更不是「包第二层会坏」。

**别过度解读这个结果**：在 MEA 10.10.0 + 传入的 client 已经是 `FunctionInvokingChatClient` 的装配下，去掉开关没有可观测差异，不等于开关没用（它可能防的是别的 MAF 版本或别的 client 形态）。能确定的只有一句：**「硬要求」「会绕过守卫与轨迹采集」这个说法目前没有行为证据支撑**，第一、三节里把它写成硬要求是沿用了既有注释。

**2026-11-14 的处置**：选了后者的一半——F1.7 改成只扫代码行，实测删掉代码行会红（假绿已修）；`BuildAgent` 的注释把「硬要求 / 会绕过守卫与轨迹」降级成「装配约定，因果未证实」，`LoopAssembly` 的 XML 注释记录了这次实测。开关的**行为必要性**仍无证据，`agent-parts.toml` 的 `no-second-function-loop-convention` 因此登记为 `unit-only`，不伪装成 wired。

### 11-13 补上的回归锁

`tests/AgentWorkbench.CoreTests/Runtime/循环驱动.cs` 八条回归锁，把上表从「半 / 缺 / 缺 / 半」补成有判据：
两轮不同工具回填、一轮批次两调用、自然收尾不多问、流式三片不丢、`MaxIterations` 真的落到 FICC、
两条出口循环次数与终态一致、中途取消循环停下且记录不完整、未知工具回填而非终止（B 的一条行为锁）。

**这些锁没有改动 Harness 的实现**——它们只是把「现在的行为」钉住，让升级 MEA 时能被发现。

### 11-14 落实的装配

② 没有独立模块，本轮给它一个「家」：`Runtime.Harness/LoopAssembly.cs` 收拢全部装配决定——
迭代预算来自 ③ 的 `IAgentLoop`，四个框架选项与 `UseProvidedChatClientAsIs` 开关给出常量，
`CreateLimits` 产出 ④ 需要的 `ToolExecutionLimits`。`PrepareRunAsync` 与 `BuildAgent` 都从这里取值，
不再散着填；两条出口共用同一份 `PreparedRun`，所以「整个拼装过程」在 Harness 只有一个入口。

`tests/AgentWorkbench.CoreTests/Runtime/循环驱动装配.cs` 五条判据：决定值正确、四个选项真落到
`FunctionInvokingChatClient` 实例、`ToolExecutionLimits` 默认值不漂移、Harness 两处都走 LoopAssembly、
开关仍在代码行。负控实测：把 `MaxConsecutiveErrorsPerRequest` 从 3 改成 5 → 两条判据红；
删掉 `BuildAgent` 的开关代码行 → F1.7 红。

**仍未闭合的**：A（Harness 看不到循环中间态，是设计缺口，不是加测试能补的）、
F 的行为必要性（需 MAF 大版本升级后在真实装配下重跑探针）。
C / D / E 已由 11-13 的八条锁覆盖，但那只是「现在的行为」，不等于框架升级后仍成立。

### 边界

上面五条**都是本格的缺口，不是缺落库、缺面板、缺报表**。补法的共同形状是：加回归锁（测试输出），不是加机制；机制 MEA 已经给了。

也别把「测试补齐」当成「循环驱动做完了」：按 v3 的判据，成功是六句可检验的话，功能数与绿灯数一律不是成功标准。这里能证明的只是「换框架版本或改装配后，循环没被悄悄改坏」。

# 附录（查漏用，改代码不必读）

## A. 框架给什么

| 层 | 类型 | 给到什么 |
|---|---|---|
| MEA | `FunctionInvokingChatClient` | 循环本体、结果回填、批次、`MaximumIterationsPerRequest`、`MaximumConsecutiveErrors`、`TerminateOnUnknownCalls` |
| MAF | `ChatClientAgent` / `ChatClientAgentOptions` | `RunAsync` / `RunStreamingAsync`、`UseProvidedChatClientAsIs`、`ChatHistoryProvider` |
| 本仓 | `ToolCallGuardChatClient` | 环内「整轮结束再判」、守卫询问、未知工具留痕 |

## B. 与其它四份部件文档的边界

① 讲「模型每轮看到什么」，② 讲「怎么从一轮走到下一轮」；③ 讲「允许走几轮、什么时候必须停」，
④ 讲「一轮里的工具怎么执行」，⑥ 讲「走过之后留下什么」。
`MaximumIterations` 是 ② 与 ③ 唯一共用的数字：② 负责把它交给框架，③ 负责定义它。

## C. 外部锚点

`docs/Agent部件全景与查漏清单.md` 第 3 块（循环驱动）给的判据原文：
「落实的证据形态：回填、批次、自然收尾、流式不丢分片各有回归锁（框架给的机制也要锁，因为装配是自己的）」；
「查漏问题：『结果回填后模型被再问一次』有测试吗？换了框架版本或改了装配，这些锁重跑过吗？」

第六节那张表就是这两句话的逐条答案：**半、缺、缺、半；没有。**
