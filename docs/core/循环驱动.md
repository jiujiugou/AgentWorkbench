# 循环驱动（六部件之②）

- **适用侧**：底座 ｜ **寿命**：现状（就近维护） ｜ **最后校准**：2026-11-23

> **类型**：Architecture（解释型）。本文解释「怎么从一轮走到下一轮、这一格能决定什么、决定不了什么」，不是事实源、不是参考手册。
> **范围**：边界归属、循环装配形状、设计取舍、失败语义、验收判断、未决问题。
> **非范围**：允许跑几轮 / 多久 / 何时停的规则（③）、单轮工具执行（④）、终态落库（⑥）、请求内容组装（①）、业务审计与「成功」的整体判据（正本六句）。
> **可枚举部分不写在这里**：文件/符号定位、配置实际值、依赖版本、测试规模都在 `docs/kb/documents/loop.toml` 的 `evidence` / `fact` 段，由 `scripts/kb_check.py` 对账；本文只写机器判不了的判断。

一句话：**让「模型 → 工具 → 结果回填 → 再问模型」这圈跑起来，直到模型自己停、或被预算拦下。**
拿掉它，一次 run 就只剩单次问答——工具调用的结果回不到模型，模型没法基于结果继续判断。

## 一、负责什么 / 不负责什么

判据只有一条：**「怎么从一轮走到下一轮」是不是本格决定的？**

| 事 | 归属 |
|---|---|
| 用哪条链跑循环（原样使用已装好的 client） | **本格**（重建不出来，是装配约定） |
| 两条出口共用一个循环与一道 guard | **本格** |
| 迭代预算怎么交给框架 | **本格**（② / ③ 之间唯一的翻译器） |
| 跑满迭代的收尾分类：主动问一次 | **本格** |
| 环上四个选项的显式取值 | **本格** |
| 识别工具意图、回填结果、再问模型 | 框架（有等价物，不重写） |
| 一轮里多个工具调用的批次与并发 | 框架 |
| 流式分片与增量产出 | 框架 |
| 未知工具名的回填语义 | 框架默认，本仓显式依赖 |
| 允许跑多久、重复几次、多少 token | ③ |
| 每轮工具怎么执行、参数校验、留痕 | ④ |
| 模型这一轮看到什么 | ① |
| 一次 run 的终态、停因、用量 | ⑥ |

依赖断了谁兜着：

| 依赖 | 提供什么 | 断了谁兜着 |
|---|---|---|
| ④ 装的函数调用环 | 循环本体、结果回填、批次 | 环不在就没有循环，② 只剩装配 |
| ③ 的迭代预算 | 「跑到几轮 / 何时停」的含义 | ② 只翻译，不自己定阈值 |
| 框架的响应对象 | 中间轮次与正文 | 中间轮次被丢，收尾判定只能靠计数猜（缺口 A） |

## 二、机制形状

一轮怎么走到下一轮，分界在「谁装、谁跑、谁判」：

```
③ 的迭代预算 ──→ CreateLimits ──→ ④ 的工具执行管道
                                        │
                     new FunctionInvokingChatClient(guard, …)
                     { MaximumIterationsPerRequest = 预算,
                       其余三项：连续错误上限 / 允许并发 / 未知工具是否终止
                                 （全部显式给出） }
                                        │
① 装配产物 → 消息 / 指令              │
                                        ▼
② BuildAgent(client, instructions)
   装配选项 { 原样使用已装好的 client, 请求选项 = … }
                                        │
              RunAsync / RunStreamingAsync ──→ MEA 驱动整圈
```

三处职责：**循环本体**由 ④ 装配、MEA 实现——函数调用环在工具执行管道里建，工具清单一同挂在请求选项上；**装配**归 ②——`BuildAgent` 把 client 原样交给 Agent，`UseProvidedChatClientAsIs` 是这里唯一的硬开关；**预算与判定**归 ③——环内 `InspectToolCall`，收尾 `InspectCompletion`。

② 在代码里没有自己的家，跨 Harness（装配决定）与 Tools（环的配置）——这是它长期没写文档的根源，也是它至今没有独立门禁的原因。

## 三、为什么这么定

**不自研循环：框架有等价物就用。** 识别工具调用、结果回填、批次、自然收尾全在框架的函数调用环里；本仓不写 `while`，也不手写「再问模型一次」。

**用哪条链跑循环：原样使用装好的 client。** `UseProvidedChatClientAsIs` 表达「让框架原样使用 ④ 装好的函数调用环，不在外面再包一层」。措辞要说准：在当前版本 + client 已是函数调用环的条件下，删掉这个开关没有可观测差异——实际测量是「装配约定，因果未证实」，不是「硬要求」。

**两条出口同一个循环、同一道 guard、同一套轨迹。** 普通与流式都走同一个执行核心，流式把整段 drain 包进同一个墙钟预算——流式不是第二条执行路径，差别只在产出形态。

**迭代预算经限额对象传递，不由 Harness 直接设。** 它是 ② 与 ③ 共用的数字，③ 定义含义，② 只负责翻译；装配常量里的那处翻译是两格之间唯一的接口。

**环上四个选项全部显式赋值，不靠隐式默认。** 框架给了选项而本仓不做决定，等于把行为交给「升级时可能变」的默认值——代码一行没改，行为变了，没有测试会红。四项仍取当前版本的默认，是有意的：不改变现有行为，只把隐式默认变成显式决定。

**跑满迭代时主动问一次收尾分类。** 框架跑满迭代不报错，而是清空工具逼模型用文本收口、正常返回；不问就与「模型主动答完」无法区分。判定在 ③，但**问这个动作**是 ② 收尾流程的一部分。

**框架没给循环状态快照，本仓不自己造一份。** 响应只暴露正文与用量，中间轮次留在消息列表里；「跑满迭代」不是框架给的信号，是 ③ 靠计数猜出来的。这是设计缺口，不是加测试能补的。

## 四、配置口径

实际键名与取值不抄在这里——`docs/kb/documents/loop.toml` 的 fact 段登记生产取值，`scripts/kb_check.py` 读宿主配置与 csproj 对账；仓库是权威。

只有迭代预算这一项由本格参与，而且不由 Harness 直接设——它经装配常量里的翻译器交给框架。四组参数分属两格：**迭代预算归 ② / ③ 交界**（② 交给框架，③ 定义含义），**run 级墙钟、重复调用上限、token 上限归 ③**。

两条判断：

- **显式胜过默认。** 环上其余三项本仓没有隐式依赖，全部显式给出；就算取值等于当前默认，也要写出来——这是防升级漂移的安全边界。
- **本格不新增旋钮。** 预算的「多少」归 ③，本格只决定「怎么交给框架」；在这里再加一个上限，同一件事就有两个口径。

## 五、失败与恢复语义

② 没有独立的失败出口：环内的失败由框架归类，终止语义归 ③，本格只负责把预算装到环上、在收尾时多问一次。

| 形态 | 记在哪 | 回填什么 | 谁能继续 |
|---|---|---|---|
| 跑满迭代 | ③ 的收尾分类（本格主动问） | 清空工具后模型用文本收口 | 模型收口，run 正常返回 |
| 连续错误到上限 | 框架终止 | 框架给的错误结果 | 框架；本格只显式给值 |
| 未知工具名 | 框架默认回填 | 「工具找不到」 | 视终止开关，本仓显式关 |
| 中途取消 | 循环停下，记录不完整 | 无 | 调用方 |
| 流式分片 | 同一执行核心、同一墙钟预算 | 产出形态不同 | 与普通出口一致 |

这也是 ② 在六部件里最特殊的地方：没有独立模块、没有独立判据登记、没有门禁会红。它是唯一一格。

## 六、怎么算验收通过

判定型用例必须**正例能绿、负控能红**；能脚本判定的禁止用 AI 判。验收以 `dotnet test` 实测为准。

| 主张 | 守它的那一组 | 强度 |
|---|---|---|
| 两轮不同工具都能回填 | 循环行为回归锁 | 当前版本实测，可信 |
| 一轮内批次两调用 | 循环行为回归锁 | 同上 |
| 自然收尾不多问 | 循环行为回归锁 | 同上 |
| 流式分片不丢 | 循环行为回归锁 | 同上 |
| 迭代上限真落到环上 | 装配判据 | 当前版本实测，可信 |
| 两条出口循环次数与终态一致 | 循环行为回归锁 | 同上 |
| 中途取消循环停下、记录不完整 | 循环行为回归锁 | 同上 |
| 未知工具回填而非终止 | 循环行为回归锁 | 同上 |
| 四项值落到框架实例属性、默认值不漂移 | 装配判据 | 当前版本实测，可信 |
| 两处都走同一处装配常量、开关仍在代码行 | 装配判据 + 结构门禁 | 代码行扫描，可信 |

**证据强度打折的地方：**

- 这组回归锁没有改动 Harness 实现，只是把「现在的行为」钉住——框架给的机制也要锁，因为装配是自己的；但锁只在当前版本下证明过，换版本或改装配必须重跑。负控实测过：改一个环上取值，对应判据会红。
- 有一次结构门禁假绿：扫的是含注释全文，删掉代码行、注释还在，断言照样绿。已改成只扫代码行，实测删行会红。别过度解读反向结论：去掉开关在当前装配下没有可观测差异，不等于开关没用——它可能防的是别的框架版本或别的 client 形态。
- 不二次包裹的行为必要性仍无证据。
- ② 是唯一既没有独立判据登记、也没有门禁会红的一格；缺口 A 是设计缺口，不是加测试能补的。

## 七、未决问题

1. **换了框架版本或改了装配，这些锁重跑过吗？** 目前只在当前版本下证明过；升级流程里没有强制重跑的入口。
2. **要不要补一份 run 内循环状态快照？** 现在 Harness 看不到中间轮次，收尾判定只能靠执行控制层私有的迭代计数猜（缺口 A）。

## 八、与其他五个部件

① 讲「模型每轮看到什么」；③ 讲「允许走几轮、什么时候必须停」；④ 讲「一轮里的工具怎么执行」；⑤ 讲「跨轮保住什么」；⑥ 讲「走过之后留下什么」。② 只回答「怎么从一轮走到下一轮」。③ 的模块名容易误认成 ②——它原名 `Runtime.Loop`，正名是因为它不驱动循环；接口只做两件事：加 run 级墙钟超时、造判定器。

迭代预算是 ② 与 ③ 唯一共用的数值：③ 定义它，② 消费它（交给框架、落到环上）。
