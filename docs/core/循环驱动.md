# 循环驱动（六部件之②）

- **适用侧**：底座 ｜ **寿命**：现状（就近维护） ｜ **最后校准**：2026-11-23

> **类型**：Architecture（解释型）。本文解释「怎么从一轮走到下一轮、这一格能决定什么、决定不了什么」，不是事实源、不是参考手册。
> **范围**：边界归属、装配路径与控制流理由、设计取舍、失败语义、验收判断、未决问题。
> **非范围**：允许跑几轮 / 多久 / 何时停的规则（③）、单轮工具执行（④）、终态落库（⑥）、请求内容组装（①）。
> **可枚举部分不写在这里**：文件/符号定位、配置实际值、依赖版本、测试规模都在 `docs/kb/documents/loop.toml` 的 `evidence` / `fact` 段，由 `scripts/kb_check.py` 对账——对不上就红。本文只写机器判不了的判断。

一句话：**让「模型 → 工具 → 结果回填 → 再问模型」这圈跑起来，直到模型自己停、或被预算拦下。**
拿掉它，一次 run 就只剩单次问答——工具调用的结果回不到模型，模型没法基于结果继续判断。

> ② 是六部件里**唯一没有独立模块的一格**：装配决定现收在 Harness 的一处装配常量里，机制本体在 MEA。这一格没有独立的机器判据登记，也没有门禁会红（见第五节）。

## 一、负责什么 / 不负责什么

判据只有一条：**「怎么从一轮走到下一轮」是不是本格决定的？**

| 事 | 归属 |
|---|---|
| 用哪条链跑循环（原样使用已装好的 client） | **本格**（重建不出来，是装配约定） |
| 两条出口共用一个 loop 与一道 guard | **本格** |
| 迭代预算怎么交给框架 | **本格**（两格之间唯一的翻译器） |
| 跑满迭代的收尾分类：主动问一次 | **本格** |
| 环上四个选项的显式取值 | **本格** |
| 识别工具意图、回填结果、再问模型 | 框架（有等价物，不重写） |
| 一轮里多个工具调用的批次与并发 | 框架 |
| 流式分片与增量产出 | 框架 |
| 未知工具名的回填语义 | 框架默认，本仓显式依赖它 |
| 允许跑多久、重复几次、多少 token | ③ |
| 每轮工具怎么执行、参数校验、留痕 | ④ |
| 模型这一轮看到什么 | ① |
| 一次 run 的终态、停因、用量 | ⑥ |

具体的类与方法定位见 `docs/kb/documents/loop.toml`，这里只判归属。

**一个容易混的点**：`Runtime.ExecutionControl` 这个模块名对应的是 **③，不是 ②**（它原名 `Runtime.Loop`，2026-11-19 正名，因为它不驱动循环）。`IAgentExecutionControl` 只做两件事——`ExecuteAsync`（加 run 级墙钟超时）与 `CreateGuard`（造判定器），它**不驱动循环**。② 在代码里没有自己的家，跨 Harness（装配决定）与 Tools（环的配置）——这是它长期没写文档的根源。

## 二、装配路径：本格与框架的分界

```
③ 的迭代预算 ──→ CreateLimits ──→ ④ 的工具执行管道
                                        │
                     new FunctionInvokingChatClient(guard, …)
                     { MaximumIterationsPerRequest = 预算,
                       其余三项：连续错误上限 / 允许并发 / 未知工具是否终止
                                 （取值见装配常量，全部显式给出） }
                                        │
① 装配产物 → run.Messages / Instructions │
                                        ▼
② BuildAgent(execution.Client, instructions)
   装配选项 { 原样使用已装好的 client, 请求选项 = … }
                                        │
              RunAsync / RunStreamingAsync ──→ MEA 驱动整圈
```

三处职责：**循环本体**由 ④ 装配、MEA 实现——函数调用环在工具执行管道里建，工具清单一同挂在请求选项上；**装配**归 ②——`BuildAgent` 把它原样交给 `ChatClientAgent`，`UseProvidedChatClientAsIs` 是这里唯一的硬开关；**预算与判定**归 ③——环内 `InspectToolCall`，收尾 `InspectCompletion`。

## 三、为什么这么定（六条）

只有六条测试答不了的取舍；判据与负控在测试里，本文不复述。

**不自研循环：MEA 有等价物就用它。**
识别工具调用、结果回填、批次、自然收尾全在 `FunctionInvokingChatClient`。`IAgentExecutionControl` 不写 `while`，Harness 不手写「再问模型一次」。

**用哪条链跑循环：原样使用装好的 client。**
`UseProvidedChatClientAsIs = true` 表达「让 MAF 原样使用 ④ 装好的函数调用环，不在外面再包一层」。**但要把措辞说准**：在当前 MEA 版本 + 传入的 client 已是 `FunctionInvokingChatClient` 的条件下，删掉这个开关**没有可观测差异**——本仓的实际测量是「装配约定，因果未证实」，不是「硬要求」。

**两条出口同一个 loop、同一道 guard、同一套轨迹。**
`RunAsync` 与 `StreamAsync` 都走同一个执行核心，流式把整段 drain 包进同一个墙钟预算——流式不是第二条执行路径，差别只在产出形态。

**迭代预算经限额对象传递，不由 Harness 直接设。**
迭代预算是 ② 与 ③ 共用的数字——③ 定义它，② 负责把它交给框架。装配常量里的那处翻译是两格之间唯一的接口。

**环上四个选项全部显式赋值，不靠隐式默认。**
框架给了选项但本仓不做决定，就等于把行为交给「升级时可能变」的默认值——代码一行没改，行为变了，没有测试会红。四项值仍取当前 MEA 版本的默认，是有意的：落实 ② 不改变现有行为，只把隐式默认变成显式决定。

**跑满迭代时主动问一次收尾分类。**
框架跑满迭代不报错，而是清空工具逼模型用文本收口、正常返回。不问就与「模型主动答完」无法区分。这条判定在 ③ 的 `InspectCompletion`，但**问这个动作**是 ② 收尾流程的一部分。

## 四、配置（只有一项归本格参与）

实际键名与取值不抄在这里——它们随宿主配置与代码默认值变。`docs/kb/documents/loop.toml` 的 fact 段登记当前生产取值，`python scripts/kb_check.py` 读 appsettings 与 csproj 对账；仓库是权威。

四组参数分属两格：**迭代预算归 ② / ③ 交界**（② 交给框架，③ 定义含义），**run 级墙钟、重复调用上限、token 上限归 ③**。三处的判定逻辑与失败语义在 `docs/core/终止与预算.md`。

只有迭代预算这一项是本格参与的配置，而且它也不由 Harness 直接设——它经装配常量里的翻译器交给框架。环上其余三项本仓没有任何隐式依赖，全部显式给出。

## 五、怎么算验收通过

判定型用例必须**正例能绿、负控能红**；能脚本判定的禁止用 AI 判。验收以 `dotnet test` 实测为准，本文不列测试文件名与条数（会漂，条数登记在 `docs/kb/documents/loop.toml` 的 fact 段）。

**已有覆盖**：两轮不同工具回填、一轮批次两调用、自然收尾不多问、流式分片不丢、迭代上限真落到环上、两条出口循环次数与终态一致、中途取消循环停下且记录不完整、未知工具回填而非终止。这些锁**没有改动 Harness 的实现**——它们只是把「现在的行为」钉住，让升级 MEA 时能被发现。装配侧另有独立一组：四项值真落到框架实例属性、限额默认值不漂移、Harness 两处都走同一处装配常量、开关仍在代码行。负控实测过：改一个环上取值 → 两条判据红。

**全仓最值得记住的一次假绿**：早期有条结构门禁扫「代码里有没有 `UseProvidedChatClientAsIs`」，它 `Assert.Contains` 扫的是**含注释的全文**，而 `BuildAgent` 的注释里本来就写着这个词。删掉代码行，注释还在，断言照样绿——证明的是「注释里有个词」，不是「代码里有这一行」，更不是「包第二层会坏」。已改成只扫代码行，实测删行会红。**别过度解读反向结论**：去掉开关在当前装配下没有可观测差异，不等于开关没用（它可能防的是别的 MAF 版本或别的 client 形态）。

**证据打折的地方**：这组回归锁验的是「现在的行为」，不等于框架升级后仍成立；不二次包裹的行为必要性仍无证据。

**还没建立的**：② 是唯一既没有独立判据登记、也没有门禁会红的一格。A（Harness 看不到循环中间态：响应里的中间轮次被丢，收尾判定只能靠执行控制层私有的迭代计数猜）是**设计缺口，不是加测试能补的**。

**明确不在本文范围的**：一次 run 的终态落库（⑥）、业务审计（动作域）、「成功」的整体判据（正本六句，功能数与绿灯数一律不是成功标准）。

# 附录（要评估框架与选型的人看，改代码不必读）

## A. 框架给了什么，没给什么

| 层 | 类型 | 给到什么 |
|---|---|---|
| MEA | `FunctionInvokingChatClient` | 循环本体、结果回填、批次、`MaximumIterationsPerRequest`、`MaximumConsecutiveErrorsPerRequest`、`TerminateOnUnknownCalls` |
| MAF | `ChatClientAgent` / `ChatClientAgentOptions` | `RunAsync` / `RunStreamingAsync`、`UseProvidedChatClientAsIs`、`ChatHistoryProvider` |
| 本仓 | `ToolCallGuardChatClient` | 环内「整轮结束再判」、守卫询问、未知工具留痕 |

**框架没给**：一次 run 的循环状态快照——响应对象只暴露正文与用量，中间轮次在消息列表里。所以「跑满迭代」不是框架给的信号，是 ③ 猜出来的（缺口 A）。

## B. 与其它五份的边界

① 讲「模型每轮看到什么」，② 讲「怎么从一轮走到下一轮」；③ 讲「允许走几轮、什么时候必须停」，④ 讲「一轮里的工具怎么执行」，⑥ 讲「走过之后留下什么」。
迭代预算是 ② 与 ③ 唯一共用的数字：② 负责把它交给框架，③ 负责定义它。

## C. 外部锚点

「回填、批次、自然收尾、流式不丢分片各有回归锁（框架给的机制也要锁，因为装配是自己的）」；
「换了框架版本或改了装配，这些锁重跑过吗？」

第五节那两件事就是这两句话的答案：锁已有，但只在当前版本下证明过。
