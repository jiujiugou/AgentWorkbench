# 循环驱动（六部件之②）

- **适用侧**：底座 ｜ **寿命**：现状（就近维护） ｜ **最后校准**：2026-11-18（当日按统一骨架重写，技术判断未变）

一句话：**让「模型 → 工具 → 结果回填 → 再问模型」这圈跑起来，直到模型自己停、或被预算拦下。**
拿掉它，一次 run 就只剩单次问答——工具调用的结果回不到模型，模型没法基于结果继续判断。

> 怎么读：第一、二节划边界与装配路径；第三节给要判断「这条是不是该自研」的人（六个决定）；
> 第四到七节是配置、排障、红线、验收；附录给要评估框架的人。
> 本文只做解释，不是事实源。**② 是六部件里唯一没有独立模块的一格**——装配决定现收在 `Runtime.Harness/LoopAssembly.cs`，
> 机制本体在 MEA。决定与证据的机器可读登记本格仍空，见第七节。

## 一、负责什么 / 不负责什么

判据只有一条：**「怎么从一轮走到下一轮」是不是本格决定的？**

| 事 | 只存在于哪 | 能重建吗 | 归属 |
|---|---|---|---|
| 用哪条链跑循环（`UseProvidedChatClientAsIs`） | `LoopAssembly` 常量 | 否 | **本格** |
| 两条出口共用一个 loop 与 guard | `Harness` 装配 | 否 | **本格** |
| 迭代预算怎么交给框架 | `LoopAssembly.CreateLimits` | 否 | **本格** |
| 跑满迭代的收尾分类：主动问一次 | `Harness.InspectCompletion()` | 否 | **本格** |
| FICC 四个选项的显式取值 | `LoopAssembly` 常量 | 否 | **本格** |
| 识别工具意图、回填结果、再问模型 | MEA `FunctionInvokingChatClient` | 是（框架） | 框架 |
| 一轮里多个工具调用的批次与并发 | MEA | 是（框架） | 框架 |
| 流式分片与增量产出 | MAF `RunStreamingAsync` | 是（框架） | 框架 |
| 未知工具名的回填语义 | MEA 默认 `TerminateOnUnknownCalls=false` | 是（框架默认） | 框架，本仓依赖这个默认 |
| 允许跑多久、重复几次、多少 token | ③ 的 guard | 否 | ③ |
| 每轮工具怎么执行、参数校验、留痕 | ④ 的 `FunctionInvoker` | 否 | ④ |
| 模型这一轮看到什么 | ① | 否 | ① |
| 一次 run 的终态、停因、用量 | ⑥ | 否 | ⑥ |

**一个容易混的点**：`Runtime.Loop` 这个模块名对应的是 **③，不是 ②**。`IAgentLoop` 只做两件事——`ExecuteAsync`（加 run 级墙钟超时）与 `CreateGuard`（造判定器），它**不驱动循环**。② 在代码里没有自己的家，跨 `Runtime.Harness`（装配决定）与 `Runtime.Tools`（FICC 配置）——这是它长期没写文档的根源。

## 二、装配路径：本格与框架的分界

```
③ AgentLoop.MaxIterations ──→ LoopAssembly.CreateLimits ──→ ④ ToolExecutionPipeline.Create
                                                                │
                                          new FunctionInvokingChatClient(guard, …)
                                          { MaximumIterationsPerRequest = N,
                                            MaximumConsecutiveErrorsPerRequest = 3,
                                            AllowConcurrentInvocation = false,
                                            TerminateOnUnknownCalls = false }
                                                                │
① Context.Compose ──→ run.Messages / Instructions                 │
                                                                ▼
② Harness.BuildAgent(execution.Client, instructions)
   ChatClientAgentOptions { UseProvidedChatClientAsIs = true, ChatOptions = … }
                                                                │
                              RunAsync / RunStreamingAsync ──→ MEA 驱动整圈
```

三处职责：**循环本体**由 ④ 装配、MEA 实现——`FunctionInvokingChatClient` 在 `ToolExecutionPipeline.Create` 里建，工具清单一同挂在 `ChatOptions.Tools`；**装配**归 ② ——`BuildAgent` 把它原样交给 `ChatClientAgent`，`UseProvidedChatClientAsIs` 是这里唯一的硬开关；**预算与判定**归 ③ ——环内 `InspectToolCall`，收尾 `InspectCompletion`。

## 三、六个决定

**1. 不自研循环：MEA 有等价物就用它。**
为什么：识别工具调用、结果回填、批次、自然收尾全在 `FunctionInvokingChatClient`。`IAgentLoop` 不写 `while`，Harness 不手写「再问模型一次」。
改它：自己写循环，就要自己处理分片、批次、取消传导与收口——而那些框架已经处理对了的。

**2. 用哪条链跑循环：原样使用装好的 client。**
为什么：`UseProvidedChatClientAsIs = true` 表达「让 MAF 原样使用 ④ 装好的函数调用环，不在外面再包一层」。**但要把措辞说准**：在 MEA 10.10.0 + 传入的 client 已是 `FunctionInvokingChatClient` 的条件下，删掉这个开关**没有可观测差异**——本仓的实际测量是「装配约定，因果未证实」，不是「硬要求」。
改它：换 MAF 大版本或换 client 形态后必须重跑探针；`no-second-function-loop-convention` 在 `agent-parts.toml` 里登记为 `unit-only`，不伪装成 wired。

**3. 两条出口同一个 loop、同一道 guard、同一套轨迹。**
为什么：`RunAsync` 与 `StreamAsync` 都走 `_loop.ExecuteAsync`，流式把整段 drain 包进同一个墙钟预算——流式不是第二条执行路径，差别只在产出形态。
改它：给流式另写一份循环，两者归类码与轨迹迟早漂移，而且漂移时两边都不报错。

**4. 迭代预算经 `ToolExecutionLimits` 传递，不由 Harness 直接设。**
为什么：`MaxIterations` 是 ② 与 ③ 共用的数字——③ 定义它，② 负责把它交给框架。`LoopAssembly.CreateLimits` 是两格之间唯一的翻译器。
改它：Harness 直接写 `FICC.MaximumIterationsPerRequest`，③ 的阈值改了这里不跟着变。

**5. FICC 四个选项全部显式赋值，不靠隐式默认。**
为什么：框架给了选项但本仓不做决定，就等于把行为交给「升级时可能变」的默认值——代码一行没改，行为变了，没有测试会红。四项值仍取 MEA 10.10 的当前默认，是有意的：落实 ② 不改变现有行为，只把隐式默认变成显式决定。
改它：删掉显式赋值，`循环驱动装配.cs` 的判据会红（实测过）。

**6. 跑满迭代时主动问一次收尾分类。**
为什么：框架跑满迭代不报错，而是清空工具逼模型用文本收口、正常返回。不问就与「模型主动答完」无法区分。这条判定在 ③ 的 `InspectCompletion`，但**问这个动作**是 ② 收尾流程的一部分。
改它：删掉那一问，`iteration_limit` 与 `succeeded` 在账本上合成一个。

## 四、配置

`Harness:Loop`（`AgentLoopOptions`，默认值以源码为准）：

| 键 | 默认 | 落到哪 | 归哪格 |
|---|---|---|---|
| `MaxIterations` | 6 | `FICC.MaximumIterationsPerRequest` | **② / ③ 交界** |
| `TimeoutSeconds` | 30 | `AgentLoopService.ExecuteAsync` 的 `CancelAfter` | ③ |
| `MaxRepeatedToolCalls` | 3 | `AgentRunGuard` | ③ |
| `MaxTokensPerRun` | 0（不限） | `AgentRunGuard` | ③ |

**只有 `MaxIterations` 是本格参与的配置**，而且它也不由 Harness 直接设——见决定 4。FICC 其余三项本仓没有任何隐式依赖，全部显式给出。

## 五、出问题先看哪

| 现象 | 先看 |
|---|---|
| 模型调了工具但没有被再问一次 | 是不是在外面包了第二层 client（决定 2）；`UseProvidedChatClientAsIs` 与 F38 |
| 一轮里多个工具调用串行了 | `AllowConcurrentInvocation` 的显式取值；本仓当前是 `false` |
| 升级 MEA 后行为变了、代码没改 | 四项 FICC 值是不是还在 `LoopAssembly` 里显式写着（决定 5） |
| 跑满迭代却记成成功 | 收尾有没有调 `InspectCompletion()`（决定 6） |
| 流式与一次性出口的轨迹不一致 | 两条路是不是还共用 `RunCoreAsync`；有没有人给流式另写了一份循环 |
| 报告说「不二次包裹」的判据绿着，但没信心 | 那条判据早期恒真过——它扫含注释全文，注释里写着这个词。现在改成只扫代码行；见第七节 |

## 六、红线

1. **不自研循环**。`IAgentLoop` 不写 `while`，Harness 不手写「再问模型一次」。判据：MEA 有等价物吗？有 → 用它的。
2. **不在工具环外再包一层**。`UseProvidedChatClientAsIs = true` 与「不挂 `AIContextProviders`」是本仓的装配约定；「包第二层会绕过守卫与轨迹」在 MEA 10.10.0 下尚未被行为断言证实（决定 2）。
3. **② 不判终止**。跑满迭代的归类在 ③ 的 guard 与 Harness 收尾，循环层只负责转。
4. **两条出口必须同一个 loop、同一道 guard、同一套轨迹**。
5. **默认值的改变必须能被发现**。依赖框架默认值可以，但要有回归锁证明「换版本后这些锁重跑过」。

## 七、怎么算验收通过

判定型用例必须**正例能绿、负控能红**；能脚本判定的禁止用 AI 判。验收以 `dotnet test` 实测为准，本文不列测试文件名与条数（会漂）。

**已有覆盖**：两轮不同工具回填、一轮批次两调用、自然收尾不多问、流式三片不丢、`MaxIterations` 真落到 FICC、两条出口循环次数与终态一致、中途取消循环停下且记录不完整、未知工具回填而非终止。这些锁**没有改动 Harness 的实现**——它们只是把「现在的行为」钉住，让升级 MEA 时能被发现。装配侧另有五条：四项值真落到框架实例属性、`ToolExecutionLimits` 默认值不漂移、Harness 两处都走 `LoopAssembly`、开关仍在代码行。负控实测过：改一个 FICC 值 → 两条判据红。

**全仓最值得记住的一次假绿**：早期有条结构门禁扫「代码里有没有 `UseProvidedChatClientAsIs`」，它 `Assert.Contains` 扫的是**含注释的全文**，而 `BuildAgent` 的注释里本来就写着这个词。删掉代码行，注释还在，断言照样绿——证明的是「注释里有个词」，不是「代码里有这一行」，更不是「包第二层会坏」。已改成只扫代码行，实测删行会红。**别过度解读反向结论**：去掉开关在当前装配下没有可观测差异，不等于开关没用（它可能防的是别的 MAF 版本或别的 client 形态）。

**证据打折的地方**：八条回归锁验的是「现在的行为」，不等于框架升级后仍成立；不二次包裹的行为必要性仍无证据。

**还没建立的**：`agent-parts.toml` 里本格仍空——② 是唯一既没有机器可读决定登记、也没有门禁会红的一格。A（Harness 看不到循环中间态：`response.Messages` 里的轮次被丢，`InspectCompletion` 靠私有 `_lastIteration` 猜）是**设计缺口，不是加测试能补的**。

**明确不在本文范围的**：一次 run 的终态落库（⑥）、业务审计（动作域）、「成功」的整体判据（正本六句，功能数与绿灯数一律不是成功标准）。

# 附录（要评估框架与选型的人看，改代码不必读）

## A. 框架给了什么，没给什么

| 层 | 类型 | 给到什么 |
|---|---|---|
| MEA | `FunctionInvokingChatClient` | 循环本体、结果回填、批次、`MaximumIterationsPerRequest`、`MaximumConsecutiveErrorsPerRequest`、`TerminateOnUnknownCalls` |
| MAF | `ChatClientAgent` / `ChatClientAgentOptions` | `RunAsync` / `RunStreamingAsync`、`UseProvidedChatClientAsIs`、`ChatHistoryProvider` |
| 本仓 | `ToolCallGuardChatClient` | 环内「整轮结束再判」、守卫询问、未知工具留痕 |

**框架没给**：一次 run 的循环状态快照——`AgentResponse` 只暴露 `.Text` 与 `.Usage`，中间轮次在 `response.Messages` 里。所以「跑满迭代」不是框架给的信号，是 ③ 猜出来的（缺口 A）。

## B. 与其它五份的边界

① 讲「模型每轮看到什么」，② 讲「怎么从一轮走到下一轮」；③ 讲「允许走几轮、什么时候必须停」，④ 讲「一轮里的工具怎么执行」，⑥ 讲「走过之后留下什么」。
`MaximumIterations` 是 ② 与 ③ 唯一共用的数字：② 负责把它交给框架，③ 负责定义它。

## C. 外部锚点

`docs/Agent部件全景与查漏清单.md` 第 3 块给本格的判据原文：「回填、批次、自然收尾、流式不丢分片各有回归锁（框架给的机制也要锁，因为装配是自己的）」；「换了框架版本或改了装配，这些锁重跑过吗？」

第七节那两件事就是这两句话的答案：锁已有，但只在当前版本下证明过。
