# 状态与记忆（Runtime.Session + Memory.Persistence · 六部件之⑤）

- **适用侧**：底座 ｜ **寿命**：现状（就近维护） ｜ **最后校准**：2026-11-13

一句话：**跨轮、跨 run 把该保住的保住**——会话对象、对话历史、长期记忆。
拿掉它，模型每轮失忆：答「没办过」→ 用户重说 → 第二张单。

> 怎么读这份文档：第一到第四节给要改代码的人，第五节给出问题的人，附录给要评估 MAF 的人。
> 决定与证据的机器可读登记在仓根 `agent-parts.toml` 的 `state-memory` 格，本文不复制。

## 一、它在一次 run 里的哪三步

```
run 前  ── 抢会话闸 → 按 sessionId 取回会话（或新建）→ 把 sessionId 写进 StateBag
          → 绑定记忆作用域（当前 run 的 session）
run 中  ── 模型调用前：ChatHistoryProvider 按 StateBag 里的 id 读历史
          → 模型调用后：把本轮新增消息（含工具往返）追加进 chat_messages
run 后  ── 写回会话快照 · 释放闸（成功/失败/取消/超时都写）
```

三个插入点里，只有中间那步在模型调用路径上；前后两步都包在 run 的外层。
历史读写走 `ChatClientAgentOptions.ChatHistoryProvider`，**不走 context provider 管道**——这一点决定了它能和 ① 的装法共存。

## 二、管什么 / 不管什么

**管**

- 会话对象按 `sessionId` 取回、写回、序列化（含快照损坏时降级重建）
- 对话历史逐条追加到 `chat_messages`：只追加、不覆盖、不裁剪
- 同一会话的 run 互斥：抢不到回 `session_busy`，拒绝不是排队
- 长期记忆的结构化条目：覆盖键、重要性、使用次数、保留期、显式遗忘
- 记忆作用域由编排层按当前 run 绑定，模型只能选「本作用域 / 全局」
- 过期数据清理：过期会话行 + 过保留期的记忆行

**不管**

- 历史裁剪 / 压缩 / 注入几条 / 占多少 token → **① 请求装配**
- 记忆的自动召回与注入 → 未建立；建立时受 ① 的约束（见决定 4）
- 界面上的对话列表 → Host（`messages` 表，与模型历史是两个源）
- 检索 / 知识库命中 → `Knowledge`，与长期记忆是两套东西
- 动作幂等（`request_id`）→ 动作层，不在记忆表里伪装幂等
- 会话归属校验（这个 id 属不属于当前主体）→ Host（S02）
- 多实例 / 跨进程互斥 → 未实现，需要数据库租约 + fence

**一个易误读点**：`agent_sessions.state_json` 不承载对话历史，只剩 `aw.session_id` 一个键；
历史在 `chat_messages`。两者职责不同、口径不同，不要互相推算。

## 三、五个决定

**1. 历史只追加，不覆盖。**
为什么：同一会话被两个 run 并发推进时，整份覆盖会互相盖掉；而且覆盖依赖一份完整快照，快照一坏整段历史就没了。
改它：要裁剪就接框架 `Compaction`（按原子组压缩、保住 tool-call/result 配对），**不要自写按条数切**——切散一对，下次模型请求直接结构报错。接之前先过决定 4。

**2. 模型历史与界面消息是两个源。**
为什么：界面要的是「用户看得见的对话」，模型要的是「含工具往返的完整上下文」。合成一个源，要么界面上出现一堆 JSON，要么模型丢了工具结果。
改它：若要统一，必须先证明「删会话」与「审计保留」两个诉求能同时满足；现在删会话只删界面，模型历史留着。

**3. 同一 sessionId 只允许一个 run，语义是拒绝不是排队。**
为什么：两个 run 并发推进同一会话，历史交叉追加、工具调用重复、审批可能下两次。
改它：MAF 的 `GetSessionLock` 是 loop 内 pending messages 的串行化，**不挡第二个 run**，不能拿来当业务闸。这条闸只在单进程成立；上多实例必须做数据库租约 + fence。

**4. 压缩与自动记忆注入不用框架。**
为什么：`CompactionProvider` 和 `ChatHistoryMemoryProvider` 都是 `AIContextProvider` 子类，
挂上去会让 MEA 在工具环外再包一层，绕过守卫与轨迹（`loop_detected`、`tool_error` 全失效）——
那是 ① 已经付代价换来的红线。
代价：模型可见历史是全量、没有 token 上限；召回只有 `LIKE` 关键词，没有自动召回。
改它：① 在真实 `ToolExecutionPipeline` 装配下重验通过后，还要补一条「压缩后 `loop_detected` 仍生效」的负控。详见附录 C。

**5. 会话存储契约还没对齐 `AgentSessionStore`。**
为什么：本仓的 `ISessionStore` + `ISessionFactory` 是 MAF `AgentSessionStore` 的手写同构版，多一层；且 key 只有字符串，拿不到 `Partitions`，租户/用户只能拼进 `sessionId`。
代价：零功能损失，但每次涉及会话的改动都要动两个接口。
改它：换成 `AgentSessionStore` 后，删掉 `ISessionFactory`，按新契约重写会话那两条测试（现在落库臂还没真跑过，见第七节）。

## 四、配置（`Harness:Memory`）

**默认值以 `MemoryOptions.cs` 为准，本表可能滞后**——这里只写「哪个键决定哪件事」。

| 键 | 默认 | 含义 |
|---|---|---|
| `SessionEnabled` | true | 关掉则每个 run 用一次性会话，无跨 run 记忆 |
| `SessionTtlMinutes` | 1440 | **会话快照**的空闲过期；`0` = 不过期 |
| `MaxCachedSessions` | 1000 | 进程内缓存条数上限；`0` = 不限 |
| `EvictionSweepSeconds` | 60 | 过期清理周期 |
| `LongTermEnabled` | true | 是否注册 `remember` / `recall`（**应为 false**，见第七节） |
| `LongTermScope` | session | 工具写入的默认作用域（`session` / `global`） |
| `MaxMemoryChars` | 2000 | 单条记忆上限，超出拒绝 |
| `RecallCandidateK` | 20 | **取库**候选上限，不是注入条数 |
| `LongTermRetentionDays` | 0 | 记忆保留天数；`0` = 不过期 |

两个容易误读的口径：

1. `SessionTtlMinutes` **不再决定模型记忆的长度**——历史在 `chat_messages`，不随 TTL 清。配置还在、行为没了。
2. `RecallCandidateK` 是「从库里取多少条」，注入几条归 ①。

## 五、出问题先看哪

| 现象 | 先看 |
|---|---|
| 重启后模型失忆 | `SessionEnabled` 是否为 true；`agent_sessions` 里有没有该行；反序列化失败会**删行降级**，看有没有那条 Warning |
| 两个会话串了历史 | provider 有没有把 `sessionId` 存进实例字段（必须每次从 `StateBag` 读）；`chat_messages.session_id` 对不对 |
| 删了会话，模型还记着 | **正常**：历史在 `chat_messages`，不随会话删。这是决定 2 的后果，不是 bug |
| 同一会话两个请求互相踩 | 闸是否生效；是不是多实例——内存锁跨进程等于没有 |
| 记忆只增不减 | `LongTermRetentionDays` 默认 0（不过期）；`MemoryRetentionService` 是否在跑 |
| 模型不记得刚调过什么工具 | `chat_messages` 里有没有 `functionCall` / `functionResult`；没写就是 provider 没拿到 `sessionId` |

## 六、红线

1. **历史只追加**：不覆盖、不裁剪、不删除。裁剪归 ①，且必须用 `Compaction`，不自写截断。
2. **provider 不持会话状态**：注册为单例、服务所有会话，`sessionId` 只能从 `StateBag[aw.session_id]` 读。存进实例字段必然串号。
3. **不开 `RequirePerServiceCallChatHistoryPersistence`**：实测一次 run 结束时工具调用与结果都已在历史里；开它只改变 `FunctionInvokingChatClient` 行为，收益为零、风险非零。
4. **序列化 `JsonSerializerOptions` 必须传 `null`**：MAF 的 source-generated 元数据在内部，传自定义实例会抛 `NotSupportedException`。
5. **作用域与互斥的边界不许糊**：模型不能指定 `scope_id`；进程内锁不能冒充分布式锁。
6. **加 `AIContextProvider` 系能力前，先解决与 ① 的冲突**：`Compaction`、`ChatHistoryMemoryProvider`
   都挂在 context provider 管道上，而 `F38` 只扫 Context / Harness 两目录——
   **本格加 provider 不会被它拦**，那是盲区，不是许可。

## 七、怎么算验收通过

判定型用例必须**正例能绿、负控能红**；能脚本判定的禁止用 AI 判。本文不列测试文件名与条数（会漂）。

**有行为证据的**：

- 会话快照损坏降级、内存版与落库版同契约
- 历史并发不丢 / 按序 / 会话隔离 / 空批次 no-op
- 工具往返完整、单条消息 `functionCall` 不丢
- 会话互斥：两个入口都回 `session_busy`
- 两个源分离（这条是**事实锁定**，不是功能验收）
- 长期记忆：覆盖键、作用域隔离、global 开关、超长拒绝、保留期、遗忘、排序、取库上限、使用次数回写
- 保留期清理：过期会话行与过期记忆行被**真删**，未过期不动
- 记忆作用域：嵌套恢复、重复释放、**并发 run 不串**

**仍是预期红的**：`LongTermEnabled` 默认值那一组（现为 `true`，按 ADR 0016 §五应为 `false`）。红是「规格未实现」的正确信号，不要改测试去迁就。具体哪几条见 `agent-parts.toml`。

**证据强度打折的地方**（别读成「已全验」；逐条原因与补法在 `agent-parts.toml` 对应条目里）：

- 会话存储的**落库臂从没真跑过**
- 会话隔离的**负控没做**
- `LongTermEnabled=false` 时不注册工具，没有测试

**还没建立的**：跨进程重启续接（没有杀进程再起的验收）、`chat_messages` 保留期（只增不减）、多实例共享会话与记忆。

# 附录（要评估 MAF 的人看，改代码不必读）

## A. MAF 在这一层给了五族能力

基线版本以各 csproj 的 `PackageReference` 为准——本表按当前版本核过，升级后需重核（MAF 的 Session / Memory API 在 1.x 期间改动过）。

| 族 | MAF 类型 | 给到的能力 | 有实现吗 |
|---|---|---|---|
| 会话状态 | `AgentSession.StateBag`、`AgentSessionStateBag`、`ProviderSessionState<T>` | 线程安全 KV；`GetValue` / `SetValue` / `TryGetValue` / `TryRemoveValue`；整体 JSON 序列化（值有反序列化缓存） | ✅ 自带 |
| 会话持久化 | `AgentSessionStore`、`AgentSessionStoreKey`、`DelegatingAgentSessionStore` | `GetSessionAsync` / `SaveSessionAsync` / `GetOrCreateSessionAsync`，**每个都带 `AIAgent`**（序列化由 store 自己调）；key = `SessionId` + `Partitions` | ⚠️ **只有抽象，无内置实现** |
| 对话历史 | `ChatHistoryProvider`、`InMemoryChatHistoryProvider` + Options | `ProvideChatHistoryAsync` / `StoreChatHistoryAsync`；`RequestMessages` 与 `ResponseMessages` 已分开；`StateKeys`；三个过滤器 + `ChatReducer` 两触发点 | ✅ 自带（内存态） |
| 历史压缩 | `CompactionProvider` + `CompactionStrategy`：`SlidingWindow` / `Truncation` / `Summarization` / `ToolResult` / `ContextWindow` / `Pipeline`；`CompactionTriggers` | 按 token / 条数 / 轮次触发；**按原子组压缩，保住 tool-call/result 配对**；可摘要、可流水线组合 | ✅ 自带 |
| 长期记忆 | `ChatHistoryMemoryProvider` + Options + Scope；`FileMemoryProvider` + `AgentFileStore` | 历史向量化语义召回（`BeforeAIInvoke` 自动注入或 `OnDemandFunctionCalling` 工具）；四维 scope；`MaxResults`、`ContextPrompt`。文件记忆：`ls` / `read` / `grep` / `write` / `delete` / `replace` | ✅ 自带（需 `VectorStore` 或 `AgentFileStore`） |

## B. 按职责分三类（机器判定用，不是给人扫的）

四问定类：给的是**实现**还是只有**抽象**？语义是否**等价**？会不会撞 **① 的红线**？存储媒介是否**匹配**？

| # | 职责 | MAF 对应 | 判定 | 依据 |
|---|---|---|---|---|
| 1 | 会话序列化 | `AIAgent.SerializeSessionAsync` / `DeserializeSessionAsync` | 接管 | 框架实现，`options` 传 `null` |
| 2 | 会话状态读写 | `AgentSession.StateBag`、`AgentSessionStateBag` | 接管 | 线程安全 KV + JSON 序列化 |
| 3 | 会话对象复用 / 写回 | `AgentSessionStore`、`AgentSessionStoreKey` | 契约接管、实现自补 | 只有抽象；方法自带 `AIAgent`；key 带 `Partitions` |
| 4 | 会话快照落库 | 无 | 自补 | `SqliteSessionStore` 必需，只是应 `: AgentSessionStore` |
| 5 | 对话历史读写 | `ChatHistoryProvider` | 基座接管、落库自补 | 框架管时机与切分，存表自己写 |
| 6 | 历史压缩 | `CompactionProvider` + 六策略 | 不能用 | `AIContextProvider` 子类，撞 `F38` |
| 7 | 会话互斥 | `GetSessionLock` | 不能当业务闸 | loop 内 pending messages 串行化，不挡第二个 run |
| 8 | 长期记忆：语义召回 | `ChatHistoryMemoryProvider` | 不能用 | 同样撞 `F38`；另需 `VectorStore`（`Knowledge.Local` 已引 sqlite-vec，本模块未引） |
| 9 | 长期记忆：结构化条目 | 无 | 自补 | 覆盖键 / `Importance` / `UseCount` / `ExpiresAt` / 遗忘 |
| 10 | 记忆作用域 | `ChatHistoryMemoryProviderScope` | 不能替代 | 只是 provider 配置项，没有「按当前 run 绑定、模型不能指定 id」的强制 |
| 11 | 保留期清理 | 无 | 自补 | `FileMemoryProvider` 也没有保留期 |
| 12 | 多实例 / 跨进程互斥 | 无 | 自补（未实现） | 框架完全不碰 |

第 1、2 条已经在用；第 3、5 条是契约接管、实现仍在自己手里——MAF 连一个 `AgentSessionStore` 的内置实现都没有。

## C. 与 ① 的冲突详情

`CompactionProvider` 和 `ChatHistoryMemoryProvider` 都是 `AIContextProvider` 子类，挂载点是 agent 的 context provider 管道。而 ① 有一条现行红线（`ContextBoundaryTests.F38`）：

> 代码里不出现 `AIContextProviders`。挂它会让 MEA 在工具环外面再包一层，绕过 `ToolExecutionPipeline` 的守卫与轨迹采集。

所以 ⑤ 想用框架原生的压缩或自动召回，**不是加个 provider 就完事**，而是要推翻或重验 ① 的那条决定。而且 `F38` 只扫 `Runtime.Context` 和 `Runtime.Harness`，⑤ 的 provider 会落在 `Memory.Persistence`，**扫不到**。

对照之下 `ChatHistoryProvider` 是安全的——它挂在 `ChatClientAgentOptions.ChatHistoryProvider`，不走 context provider 管道。

一句话分界：**历史「读写」走 `ChatHistoryProvider`（安全）；历史「压缩」和记忆「注入」走 `AIContextProvider`（撞 ①）。**
