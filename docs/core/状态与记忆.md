# 状态与记忆（Runtime.Session + Memory.Persistence · 六部件之⑤）

- **适用侧**：底座 ｜ **寿命**：现状（就近维护） ｜ **最后校准**：2026-11-23

> **类型**：Architecture（解释型）。本文解释"跨轮、跨 run 到底保住什么、由谁保管、坏了怎么收场"，不是事实源、不是参考手册。
> **范围**：边界归属、run 内插入点、存活期、存储取舍、失败语义、验收判断、未决问题。
> **非范围**：历史裁剪与请求装配、记忆的自动召回、界面会话列表、动作幂等、会话归属校验。
> **可枚举部分不写在这里**：文件/符号定位、配置实际值与代码默认、依赖版本、测试规模都在 `docs/kb/documents/memory.toml` 的 `evidence` / `fact` 段，由 `scripts/kb_check.py` 对账；本文只写机器判不了的判断。

一句话：**跨轮、跨 run 把该保住的保住**——会话对象、对话历史、长期记忆。
拿掉它，模型每轮失忆：答「没办过」→ 用户重说 → 第二张单。

## 一、负责什么 / 不负责什么

判据只有一条：**「这条状态跨过 run 之后还在不在」是不是本格决定的？**

| 事 | 归属 |
|---|---|
| 会话对象按 sessionId 取回、写回、序列化（含快照损坏时降级重建） | **本格** |
| 对话历史逐条追加：只追加、不覆盖、不裁剪 | **本格** |
| 同一会话的 run 互斥：抢不到回拒绝码，拒绝不是排队 | **本格** |
| 长期记忆的结构化条目：覆盖键、重要性、使用次数、保留期、显式遗忘 | **本格** |
| 记忆作用域按当前 run 绑定，模型只能选「本作用域 / 全局」 | **本格** |
| 过期数据清理：过期会话行 + 过保留期的记忆行 | **本格** |
| 历史裁剪 / 压缩 / 注入几条 / 占多少 token | ① |
| 记忆的自动召回与注入 | 未建立（召回归本格、注入归 ①） |
| 界面上的对话列表 | 应用层 |
| 检索 / 知识库命中 | 领域 |
| 动作幂等（请求号） | 领域（不在记忆表里伪装幂等） |
| 会话归属校验（这个 id 属不属于当前主体） | 应用层 |
| 多实例 / 跨进程互斥 | 未实现（归本格；需数据库租约 + fence） |

一个易误读点：会话快照不承载对话历史，历史单独一张表。两者职责不同、口径不同，不要互相推算。

依赖断了谁兜着：

| 依赖 | 提供什么 | 断了谁兜着 |
|---|---|---|
| 框架的历史 provider | 历史读写的时机与切分 | 缺省退回内存版，进程一停历史全丢 |
| 会话存储 | sessionId → 会话对象 | 取不到就新建；快照坏了降级重建，旧状态丢 |
| 会话闸 | 同一会话只放一个 run | 闸失效 = 并发推进，历史交叉追加、审批可能下两次 |
| 记忆作用域绑定 | 当前 run 的 session 作用域 | 没绑上就落到全局，模型能写全局 |
| 保留期清理 | 把过期行真删掉 | 不跑则表只增不减 |

## 二、机制形状

一次 run 跨三步，只有中间那步在模型调用路径上：

```
run 前  ── 抢会话闸 → 按 sessionId 取回会话（或新建）→ 把 sessionId 写进会话状态袋
          → 绑定记忆作用域（当前 run 的 session）
run 中  ── 模型调用前：历史 provider 按状态袋里的 id 读历史
          → 模型调用后：把本轮新增消息（含工具往返）追加进对话历史
run 后  ── 写回会话快照 · 释放闸（成功/失败/取消/超时都写）
```

前后两步包在 run 的外层；历史读写走 `ChatHistoryProvider`，**不走 context provider 管道**——这一点决定了它能和 ① 的装法共存。

什么东西活多久：

| 东西 | 活多久 | 谁清 |
|---|---|---|
| 会话对象 | 进程内缓存，空闲过期后不再复用 | 过期清理 |
| 对话历史 | 一直追加，不随会话 TTL 清 | 只增不减（保留期未建立） |
| 长期记忆条目 | 过保留期才清；保留期不设则不清 | 保留期清理 |
| 记忆作用域 | 一次 run | run 收尾释放（嵌套按栈恢复） |
| 会话闸 | 一次 run | 成功 / 失败 / 取消 / 超时都释放 |

这张表是本格与 ① 的分界：活得比 run 长的东西归这里，只在一次请求里成立的东西归 ①。

## 三、为什么这么定

只有这几条测试答不了的取舍；判据与负控在测试里，本文不复述。

**历史只追加，不覆盖。** 同一会话被两个 run 并发推进时，整份覆盖会互相盖掉；而且覆盖依赖一份完整快照，快照一坏整段历史就没了。要裁剪就接框架的 `Compaction` 机制（按原子组压缩、保住 tool-call/result 配对），不要自写按条数切——切散一对，下次模型请求直接结构报错。`RequirePerServiceCallChatHistoryPersistence` 也不开：实测一次 run 结束时工具调用与结果都已在历史里，开它收益为零、风险非零。

**模型历史与界面消息是两个源。** 界面要的是「用户看得见的对话」，模型要的是「含工具往返的完整上下文」。合成一个源，要么界面上出现一堆 JSON，要么模型丢了工具结果。若要统一，必须先证明「删会话」与「审计保留」两个诉求能同时满足——现在删会话只删界面，模型历史留着，这是本决定的直接后果，不是 bug。

**同一 sessionId 只允许一个 run，语义是拒绝不是排队。** 两个 run 并发推进同一会话，历史交叉追加、工具调用重复、审批可能下两次。框架的 `GetSessionLock` 是环内 pending messages 的串行化，不挡第二个 run，不能拿来当业务闸。这条闸只在单进程成立；上多实例必须做数据库租约 + fence。

**压缩与自动记忆注入不用框架，因为撞 ① 的红线。** `CompactionProvider` 和 `ChatHistoryMemoryProvider` 都是 `AIContextProvider` 子类，挂上去会让框架在工具环外再包一层，绕过守卫与轨迹（`loop_detected`、`tool_error` 全失效）——那是 ① 已经付代价换来的红线。代价：模型可见历史是全量、没有 token 上限；召回只有关键词匹配，没有自动召回。① 在真实工具执行管线装配下重验通过后，还要补一条「压缩后 `loop_detected` 仍生效」的负控。另有一个盲区要记牢：结构门禁 `F38` 只扫 ① 与 ② 的源码目录，本格加的 provider 落在本模块，扫不到——那不是许可，是本格必须自己守的约束。

**框架能给到哪一层，决定哪些要自补。** 会话状态读写与整体序列化可以接管；会话对象的取 / 存 / 取或建只有抽象、没有内置实现，只能接管契约、实现自补；对话历史同理，时机与切分归框架、存表自己写。长期记忆的结构化条目、保留期清理、多实例互斥框架完全不碰，全要自补；记忆作用域也不能靠框架的 scope 配置——那只是 provider 配置，没有「按当前 run 绑定、模型不能指定 id」的强制。历史压缩与语义召回虽然现成，但如上一条不能用——不是多余，是撞线。

**会话存储契约还没对齐 `AgentSessionStore`。** 本仓手写的契约是它的同构版，多一层；且 key 只有字符串，拿不到 `Partitions`，租户 / 用户只能拼进 `sessionId`。代价是零功能损失，但每次涉及会话的改动都要动两个接口。换成 `AgentSessionStore` 后要删掉自建的工厂接口，按新契约重写会话那两条测试（现在落库臂还没真跑过）。另有一条实现硬约束：序列化会话时 `JsonSerializerOptions` 必须传 `null`——框架的 source-generated 元数据在内部，传自定义实例会抛 `NotSupportedException`。

## 四、配置口径

值不抄在这里——键与启动实际值在 `docs/kb/documents/memory.toml` 的 `fact` 段对账，代码默认以选项类为准。

三条判断：

1. **长期记忆默认必须往「关」倒，且「停用不删」。** 关掉开关是停止写入与召回，不是删数据；现在的默认方向与规格相反，这是预期红，不要改测试迁就。
2. **会话 TTL 不再决定模型记忆的长度。** 历史在对话历史表里，不随 TTL 清；配置还在、行为没了。
3. **召回候选上限是「从库里取多少条」**，注入几条归 ①——两个数不要互相推算。

## 五、失败与恢复语义

本格大多数失败不是「run 失败」，而是「记忆缺口」：模型照常答，只是答得比有记忆时差。唯一会让 run 停下的是会话闸。

| 形态 | 记在哪 | 回填什么 | 谁能继续 |
|---|---|---|---|
| 会话快照损坏 | 反序列化失败处 | 降级重建一个空会话 | 当前 run 继续；历史从独立表照读 |
| 同一会话的第二个 run | 会话闸 | 拒绝码 | 调用方；不排队、不阻塞 |
| 两个 run 并发追加历史 | 对话历史表 | 各自的追加行 | 两边都继续，不互相覆盖 |
| 过期会话行 / 过保留期记忆行 | 清理任务 | 无（真删） | — |
| 作用域嵌套 / 重复释放 | 作用域栈 | 恢复上一层 | 当前 run 继续 |
| 多实例并发 | 无 | 无 | 未实现；闸只在单进程成立 |
| 落库臂读写失败 | 没有验收出口 | — | 未验证，见第六节 |

## 六、怎么算验收通过

判定型用例必须**正例能绿、负控能红**；能脚本判定的禁止用 AI 判。验收以 `dotnet test` 实测为准，本文不列测试文件名与条数（会漂）。

| 主张 | 守它的那一组 | 强度 |
|---|---|---|
| 会话快照损坏能降级重建 | 会话契约组 | 落库臂没真跑过 |
| 内存版与落库版同契约 | 会话契约组 | 同上 |
| 历史并发不丢、按序、会话隔离、空批次 no-op | 历史行为组 | 可信 |
| 工具往返完整、单条消息的 `functionCall` 不丢 | 历史行为组 | 可信 |
| 两个入口抢同一会话都回拒绝码 | 会话闸组 | 可信 |
| 模型历史与界面消息是两个源 | 事实锁定（不是功能验收） | 可信 |
| 长期记忆：覆盖键、作用域隔离、全局开关、超长拒绝、保留期、遗忘、排序、取库上限、使用次数回写 | 长期记忆组 | 可信 |
| 过期会话行与过期记忆行被真删、未过期不动 | 保留期组 | 可信 |
| 记忆作用域：嵌套恢复、重复释放、并发 run 不串 | 作用域组 | 可信 |
| 长期记忆默认应为关 | 规格判据 | **预期红** |

**证据强度打折的地方（别读成「已全验」）：**

- 会话存储的**落库臂从没真跑过**。
- 会话隔离的**负控没做**。
- 长期记忆关闭时不注册工具，没有测试。

## 七、未决问题

1. **要不要现在切到 `AgentSessionStore` 契约？** 切了要删自建工厂接口、按新契约重写会话测试，而落库臂还没真跑过——先补跑还是先切，未定。
2. **跨进程重启怎么续接？** 现在没有「杀进程再起」的验收。
3. **对话历史要不要保留期？** 现在是只增不减；定保留期就要同时定「删了之后模型看到什么」。
4. **多实例共享会话与长期记忆怎么做？** 需要数据库租约 + fence，现在完全没做。

## 八、与其他五个部件

① 讲「模型每轮看到什么」，本格只把历史与记忆拿出来、追加回去，注入几条与怎么压缩归 ①；② 讲「怎么从一轮走到下一轮」，本格的插入点借在它的前后；③ 讲「允许走几轮、什么时候停」；④ 讲「一轮里的工具怎么执行」，工具往返由它产生、本格只负责逐条追加；⑥ 讲「走过之后留下什么」，账本与会话 / 记忆是两套表，不要互相推算。

共用数值：会话 TTL 与记忆保留期由本格定义，只清本格自己的表；召回候选上限由本格定义、① 消费（取多少条 vs 注入几条）。历史长度没有数字——框架与本仓都不给它设上限。
