# 状态与记忆（Runtime.Session + Memory.Persistence · 六部件之⑤）

- **适用侧**：底座
- **寿命**：现状（就近维护）
- **最后校准**：2026-11-24
- **类型**：Architecture（解释型）

> 本文解释跨轮、跨 Run 的状态如何保留，谁负责读取和写回，以及并发、损坏和过期时如何处理。
>
> **范围**：状态分类、存活期、Run 内插入点、持久化取舍、并发控制、长期记忆、失败恢复、验收判断和未决问题。
>
> **非范围**：历史裁剪与请求装配（①）、模型循环（②）、运行预算（③）、工具执行（④）、界面会话列表的具体实现、动作幂等、会话归属校验。
>
> **事实来源**：文件与符号定位、配置实际值与代码默认、依赖版本、测试规模、用例名和预设变异点，分别由 `docs/kb/documents/memory.toml` 与 `docs/kb/contracts/memory.toml` 维护，并由 `scripts/kb_check.py` 对账。本文只解释这些实现背后的架构判断。

> **本文为什么存在**：服务于两件事——**交接边界**（告诉要改这段代码的人哪里不能碰）和**局部验收标准**（这一格做到什么算完成）。§7 的每条验收都从前面各节推导；测试与契约是它的执行形式，不反过来定义边界。本文不与正本六句比大小：六句回答项目成没成，这里回答这一格做完没做完。

**跨 Run 的状态不是一份数据，是五份寿命完全不同的东西。**

把它们混成一个 Session 容器，后面所有的互相覆盖、顺序错乱和清理错误都从这一步开始：拿会话 TTL 去清对话历史、拿历史表充当长期记忆、把一次 Run 的作用域留到下一次。

本格的目标不是让模型记得更多，是让每一份状态在它该在的地方、活它该活的时间。

## 1. 整体运行模型

模型回答「没办过」，用户把同一句话又说了一遍，系统开出第二张单。

这不一定是模型记忆能力的问题。也可能是上一轮产生的信息没有被系统保留下来，下一次 Run 根本没有获得它。

还有一类问题更隐蔽：会话还在，对话历史也在，但两个 Run 几乎同时推进同一段对话。模型分别在不同的上下文片段中继续推理，最终产生互相冲突的结果。

前者是**状态丢失**，后者是**状态错乱**。

只解决持久化，不能解决并发；只解决并发，也不能保证下一次 Run 能够恢复之前的信息。

因此，Runtime.Session + Memory.Persistence 必须回答三个问题：

1. **保留什么**：哪些状态需要跨越一次 Run，继续参与后续运行？
2. **如何使用**：当前 Run 在什么时机读取、更新和释放这些状态？
3. **如何保证一致性**：多个 Run 同时运行、数据损坏或超过保留期时，系统怎样避免产生错误状态？

本格的责任判据是：

**一项状态是否需要跨越 Run 存在，以及它的存储、恢复和释放是否由本格决定。**

按这三问，本格的东西分成两部分：一次 Run **在链上**碰什么（会话闸、记忆作用域、会话对象、历史读写），和**不在链上**的持久化设施（会话快照、对话历史、长期记忆条目的存储与生命周期）。

### 1.1 一次 Run 如何使用状态

整个 Run 分为 Run 前、Run 中和 Run 后。右边标出这一步碰的是哪份状态、它活多久：

```
Run 前
    ↓
抢占会话闸                          ← 会话闸（Run 结束释放）
    ↓
按 sessionId 取回会话或新建会话        ← 会话快照（会话 TTL）
    ↓
将 sessionId 放入请求状态袋
    ↓
绑定当前 Run 的记忆作用域            ← 记忆作用域（Run 结束释放）
    ↓
Run 中
    ↓
模型请求前：历史 Provider 读取对话历史  ← 对话历史（无保留期）
    ↓
框架驱动模型与工具交互
    ↓
本轮结束：追加新增消息（含工具往返）     ← 对话历史
    ↓
Run 后
    ↓
写回会话快照                        ← 会话快照
    ↓
释放记忆作用域
    ↓
释放会话闸
```

读这张图只要看两件事：**带「Run 结束释放」的两行是锁，Run 一结束就必须消失；其余三行是数据，各活各的时间。** 锁和数据在图上交错出现，实际上也是交错发生的——抢完闸才取会话，取完会话才绑作用域，而读历史和写回快照之间夹着整个模型循环。

三处职责不能混淆：

- 会话身份由编排层维护。
- 历史读取和写入时机由框架的历史 Provider 管理。
- 状态存什么、如何持久化、活多久，由本格负责。

这条链只回答「什么时候碰」。每一步碰到的到底是什么、它存在哪里、活多久，在 §3。§4 讲链上那两把锁（会话闸与记忆作用域）在并发下怎么守住，§5 讲上面每一步失败时会变成什么样。

### 1.2 五类状态与存活期

三类跨 Run 数据、两类 Run 内控制状态，各活各的时间：

| 状态     | 保存什么         | 活多久       | 释放或清理方式          |
| ------ | ------------ | --------- | ---------------- |
| 会话快照   | 非历史的会话状态     | 会话生命周期    | 空闲过期、TTL 或损坏重建   |
| 对话历史   | 用户、模型及工具往返消息 | 跨 Run 持续存在 | 当前只追加，尚未建立保留期    |
| 长期记忆条目 | 结构化的记忆内容     | 跨会话存在     | 按记忆保留期清理         |
| 记忆作用域  | 当前 Run 的记忆归属 | 一次 Run    | Run 收尾释放，嵌套按栈恢复  |
| 会话闸    | 当前会话的独占占位    | 一次 Run    | 成功、失败、取消、超时均释放   |

这里最重要的不是五个名字，而是不能混用它们的生命周期：

- 不能拿会话 TTL 清理对话历史。
- 不能拿对话历史表充当长期记忆表。
- 不能拿长期记忆表实现业务幂等。
- 不能把一次 Run 的记忆作用域保留到下一次 Run。
- 不能让会话闸在 Run 结束后继续占用。

**跨 Run 的信息保留和 Run 内的执行控制，是两件不同的事。**

### 1.3 各环节由谁负责

| 环节         | 控制者          | 决策依据           | 执行责任    |
| ---------- | ------------ | -------------- | ------- |
| 会话身份       | 编排层          | 请求携带的 sessionId | 编排层     |
| 会话闸占用与释放   | Runtime.Session | 该 sessionId 是否已被占 | Runtime.Session |
| 会话快照恢复与写回  | Runtime.Session | sessionId 对应的记录 | 存储实现    |
| 记忆作用域绑定与释放 | 编排层          | 当前 Run 的归属     | 编排层     |
| 历史读取       | 框架历史 Provider | 状态袋里的 sessionId | 历史存储    |
| 历史追加       | 框架历史 Provider | 本轮新增消息         | 历史存储    |
| 记忆写入、召回与遗忘 | 模型经工具请求      | 当前作用域          | 记忆存储    |
| 保留期清理      | 后台清理任务       | 各自定义的保留期       | 存储实现    |
| 删除会话       | 应用层          | 应用层            | 应用层     |
| 会话归属与租户校验  | 应用层          | 业务规则           | 应用层     |

这里同样要分清四种东西：**谁建立、谁释放、谁判断能不能进入、谁承担数据正确性**。检查发生在谁内部，不等于所有权归谁。

例如，快照损坏后要不要重建，由本格决定；但重建出来的会话属于哪个用户，本格不问——它只认编排层给的 sessionId。同理，清理任务由本格跑，但删不删一条会话由应用层的产品决策定。

本格明确不负责：模型循环、运行预算、业务权限、账本持久化、会话归属校验。这些分别属于 ②、③、应用层和 ⑥。

## 2. 一次 Run 如何使用这些状态

上一节给了顺序。这一节按顺序走一遍，每一步回答两个问题：为什么必须在这一步做，以及不做会错成什么样。

### 2.1 抢占会话闸：先拿到独占权

Run 开始时，首先抢占当前 sessionId 对应的会话闸。

这是因为后续操作不仅会读取会话，还可能修改会话快照、追加对话历史和更新其他状态。

如果两个 Run 同时推进同一会话，即使历史采用追加，也可能产生交错的对话顺序：

```
Run A                         Run B

读取历史 H                    读取历史 H
    ↓                            ↓
处理用户问题 A                处理用户问题 B
    ↓                            ↓
生成部分结果                  生成部分结果
    ↓                            ↓
追加消息 A                    追加消息 B
```

最后历史可能变成：

```
H → A 的部分消息 → B 的部分消息 → A 的剩余消息
```

这不是普通的数据覆盖，而是整个对话顺序失去一致性。模型下一次读取时，可能面对一份混合了两个并发过程的历史。

所以同一个 sessionId 同一时间只允许一个 Run 进入。抢占失败时不开始本次 Run、不进入正常工具执行过程、不创建本次执行轨迹，调用方收到拒绝结果。

闸怎么拒绝、怎么释放、边界到哪里，在第 4.1 节展开——那里只讲锁本身，不重复这里的流程位置。

### 2.2 取得会话：按 sessionId 恢复或新建对象

成功取得会话闸后，编排层按照 sessionId 取得会话对象。如果会话存在就恢复它，不存在就建立新的。

会话对象的身份由编排层维护。不能假定框架自带的会话对象天然拥有业务意义上的 sessionId。

因此每次 Run 开始时，编排层都必须将当前 sessionId 写入请求状态袋，供后续历史 Provider 和记忆工具使用。

**这一步必须发生在历史 Provider 读取历史之前**，否则 Provider 无法知道本次 Run 应该读取哪个会话的历史。

会话快照只恢复非历史状态，对话历史独立存储、后续由 Provider 根据 sessionId 读取。因此即使会话快照过期或损坏，只要历史表还在，就能通过新的会话对象继续使用之前的对话历史。

这里还有一条责任边界：

**本格只认当前编排层提供的 sessionId，不负责判断它属于哪个主体或租户。**

会话归属校验属于应用层。把主体身份、租户关系或业务权限塞进底座，会让状态存储层承担不属于它的业务职责。

### 2.3 绑定记忆作用域：归属由编排层确定

取得会话并写入状态袋后，绑定当前 Run 的记忆作用域。

记忆工具需要知道三件事：当前记忆应该保存在哪个 Session 名下、召回应该查哪个作用域、是否使用全局记忆。

但不能让模型通过工具参数直接指定任意 scope_id。**否则模型可以指定其他会话的 scope_id，把某个会话的记忆写入另一个会话——隐私边界就被交给了模型。**

因此作用域由编排层根据当前 Run 建立，模型只能选择「本作用域」或「全局」这样的粗粒度使用方式。

如果当前不处于任何 Run 内，又没有明确指定使用全局作用域，则应拒绝记忆操作，而不是猜测记忆归属。当前默认作用域指向 Session，因此无法确定当前作用域时返回「无法确定作用域」。

作用域在并发与嵌套下怎么保持隔离，在 §4.2 展开。

### 2.4 读取历史：Provider 根据会话读取模型上下文

Run 具备会话身份之后，模型请求前由框架历史 Provider 读取对应的对话历史。

```
当前 Run
    ↓
读取状态袋中的 sessionId
    ↓
History Provider
    ↓
读取该 sessionId 的模型历史
    ↓
交给框架组装模型请求
```

历史的读取和追加通过历史 Provider 完成，而不是通过 `AIContextProviders` 注入。这是本格与 ① 请求装配之间的重要边界。

历史 Provider 负责三件事：模型请求前读取历史、模型调用后取得本轮新增消息、把新增消息追加到对应记录。

本格提供的是历史存储、作用域键和数据生命周期。① 负责本轮输入和指令如何进入模型请求，不接管历史存储。这两条路径必须保持分离。

### 2.5 追加历史：不覆盖之前的对话

模型调用完成后，将本轮新增消息追加进对话历史。新增内容包含本轮的工具往返消息，而不是只有用户和模型最终展示的文本。

历史采用逐条追加，不使用整份快照覆盖。原因是两个不同会话的 Run 可以并行推进，覆盖式写入容易让后写入的一份状态抹掉先前写入的内容。

追加只能保证新消息不覆盖旧消息，**并不自动保证同一会话的并发写入顺序正确**。因此：

- 不同 sessionId 的 Run 可以并行追加各自的历史。
- 同一个 sessionId 的 Run 必须通过会话闸串行化。
- 如果存在绕过会话闸的同会话写入，追加本身不能保证对话顺序一致。

当前不强制每轮单独执行一次历史落库。实际运行中，一次 Run 结束时工具调用和工具结果已经进入历史，额外逐轮强制写入没有明确收益，反而多一条写入路径和一层状态管理负担。未来若要改变保存时机，应先证明现有的追加时机无法满足需求。

### 2.6 模型历史与界面消息必须分开

这里有一个最容易产生误解的地方：

**界面展示的对话，不等于模型使用的完整历史。**

界面需要展示用户和模型看得见的内容；模型需要的是完整上下文，包括工具调用、工具结果以及其他框架消息。一轮带工具调用的对话，两边形状本来就不同：

```
界面消息：            模型历史：

用户提问              用户消息
模型回答              模型工具调用请求
                      工具执行结果
                      模型最终回答
```

因此两者条数和结构不同是正常情况。不能为了让两边看起来一致就把工具往返塞进界面消息——那样界面会展示大量内部 JSON；反过来只保存界面消息，模型又会失去工具调用结果。

这两个数据源分离后，也产生了两个必须明确的现状：

- 删除会话时，目前界面那份数据被删除，但模型历史仍然存在。
- 失败 Run 可能在界面留下一条孤立提问，而模型历史没有对应的完整记录。

这两种行为目前只是锁定了系统现状，并没有定义它们是否应该成为长期产品行为。删除会话是否同步删除模型历史、失败 Run 应如何呈现在两份数据中，属于未决问题，见 §8.2。

### 2.7 Run 结束：保存快照并释放控制状态

Run 无论成功、失败、取消还是超时，都要进入统一的收尾过程。

```
Run 结束
    ↓
处理会话快照写回
    ↓
释放记忆作用域
    ↓
释放会话闸
```

会话快照只保存非历史状态，不把完整对话历史重新写入快照——历史已经通过独立 Provider 追加，不应该再用快照覆盖。

记忆作用域在 Run 结束后必须释放。会话闸也必须释放，避免后续 Run 永远无法进入。释放操作需要幂等，不能因为重复清理就影响其他 Run 后来取得的占位。

至此一次 Run 完成了状态的读取、使用、更新和释放。

### 2.8 本阶段必须成立的契约

| 契约               | 主张                     | 结论                              |
| ---------------- | ---------------------- | ------------------------------- |
| `MEM-APPEND-001` | 历史只追加、不通过整份覆盖；不强制逐轮落库 | 有判据：追加形状 + 实测一轮结束时工具往返已在历史中     |
| `MEM-SOURCE-001` | 模型历史与界面消息分别保存，允许结构不同  | 有判据：一轮工具对话中两边条数不同，工具消息只在模型历史中 |

会话闸与记忆作用域这两把锁的契约在 §4 末尾给出——它们的语义在这里只是流程位置。

这一阶段结束后，Run 已经知道该读哪份历史、该写回哪份状态、记忆算谁的。但这些东西具体存在哪、能存多久、满了怎么办，还没有回答。

## 3. 状态如何存储与存活

> 这一节讲的是「碰到的那个东西本身」：它保存什么、允不允许改、怎么被清理。链上的时机已在 §2 讲完，这里不重复。

三类跨 Run 数据的责任完全不同，不能因为都跟模型上下文有关，就把它们塞进同一张表。有四种看起来省事的合并，后果分别是：

| 看起来省事的做法       | 具体会错成什么                  |
| -------------- | ------------------------ |
| 把对话历史压进会话快照    | 快照坏一次，整个会话的历史一起丢         |
| 用会话 TTL 清理对话历史 | 会话过期，模型下一轮什么都不知道         |
| 拿历史表当长期记忆表     | 长期记忆退化成没有边界的第二份对话        |
| 拿长期记忆表做业务幂等    | 一次记忆覆盖把业务键打乱，重放判错        |

前三种在下面三节逐条说明。第四种不属于本格——业务幂等归动作闸——列在这里是因为它最容易被顺手用上。

### 3.1 会话快照：保存会话对象，不保存对话历史

会话对象负责保存一次连续对话需要恢复的非历史状态。

它可以存在于进程内缓存，也可以由落库版本跨进程重启续接。进程内缓存有条数上限，空闲过期后不再复用；落库版本通过会话记录恢复对象，但仍然受会话 TTL 约束。

**快照中不保存完整对话历史。** 原因是两者承担不同责任：快照负责恢复会话对象，历史负责恢复模型已经经历的对话。如果把历史压进快照，一次快照损坏就可能同时丢失整个会话的历史。

### 3.2 对话历史：保存模型实际使用的对话消息

对话历史独立于会话快照存储，采用逐条追加。会话对象被过期清理或损坏后，重新创建的会话仍然能够根据 sessionId 读取之前的历史。

因此：

**会话 TTL 不决定模型历史的长度。**

会话对象过期，只意味着会话对象不再复用，不意味着对话历史也应当被删除。当前历史采用只增不减的策略，**尚未建立保留期**。

### 3.3 长期记忆：结构化条目，不是另一份对话历史

对话历史回答「这个会话之前发生了什么」，长期记忆回答「哪些信息值得在不同会话中继续保留」。

长期记忆以结构化条目存在，不是把整段对话原样复制进一个记忆表。一条记忆应当有明确的内容和作用域。记忆表负责保存条目，记忆工具负责向模型提供写入、召回和遗忘的能力。

它不承担完整对话历史存储，也不负责把所有历史自动转换为记忆。因此记忆的写入和召回都由模型通过工具显式请求。

### 3.4 写入：限制内容规模与重复数据

记忆写入必须限制摘要内容长度。超过字符上限的内容直接拒绝，而不是允许模型把整段对话塞进记忆表——这不是存储优化，而是避免长期记忆退化成另一份没有边界的对话历史。

相同覆盖键写入时执行覆盖，而不是新增。覆盖只更新内容类字段：

- 记忆标识沿用原行；
- 创建时间沿用原行；
- 使用次数沿用原行；
- 记忆内容等允许更新的字段按写入要求修改。

这样，一条已经被使用多次的记忆不会因为内容更新就被误认为一条全新的记忆。反过来做——覆盖时先删后插——标识和使用次数都会丢，一条常用记忆会被重置成刚创建的样子，召回排序也跟着错。没有覆盖键时才新增记录。

覆盖键语义与 3.5 的统计回写同属一条契约 `MEM-RECALL-001`——两半都要成立，缺一半这条契约就不算兑现。

### 3.5 召回：读取成功不应依赖统计更新成功

记忆召回的主要任务是取得符合当前作用域和查询条件的条目。召回时会顺带更新使用次数，但使用次数属于辅助统计。

如果统计回写失败，不能因此让原本成功的召回失败。否则一个用于观测的附属写操作，就成了记忆系统可用性的单点。

**读取记忆成功，不应该因为统计字段更新失败而整体失败。**

### 3.6 遗忘：删除操作必须幂等

遗忘操作需要具备幂等语义：

- 第一次删除成功，条目不再参与后续召回。
- 再次删除同一条目，返回「没有」，而不是抛出异常。
- 不存在的条目不能因为重复删除而破坏整个工具调用。

遗忘的目标是让该条记忆不再存在于可查询的记忆集合中。

### 3.7 记忆工具只返回结构化结果

记忆工具返回结构化条目和工具结果，不直接生成系统 Prompt，也不决定注入多少条记忆。

```
模型调用 remember
    ↓
记忆持久化
    ↓
返回：已记住

模型调用 recall
    ↓
查询当前作用域记忆
    ↓
返回：无命中 / 候选摘要
```

本格负责：条目存储、写入和覆盖、召回、使用次数更新、显式遗忘、保留期清理。

本格不负责：生成 Prompt 文本、决定候选记忆注入多少条、把长期记忆自动附加到每次模型请求。这些属于 ① 请求装配。这样可以避免记忆持久化层和请求装配层各自建一套注入机制。

候选上限与最终注入条数是两个数量，分工见 §6.3。

### 3.8 本阶段必须成立的契约

| 契约                  | 主张                                      | 结论                    |
| ------------------- | --------------------------------------- | --------------------- |
| `MEM-RECALL-001`    | 覆盖键更新内容时保留标识、创建时间和使用次数；无覆盖键时新增；统计回写失败不阻断召回 | 有判据：覆盖键、无键新增和统计回写分别验证 |

存储形状、读写语义到这里就定完了。剩下两类问题没法在正常情况下回答：**并发时这几把锁怎么守**，以及**每一步失败时会变成什么样**。

## 4. 并发与隔离

> 会话闸和记忆作用域在两处出现：§2 讲它们在流程里的位置，这里讲它们本身的语义。并发相关的失败几乎都来自把「位置」当成「保证」——位置对了，锁没守住，照样出错。

### 4.1 会话闸：拒绝不排队

**会话闸采用拒绝语义，不采用排队语义。**

如果会话已经被占用，第二个 Run 立即收到拒绝码，不等待前一个释放。理由是排队会引入不可预测的等待：用户提交的第二条消息可能在很久之后才被处理，上下文已经发生变化。

**拒绝比延迟执行更诚实。**

一次性和流式入口必须保持相同的拒绝语义。流式入口通过事件返回拒绝，而不是抛出异常——否则界面会把一次正常的并发冲突读成服务故障。

会话闸采用原子占位，不设置等待队列。

释放必须幂等，尤其要避免这个顺序：

```
Run A 占用会话闸
    ↓
Run A 释放
    ↓
Run B 取得新的占位
    ↓
Run A 的迟到重复释放到达
    ↓
错误地删除 Run B 的占位
```

因此释放不能仅凭 sessionId 删除当前占位，还必须保证只释放自己取得的那一次占位。

### 4.2 记忆作用域：嵌套和并发必须相互隔离

记忆作用域与会话闸不同：会话闸控制谁能进入会话，作用域控制当前 Run 的记忆操作归属于谁。

当前实现用异步上下文承载作用域，为的是让并发 Run 各自拥有独立的执行上下文：

```
Run A                         Run B

绑定 Scope A                  绑定 Scope B
    ↓                            ↓
记忆写入 A                    记忆写入 B
    ↓                            ↓
释放 Scope A                  释放 Scope B
```

如果改用共享的普通字段，后开始的 Run 会覆盖先开始的 Run 设置的作用域——A 会话的偏好就可能被写到 B 名下。

异步上下文还必须正确处理嵌套：

- 进入内层作用域时保存外层；
- 内层结束时恢复外层，而不是直接清空整个上下文；
- 重复释放不能破坏外层作用域；
- 并发 Run 之间不能串用作用域。

在没有当前 Run、也没有明确全局请求时，宁可拒绝记忆操作，也不能猜测归属。

### 4.3 单进程边界

当前会话闸只保证单进程范围内的并发安全。

如果未来采用多实例部署，不能假定各实例内存中的占位能够互相协调。必须引入数据库租约与 fencing 机制，才能保护跨实例的会话所有权。

这条边界同时是 §8.1 的第一条假设和 §8.2 的第 4 条未决——现在靠它，将来要不要换，是两件事。

### 4.4 这一段必须成立的契约

| 契约              | 主张                                | 结论                                      |
| --------------- | --------------------------------- | --------------------------------------- |
| `MEM-GATE-001`  | 同一会话一次只允许一个 Run，不排队；释放后可以再次进入    | 有判据：占用、释放、重复释放、不同会话并行、两个入口均返回拒绝码        |
| `MEM-SCOPE-001` | 记忆作用域按当前 Run 绑定，模型不能指定任意 scope_id | 有判据：嵌套恢复、重复释放、并发不串；模型侧指定 id 无专门断言，见 §7.2 |

## 5. 失败与恢复

> 本节按失败类型组织，不按子系统重讲一遍。同一个边界往往在多处同时失效：单进程假设既限制会话闸，也限制跨实例部署。按子系统拆开要讲四遍，按失败类型看才能看清这道保护挡住了什么。

本格的失败不一定意味着 Run 必须失败。很多情况下系统可以降级继续，只是缺少部分历史状态或记忆能力。

### 5.1 会话快照损坏：允许重建，不能连带丢失历史

快照可能因为序列化错误或数据损坏而无法恢复。这种情况不能让会话永久卡死。

```
读取会话快照
    ↓
反序列化
    │
    ├── 成功
    │     ↓
    │   恢复会话
    │
    └── 失败
          ↓
       删除损坏记录
          ↓
       记录告警
          ↓
       建立新会话
          ↓
       独立读取原有历史
```

由于对话历史不在快照中，重建会话对象不应该同时丢失历史——损坏的可以重建，历史继续从独立存储读。

这里还有一条重要的异常边界：

**取消不能被快照降级分支误吞。**

如果异常实际是取消操作，就应该原样向上传播，而不是把取消误认为快照损坏、重新建一个会话。

这条契约是 `MEM-SNAPSHOT-001`，当前只有半验：内存臂真跑，落库臂只有源码结构断言（见 §7.2）。

### 5.2 过期数据：读取过滤不等于真正清理

会话数据和长期记忆都有各自的保留策略。过期数据不能只依赖查询时过滤——记忆查询已经排除过期条目，并不能证明过期记录已经从数据库删除，它们可能仍然长期占用存储。

因此要区分两件事：

**读取路径过滤**：查询时不返回已经过期的条目。
**后台清理**：实际删除已经过期的数据行。

验证清理是否成功，必须直接检查仓储或数据库状态，而不是确认召回结果里没有过期记忆。

清理任务本身也要保证持续运行：一轮清理异常不能导致整个后台循环退出，应记录警告并允许后续周期继续执行。

这条契约是 `MEM-RETENTION-001`。读路径过滤与后台清理各自有判据，不能互相替代——确认召回结果里没有过期记忆，不能证明那些行已经被删掉。

### 5.3 落库读写失败：不能把未验证的恢复行为写成保证

内存版和落库版是两种不同的存储实现。不能因为内存版行为符合预期，就推断落库版在数据库故障时具有相同的降级能力。

目前落库会话存储的部分读写失败路径没有完整验收。因此不能宣称：

- 数据库不可用时一定可以自动降级；
- 所有写回失败都不会影响 Run；
- 取消、超时和普通读写异常都已经被正确区分。

在没有验证之前，这些是实现缺口，不是已经具备的恢复能力。

### 5.4 长期记忆清理与会话清理不能互相代替

两类数据的生命周期不同，清理责任也不同。

会话 TTL 清理会话对象及会话记录；记忆保留期清理长期记忆条目；对话历史目前没有建立保留期，不应被前两种清理任务顺带删掉。

尤其不能因为用户删了一条界面会话，就默认所有模型历史和长期记忆都应同时删除。这涉及不同数据源的删除语义，需要由明确的产品和架构决策决定。

## 6. 配置与架构约束

> 具体取值不在本文维护，由 `memory.toml` 的事实声明与仓库配置作为权威。这里只留与架构直接相关的判断。

### 6.1 默认值必须往「少做」倒

**长期记忆默认关闭。**

关闭意味着不提供记忆写入、不提供记忆召回、相关工具不进入模型工具目录。但关闭不等于删除已有数据——**这是能力开关，不是数据销毁开关**。

之所以要求默认关，是因为如果默认开放，模型可能在还没建立记忆策略时就频繁写入整段对话，产生大量噪音条目，进一步污染后续召回。只有明确启用后，才开放相关工具。

这条判断和工具执行的默认值方向是同一条：配置缺失、装配遗漏时，系统应该少做一件事，而不是多做一件。

这条契约是 `MEM-DEFAULT-001`，当前是预期红：默认值与规格相反，红是正确信号，不能改测试凑绿。

### 6.2 三个数值各管什么

| 数值     | 所属对象      | 责任         |
| ------ | --------- | ---------- |
| 会话 TTL | 会话快照与会话记录 | 本格定义       |
| 记忆保留期  | 长期记忆条目    | 本格定义       |
| 召回候选上限 | 长期记忆查询    | 本格定义，① 消费结果 |
| 历史长度   | 对话历史      | 当前没有统一数字上限 |

三种数值不能互相推算：

- 会话过期不代表历史过期。
- 记忆过期不代表会话过期。
- 候选上限也不代表最终请求注入数量。

每个数值只负责自己的数据和阶段。对话历史当前没有独立长度配置，也不要为了形式上统一就人为造一个没有行为语义的上限。

### 6.3 候选上限不等于注入数量

- **召回候选上限**：记忆库最多取多少条候选，由本格定义，限制存储查询和候选集规模。
- **请求注入数量**：最终有多少条记忆进入本轮请求，由 ① 决定，属于请求装配和上下文预算。

不能把候选上限直接当成注入条数，也不能让记忆持久化层自行生成 Prompt 并决定模型看到多少条。

## 7. 契约验收：如何证明状态与记忆机制成立

本节不是测试清单，而是把前面各节的主张转成可核对的东西。

验收遵循五条：每项判定契约都要有正例和负控；负控要证明错误行为会被发现，而不是只证明某次调用没成功；能由脚本判断的事实不交给模型评价；以实际运行结果为依据，不以测试文件存在为依据；不把局部通过扩大成整条成立。

契约的稳定身份、实现定位、用例名、预设变异点和证据强度都在 `docs/kb/contracts/memory.toml`。本节只留结论：**哪几条有独立判据，哪几条没有。**

### 7.1 八条契约与当前证据

| 契约                  | 主张                                        | 结论                         |
| ------------------- | ----------------------------------------- | -------------------------- |
| `MEM-APPEND-001`    | 历史只追加、不通过整份覆盖；不强制逐轮落库                    | 有判据：追加形状 + 实测一轮结束工具往返已在历史中 |
| `MEM-SOURCE-001`    | 模型历史与界面消息分别保存，允许结构不同                     | 有判据：条数不同，工具消息只在模型历史中       |
| `MEM-GATE-001`      | 同一会话一次只允许一个 Run，不排队；释放后可再次进入             | 有判据：五个场景 + 两个入口均回拒绝码       |
| `MEM-SCOPE-001`     | 作用域按 Run 绑定，模型不能指定任意 scope_id             | 有判据：嵌套恢复、重复释放、并发不串用        |
| `MEM-SNAPSHOT-001`  | 快照损坏可降级重建，取消不能被吞                           | **半验**：内存臂通过，落库臂只有源码结构断言    |
| `MEM-DEFAULT-001`   | 长期记忆默认关闭，关闭时停止写入和召回，不删除数据                  | **预期红**：当前默认值与规格相反          |
| `MEM-RECALL-001`    | 覆盖键保留标识与使用次数；无键新增；统计回写失败不阻断召回              | 有判据：三种情况分别验证               |
| `MEM-RETENTION-001` | 过期数据必须被真正删除，而不只是查询过滤                       | 有判据：直接查仓储，验证未过期与过期处理不同     |

除契约外还必须保持的架构约束：记忆工具只返回结构化结果；摘要超字符上限必须拒绝；候选上限由本格管理、注入数量由 ① 管理；显式遗忘重复执行不应造成异常。具体用例和负控定位由契约层维护。

### 7.2 四类不能读成「已证明」的结论

**一、落库臂没有真跑。** 所谓两种存储实现的行为对照，实际是两个内存版独立实例的逐字段比较。落库版只有源码结构断言，没有完整真实运行，不能说两种实现通过了同等强度的验证。

**二、会话隔离没有负控。** 目前没有证明「一旦隔离被破坏，测试一定会红」。测试数据分别运行，不能当作完整的隔离安全证明。

**三、默认关闭时的工具注册没有独立测试。** 现在只有默认值预期红，没有独立验证工具不会进入模型目录。不能把默认值测试等同于工具目录准入已验证。

**四、进程重启后的续接没有验收。** 落库存储的结构存在，不等于证明杀进程、重启后能恢复完整会话和历史。

`MEM-DEFAULT-001` 的红是正确信号：预期规格是默认关闭，当前默认值与规格相反。这个红表示实现尚未满足架构要求，**不能通过修改测试把它变绿**。

### 7.3 本部件算通过的标准

不能用「模型能记住上一轮」判断完成。至少要能回答：

1. 五类状态没有互相借用生命周期——没有拿 TTL 清历史、拿历史充当记忆；
2. 同一会话的第二个 Run 被拒绝，而不是排队或并行；
3. 记忆作用域由编排层建立，模型无法指定任意 scope_id；
4. 新增消息逐条追加，含工具往返；界面与模型两份数据形状不同是正常结果；
5. 快照损坏能重建，且取消不被误吞；
6. 过期数据被真正删除，而不只是查询过滤；
7. 未验证的行为明确登记，不因为别的契约通过就宣称整个部件完成。

最终以 `scripts/ci.sh` 和 `dotnet test` 的实际执行结果为准，不以测试数量或测试名称为准。

## 8. 安全假设与未决问题

### 8.1 当前机制依赖的安全假设

**会话闸只保证单进程范围。** 当前并发保护依赖本进程内的原子占位，多实例部署后不能继续假设它天然有效。

**会话身份由编排层提供。** 本格依赖可信的 sessionId，但不负责验证它属于哪个用户或租户，这个判断归应用层。

**记忆作用域不能由模型任意指定。** 必须由当前 Run 建立可信作用域，不能把隐私边界交给模型参数。

**会话快照和对话历史独立存在。** 快照损坏可以重建，但历史能否恢复还依赖其独立存储是否正常。

**长期记忆与对话历史使用不同的生命周期。** 不能把会话存活期和记忆保留期混成一个清理策略。

### 8.2 未决问题

1. **是否切换到框架的会话存储契约？**
   如果切换，需要移除现有自建工厂接口，并按新契约重新编写会话测试。当前落库存储还没有完整真实验证，先补跑还是直接切换，尚未决定。

2. **进程重启后如何验证会话续接？**
   当前没有完整的杀进程、重启、恢复会话、继续历史的验收。

3. **对话历史是否建立保留期？**
   当前只追加。未来若决定删除历史，必须同时确定删除后模型下一轮应该看到什么，不能只设计数据库清理。

4. **多实例如何共享会话和长期记忆？**
   当前会话闸仅支持单进程。多实例需要数据库租约和 fencing，尚未实现。

5. **失败 Run 和删除会话的两份数据如何处理？**
   界面消息与模型历史存在不同步的现状，但没有确定应该采用什么产品行为。

6. **历史压缩之后，重复调用检测还能否正常工作？**
   ① 在真实工具执行管线装配下重新验证后，需要补压缩场景的负控，确认消息压缩不会破坏 ④ 的重复调用判定。

7. **落库臂的读写失败应该如何收口？**
   当前缺少完整的失败恢复验收，需要明确数据库读取、写入和取消分别应该如何处理。

## 9. 与其他五个部件的关系

本格管理跨 Run 状态，但不独立决定整个模型上下文和执行过程。

| 部件           | 负责的问题            | 与本格的关系                      |
| ------------ | ---------------- | --------------------------- |
| ① 请求装配       | 模型每轮看到什么         | 本格提供历史和记忆来源，① 决定如何裁剪、压缩和注入  |
| ② 框架层（MEA）   | 如何从一轮走到下一轮       | 本格借助其 Run 前后插入点完成状态读取、追加和收尾 |
| ③ 终止与预算      | 允许运行多少轮、多久、重复多少次 | 本格不拥有预算规则                   |
| ④ 工具执行       | 一轮里的工具如何执行       | 工具往返产生的消息由本格追加进模型历史         |
| ⑤ 状态与记忆（本部件） | 跨 Run 保留什么       | 管理会话、历史、长期记忆及其运行状态          |
| ⑥ 轨迹与观测      | 运行过程留下什么         | 管理账本与运行证据，本格的数据表不替代账本       |

三个边界尤其重要：

**① 与 ⑤：历史和记忆的存储不等于模型注入。**
⑤ 提供历史和记忆数据，① 决定本轮真正用什么、怎么进请求。召回多少条候选与最终注入多少条，是两个不同的决策。

**② 与 ⑤：框架拥有 Run 生命周期，⑤ 利用插入点维护状态。**
⑤ 不重复实现 Run 编排，也不拥有模型循环。

**⑥ 与 ⑤：账本和会话状态是两套数据。**
账本记录运行发生过什么，会话和记忆保存后续运行需要什么。不能用账本代替会话存储，也不能用会话快照代替运行轨迹。

### 9.1 共用数值的责任归属

| 数值       | 定义者        | 使用者        |
| -------- | ---------- | ---------- |
| 会话 TTL   | ⑤          | 会话存储与清理机制  |
| 长期记忆保留期  | ⑤          | 记忆持久化与清理机制 |
| 记忆召回候选上限 | ⑤          | 记忆查询       |
| 最终记忆注入数量 | ①          | 请求装配       |
| 对话历史长度   | 当前没有统一数值上限 | ① 与框架历史机制  |

---

**本格最终要保证的不是模型看起来记得很多，而是跨越 Run 之后仍然能够正确恢复需要的信息，同时不让不同会话、不同主体和不同执行过程互相污染。**

会话负责连续性，对话历史负责还原上下文，长期记忆负责跨会话复用；会话闸保证并发边界，记忆作用域保证归属边界。

**保住该保留的，隔离不该混合的，释放已经结束的状态。**

Runtime.Session 的核心责任是一句话：**模型可以提出「记住这个」，但什么值得跨 Run 留下、存在哪、活多久、什么时候必须放掉，全部由模型之外的机制决定。**
