# 工具执行（Runtime.Tools + Tools.Builtin + Tools.Mcp · 六部件之④）

- **适用侧**：底座 ｜ **寿命**：现状（就近维护） ｜ **最后校准**：2026-11-22

> **类型**：Architecture（解释型）。本文解释"一次工具调用从模型意图到结果之间发生什么、谁拥有决策权、失败怎么收口"，不是事实源、不是参考手册。
> **范围**：工具执行部件的边界、控制流、依赖契约、失败语义、配置口径、已验/未验。
> **非范围**：业务权限与幂等（动作闸，见 `ActionGateway`）、工具实现本身（各域 / Builtin / MCP server）、账本落库与回放界面（应用层）。
> 状态位与路径由 `DocsHygieneTests` 检查；行为判据在测试里（真实文件见 §6）。实现声明的定位与证据状态见 [证据追溯索引](../engineering/证据追溯索引.md)。

一句话：**把模型生成的工具调用，在真正执行之前过一遍判定，执行之后留下能回放的账。**
拿掉它，模型说「我查过了」就真的查了——谁看的、参数是什么、结果有没有截断、是不是被拒过，全无痕迹。

## 一、职责与边界

判据只有一条：**这一步是不是「一次工具调用从模型意图到执行结果」之间发生的事？**

一行 = 一个归属判断。中间列是代码中落地的位置（路径相对 `src/`；`P=` 指 `Core/Runtime/AgentWorkbench.Runtime.Tools/`）。**列路径是为定位，不是行号流水账**；行号会随代码漂，需用时按方法名现查。

| 事 | 落在哪（类 / 方法 · 文件） | 归属 |
|---|---|---|
| 一次调用的参数/结果/异常/是否截断 | `ToolCallTrace`，由 `ToolExecutionRun.BeginCall` / `CompleteCall` 写 · `P/ToolExecutionPipeline.cs` | **本格** |
| 参数畸形时的可归因拒绝码 | `ToolExecutionPipeline.ValidateArguments` 现算 · 同文件 | **本格** |
| 未知工具名「曾被调用过」这一笔 | `ToolCallGuardChatClient.Report` 观察层 · `P/ToolCallGuardChatClient.cs` | **本格** |

| 「该不该让这个主体做这件事」的业务判定 | 动作域 PDP + 规则 · `Core/Ports` 之外 | 边界外（动作闸） |

### 1.1 五维边界（不只按调用顺序定义）

正常调用顺序见 §2，但顺序**不等于**边界。按控制权/决策权/执行责任/状态所有权/外部接口五维拆开：

| 维度 | 本格的答案 |
|---|---|
| **控制权** | 循环由框架的 `FunctionInvokingChatClient` 控制；本格只在 `FunctionInvoker` 回调里插入判定，不拥有循环。 |
| **决策权** | 本格只判"这一调用能不能发出"（守卫/校验/审批）；**不判业务对错**（那是 PDP+规则），**不判结果够不够**（那是领域 `IToolResultVeto`）。 |
| **执行责任** | 副作用由工具实现产生（`context.Function.InvokeAsync`）；本格不实现工具。走动作闸的工具，副作用由 `ActionRunService` 在工具内部产生（见 §2.3）。 |
| **状态所有权** | 轨迹 `ToolCallTrace` / `UnknownCalls` / `ToolFailures` / `Stop` 由本格的 `ToolExecutionRun` 持有；落库与回放归应用层。 |
| **外部接口** | 对模型：`FunctionInvoker` 回调 + 回填文本；对领域：`IToolResultVeto`、`IAgentRunGuard`、`IToolApprover` 三个端口；对配置：`IOptions` / `IOptionsMonitor`。参数对底座是不透明数据。 |

一个容易混的点：**白名单和审批是两样东西，配置也是两节。** 白名单答「能不能用」（能力边界），审批答「要不要先问人」（信任边界）；一个工具可以「允许用、但每次问」。揉成一个接口，这种状态就表达不出来。

### 1.2 依赖契约（不是只列名字）

| 依赖 | 依赖什么能力 | 数据形状 | 失败时谁能继续 | 失败归属 |
|---|---|---|---|---|
| MEA `FunctionInvokingChatClient` | 工具环本体、结果回填、批次 | `FunctionInvocationContext`（`Arguments` 为 `AIFunctionArguments`） | 不能——本格的 `FunctionInvoker` 就是它调用的 | 框架 |
| ③ `IAgentRunGuard` | 判重复调用 / token 预算 | `ToolCallObservation`（迭代号/名字/参数） | 能——为 `null` 时环内不做提前终止 | ③ 给阈值，本格给执行点 |
| `IToolApprover` | `Ask` 级问人 | `ToolApprovalRequest(toolName, arguments)` → bool | 能——为 `null` 时所有 `Ask` 按拒绝（fail-closed） | **实现事实**：`src/` 下无实现、无 DI 注册，生产 `Approver=null`；唯一实现是测试桩。当前生产若配 `Ask` 会一律拒绝，不会真问人 |
| `IToolResultVeto` | 调用后判结果能不能当依据 | `(string toolName, string? result)` → `AgentRunStop?` | 能——为 `null` 时不否决 | 领域判定 |
| MCP 目录 / `ToolCatalog` | 汇总各 provider 的工具 | `AIFunction` 列表 | 能——空目录时模型无工具可调 | 提供方 |
| 配置 `IOptions<T>` / `IOptionsMonitor<T>` | 取值 | 见 §4 | 能——缺节时取代码默认 | 配置 |

## 二、一次调用走哪几步

模型在工具环里请求一个工具，走的是 `FunctionInvoker`——`ToolExecutionPipeline.Create` 里设的那个回调（`P/ToolExecutionPipeline.cs`，方法 `Create`）。

**这是一条线性路径，没有"Gateway 分支"。** 所有工具——包括要过四道闸的 `propose_action`——都依次经过下面六步。这一条是本次改造纠正的最重要事实：旧版文档写的 `gateway.Handles / gateway.ExecuteAsync` 分支在真实代码中零命中（见 §6 与证据索引 `IMPL-T03`）。

```
步骤 / 方法（在 P/ToolExecutionPipeline.cs，行号会漂，按方法名找）  做什么
 1. run.BeginCall(...)                    轨迹先记一笔（迭代号/名字/参数）
 2. limits.Guard?.InspectToolCall(...)    重复调用 / token 预算（阈值来自 ③）
        命中 → CompleteCall + run.StopAt + Terminate=true，不再回问模型
 3. ValidateArguments(function, args)     按工具自己的 schema 挡畸形参数
        命中 → ValidationPayload 回填，工具不执行（error=argument_validation_failed）
 4. InspectApprovalAsync(...)             Auto 放行 / Deny 拒 / Ask 问人
        拒绝 → DenialPayload 回填给模型，工具绝不执行
 5. context.Function.InvokeAsync(...)     真正执行
        → run.CompleteCall（轨迹存截断版，事件带完整版）
        → limits.Veto?.Inspect（调用后问「这结果能不能当依据」）
        → return Truncate(text) 给模型
 6. catch (Exception ex)                  记一笔（MarkToolFailure + CompleteCall）后原样抛回 MEA
```

### 2.1 三处顺序为什么不能挪

- **守卫在审批前**：守卫判「整轮要不要停」，是更上层的止损；已决定停的调用不必再打扰审批人。
- **参数校验在审批前**：畸形参数不必去打扰审批者；挡下后把可归因拒绝码作为结果回填，让模型自己改参数，与「被拒」「工具失败」在轨迹里分得开。注意这里用的是**工具自己的 `AIFunction.JsonSchema`**，只判 `required` 与 `type`；enum/pattern/嵌套仍交给 MEA 的参数绑定，绑定失败按工具异常归类。
- **落轨迹在问否决前**：拒答时那份命中仍是证据，事后要能查「它看到了什么才拒的」。

### 2.2 否决（`ToolResultVeto`）的准确语义

调用后 `limits.Veto?.Inspect(toolName, text)`：

- 输入：`toolName` + **未截断的完整结果** `text`（与轨迹里的截断版不同）。
- 输出：`AgentRunStop?`。`null` = 不否决；非 `null` = 必须终止。
- 否决后果：`run.StopAt(veto)` + `context.Terminate = true`，**结果仍回填给模型**，本轮不再回问；**不改轨迹内容、不抛异常**。拒绝原因在 `run.Stop` 里，不在返回值里。
- 领域实现：`McpKnowledgeVeto` 只匹配 `mcp__rag__search_knowledge`，`SufficiencyGate` 判不足时返回 `AgentRunStop(Refused, KnowledgeInsufficient, ...)`。
- **未验证**：否决分支暂无独立负控（见 [证据追溯索引](../engineering/证据追溯索引.md) 的 `UNKNOWN-VETO`）。

### 2.3 Gateway 路径在哪里（纠正旧文档）

**动作闸不在这条管线的分支里，而在 `propose_action` 这个工具的实现内部。**

```
模型请求 propose_action
  → 本格六步（它也是一个 AIFunction，走同样的校验/审批/调用）
  → ProposeActionTool 内部调 ActionRunService.SubmitDeferredAsync
  → ActionGateway 四道闸（Schema → Permission → BusinessRule → Audit）
  → 审批挂起 / 幂等领取 / 执行体 / 审计
```

含义：

- 走闸工具的**参数**由动作自己的 `ActionSpec.Schema` 判（在 `ActionGateway` 内），不是本格的 `ValidateArguments`——但本格的 `ValidateArguments` 仍先判 `propose_action` 这个工具本身的形状。两者是**嵌套关系**，不是二选一。
- 本格的审批（`ToolApprovalPolicy`）与动作闸的审批（`ActionSpec.RequiresApproval`）是两回事。前者答"这个工具调用要不要问人"，后者答"这个业务动作要不要问人"。
- **实现事实（2026-11-22 核对）**：当前生产链路里本格审批**不会问人**——`src/` 下没有 `IToolApprover` 的实现或 DI 注册（唯一实现是测试桩 `tests/AgentWorkbench.TestKit/PipelineDriver.cs` 的 `StubApprover`），`AgentHub` 构造 `HarnessRunRequest` 时也未传 `Approver`，故 `limits.Approver = null`，`InspectApprovalAsync` 对任何 `Ask` 直接返回 `Unavailable`（fail-closed 拒绝）。当前配置 `Harness:Approval.Default=Auto`、Overrides 空，因此实际不会走到 `Ask`。**真正问人的是动作闸**（`ActionRunService` 按 `ActionSpec.RequiresApproval` 挂起）。
- 因此"会不会问两次"在**当前代码里不是待定问题，而是本格那一层根本没启用**。若将来接入 `IToolApprover` 实现，两者的关系才需要重新裁决——那属于 Open Question，见 §七。

## 三、为什么这么定（设计理由，测试答不了的取舍）

**循环本体用框架的，本格只装。**
`FunctionInvokingChatClient` 已实现「识别工具意图 → 执行 → 回填 → 再问」，`MaximumIterationsPerRequest` 等四个选项全部显式赋值、不靠隐式默认（`LoopAssembly` 给值）。这是"不造轮子"判据的结论：框架有等价物就用它的。

**目录层做延迟解析，不在构造期取 provider。**
`IAgentToolProvider.GetTools()` 每次调用现去 DI 取；provider 内部可能依赖知识库或文档仓储，构造期解析会形成 DI 环。过滤发生在**汇总之后**，同名按 Ordinal 去重。

**MCP 准入默认是关的。**
能力画像从 server 标注读，公式为：
`ExposeToModel && DestructiveHint != true && (ReadOnlyHint == true || TrustedReadOnly 点名)`
即 `DestructiveHint=true` 永不进目录（信任名单也翻不了）；`ReadOnlyHint=true` 可进；什么都没声明按「会写」处理，只有 `TrustedReadOnly` 逐个点名才进。`AllowTools` 留空 = 一个都不放行。
**实现事实**：见 `Core/Tools/AgentWorkbench.Tools.Mcp/McpToolRegistry.cs` 的 `McpToolCapability.From`（**不在 `P/` 前缀下**，`P/` 只指 Runtime.Tools）；测试 `TEST-S04_08`–`11` 用真实策略覆盖。
**不能当安全证明**：`ReadOnlyHint` / `DestructiveHint` 是 **server 自报的标注**（MCP SDK 的 `Annotations`），不是我方验证过的行为。一个标 `ReadOnly=true` 的工具实际写了东西，这套准入不会发现。它防的是"误把写工具挂给模型"，不防"恶意或被攻陷的 server"（见 §5 Open Questions）。

**两轴分开（沙箱轴与审批轴）。**
白名单答"能不能用"（能力边界），审批答"要不要先问人"（信任边界）。本格把它落成两个配置节、两个策略类。合并的代价是丢掉「允许但每次问」这个状态。

## 四、配置：默认值与启动实际值

**区分两件事**：代码里的 default 值，和本仓 `appsettings.json` 实际配的值。二者不同时，以启动实际值为准。

| 节 | 键 | 代码默认 | 本仓启动实际值 | 绑定方式 |
|---|---|---|---|---|
| `Harness:ToolExecution` | `MaxResultChars` | 400 | 未配节 → 取 400 | `IOptions<T>`（**不热重载**） |
| `Harness:ToolExecution` | `ApprovalTimeoutSeconds` | 120 | 未配节 → 取 120；`<=0` 表示不设上限（仅测试用） | `IOptions<T>` |
| `Harness:Tools` | `Whitelist` | 6 项：`get_current_time` / `calculator` / `mcp__rag__*` / `list_documents` / `remember` / `recall` | **7 项，多 `propose_action`** | `IOptionsMonitor<T>`（热重载） |
| `Harness:Approval` | `Default` | `Auto` | `Auto` | `IOptionsMonitor<T>` |
| `Harness:Approval` | `Overrides` | 空 | 空 | `IOptionsMonitor<T>` |
| `Mcp:Servers[]` | `AllowTools` | 空（= 一个都不放行） | rag: `search_knowledge`；erpnext: 3 项 | `IOptionsMonitor<T>` |
| `Mcp:Servers[]` | `ExposeToModel` | `true` | rag 未配 → `true`；erpnext 显式 `false` | `IOptionsMonitor<T>` |
| `Mcp:Servers[]` | `TrustedReadOnly` | 空 | rag: `search_knowledge`；erpnext: `frappe_get_doc` | `IOptionsMonitor<T>` |

容易误读的三点：

1. **白名单为空 = 全关，不是全开。** 代码默认 6 项、启动实际 7 项（多 `propose_action`）；把它删空等于关掉全部工具。默认必须取"没想清楚就不能全给"的值。要查当前值跑配置命令，别抄本文——这是会漂的事实。
2. `ToolPolicy` 只支持精确名和尾部 `*`，不支持中间通配、正则、否定式。白名单是安全边界，必须能一眼读完并逐个签字。
3. 模型说「我没有这个能力」时，先看启动日志 `MCP server X 连上：放行 n/m` 那一行——`AllowTools` 拼错会静默少工具；再看能力画像明细，确认没被 `destructive=true` 挡掉。

**依赖版本（实现事实，2026-11-22 核对）**：MEA `Microsoft.Extensions.AI 10.10.0`；MAF `Microsoft.Agents.AI 1.23.0`（在本格的上游部件，不在本格 csproj）；MCP `ModelContextProtocol 2.4.0`。版本来自各 `*.csproj`，无集中 Version 变量。本节只陈述引用版本，**不声称框架行为符合本文描述**——框架能力以官方与实测为准。

## 五、失败、异常与恢复语义

| 失败形态 | 记在哪 | 回填给模型什么 | 谁能继续 | 归类 |
|---|---|---|---|---|
| 参数畸形 | `ToolCallTrace.Error = argument_validation_failed` | `ValidationPayload`（含 detail） | 模型可改参数重试 | 本格 |
| 审批拒绝 | `ToolCallTrace.Error = <denial code>` | `DenialPayload` | 模型换路或收口 | 本格；超时/通道故障归 `Unavailable` |
| 未知工具名 | `UnknownCalls`（**不在** `Traces` 里） | MEA 自己回填"工具找不到"，本格不改语义 | 视 `TerminateOnUnknownCalls`，本仓显式 `false` | 观察层 |
| 工具抛异常 | `ToolFailures` + `ToolCallTrace.Error` | 原样抛回 MEA，由它决定回填还是传播 | 框架 | 工具实现 |
| 守卫/否决判停 | `run.Stop`（`AgentRunStop`） | 结果仍回填，`Terminate=true` | 收口，不再回问 | ③ / 领域 |
| 超时（调用） | 见 `McpToolInvoker` 超时分类 | `Unavailable → Unknown → 只查证不重放` | 动作闸查证分支 | 底座（第 4 句） |

**两本账不要合并**：模型请求了不存在的名字 → `UnknownCalls`（观察层补记，走不到 `FunctionInvoker`）；工具执行抛异常 → `ToolFailures` + `ToolCallTrace.Error`。两者都叫「失败」，读者不同。

**截断、轨迹、回放是三件事，不要混为一谈**：

- 截断 = 按 `MaxResultChars` 取前 N 字，并置 `Truncated` 标志；
- 轨迹 = `Traces` 里存**截断版**（省账本），`ToolCompleted` 事件带**完整版**（流式出口的来源面板要用）；回填给模型的也是截断版（按同一上界）；
- 回放 = 应用层拿轨迹重建，本格只产出，不落库、不渲染界面。

## 六、怎么算验收通过

判定型用例必须**正例能绿、负控能红**；能脚本判定的禁止用 AI 判。验收以 `dotnet test` 实测为准。

**测试文件的真实位置（本次核对修正）**：

| 主张 | 真实测试文件 | 覆盖 |
|---|---|---|
| 目录/白名单（S04 各格） | `tests/AgentWorkbench.ApplicationTests/Flow/S04ContractTests.cs` | 15 个方法：`S04_01`–`S04_15` |
| 上界/畸形参数/工具异常 | `tests/AgentWorkbench.CoreTests/Runtime/Tools/ToolCallGapTests.cs` | 3 条 |
| 超时归类/只查证不重放 | `tests/AgentWorkbench.ApplicationTests/ActionGateway/TimeoutClassificationTests.cs`、`TimeoutReconciliationTests.cs`、`ToolCallTimeoutTests.cs` | 20 条 + 变异自证 |

**已验的**：

- 白名单精确匹配、大小写敏感、空表全关、尾部 `*` 只按前缀（`S04_08`–`11` 用真实策略）
- 同名去重、多提供方汇总后过滤（**目录本身**的判据，`S04_12`–`13` 用 MockPolicy）
- 清单外工具：不执行、不抛异常、模型能收到回填、整轮结束留痕、流式分片只记一笔（`S04_03,05–07`）
- 工具调用被执行、参数与结果完整进轨迹、结果回填给模型（`S04_02,14,15`）
- 内容上界、畸形参数调用前挡下、工具异常转结果回填不炸整轮（`ToolCallGapTests` 三条）

**证据强度打折的地方（不要当完整证明）**：

- `S04_08`–`11` 用 **RealPolicy**（精确名 / 尾部 `*` / 空表 / 接进目录）；`S04_12`–`13` 用 **MockPolicy**，只验目录去重与汇总，不是白名单证据。`S04_01` 经 `CreateCatalog→MockPolicy`；`02`–`07` 的工具直接进 `ChatOptions.Tools`，**根本没过策略**——读这几条时别当成白名单证据。真实 `ToolPolicy.IsAllowed` 写错，01–07 与 12–13 照样全绿。
- 超时归类与只查证不重放：代码层判据绿（见证据索引 `TEST-Q4`），但**真站点外部闭环未验**（`UNKNOWN-4`），不列入"已验的外部行为"。

## B. 与其它五份的边界

① 讲「模型每轮看到什么」（含工具清单挂请求）；② 讲「怎么从一轮走到下一轮」；③ 讲「允许走几轮、什么时候停」（本格提供执行点）；⑤ 讲「跨轮保住什么」；⑥ 讲「走过之后留下什么」（本格产出 `ToolCallTrace`，⑥ 把它写进账本）。

`MaxIterations` 是 ② 与 ③ 共用的数字：② 交给本格，本格经 `ToolExecutionLimits` 落到 FICC，③ 定义它的含义。
