# 工具执行（Runtime.Tools + Tools.Builtin + Tools.Mcp · 六部件之④）

- **适用侧**：底座 ｜ **寿命**：现状（就近维护） ｜ **最后校准**：2026-11-18

一句话：**把模型生成的工具调用，在真正执行之前过一遍判定，执行之后留下能回放的账。**
拿掉它，模型说「我查过了」就真的查了——谁看的、参数是什么、结果有没有截断、是不是被拒过，全无痕迹。

> 怎么读：一、二给要改代码的人——每行、每步都标了落在哪个文件、哪个方法；三只记三条「为什么这么定」（设计理由，测试答不了）；四是配置；五是验收，也是不读实现代码时唯一的入口；附录给要评估框架与选型的人。
> 本文只做解释，不是事实源。行为判据在测试里（见下）：

## 一、负责什么 / 不负责什么

判据只有一条：**这一步是不是「一次工具调用从模型意图到执行结果」之间发生的事？**
一行 = 一个归属判断。中间那列是真正在代码里落地的位置（路径相对 `src/`，`P=` 指 `Core/Runtime/AgentWorkbench.Runtime.Tools/`），读到某个名字照着它去开文件：

| 事 | 落在哪（类 / 方法 · 文件） | 能重建吗 | 归属 |
|---|---|---|---|
| 一次调用的参数 / 结果 / 异常 / 是否截断 | `ToolCallTrace` 记录，由 `ToolExecutionRun.BeginCall/CompleteCall` 写 · `P/ToolExecutionPipeline.cs:65,123,129` | 否 | **本格** |
| 参数畸形时的可归因拒绝码 | `ToolExecutionPipeline.ValidateArguments` 现算 · 同文件 `:365` | 否 | **本格** |
| 未知工具名「曾被调用过」这一笔 | `ToolCallGuardChatClient.Report` 观察层 · `P/ToolCallGuardChatClient.cs:77` | 否 | **本格** |
| 「能不能用」的白名单判定 | 配置 → `ToolPolicy.IsAllowed` · `P/Safety/ToolPolicy.cs:34` | 否 | **本格**（准入） |
| 「要不要先问人」的审批级别 | 配置 → `ToolApprovalPolicy.Decision` · `P/Safety/ToolApprovalPolicy.cs:44` | 否 | **本格**（执行） |
| 结果能不能当依据 | `IToolResultVeto.Inspect` 由领域实现 · 端口在 `P/ToolExecutionPipeline.cs:46` | 否 | **本格给口，领域给判定** |
| 循环本体（调工具→回填→再问） | MEA `FunctionInvokingChatClient`（NuGet，不在本仓） | 是（框架） | ② 框架 |
| 允许跑几轮 / 多久 / 重复几次 | `IAgentRunGuard.InspectToolCall` · `Core/Foundation/AgentWorkbench.Shared/Execution/AgentRunStop.cs:45` | 否 | ③ 终止与预算 |
| 「该不该让这个主体做这件事」的业务判定 | 动作域 PDP + 规则 · `Core/Ports` 之外 | 否 | 边界外（动作闸） |
| 工具本身（查单、检索、计算） | 各域 / Builtin / MCP server 的实现类 | 是 | 提供者，不在本格 |
| 账本落库、回放界面 | 应用层 | 是 | 应用层 |

按这条判据切开：

**本格管（7 条）**

- 目录：把各提供方的工具汇总、过滤、去重，决定模型能看见哪些
- 准入：按能力标注决定 MCP 工具进不进模型目录（**默认是关的**）
- 环内观察：未知工具不执行、但整轮结束要留痕
- 调用前判定：重复 / token 预算（③ 给阈值，本格给执行点）
- 调用前校验：按工具 schema 挡畸形参数，回填可归因拒绝码
- 审批：Auto / Ask / Deny 三态，Ask 无应答一律 fail-closed
- 调用后：落轨迹（含截断标志）、问否决器、把结果按同一上界回填给模型

**不归本格**

- `Runtime.Harness` 挂工具清单到请求 → ① + ② 的交界
- `ActionGateway` 的业务权限与幂等 → 边界外，不是本格的编译单元
- 白名单与审批的**取值内容**（哪个工具该放行、该问谁）→ 配置与领域，本格只执行判定

一个容易混的点：**「白名单」和「审批」是两样东西，配置也是两节。** 白名单答「能不能用」，审批答「要不要先问人」；一个工具可以「允许用、但每次问」。揉成一个接口，这种状态就表达不出来。

## 二、一次调用走哪几步

模型在工具环里请求一个工具，走的是 `FunctionInvoker`——`ToolExecutionPipeline.Create` 在 `P/ToolExecutionPipeline.cs:195` 设的那个回调。
七道判断全写在 `:197–293` 这一个方法体里，顺序是位置敏感的。右列是照着代码抄的调用式与行号，按它去开文件：

```
步骤 / 方法（在 ToolExecutionPipeline.cs）   行     这一步做什么
 1. run.BeginCall(...)                    :198    轨迹先记一笔（迭代号/名字/参数）
 2. limits.Guard?.InspectToolCall(...)    :203    重复调用 / token 预算（阈值来自 ③）
        命中 → CompleteCall + run.StopAt + Terminate=true，不再回问模型（:205–212）
 3. gateway.Handles / gateway.ExecuteAsync :218/223  登记过的外部工具 → 归一成业务动作过四道闸
 4. ValidateArguments(function, args)     :239    按工具自己的 schema 挡畸形参数（实现在 :365）
 5. InspectApprovalAsync(...)             :252    Auto 放行 / Deny 拒 / Ask 问人（实现在 :307）
        拒绝 → DenialPayload 回填给模型，工具绝不执行（:258–261）
 6. context.Function.InvokeAsync(...)     :266    真正执行
        → run.CompleteCall（轨迹存截断版，事件带完整版）:270
        → limits.Veto?.Inspect（调用后问「这结果能不能当依据」）:274
        → return Truncate(text) 给模型 :283
 7. catch (Exception ex)                  :285    记一笔（MarkToolFailure + CompleteCall）后原样抛回 MEA
```

三处顺序不能挪：

- **守卫在审批前**：守卫判「整轮要不要停」，是更上层的止损；已决定停的调用不必再打扰审批人。
- **动作闸在参数校验前**：走闸时该由**动作的 Schema** 判参数，不是工具自己的 schema；且工具的畸形参数不该去触发四道闸。
- **落轨迹在问否决前**：拒答时那份命中仍是证据，事后要能查「它看到了什么才拒的」。

## 三、为什么这么定（三条）

只有三条测试答不了的取舍；其余判据与负控在测试里，本文不复述。

**循环本体用框架的，本格只装。**
`FunctionInvokingChatClient` 已经实现「识别工具意图 → 执行 → 回填 → 再问」，`MaximumIterationsPerRequest` 等四个选项全部显式赋值、不靠隐式默认（`LoopAssembly` 给值）。

**目录层做延迟解析，不在构造期取 provider。**
`IAgentToolProvider.GetTools()` 每次调用现去 DI 取；provider 内部可能依赖知识库或文档仓储，构造期解析会形成 DI 环。过滤发生在**汇总之后**，同名按 Ordinal 去重。

**MCP 准入默认是关的。**
能力画像从 server 标注读——`DestructiveHint=true` 永不进目录（信任名单也翻不了）；`ReadOnlyHint=true` 可进；什么都没声明按「会写」处理，只有 `TrustedReadOnly` 逐个点名才进。`AllowTools` 留空 = 一个都不放行。

## 四、配置

| 节 | 键 | 默认 | 含义 |
|---|---|---|---|
| `Harness:ToolExecution` | `MaxResultChars` | 400 | 轨迹里保存的工具结果最大字符数 |
| `Harness:ToolExecution` | `ApprovalTimeoutSeconds` | 120 | `Ask` 的管道侧超时兜底；`<=0` 表示不设上限（仅测试用） |
| `Harness:Tools` | `Whitelist` | 见下 | 工具名白名单；空 = 一个都不放行；只支持精确名与尾部 `*` |
| `Harness:Approval` | `Default` | `Auto` | 未覆盖工具的审批级别；不显式提升就永不打扰用户 |
| `Harness:Approval` | `Overrides` | 空 | 工具名 → `Auto` / `Ask` / `Deny` |
| `Mcp:Servers[]` | `AllowTools` | 空 | 该 server 允许拉进来的工具名；空 = 一个都不放行 |
| `Mcp:Servers[]` | `ExposeToModel` | — | 该 server 的工具能否进模型目录 |
| `Mcp:Servers[]` | `TrustedReadOnly` | 空 | 未声明标注但由我们担保只读的工具名 |

两个容易误读的口径：

1. 白名单**默认非空**（`get_current_time` / `calculator` / `mcp__rag__*` / `list_documents` / `remember` / `recall`）。但为空时是**全关**，不是全开——把配置删空等于关掉全部工具，不等于「都给」。默认必须是「没想清楚就不能全给」的取值。
2. `ToolPolicy` 只支持精确名和尾部 `*`，不支持中间通配、正则、否定式。白名单是安全边界，必须能一眼读完并逐个签字。
3. 模型说「我没有这个能力」时，先看启动日志 `MCP server X 连上：放行 n/m` 那一行——`AllowTools` 拼错会静默少工具；再看能力画像明细，确认没被 `destructive=true` 挡掉。

## 五、怎么算验收通过

判定型用例必须**正例能绿、负控能红**；能脚本判定的禁止用 AI 判。验收以 `dotnet test` 实测为准，本文不列测试文件名与条数（会漂）。

**本格已验的**：

- 白名单精确匹配、大小写敏感、空表全关、尾部 `*` 只按前缀、同名去重、多提供方汇总后过滤（S04 的 08–13）
- 清单外工具：不执行、不抛异常、模型能收到回填、整轮结束留痕、流式分片只记一笔（S04 的 03、05–07）
- 工具调用被执行、参数与结果完整进轨迹、结果回填给模型（S04 的 02、14、15）
- 内容上界、畸形参数调用前挡下、工具异常转结果回填不炸整轮（`ToolCallGapTests` 三条）

**证据强度打折的地方**：

- S04 的 01–07 用 **Mock 策略**，只验目录与守卫；真实 `ToolPolicy.IsAllowed` 写错它们照样全绿。08–11 才换成真实策略补上这一层——读那几条时别把 01–07 当白名单证据。
- 装配判据使用脚本化模型（`/ScriptedChatClient`），不碰真模型。真模型会不会按剧本调工具、会不会编参数，这组测试答不了。
- `DynamicallyOpenAITool` 等 MEA 扩展点本格**有意不接**，目前没有独立负控——这是决定，不是已验。


**明确不在本文范围的**：业务权限与幂等（动作闸）、工具实现本身（各域 / MCP server）、账本落库与回放（应用层）。

# 附录（要评估框架与选型的人看，改代码不必读）

## A. 框架给了什么 / 没给什么

| 层 | 类型 | 给到什么 | 本仓补什么 |
|---|---|---|---|
| MEA | `FunctionInvokingChatClient` | 工具环本体、结果回填、批次、四个 FICC 选项 | `FunctionInvoker` 里七道判断 |
| MEA | `AIFunctionFactory` / `AIFunction` | 把委托登记成工具、按 schema 绑定参数 | `ValidateArguments` 的拒绝码与回填 |
| MEA | `ChatOptions.Tools` | 工具清单随请求下发 | 目录裁剪与准入 |
| MAF | `ChatClientAgent` | `RunAsync` / `RunStreamingAsync` | 无 |
| MCP SDK | `McpClientTool.ProtocolTool.Annotations` | `ReadOnly` / `Destructive` / `Idempotent` 标注 | 能力画像与默认关的准入（SDK 标注在 `WithName` 后无人可读） |
| 框架 | — | 审批挂起、幂等领取、未知工具留痕、内容上界 | 全部自补 |

**「未知工具」有两本账，不要合并**：模型请求了不存在的名字 → `UnknownCalls`（观察层补记，走不到 `FunctionInvoker`）；工具执行抛异常 → `ToolCallTrace.Error` + `ToolFailures`。两者都叫「失败」，读者不同。

## B. 两轴的出处

「沙箱轴与审批轴分开」参照的是成熟 agent 的分法（Codex 的沙箱策略与审批策略各自独立）：能不能用是**能力边界**，要不要问人是**信任边界**。本格把它落成两个配置节、两个 `IOptionsMonitor`、两个策略类——合并的代价是丢掉「允许但每次问」这个状态。

注意本格只管**要不要问人**；**问谁、依据哪条制度、批完去哪个系统里变成什么**全在动作域。最接近「轮子」的一处是审批挂起：MAF 1.23 有 `ToolApprovalAgent`，但它是进程内同步交互，不带持久化挂起、外部审批人、业务规则与幂等——职责不同，但它是第一个该盯的候选（若 MAF 补上持久化审批，本格的自写三态就该按「有等价物就用它的」处理）。

## C. 与其它五份的边界

① 讲「模型每轮看到什么」（含工具清单挂请求）；② 讲「怎么从一轮走到下一轮」；③ 讲「允许走几轮、什么时候停」（本格提供执行点）；⑤ 讲「跨轮保住什么」；⑥ 讲「走过之后留下什么」（本格产出 `ToolCallTrace`，⑥ 把它写进账本）。

`MaxIterations` 是 ② 与 ③ 共用的数字：② 交给本格，本格经 `ToolExecutionLimits` 落到 FICC，③ 定义它的含义。
