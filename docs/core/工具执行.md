# 工具执行（Runtime.Tools + Tools.Builtin + Tools.Mcp · 六部件之④）

- **适用侧**：底座
- **寿命**：现状（就近维护）
- **最后校准**：2026-11-23
- **类型**：Architecture（解释型）

> 本文解释工具从进入模型可见清单，到模型发起调用，再到执行结果返回的完整过程。重点是定义工具准入、调用控制、执行收口和失败恢复的责任边界，以及这些行为应当如何验证。
>
> **范围**：能力准备、调用执行、动作闸边界、失败语义、架构契约与验收。
>
> **非范围**：业务权限和幂等的具体实现、工具自身的业务逻辑、账本落库与回放界面。
>
> **事实来源**：文件与符号定位、实际配置、依赖版本、测试规模、用例名与预设变异点，全部由 `docs/kb/documents/tools.toml` 和 `docs/kb/contracts/tools.toml` 维护，`scripts/kb_check.py` 负责对账。本文只解释这些事实背后的架构判断——凡正文提到「某处代码」，具体定位在 TOML，不在正文。

> **本文为什么存在**：服务于两件事——**交接边界**（告诉要改这段代码的人哪里不能碰）和**局部验收标准**（这一格做到什么算完成）。§7 的每条验收都从前面的边界推导；测试与契约是它的执行形式，不反过来定义边界。本文不与正本六句比大小：六句回答项目成没成，这里回答这一格做完没做完。

模型提出的是**执行请求，不是执行授权**。

它可以选择一个可见工具、生成调用参数、根据结果继续思考，但不能自行决定工具是否应该暴露、调用是否满足执行条件、当前工具环是否应该停止，以及外部执行失败后能否安全重放。

Runtime.Tools 的职责，就是在模型意图和工具执行之间建立明确的控制边界，并在执行之后形成可追溯的结果。拿掉这一层，模型说「我查过了」就真的算查了：谁看的、参数是什么、结果有没有截断、调用是否被拒绝，都缺少统一的记录和控制。

## 1. 整体运行模型

工具执行不是模型生成调用后直接进入工具实现。从整个生命周期看，它包含两个不同的过程：**能力准备**决定模型能看到什么，**调用执行**决定一次具体请求能不能执行、结果如何收口。两者相互衔接，但不是同一条执行链上的连续步骤。

### 1.1 能力准备：工具如何进入模型可见清单

工具来自不同提供方。Runtime.Tools 将它们汇总成统一目录，再按准入策略过滤。

```text
Builtin 工具 ──────┐
                   │
MCP 工具 ──────────┼──→ 提供方汇总
                   │         ↓
其他工具提供方 ────┘       同名去重
                             ↓
                          准入过滤
                             ↓
                       模型可见工具清单
                             ↓
                        随请求提供给模型
```

这条链解决的是工具能力准入：它决定模型可以选择哪些工具，但不负责决定每一次具体调用能否执行。工具进入清单只说明它具备被请求的资格，不意味着已获得执行许可。

### 1.2 调用执行：一次工具请求如何落地

模型在工具环中提出调用请求，由 MEA 框架完成工具名称分发。已知工具进入 Runtime.Tools 提供的执行回调；未知工具进不了这个回调，由观察层单独记录。

```text
模型产生工具调用意图
          │
          ↓
      框架分发
          │
      ┌───┴────┐
      │        │
    未知工具   已知工具
      │        │
      ↓        ↓
   观察层     开始调用记录
      │        │
      │        ↓
      │      运行守卫
      │        │
      │        ↓
      │      参数校验
      │        │
      │        ↓
      │      工具级审批
      │        │
      │        ↓
      │      工具执行
      │        │
      │        ↓
      │      成功结果落账
      │        │
      │        ↓
      │      结果否决
      │        │
      │        ↓
      │      结果回填
      │
      ↓
  框架处理未知工具结果
```

工具执行抛出异常时不沿正常结果路径继续，而是进入独立异常路径。因此调用执行有三个出口：**前置拦截**（工具尚未执行就被拒绝或终止）、**正常收口**（执行成功后记录、判定、回填）、**异常旁路**（记录失败后交还框架）。

### 1.3 各阶段由谁负责

| 阶段 | 控制者 | 决策依据 | 执行责任 |
|---|---|---|---|
| 工具来源 | 各工具提供方 | 提供方自己的工具定义 | 各工具提供方 |
| 目录汇总与准入 | Runtime.Tools | 白名单与工具元数据 | Runtime.Tools |
| 工具名称分发 | ② MEA 框架 | 工具名称匹配 | 框架 |
| 调用开账 | Runtime.Tools | 当前工具调用 | Runtime.Tools |
| 运行守卫 | Runtime.Tools | ③ 提供的运行约束 | Runtime.Tools |
| 参数校验 | Runtime.Tools | 工具 Schema | Runtime.Tools |
| 工具级审批 | Runtime.Tools | 审批策略与审批端口 | Runtime.Tools |
| 工具执行 | 工具提供方 | 工具自身逻辑 | 工具提供方 |
| 业务动作授权 | 动作闸 | PDP 与业务规则 | 动作闸执行体 |
| 结果否决 | Runtime.Tools | 领域提供的判断 | Runtime.Tools 控制工具环 |
| 账本落库与回放 | 应用层 | 应用层 | 应用层 |
| 工具循环 | ② MEA 框架 | 框架及③的运行约束 | 框架 |

这里要区分四种权力：**控制权**（谁驱动过程往前走）、**决策权**（谁判断当前行为是否允许）、**执行责任**（谁真正产生外部行为）、**状态所有权**（谁维护运行状态）。检查发生在谁内部，不等于决策权就归谁。

例如，知识检索结果是否足以作为回答依据，由领域实现判定；结果被否决后是否停止当前工具环，由 Runtime.Tools 执行——本格不评价领域判定本身是否正确。同样，Runtime.Tools 不负责模型循环、不负责业务权限、也不负责账本持久化，这些分别属于其他部件。

## 2. 能力准备：决定哪些工具可以被模型使用

本阶段要解决三个问题：如何汇总不同提供方的工具、哪些工具允许进入模型目录、如何理解工具提供方声明的能力和信任边界。

### 2.1 汇总、去重与过滤

工具目录由多个提供方共同构成，不能假定所有提供方都能在构造阶段安全解析：部分提供方内部依赖知识库、文档仓储这类服务，在构造期提前取实例可能形成 DI 依赖环。因此采用**延迟解析**——需要构建目录时再去取提供方。

处理顺序是固定的：先汇总、再去重、最后过滤。三步各有理由——先汇总，目录才能看到完整候选集合；再去重，同名工具不会因为出现在多个提供方里而重复进入；最后过滤，让统一准入策略作用于汇总后的最终候选，而不是逐个提供方各过滤一遍。同名工具按序数比较去重。

目录汇总由 Runtime.Tools 负责，具体工具的行为仍由工具提供方负责。

### 2.2 白名单：工具能不能进入目录

白名单回答的是「这个工具是否允许暴露给模型」，它控制的是能力边界，不是具体调用时的人工审批。

策略采用**默认关闭**：白名单为空时一个工具也不放行。这不是为了少写代码，而是配置错误时系统应该少暴露一个工具，而不是意外多暴露一个可能写数据的工具。

匹配形式也被刻意限制在能逐项读完的范围：精确名称，以及尾部的通配符。不支持中间通配、正则和否定式。理由是白名单本身就是一条准入边界，它的判断必须能被一个人从头到尾审一遍——需要解释匹配器行为的规则，就不是可审查的边界。

### 2.3 MCP：工具声明不能代替行为验证

MCP 工具额外带能力标注，准入使用这些标注：

| MCP 标注 | 目录准入行为 |
|---|---|
| 声明为破坏性 | 永不进入目录，信任名单也不能覆盖 |
| 声明为只读 | 可以进入目录 |
| 没有声明相关标注 | 按可能写入处理，必须逐个明确放行 |

这样做的目的是降低「误把一个有写能力的远程工具暴露给模型」的概率。但必须说清这些标注的来源：它们由 MCP Server 自己声明。

```
MCP Server 声明：    只读
实际执行：           UPDATE orders SET status = 'cancelled'
```

Runtime.Tools 无法只凭自报标注发现这种行为。所以 MCP 标注是一项**准入依据，不是安全证明**：它防误用，不防恶意或已被攻陷的 Server。这条边界不因为准入规则写得多细而改变。

### 2.4 本阶段必须成立的契约

核心契约：**不符合准入策略的工具，不得进入模型可见清单**（`TOOL-ADMISSION-001`）。

| 契约 | 应当成立的行为 | 必须阻止的行为 |
|---|---|---|
| 精确匹配 | 符合名称规则的工具放行 | 不匹配的工具意外放行 |
| 大小写 | 按既定比较规则匹配 | 比较规则被意外改变 |
| 空白名单 | 不放行任何工具 | 默认全部开放 |
| 尾部通配 | 按前缀规则放行 | 不支持的通配方式被错误解释 |
| 同名去重 | 保留唯一工具名 | 重复工具进入目录 |
| 多提供方汇总 | 所有提供方参与汇总 | 只取第一个提供方 |
| MCP 破坏性标注 | 不进入模型目录 | 被白名单覆盖 |
| MCP 未声明标注 | 按可能写入处理 | 未声明却自动开放 |

这一阶段结束后系统得到最终工具清单。模型只能从这份清单里产生调用意图，但每一次具体调用仍然要经过执行控制。

## 3. 调用执行：决定一次具体请求是否能够执行

能力准备解决的是「能不能看见」，调用执行解决的是「这一次能不能执行」。一次已知工具调用进入执行回调后，先开账，再经过三个前置拦截点，随后进入工具执行和成功收口。

```text
模型请求已知工具
       ↓
    开账
       ↓
    运行守卫
       ↓
    参数校验
       ↓
    工具级审批
       ↓
    工具执行
       │
       ├── 成功
       │     ↓
       │   结果落账
       │     ↓
       │   结果否决
       │     ↓
       │   结果回填
       │
       └── 异常
             ↓
           失败记录
             ↓
           原样抛回框架
```

前置拦截是依次执行的三个独立判定点：每个判定用自己的依据，前一道放行只表示可以进入下一道，不代表下一道也会放行。

### 3.1 开账：先记录模型提出了什么请求

进入执行回调后，首先建立一条尚未完成的调用轨迹，记下当前迭代号、工具名称和原始参数。

开账发生在所有前置拦截之前。理由是：参数校验失败、审批拒绝或运行守卫触发，都意味着一次工具调用请求确实发生过。如果只有真正执行成功的工具才留下记录，系统就无法解释模型曾经请求过什么，也无法还原调用为什么没有落地。

所以开账记录的是**调用意图**，不是执行成功事实。一条调用从开账开始，必须在后续每条路径上完成收口。

### 3.2 运行守卫：当前工具环是否应该继续

开账之后先执行③提供的运行守卫。③负责定义运行约束和阈值，Runtime.Tools 负责在工具执行点实施检查。

把守卫放在参数校验和审批之前，是因为它回答的是更上层的问题：**当前工具环还有没有继续执行的资格**。如果整轮已经触及停止条件，就没有必要再校验参数、更没必要打扰审批者。

守卫触发后：保留调用轨迹、记录终止原因、不执行当前工具、当前工具环不再回问模型。守卫为空时环内不执行这些提前终止检查。

要强调的是，守卫不是业务权限检查，也不判断工具的业务行为是否正确——它管的是「还能不能继续跑」，不是「该不该做这件事」。

### 3.3 参数校验：工具请求是否符合输入契约

运行守卫放行后，检查参数是否符合工具自身声明的 Schema。本格只做基础约束（必填与类型），`enum`、`pattern`、嵌套结构这些更完整的约束交给框架的参数绑定。

因此两类失败必须分开：**本格基础校验失败**生成可归因的拒绝码、回填结构化拒绝载荷、工具不执行，模型可以据此调整参数；**框架参数绑定失败**按工具异常路径归类，不冒充本格的 Schema 拒绝。混成一类，模型就分不清「我传错了」和「工具内部炸了」。

把校验放在审批之前，是因为畸形参数不该占用审批者的注意力：需要人判断的是一次有效的调用，不是替工具处理明显错误的输入。

### 3.4 工具级审批：当前调用是否需要人工许可

参数校验通过后执行工具级审批策略：自动放行、直接拒绝、请求人工审批三种。

**没有审批者时，任何「请求审批」都按拒绝处理**（`TOOL-APPROVAL-001`）。这条 fail-closed 是安全默认值，不是功能分支：配置上要求人工同意，而系统里没有审批者，正确反应是拒绝，而不是悄悄放行。

当前生产环境没有工具级审批的实现，装配时也没有传入审批者，加上默认策略是自动放行，所以正常生产路径不会走到「请求审批」。真正会挂起等人工决定的是动作闸，见 §4。

工具级审批与白名单不能合并成一条策略，因为两者回答的问题不同：白名单问「这个工具能不能被使用」，审批问「这次调用要不要先问人」。一个工具完全可以被允许使用，但每次调用都要审批。合成一条，就没法表达这种组合。

### 3.5 工具执行：进入真正的工具实现

三道拦截全部通过后才调用工具实现。具体行为由提供方负责：内置工具由自己实现，MCP 工具由对应 Server 提供，`propose_action` 则把业务动作请求交给动作闸。Runtime.Tools 不实现查询、检索、计算这些业务逻辑，也不替工具推断执行结果。

需要注意：进入工具实现不等于一定产生外部副作用。普通查询只读数据，业务动作工具可能进一步触发订单写入、审批挂起等真实行为——这些由工具提供方及其内部机制负责。成功返回则进正常收口，抛异常则进异常旁路。

### 3.6 成功收口：一次执行产生三个不同用途的结果

工具成功返回后，结果不能直接交回模型，因为同一份结果要服务三个读者：执行轨迹要控制存储量，应用层来源面板要完整内容，模型上下文要控制增长。因此一次成功调用产生三个产物：

| 产物 | 使用的数据 | 读者 | 目的 |
|---|---|---|---|
| 执行轨迹 | 截断版 + 截断标志 | 回放、审计 | 控制账本数据量 |
| 完成事件 | 完整版 | 应用层来源面板 | 保留完整来源内容 |
| 模型回填 | 截断版 | 模型 | 控制上下文增长 |

三者不能相互替代，混用会出方向相反的错：轨迹存全文，大型输出能撑爆账本；完成事件只存截断版，面板显示不全；把完整结果回填模型，设上界就等于没设过。轨迹与回填用同一个上界，只是它们恰好都读截断版，不是因为它们是一回事。

这条契约是 `TOOL-RESULT-001`。顺序上，先完成结果记录，再判否决，最后回填——记录必须在否决之前，否则被否决的那次结果就没有证据。

### 3.7 结果否决：执行成功不代表结果足以继续使用

结果记录完成后，把**未截断的完整结果**交给领域提供的否决端口。传完整版而不是截断版，是因为判断不能建立在可能已经丢了内容的文本上。

接口语义很简单：返回空表示不否决；返回非空表示**必须终止当前工具环**。发生否决时：已产生的结果保留、轨迹不改、终止原因单独记录、原始结果仍然回填给模型、本轮不再回问模型、不用抛异常表达否决（`TOOL-VETO-001`）。

```text
知识检索执行成功 → 完整结果落账 → 领域判断：证据不足
      → 记录终止原因 → 截断版仍然回填 → 当前工具环停止
```

这里区分两个不同的问题：工具是否成功执行，和结果是否足以支撑 Agent 继续。前者属于工具执行，后者属于领域判断。当前领域实现只对特定工具生效（主要是知识检索）。本格不评价领域判得对不对，只负责按判定控制工具环。

### 3.8 结果回填：由框架继续驱动工具环

没有否决时，把截断版结果交还 MEA 框架。框架负责接收结果、放回对话上下文、决定是否继续发起模型请求、识别后续工具调用、驱动下一轮。发生否决时结果照样回填，只是本轮不再回问模型。

所以 Runtime.Tools 不拥有模型循环，只提供执行结果和必要的终止信息。

### 3.9 异常旁路：工具抛出异常时如何收口

工具执行抛异常时不进正常收口链，而是记录失败、记录异常轨迹、然后**原样抛回框架**。本格不把异常伪装成成功结果，也不自行把所有异常转换成普通返回值——转成可处理的错误结果还是向外传播，由 MEA 框架决定。

还有一条容易忽略的约束：**异常发生不代表外部副作用一定没有发生**。远程调用可能已经写入成功，只是响应在途中丢了。Runtime.Tools 不应仅凭异常就推断外部系统状态；业务动作的未知状态由动作闸查证，见 §5.2。

### 3.10 调用轨迹必须形成完整收口

开账之后，每条路径都必须在返回或传播异常之前完成自己的记录收口——守卫拒绝、校验拒绝、审批拒绝、执行异常、执行成功，五条路径无一例外。否则账本会留下无法解释的未完成记录：系统明明拦住了工具，却说不清那次调用最后怎么了。

这条纪律在当前实现在尤其重要：轨迹没有独立的「已完成」标志，收口靠显式写入结果或错误码；而工具确实返回空值时，与「没写过」在数据上同形。也就是说，事后无法只凭值判断收口有没有做，只能靠每条路径都显式写一次来保证。这是实现层的编码约束，改轨迹数据结构时才有机会去掉。

## 4. 动作闸：工具调用控制与业务执行安全的分界

前面的 Runtime.Tools 是通用的工具调用控制层，它不应该知道订单修改规则、用户业务权限，也不该自己决定业务动作能否真正执行。当模型需要发起业务动作时，通过 `propose_action` 把请求交给动作闸。

### 4.1 动作闸在工具实现内部

`propose_action` 本身也是一个普通工具，因此同样进入统一的执行回调，**不存在绕过本格的第二条执行路径**。

```text
模型请求 propose_action
        ↓
运行守卫 → 工具 Schema 校验 → 工具级审批
        ↓
执行 propose_action
        ↓
工具内部提交业务动作
        ↓
Schema → Permission → BusinessRule → Audit
        ↓
审批挂起 / 幂等领取 / 执行体 / 审计
```

动作闸是 `propose_action` 内部的业务执行机制，不是 Runtime.Tools 的另一条工具执行路径。这一点值得写明：旧版文档曾描述过一条独立的网关分支，后来在真实代码里零命中，那段描述不是简化，是错的。

### 4.2 两层校验不是重复校验

| 校验层 | 校验对象 | 解决的问题 |
|---|---|---|
| Runtime.Tools | `propose_action` 自身参数 | 工具调用是否满足工具输入契约 |
| 动作闸 | 业务动作的 Schema | 业务动作参数是否满足业务契约 |

第一层保证工具调用接口正确，第二层保证业务动作符合声明的业务结构。两层是嵌套关系，不是二选一。

### 4.3 两层审批也不是同一种审批

| 审批层 | 回答的问题 | 当前状态 |
|---|---|---|
| Runtime.Tools 工具级审批 | 这次调用 `propose_action` 是否需要询问 | 生产没有审批者，请求审批一律拒绝 |
| 动作闸业务审批 | 这个业务动作是否需要人工许可 | 由动作闸负责，会真正挂起 |

所以当前代码不存在两层审批重复询问的问题——第一层根本没有启用。将来接上工具级审批后才需要重新裁定分工，那属于未决问题（见 §8.2）。审批人本身的设计缺口另记在 `docs/plans/P05-审批人是操作者本人.md`。

### 4.4 动作闸承担哪些责任

Runtime.Tools 不判断：当前主体有没有修改订单的权限、订单是否满足业务规则、某项操作是否需要业务审批、幂等键如何生成和领取、外部动作超时后是否已经执行、外部副作用能否安全重放。这些属于动作闸的 PDP、业务规则、审批、幂等和执行责任。

两层之间的最终边界是一句话：**Runtime.Tools 决定工具调用能否进入工具实现，动作闸决定业务动作能否真正执行。**

## 5. 失败与恢复：每个阶段失败后意味着什么

前面定义的是正常过程。这一节不重复机制，只按发生阶段说明失败后状态变成什么、谁能继续。

| 阶段 | 失败形态 | 记录与结果 | 后续责任 |
|---|---|---|---|
| 工具分发 | 未知工具名 | 观察层独立记账，不进执行轨迹；框架回填工具不存在 | 框架按未知工具策略处理 |
| 运行守卫 | 重复调用 / 超预算 | 轨迹记录归类码与终止原因；当前工具环停止 | 收口 |
| 参数校验 | 参数畸形 | 轨迹与拒绝码；回填结构化载荷；工具不执行 | 模型可以调整参数 |
| 工具审批 | 策略拒绝 / 请求审批但无审批者 | 轨迹与拒绝码；回填拒绝载荷；工具不执行 | 模型换路或收口 |
| 工具执行 | 普通异常 | 失败记录与异常轨迹；原样抛回框架 | 框架 |
| 普通工具超时 | 调用失败 | 按工具失败处理；不推断外部副作用，也不由本格重放 | 框架与模型处理错误结果 |
| 业务动作执行 | 外部状态未知 | 不猜测实际执行结果 | 动作闸按业务键查证 |
| 结果否决 | 领域判定不可接受 | 结果仍回填；轨迹不改；单独记录终止原因 | 当前工具环停止 |

### 5.1 未知工具与工具异常为什么分开记录

两者都属于失败，但发生在不同阶段。未知工具发生在框架分发阶段，**根本进不了执行回调**，本格没有机会生成正常调用轨迹，只能由观察层单独记账。工具异常则已经进入回调、已经建账、工具实现已经被调用过，由本格记录失败和异常轨迹。

读者和用途不同，所以不合并。**工具调用意图的记录，不等于工具执行的轨迹。**

### 5.2 普通工具超时与业务动作状态未知必须区分

超时不都需要业务查证，要按工具行为区分。

**普通读取工具超时**（检索、查询）：本格按工具失败处理，不自行重放，也不推断远端状态；错误结果交框架，是否再查由模型根据错误结果决定。

**业务写动作状态未知**（下单请求已发出、响应在路上丢了）：此时不能假定对方没做。直接重放可能产生第二笔。所以经动作闸执行的写动作遵守 **不可用 → 未知 → 只查证不重放**，由动作闸按业务键查实际状态（`TOOL-RECOVERY-001`）。

这条规则不能泛化成「所有工具超时都要查证」，也不能因为普通工具可以重查，就认为写动作可以直接重放。

### 5.3 截断、轨迹与回放是不同的事情

截断由 Runtime.Tools 负责，轨迹由 Runtime.Tools 产生，账本持久化和回放视图由应用层负责；三个结果版本之间的关系见 §3.6。本格只负责生成记录，不负责重建整个回放界面。

## 6. 配置与架构约束

具体取值不在本文维护，由 `tools.toml` 的事实声明与仓库配置作为权威。这里只留与架构直接相关的判断。

### 6.1 默认值的方向

**能力准入默认关闭**：白名单为空意味着没有工具进入目录。

**审批默认放行，但不等于无条件安全**：自动放行只适用于不需要人工询问也能安全执行的工具；需要人工许可的业务动作由动作闸管。

**请求审批但没有审批者时必须拒绝**：不能因为端口缺失就放行。

三条合起来是一条判断：**所有默认值都必须往「少做」的一侧倒**。配置缺失、装配遗漏、端口没接——这些都应该是工具少跑一次，而不是多跑一次。

### 6.2 白名单规则必须可读、可审查

只支持精确名与尾部通配，不支持中间通配、正则、否定式。这不是实现能力不足，而是这条边界要能被逐项检查：一份需要解释匹配器行为的准入配置，实际上没人能审。

### 6.3 排查「模型看不到工具」时先查目录

当模型表示没有某项工具能力时，先查两处：启动日志里的放行条数（配置是否把工具过滤掉了），以及能力画像明细（具体工具是否被准入规则或破坏性标注挡掉）。不要直接把「没使用工具」归因于模型能力。

### 6.4 框架循环选项必须显式配置

工具循环由 MEA 框架提供，本仓不重复实现工具意图识别、执行调度、结果回填和多轮循环。框架相关的循环选项全部显式赋值，不依赖隐式默认——否则框架升级时默认值一变，本仓行为会跟着无声漂移。

## 7. 契约验收：如何证明前面的机制成立

本节不是测试清单，而是把前面各节的主张转成可核对的东西。验收遵循五条：每项判定契约都要有正例和负控；负控要证明错误行为会被发现，而不是只证明某次调用没成功；能由脚本判断的事实不交给模型评价；以实际运行结果为依据，不以测试文件存在为依据；不把局部通过扩大成整条成立。

契约的稳定身份、实现定位、用例名、预设变异点和证据强度，都在 `docs/kb/contracts/tools.toml`。本节只留结论：**哪几条有独立判据，哪几条没有。**

| 契约 | 主张 | 结论 |
|---|---|---|
| `TOOL-ADMISSION-001` | 未准入工具不得进入模型清单 | 有判据，但是**混合强度**：准入规则有真实策略证据，目录去重与汇总只有 Mock 证据 |
| `TOOL-APPROVAL-001` | 无审批者时请求审批必须拒绝 | 有判据：三态各有断言（拒绝 / 直接拒 / 不打扰审批者），fail-closed 的负控已实测 |
| `TOOL-RESULT-001` | 三个产物各用约定版本 | 有判据：三个读者分别断言，事件带全文、轨迹带截断版，负控已实测 |
| `TOOL-VETO-001` | 否决必须停环且保留结果 | **无独立判据**：删掉终止标志不会红 |
| `TOOL-RECOVERY-001` | 状态未知不得直接重放 | 代码层有判据；**外部闭环未验** |

其余主张（开账、守卫、校验、异常旁路、轨迹收口）**故意不给 ID**：它们的边界不跨部件、也没有对外承诺，证据在 §3 对应小节指的那几组测试里。给每一条都发 ID，只会多出第五套编号，没人维护。

### 7.1 三条证据限制

**一、工具执行测试不等于真实准入策略测试。** 有一部分装配用例把工具直接挂进请求，没有经过真实白名单；目录去重与汇总用的是 Mock 策略。只有专门那几条真实策略用例才能作为准入规则的直接证据。

**二、脚本化模型不等于真实模型验证。** 当前装配测试用脚本化模型，能验证已知场景下的调用装配、执行回调和结果处理，但不能证明真实模型一定会选对工具、生成合法参数、遵守工具使用约束。这一项没有契约 ID——它不属于任何单条契约，是模型行为层的空白。

**三、预设变异点不等于变异验证。** 一条负控的完整验证要四步：设计变异、真改生产代码、跑测试确认变红、恢复代码再确认变绿。TOML 里记的是**设计**，不是实验结论。本仓历史上有过变异自证，但这次校准没有逐条重跑，所以本文不把它们表述为本轮的验证结果。真实实验记录应放 `docs/plans/`，一条实验一个文件。

### 7.2 本部件算通过的标准

不能用「已经能调用工具」判断完成。至少要能回答：

1. 不符合准入规则的工具不会进入模型清单；
2. 已知工具调用必须经过守卫、校验与审批三道拦截；
3. 执行成功后，轨迹、完成事件、回填各用规定的版本；
4. 每条路径都完成了轨迹收口，包括拒绝路径；
5. 领域否决能停止工具环，同时保留已产生的结果；
6. 业务动作的授权、审批、幂等与外部查证归动作闸，不算进本部件；
7. 未验证的行为明确登记，不因为别的测试通过就宣称完整成立。

最终以 `scripts/ci.sh` 和 `dotnet test` 的实际执行结果为准，不以测试数量或测试名称为准。

## 8. 安全假设与未决问题

### 8.1 当前依赖的假设

**MCP 标注来自提供方自身。** 准入用它过滤工具，但无法保证远程 Server 的真实行为；这套措施防误用，不防恶意或已被攻陷的 Server。

**工具级审批没有生产实现。** 默认放行，需要人工许可的业务动作由动作闸负责。

**结果否决依赖领域判定。** Runtime.Tools 不独立评价领域结果质量，只执行领域的终止决定。

**工具异常不能推断外部副作用状态。** 远程写操作超时，可能已经写成功了，不能直接重放。

### 8.2 未决问题

1. **接上工具级审批后，两层审批会不会重复问？** 现在这层没启用，问题不存在；接上后需要重裁分工。
2. **MCP 标注被伪造、Server 被攻陷怎么办？** 当前准入无法独立验证工具行为。是否引入能力校验、隔离或更强信任模型，未决定。
3. **框架补齐相关能力后要不要撤掉自写部分？** 框架已有进程内审批，但不带持久化挂起、外部审批人、业务规则和幂等；若补齐，按「有等价物就用它的」重评。
4. **结果否决没有独立负控。** `TOOL-VETO-001` 的缺口尚未关闭。
5. **真实模型的工具选择和参数生成未验证。** 无契约 ID，属模型行为层。
6. **外部状态未知时的查证与不重放闭环未验。** `TOOL-RECOVERY-001` 的缺口尚未关闭，证据见 `docs/验收映射.md` 第 4 句。

## 9. 与其他五个部件的关系

| 部件 | 负责的问题 | 与本部件的关系 |
|---|---|---|
| ① 请求装配 | 模型每轮看见什么 | 提供模型可见的工具清单和请求上下文 |
| ② 框架层（MEA） | 如何从一轮走到下一轮 | 提供工具环、工具分发、结果回填和循环控制 |
| ③ 终止与预算 | 允许运行多少轮、多久、重复多少次 | 定义运行约束，本部件在执行点应用 |
| ④ 工具执行（本部件） | 工具如何准入、执行和收口 | 控制模型意图进入工具实现的过程 |
| ⑤ 状态与记忆 | 跨轮保留什么 | 为后续工具调用提供持续状态 |
| ⑥ 轨迹与观测 | 运行过程如何追溯 | 接收本部件产出的工具轨迹和完成事件，写入账本 |

三个边界需要明确：**② 拥有工具循环**，本部件不重复实现；**③ 定义预算语义**，本部件只在执行点应用；**⑥ 拥有账本持久化**，本部件只产出轨迹和事件。

迭代上限是②与③共用的数字：③ 定义它的预算含义，② 把它传进框架选项，本部件负责相关装配，但不拥有预算定义权。

六个部件合起来构成一条完整运行链：请求准备决定模型能看到什么，框架驱动模型持续运行，终止与预算限制运行边界，工具执行控制外部调用，状态与记忆维持跨轮信息，轨迹与观测保存运行证据。

Runtime.Tools 在其中的核心责任是一句话：**模型可以提出工具调用，但工具能否进入执行体、结果是否允许继续使用、调用失败后如何收口，都必须有模型之外的明确控制机制。**
