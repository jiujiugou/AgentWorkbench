# 工具执行（Runtime.Tools + Tools.Builtin + Tools.Mcp · 六部件之④）

- **适用侧**：底座 ｜ **寿命**：现状（就近维护） ｜ **最后校准**：2026-11-23

> **类型**：Architecture（解释型）。本文解释"一次工具调用从模型意图到结果之间发生什么、谁拥有决策权、失败怎么收口"，不是事实源、不是参考手册。
> **范围**：边界归属、控制流形状、设计理由、失败语义、验收判断、未决问题。
> **非范围**：业务权限与幂等（动作闸）、工具实现本身、账本落库与回放界面。
> **可枚举部分不写在这里**：文件/符号定位、配置实际值、依赖版本、测试规模都在 `docs/kb/documents/tools.toml` 的 `evidence` / `fact` 段，由 `scripts/kb_check.py` 对账——对不上就红。本文只写机器判不了的判断。

一句话：**把模型生成的工具调用，在真正执行之前过一遍判定，执行之后留下能回放的账。**
拿掉它，模型说「我查过了」就真的查了——谁看的、参数是什么、结果有没有截断、是不是被拒过，全无痕迹。

## 一、谁拥有什么判断

归属判据只有一条：**这一步是不是发生在「模型意图 → 执行结果」之间？** 具体的类与方法定位见 `docs/kb/documents/`，这里只判归属。

| 事 | 归属 |
|---|---|
| 一次调用的参数 / 结果 / 异常 / 是否截断 | **本格**（轨迹由本格持有） |
| 参数畸形时的可归因拒绝码 | **本格** |
| 未知工具名「曾被请求过」这一笔 | **本格**（观察层，走不到执行回调） |
| 「能不能用」的白名单判定 | **本格**（准入配置） |
| 「要不要先问人」的工具级审批 | **本格**（执行配置） |
| 结果能不能当依据 | **本格给端口，领域给判定** |
| 循环本体（调工具 → 回填 → 再问模型） | ② 框架层（MEA） |
| 允许跑几轮 / 多久 / 重复几次 | ③ 终止与预算 |
| 「该不该让这个主体做这件事」 | 边界外，动作闸的 PDP + 业务规则 |
| 工具本身（查单、检索、计算） | 工具提供方 |
| 账本落库、回放界面 | 应用层 |

### 1.1 五维边界（不只按调用顺序定义）

顺序见 §2，但顺序**不等于**边界。按控制权 / 决策权 / 执行责任 / 状态所有权 / 外部接口拆开：

| 维度 | 本格的答案 |
|---|---|
| **控制权** | 循环由框架的 `FunctionInvokingChatClient` 控制；本格只在执行回调里插入判定，不拥有循环。 |
| **决策权** | 只判"这一调用能不能发出"（守卫 / 校验 / 审批）；**不判业务对错**（PDP + 规则），**不判结果够不够**（领域否决）。 |
| **执行责任** | 副作用由工具实现产生；本格不实现工具。走动作闸的工具，副作用在其内部由 `ActionRunService` 产生（见 §2.3）。 |
| **状态所有权** | 轨迹、未知调用、工具失败、终止原因由本格持有；落库与回放归应用层。 |
| **外部接口** | 对模型：执行回调 + 回填文本；对领域：结果否决、运行守卫、工具审批三个端口；对配置：`IOptions` / `IOptionsMonitor`。参数对底座是不透明数据。 |

一个容易混的点：**白名单和审批是两样东西。** 白名单答「能不能用」（能力边界），审批答「要不要先问人」（信任边界）；一个工具可以「允许用、但每次问」。揉成一个接口，这种状态就表达不出来。

### 1.2 依赖契约

| 依赖 | 它提供什么 | 断了谁兜着 |
|---|---|---|
| MEA 的 `FunctionInvokingChatClient` | 工具环本体、结果回填、批次 | 本格执行回调就是它调用的，它不在就没有本格 |
| ③ 的运行守卫 | 判重复调用 / token 预算 | 为 `null` 时环内不做提前终止；阈值由 ③ 定，执行点在本格 |
| 工具审批端口 | `Ask` 级问人 | 为 `null` 时所有 `Ask` 按拒绝（fail-closed）；**当前生产没有实现，见 §2.3** |
| 结果否决端口 | 调用后判结果能不能当依据 | 为 `null` 时不否决 |
| MCP 目录 / `ToolCatalog` | 汇总各提供方的工具 | 空目录时模型没有工具可调 |
| 配置 | 策略与执行参数 | 缺配置节时取代码默认 |

## 二、一次调用走哪几步

模型在工具环里请求一个工具，进入本格设的执行回调。**这是一条线性路径，没有"Gateway 分支"**——所有工具，包括要过四道闸的 `propose_action`，都依次走同样六步。旧版文档写的 `gateway.Handles / ExecuteAsync` 分支在真实代码里零命中，这是本次校准纠正的最重要一条。

| 步 | 做什么 | 挡住之后 |
|---|---|---|
| 1 | 先记轨迹（迭代号 / 工具名 / 参数） | — |
| 2 | 运行守卫：重复调用 / token 预算 | 记轨迹 + 记终止原因 + 本轮不再回问模型 |
| 3 | 按工具自己的 schema 校验参数 | 回填结构化拒绝载荷，工具不执行 |
| 4 | 工具级审批：`Auto` 放行 / `Deny` 拒 / `Ask` 问人 | 回填拒绝载荷，工具绝不执行 |
| 5 | 真正执行 → 记轨迹（截断版）→ 结果否决 → 回填（截断版） | 否决时仍回填，但本轮不再回问 |
| 6 | 工具抛异常：记失败 + 记轨迹，然后**原样抛回框架** | 由框架决定转成错误结果还是向外传播 |

### 2.1 三处顺序为什么不能挪

- **守卫在审批前**：守卫判「整轮要不要停」，是更上层的止损；已决定停的调用不必再打扰审批人。
- **参数校验在审批前**：畸形参数不该占用审批者的注意力；挡下后把可归因的拒绝码回填，模型能自己改。校验用工具自报的 `JsonSchema`，只判 `required` 与 `type`；`enum` / `pattern` / 嵌套仍交给框架的参数绑定，绑定失败按工具异常归类。
- **落轨迹在结果否决前**：拒答时那份命中仍是证据，事后要能查「它看到了什么才拒的」。

### 2.2 结果否决的语义

调用完成后，把**未截断的完整结果**交给否决端口（与轨迹里的截断版不同）：

- 返回 `null` = 不否决；非 `null` = 必须终止当前工具环。
- 否决后果：**结果仍回填给模型**，但本轮不再回问；**不改轨迹内容、不抛异常**。终止原因单独存，不在返回值里。
- 领域实现只对特定工具生效（知识检索），判定不足时给出终止原因。
- **未验证**：否决分支没有独立负控（`UNKNOWN-VETO`）。

### 2.3 动作闸在哪一层

**动作闸不在这条管线的分支里，而在 `propose_action` 这个工具的实现内部。**

```
模型请求 propose_action
  → 本格六步（它本身也是一个工具，走同样的校验/审批/调用）
  → 工具内部提交业务动作
  → 动作闸四道闸：Schema → Permission → BusinessRule → Audit
  → 审批挂起 / 幂等领取 / 执行体 / 审计
```

含义：

- **两层校验是嵌套，不是二选一**：先由本格判 `propose_action` 这个工具自身的参数形状，再由动作闸按 `ActionSpec.Schema` 判业务参数。
- **两层审批是两回事**：本格答「这个工具调用要不要问人」，动作闸答「这个业务动作要不要问人」。
- **当前生产里本格审批不会真问人**：没有生产实现、装配时也未传审批者，任何 `Ask` 都按拒绝处理；而当前配置默认 `Auto`，所以实际走不到 `Ask`。真正会挂起等人的是动作闸。这条缺口的登记与边界见 `docs/plans/P05-审批人是操作者本人.md`。
- 因此"会不会问两次"在当前代码里不是待定问题——本格那一层根本没启用。将来接上审批实现，才需要重裁两者关系（§7）。

## 三、为什么这么定

**循环本体用框架的，本格只装。** 框架已实现「识别工具意图 → 执行 → 回填 → 再问」，本格不重复实现；四个循环选项全部显式赋值，不靠框架隐式默认——升级框架改了默认值时，本仓行为不该跟着变。这是"不造轮子"判据的结论。

**目录层延迟解析，不在构造期取提供方。** 提供方内部可能依赖知识库或文档仓储，构造期解析会形成 DI 环。过滤发生在汇总之后，同名按序数去重。

**MCP 准入默认关。** `DestructiveHint` 为真永不进目录（信任名单也翻不了）；`ReadOnlyHint` 为真可进；什么都没声明按「会写」处理，只有被逐个点名才进；白名单留空 = 一个都不放行。

**这套机制不能当安全证明。** 那些标注是 server 自报的，不是我方验证过的行为。一个标了只读的工具实际写入，这套准入发现不了。它防的是"误把写工具挂给模型"，不防"恶意或被攻陷的 server"（§7）。

**白名单轴与审批轴分离。** 两个配置节、两个策略类。合并的代价是丢掉「允许但每次问」这个状态。

## 四、配置口径（只讲判断，值不抄）

实际值随配置变，本文不复制。要查就跑 `python scripts/kb_check.py`——它读 `appsettings` 与 `csproj` 对账，`documents/*.toml` 的 `fact` 段是声明，仓库是权威。

三条判断：

1. **默认必须往"关"倒。** 白名单为空 = 全部关闭，不是全部开放；审批默认 `Auto` 只在"没人问也安全"时成立。
2. **白名单是安全边界，必须一眼读完。** 只支持精确名和尾部 `*`，不支持中间通配、正则、否定式——不是为了省事，是为了能逐个签字。
3. **模型说「我没有这个能力」时先查两处**：启动日志里 MCP 放行条数（配置拼错会静默少工具），以及能力画像明细（可能被 destructive 标注挡掉）。

## 五、失败怎么分账

| 失败形态 | 记在哪 | 回填给模型什么 | 谁能继续 |
|---|---|---|---|
| 参数畸形 | 轨迹 + 校验拒绝码 | 结构化载荷（含原因） | 模型改参数重试 |
| 审批拒绝 | 轨迹 + 拒绝码 | 结构化拒绝载荷 | 模型换路或收口 |
| 未知工具名 | 独立的一本账，**不进轨迹** | 框架自己回填"工具找不到" | 视「遇到未知工具是否终止」开关，本仓显式关 |
| 工具抛异常 | 失败账 + 轨迹 | 原样抛回框架，由它决定 | 框架 |
| 守卫 / 否决判停 | 独立字段（终止原因） | 结果仍回填 | 收口，不再回问 |
| 调用超时 | 超时分类 | `不可用 → 未知 → 只查证不重放` | 动作闸的查证分支（第 4 句） |

**两本账不要合并**：模型请求了不存在的名字，走不到执行回调，只能由观察层补记；工具执行抛异常，是本格记的失败。两者都叫「失败」，读者不同。

**截断、轨迹、回放是三件事**：截断按上界取前 N 字并置标志；轨迹存截断版（省账本），完成事件带完整版（来源面板要用），回填给模型的也是截断版；回放由应用层拿轨迹重建，本格只产出。

## 六、怎么算验收通过

判定型用例必须**正例能绿、负控能红**；能脚本判定的禁止用 AI 判。验收以 `scripts/ci.sh` / `dotnet test` 实测为准，**不以"测试文件存在"为准**。

| 主张 | 守它的那一组 | 强度 |
|---|---|---|
| 白名单精确匹配 / 大小写 / 空表全关 / 尾部 `*` | S04 的 08–11 | 真实策略，可信 |
| 并列目录去重与汇总后过滤 | S04 的 12–13 | Mock 策略，只证目录行为 |
| 清单外工具不执行、留痕、回填 | S04 的 03、05–07 | 可控 |
| 参数与结果进轨迹、结果回填 | S04 的 02、14–15 | 可控 |
| 内容上界 / 畸形参数挡下 / 异常不炸整轮 | ToolCallGap 三条 | 可控 |
| 超时归类、只查证不重放 | 超时三组 | **代码层绿，外部闭环未验**（`UNKNOWN-4`） |

**证据强度打折的地方，别当完整证明：**

- S04 的 01 与 02–07 **根本没经过策略**（工具直接挂进请求），12–13 用 Mock——真实白名单写错，这几条照样全绿。只有 08–11 是策略证据。
- 装配判据用脚本化模型，不碰真模型：真模型会不会按剧本调工具、会不会编参数，这组答不了（`UNKNOWN-MODEL`）。
- 结果否决分支没有独立负控（`UNKNOWN-VETO`）；框架的其它扩展点本格有意不接，没有负控——那是决定，不是已验。

## 八、与其他五个部件

① 讲「模型每轮看到什么」（含工具清单怎么随请求下发）；② 讲「怎么从一轮走到下一轮」；③ 讲「允许走几轮、什么时候停」（本格给执行点）；⑤ 讲「跨轮保住什么」；⑥ 讲「走过之后留下什么」（本格产出轨迹，⑥ 写进账本）。

`MaxIterations` 是 ② 与 ③ 共用的数字：② 交给本格，本格落到框架选项，③ 定义它的含义。
