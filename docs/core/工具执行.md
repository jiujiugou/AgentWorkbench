# 工具执行（Runtime.Tools + Tools.Builtin + Tools.Mcp · 六部件之④）

- **适用侧**：底座 ｜ **寿命**：现状（就近维护） ｜ **最后校准**：2026-11-18

一句话：**把模型生成的工具调用，在真正执行之前过一遍判定，执行之后留下能回放的账。**
拿掉它，模型说「我查过了」就真的查了——谁看的、参数是什么、结果有没有截断、是不是被拒过，全无痕迹。

> 怎么读：第一、二节给要改代码的人（边界与一次调用的位置）；第三节给要判断「这条判定该放哪」的人
> （七个决定）；第四到七节给配置、排障、红线、验收；附录给要评估框架与选型的人。
> 本文只做解释，不是事实源。决定与证据的机器可读登记在仓根 `agent-parts.toml` 的 `tool-execution` 格；
> 行为判据在 `tests/.../Flow/S04ContractTests.cs` 与 `CoreTests/Runtime/Tools/ToolCallGapTests.cs`。

## 一、负责什么 / 不负责什么

判据只有一条：**这一步是不是「一次工具调用从模型意图到执行结果」之间发生的事？**

| 事 | 只存在于哪 | 能重建吗 | 归属 |
|---|---|---|---|
| 一次调用的参数 / 结果 / 异常 / 是否截断 | `ToolCallTrace`，内存 | 否 | **本格** |
| 参数畸形时的可归因拒绝码 | `ValidateArguments` 现算 | 否 | **本格** |
| 未知工具名「曾被调用过」这一笔 | `ToolCallGuardChatClient` 观察层 | 否 | **本格** |
| 「能不能用」的白名单判定 | 配置 → `ToolPolicy` | 否 | **本格**（准入） |
| 「要不要先问人」的审批级别 | 配置 → `ToolApprovalPolicy` | 否 | **本格**（执行） |
| 结果能不能当依据 | `IToolResultVeto` 由领域实现 | 否 | **本格给口，领域给判定** |
| 循环本体（调工具→回填→再问） | MEA `FunctionInvokingChatClient` | 是（框架） | ② 框架 |
| 允许跑几轮 / 多久 / 重复几次 | ③ 的 guard | 否 | ③ 终止与预算 |
| 「该不该让这个主体做这件事」的业务判定 | 动作域 PDP + 规则 | 否 | 边界外（动作闸） |
| 工具本身（查单、检索、计算） | 各域 / Builtin / MCP server | 是 | 提供者，不在本格 |
| 账本落库、回放界面 | 应用层 | 是 | 应用层 |

按这条判据切开：

**本格管（7 条）**

- 目录：把各提供方的工具汇总、过滤、去重，决定模型能看见哪些
- 准入：按能力标注决定 MCP 工具进不进模型目录（**默认是关的**）
- 环内观察：未知工具不执行、但整轮结束要留痕
- 调用前判定：重复 / token 预算（③ 给阈值，本格给执行点）
- 调用前校验：按工具 schema 挡畸形参数，回填可归因拒绝码
- 审批：Auto / Ask / Deny 三态，Ask 无应答一律 fail-closed
- 调用后：落轨迹（含截断标志）、问否决器、把结果按同一上界回填给模型

**不归本格**

- `Runtime.Harness` 挂工具清单到请求 → ① + ② 的交界
- `ActionGateway` 的业务权限与幂等 → 边界外，不是本格的编译单元
- 白名单与审批的**取值内容**（哪个工具该放行、该问谁）→ 配置与领域，本格只执行判定

一个容易混的点：**「白名单」和「审批」是两样东西，配置也是两节。** 白名单答「能不能用」，审批答「要不要先问人」；一个工具可以「允许用、但每次问」。揉成一个接口，这种状态就表达不出来。

## 二、一次调用走哪几步

模型在工具环里请求一个工具，走的是 `FunctionInvoker`（`ToolExecutionPipeline.Create` 里设的回调）。七道判断，顺序是位置敏感的：

```
模型请求工具
  │
  1. BeginCall                    轨迹先记一笔（迭代号/名字/参数）
  │
  2. Guard.InspectToolCall        重复调用 / token 预算（③ 的阈值）
  │     命中 → 记轨迹、context.Terminate = true、不再回问模型
  │
  3. IToolCallGateway             策略表里登记过的外部工具 → 归一成业务动作过四道闸
  │
  4. ValidateArguments            按工具自己的 schema 挡畸形参数
  │
  5. InspectApproval              Auto 放行 / Deny 拒 / Ask 问人
  │     拒绝 → 结构化载荷回填给模型，工具绝不执行
  │
  6. Function.InvokeAsync         真正执行
  │     → CompleteCall（轨迹存截断版，事件带完整版）
  │     → Veto.Inspect（调用后问「这结果能不能当依据」）
  │     → return Truncate(text) 给模型
  │
  7. catch                        异常原样抛回 MEA，但先在这里记一笔
```

三处顺序不能挪：

- **守卫在审批前**：守卫判「整轮要不要停」，是更上层的止损；已决定停的调用不必再打扰审批人。
- **动作闸在参数校验前**：走闸时该由**动作的 Schema** 判参数，不是工具自己的 schema；且工具的畸形参数不该去触发四道闸。
- **落轨迹在问否决前**：拒答时那份命中仍是证据，事后要能查「它看到了什么才拒的」。

## 三、七个决定

**1. 循环本体用框架的，本格只装。**
为什么：`FunctionInvokingChatClient` 已经实现「识别工具意图 → 执行 → 回填 → 再问」，`MaximumIterationsPerRequest` 等四个选项全部显式赋值、不靠隐式默认（`LoopAssembly` 给值）。
改它：任何「自己写 while 再问一次」都是重写框架；要改的是装配决定，不是循环。

**2. 目录层做延迟解析，不在构造期取 provider。**
为什么：`IAgentToolProvider.GetTools()` 每次调用现去 DI 取；provider 内部可能依赖知识库或文档仓储，构造期解析会形成 DI 环。过滤发生在**汇总之后**，同名按 Ordinal 去重。
改它：改成构造期缓存，测试装配会先炸；去掉去重，模型看到两个同名工具，调用结果不可判定。

**3. MCP 准入默认是关的。**
为什么：能力画像从 server 标注读——`DestructiveHint=true` 永不进目录（信任名单也翻不了）；`ReadOnlyHint=true` 可进；什么都没声明按「会写」处理，只有 `TrustedReadOnly` 逐个点名才进。`AllowTools` 留空 = 一个都不放行。
改它：默认改成「没声明也放行」，等于把「server 没告诉我们」当成「它保证安全」——那正是「静默少工具」的反面：静默多给一个写工具。

**4. 未知工具只观察、不改语义。**
为什么：MEA 默认 `TerminateOnUnknownCalls=false`，把「工具找不到」回填给模型让它自我纠正——这是成熟做法。但回填发生在框架内部，走不到 `FunctionInvoker`，不单独记一笔事后就查不到「模型曾请求过不存在的工具」。观察层只记，不拦。
改它：改成抛异常或直接跳过，模型失去自我纠正入口；或把 `TerminateOnUnknownCalls` 改 true，必须重新证明模型仍能看到错误。

**5. 白名单与审批是正交两轴，各自热重载。**
为什么：`IToolPolicy`（能不能用）与 `IToolApprovalPolicy`（要不要问人）各持一条 `IOptionsMonitor`，改配置下个 run 生效、互不影响。`IToolApprover` 契约 fail-closed——超时、断连、无人应答、通道故障一律返回 false；管道侧另有 `ApprovalTimeoutSeconds` 兜底，两侧都往「不放行」倒。
改它：合并成一个接口，就表达不了「允许但每次问」；审批者返回 null 当「没意见」，等于没批准也执行。

**6. 轨迹存截断版，事件带完整版。**
为什么：账本有上界（外部输入长度不可控），但来源面板要用完整命中。`Truncated` 标志必须一起记——没有它，回放时「只看到前 N 字」与「本来就短」看起来一样。进模型的结果按同一上界截断：只截轨迹会把全文留在模型上下文里，上界白设。
改它：把 `return Truncate(text)` 改成 `return text`，内容上界这条能力就没有了（负控已做）。

**7. 拒绝、畸形、异常是三种不同的回填。**
为什么：参数畸形给 `argument_validation_failed`；审批拒绝给 `approval_policy_denied` / `approval_user_denied` / `approval_unavailable`；工具异常记 `ToolCallTrace.Error` 并把异常原样抛回 MEA。三者在轨迹与给模型的文本里都分得开，回放才能归因。
改它：把拒绝当成工具失败，或把异常吞成空结果，「被拒」与「跑坏了」在账本上合二为一。

## 四、配置

| 节 | 键 | 默认 | 含义 |
|---|---|---|---|
| `Harness:ToolExecution` | `MaxResultChars` | 400 | 轨迹里保存的工具结果最大字符数 |
| `Harness:ToolExecution` | `ApprovalTimeoutSeconds` | 120 | `Ask` 的管道侧超时兜底；`<=0` 表示不设上限（仅测试用） |
| `Harness:Tools` | `Whitelist` | 见下 | 工具名白名单；空 = 一个都不放行；只支持精确名与尾部 `*` |
| `Harness:Approval` | `Default` | `Auto` | 未覆盖工具的审批级别；不显式提升就永不打扰用户 |
| `Harness:Approval` | `Overrides` | 空 | 工具名 → `Auto` / `Ask` / `Deny` |
| `Mcp:Servers[]` | `AllowTools` | 空 | 该 server 允许拉进来的工具名；空 = 一个都不放行 |
| `Mcp:Servers[]` | `ExposeToModel` | — | 该 server 的工具能否进模型目录 |
| `Mcp:Servers[]` | `TrustedReadOnly` | 空 | 未声明标注但由我们担保只读的工具名 |

两个容易误读的口径：

1. 白名单**默认非空**（`get_current_time` / `calculator` / `mcp__rag__*` / `list_documents` / `remember` / `recall`）。但为空时是**全关**，不是全开——把配置删空等于关掉全部工具，不等于「都给」。默认必须是「没想清楚就不能全给」的取值。
2. `ToolPolicy` 只支持精确名和尾部 `*`，不支持中间通配、正则、否定式。白名单是安全边界，必须能一眼读完并逐个签字。

## 五、出问题先看哪

| 现象 | 先看 |
|---|---|
| 模型说「我没有这个能力」 | 启动日志 `MCP server X 连上：放行 n/m` 那一行——`AllowTools` 拼错会静默少工具；再看能力画像明细，确认没被 `destructive=true` 挡掉 |
| 工具没执行，轨迹里有拒绝码 | `argument_validation_failed` → 模型给的参数不合 schema；`approval_*` → 审批级别被提升了 |
| 工具执行了但结果被截断 | `ToolCallTrace.Truncated`；完整版在 `ToolCompleted` 事件里，不在轨迹里 |
| 轨迹里没有这一步，界面也不显示 | 是不是清单外的调用——那种只进 `UnknownCalls`，不进 `Traces`（回填在 MEA 内部，到不了 `FunctionInvoker`） |
| 同名工具只剩一个 | `ToolCatalog` 的 `DistinctBy`；MCP 侧还有一条「工具名冲突，已跳过」的 Warning |
| 改了白名单配置没生效 | 两轴各走自己的 `IOptionsMonitor`；确认改的是 `Harness:Tools:Whitelist` 不是 `Harness:Approval` |
| 审批框没弹出来 | `ToolApprovalOptions.Default` 是 `Auto`——必须在 `Overrides` 里显式提升到 `Ask` |
| 审批一直不返回 | 两侧都 fail-closed：`IToolApprover` 的通道 + `ApprovalTimeoutSeconds` 管道兜底；查哪一侧先超时 |

## 六、红线

1. **不重写循环本体**：判据是「这段机制 MEA 有等价物吗？」有 → 用它的；本格只装、只判、只记。
2. **零垂直业务语义**：不出现「采购单」「审批金额档位」这类词。业务判定在动作域，本格只给端口。
3. **未知工具不中止**：保留 MEA 的回填语义，观察层只补一笔；改 `TerminateOnUnknownCalls` 要先重验。
4. **拒绝必须 fail-closed**：无人可问、超时、通道故障一律不放行；审批者不能返回 null 当沉默的默认。
5. **白名单默认空、MCP 默认关**：「没配置」不等于「都允许」。
6. **事件与轨迹双轨不能合并**：轨迹要上界、事件要完整——两者读者不同，合并必丢一头。
7. **加一项工具判定要做三件事**：判定点 → 能落进 `ToolCallTrace` → 有负控证明改它会红。缺第三步，前两步等于没做。

## 七、怎么算验收通过

判定型用例必须**正例能绿、负控能红**；能脚本判定的禁止用 AI 判。验收以 `dotnet test` 实测为准，本文不列测试文件名与条数（会漂）。

**本格已验的**：

- 白名单精确匹配、大小写敏感、空表全关、尾部 `*` 只按前缀、同名去重、多提供方汇总后过滤（S04 的 08–13）
- 清单外工具：不执行、不抛异常、模型能收到回填、整轮结束留痕、流式分片只记一笔（S04 的 03、05–07）
- 工具调用被执行、参数与结果完整进轨迹、结果回填给模型（S04 的 02、14、15）
- 内容上界、畸形参数调用前挡下、工具异常转结果回填不炸整轮（`ToolCallGapTests`，对应 `agent-parts.toml` 三条 capability）

**证据强度打折的地方**：

- S04 的 01–07 用 **Mock 策略**，只验目录与守卫；真实 `ToolPolicy.IsAllowed` 写错它们照样全绿。08–11 才换成真实策略补上这一层——读那几条时别把 01–07 当白名单证据。
- 装配判据使用脚本化模型（`/ScriptedChatClient`），不碰真模型。真模型会不会按剧本调工具、会不会编参数，这组测试答不了。
- `DynamicallyOpenAITool` 等 MEA 扩展点本格**有意不接**，目前只有决定留痕、没有独立负控（见 `agent-parts.toml` 对应注释）。

**还没建立的**：把「能进模型目录的工具」与「策略表里登记过的工具」在装配期强制对齐——现在两处独立，靠人记得一起改；这是直连闸那一层最该补的负控。

**明确不在本文范围的**：业务权限与幂等（动作闸）、工具实现本身（各域 / MCP server）、账本落库与回放（应用层）。

# 附录（要评估框架与选型的人看，改代码不必读）

## A. 框架给了什么 / 没给什么

| 层 | 类型 | 给到什么 | 本仓补什么 |
|---|---|---|---|
| MEA | `FunctionInvokingChatClient` | 工具环本体、结果回填、批次、四个 FICC 选项 | `FunctionInvoker` 里七道判断 |
| MEA | `AIFunctionFactory` / `AIFunction` | 把委托登记成工具、按 schema 绑定参数 | `ValidateArguments` 的拒绝码与回填 |
| MEA | `ChatOptions.Tools` | 工具清单随请求下发 | 目录裁剪与准入 |
| MAF | `ChatClientAgent` | `RunAsync` / `RunStreamingAsync` | 无 |
| MCP SDK | `McpClientTool.ProtocolTool.Annotations` | `ReadOnly` / `Destructive` / `Idempotent` 标注 | 能力画像与默认关的准入（SDK 标注在 `WithName` 后无人可读） |
| 框架 | — | 审批挂起、幂等领取、未知工具留痕、内容上界 | 全部自补 |

**「未知工具」有两本账，不要合并**：模型请求了不存在的名字 → `UnknownCalls`（观察层补记，走不到 `FunctionInvoker`）；工具执行抛异常 → `ToolCallTrace.Error` + `ToolFailures`。两者都叫「失败」，读者不同。

## B. 两轴的出处

「沙箱轴与审批轴分开」参照的是成熟 agent 的分法（Codex 的沙箱策略与审批策略各自独立）：能不能用是**能力边界**，要不要问人是**信任边界**。本格把它落成两个配置节、两个 `IOptionsMonitor`、两个策略类——合并的代价是丢掉「允许但每次问」这个状态。

注意本格只管**要不要问人**；**问谁、依据哪条制度、批完去哪个系统里变成什么**全在动作域。最接近「轮子」的一处是审批挂起：MAF 1.23 有 `ToolApprovalAgent`，但它是进程内同步交互，不带持久化挂起、外部审批人、业务规则与幂等——职责不同，但它是第一个该盯的候选（若 MAF 补上持久化审批，本格的自写三态就该按「有等价物就用它的」处理）。

## C. 与其它五份的边界

① 讲「模型每轮看到什么」（含工具清单挂请求）；② 讲「怎么从一轮走到下一轮」；③ 讲「允许走几轮、什么时候停」（本格提供执行点）；⑤ 讲「跨轮保住什么」；⑥ 讲「走过之后留下什么」（本格产出 `ToolCallTrace`，⑥ 把它写进账本）。

`MaxIterations` 是 ② 与 ③ 共用的数字：② 交给本格，本格经 `ToolExecutionLimits` 落到 FICC，③ 定义它的含义。
