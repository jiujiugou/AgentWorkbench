# 请求装配（Runtime.Context · 六部件之①）

- **适用侧**：底座 ｜ **寿命**：现状（就近维护） ｜ **最后校准**：2026-11-18（当日按统一骨架重写，技术判断未变）

一句话：**把「本轮输入 + 指令」整理成一次模型请求的输入**——消息形态、注入形态、空指令判定在这里收口。
拿掉它，指令会混进对话历史每轮累积、或两级设置被 MAF 拼成两遍——两种错都不会报错，只会让模型看到不该看到的东西。

> 怎么读：第一、二节给要改代码的人（边界与装配路径）；第三节给要判断「这条注入归谁」的人（五个决定）；
> 第四到七节是配置、排障、红线、验收；附录给要评估框架的人。
> 本文只做解释，不是事实源。决定与证据的机器可读登记在仓根 `agent-parts.toml` 的 `request-assembly` 格。

## 一、负责什么 / 不负责什么

判据只有一条：**「模型这一轮实际看到的东西」是不是本格组装的？**

| 事 | 只存在于哪 | 能重建吗 | 归属 |
|---|---|---|---|
| 本轮输入单独成一条 `user` 消息 | `ContextPlan.Messages` | 否 | **本格** |
| 指令的空判定与首尾空白处理 | `Compose` 现算 | 否 | **本格** |
| 指令走 `ChatOptions.Instructions` 而非消息 | `ContextPlan.Instructions` | 否 | **本格** |
| 历史 provider 的转交 | `CreateChatHistoryProvider()` | 否 | **本格（只转交）** |
| 历史从哪来、怎么存、跨 run 记忆 | `ChatHistoryProvider` / `Memory.Persistence` | 是 | ⑤ 状态与记忆 |
| 参考片段的检索 / 内容 / 权限 / 字符预算 | — | — | **尚未建立**（见第七节） |
| 把 `Instructions` 放进 `ChatOptions` | `Harness/BuildAgent` | 是 | 装配动作，属 Harness |
| 每次请求带当前工具清单 | `Harness/BuildAgent` | 是 | ① + ② 交界 |
| 循环本体、回填、工具执行 | MEA / ④ | 是 | ② / ④ |
| 模型怎么调（超时 / 重试 / 用量） | `Runtime.Model` | 是 | 模型层 |
| 跑几轮、跑多久、何时停 | ③ | 否 | ③ 终止与预算 |

**本格管（4 条）**：消息形态、指令形态、注入形态、历史 provider 转交。

一个容易混的点：**本格只产出 `ContextPlan`（数据），不包装 `IChatClient`。** 把数据放进 `ChatOptions` 是 Harness 的装配动作；本格不做，是为了不给工具环外再套一层。

## 二、装配路径

```
HarnessRunRequest(Input, Instructions)
  │
  ├─ ContextComposer.Compose(new ContextRequest(Input, Instructions))
  │     ├─ Input 为空/空白 → 抛 ArgumentException（不静默收口）
  │     ├─ Messages = [ 一条 ChatMessage(User, Input) ]     ← 永远只有一条
  │     └─ Instructions = Options.Enabled && 有内容 ? Trim 后原文 : null
  │
  ├─ Harness.BuildAgent(execution.Client, plan.Instructions)
  │     └─ ChatClientAgentOptions.ChatOptions.Instructions = plan.Instructions  ← 只设这一次
  │
  └─ 历史由 MAF 的 ChatHistoryProvider 追加（不进 ContextPlan）
        ├─ 内存版：框架自带
        └─ 落库版：Memory.Persistence 用 Replace 覆盖
```

`ContextPlan.Messages` 永远只有一条——历史不在 plan 里。这是 2026-11-14 重构后的形状：历史交给 `ChatHistoryProvider`，本类不包装任何 `IChatClient`。

## 三、五个决定

**1. 本轮输入永远单独成一条 `user` 消息。**
为什么：历史由 `ChatHistoryProvider` 追加；揉成拼接文本后，回放与轨迹里分不清「模型看到的上一轮」和「用户这次说的话」。
改它：把历史拼进 Input，S03 那条 `Assert.Single(messages)` 会红——那不是形式主义，是在守「这一轮的话」的边界。

**2. 指令为空或全空白返回 `null`，不返回空串。**
为什么：`ChatOptions.Instructions` 收到空串等于「注入了一条空指令」，和「没有指令」在模型眼里不是一回事；`null` 才是「不注入」。
改它：把 `IsNullOrWhiteSpace` 去掉，用户输一串空格就往每轮请求塞空白指令。

**3. 注入走 `ChatOptions.Instructions`，不挂 `AIContextProviders`。**
为什么：MAF 每轮随请求下发 Instructions，且不进 `ChatHistoryProvider` 记录的历史。挂 context provider 会让 MEA 在 `FunctionInvokingChatClient` 外面再包一层，绕过 `ToolExecutionPipeline` 的守卫与轨迹——实测同参重复调用不再判 `loop_detected`，工具异常不再归类 `tool_error`。结构门禁 `F38` 钉住「代码里不出现 `AIContextProviders`」。
改它：先过 F38，再证明换装法后守卫与轨迹仍生效。

**4. 指令只设一次：agent 级，run 级不带。**
为什么：MAF 合并 agent 级 / run 级 `ChatOptions` 时，两级 `Instructions` 是**换行拼接**而非覆盖；两处都设，同一句会重复进每轮请求（实测 `A\nA`）。run 级 options 只带温度。
改它：在 run 级再加一次 Instructions，`生产装配形状_run级带 Temperature 时指令不丢也不重复` 会红。

**5. 历史 provider 只转交，不决定存哪。**
为什么：`CreateChatHistoryProvider()` 把 DI 注入的 provider 交给 Agent；内存版是框架默认，落库版由 `Memory.Persistence` 用 `Replace` 覆盖。本格写死实现，⑤ 就换不掉了。
改它：在这里 new 一个具体 provider，落库那条臂立刻失效。

## 四、配置（`Harness:Context`）

| 键 | 默认 | 含义 |
|---|---|---|
| `Enabled` | true | 是否启用请求装配；关闭后 `ContextPlan.Instructions` 恒为 `null` |

只有一个键。历史条数归 MAF 的 `ChatHistoryProvider`（框架无统一条数开关）；片段字符预算要等片段注入真正接进 run 时再加——现在加就是死配置。

## 五、出问题先看哪

| 现象 | 先看 |
|---|---|
| 每轮请求里指令重复两遍 | 是不是 agent 级和 run 级都设了 `Instructions`（决定 4）；F38 只钉「设一次」的位置 |
| 指令混进了对话历史 | 是不是把 Instructions 塞进了 `run.Messages` 或 `ChatHistoryProvider` |
| 守卫与轨迹突然失效（`loop_detected` / `tool_error` 不再判） | 有没有挂 `AIContextProviders`、或包了第二层 `IChatClient`（决定 3） |
| 用户输空格也注入了一条指令 | `Compose` 里 `IsNullOrWhiteSpace` 是不是被去掉了 |
| 历史查不到 / 串会话 | provider 是不是落库版；`StateBag` 里的 `sessionId` 对不对（属 ⑤） |
| 想加片段注入却发现没字段 | `HarnessRunRequest` 与 `ContextRequest` 都没有 `Fragments`——这条路完全不存在（见第七节） |

## 六、红线

1. **不重写框架已有的东西**：`ChatHistoryProvider`、`ChatOptions`、工具清单都是框架的，动手前先问能不能配出来。
2. **零垂直业务语义**：不出现合同、工业、仓储、单证这类词（AC-02，F37 源码门禁）。
3. **职责单向**：只依赖 `Shared` 与 MAF/MEA 抽象，不认识 Harness 流水线、工具/模型实现；本格只产出 `ContextPlan`，不包装 `IChatClient`。
4. **注入形态只有一条**：指令走 `ChatOptions.Instructions`，**不挂** `AIContextProviders`、不自写装饰器——后者会绕过守卫与轨迹（F38 是源码门禁）。
5. **指令不进历史**：注入的是模型请求选项，不是 `run.Messages` / 会话历史。
6. **指令只设一次**：见决定 4；run 级 options 再带一份会重复。
7. **加一项上下文能力要做三件事**：配置键 → 判定 / 预算 → 能证明「模型这一轮实际收到了什么」。缺第三步，前两步等于没做。

## 七、怎么算验收通过

判定型用例必须**正例能绿、负控能红**；能脚本判定的禁止用 AI 判。验收以 `dotnet test` 实测为准，本文不列测试文件名与条数（会漂）。

**已有证据**：指令每轮进请求且不进历史；本轮输入独立成一条 `user`；工具往返完整留在历史；不另包函数环；run 级 options 只带温度时指令不丢也不重复；停用与空指令零注入。对应 `agent-parts.toml` 的 `maf-injection-equivalence` 与 `instruction-assigned-once`。

**证据打折的地方**：`maf-injection-equivalence` 的 6 条都跑在独立最小装配上，没走 `AgentHarnessService.BuildAgent`；真实 `ToolExecutionPipeline` 下 ③ `loop_detected` / ④ `tool_error` + 轨迹仍只有单测证据。

**还没建立的**：

- **参考片段注入**：`HarnessRunRequest` 没有 `Fragments` 字段，`ContextRequest` 也没有——片段进模型这条路**完全不存在**，不是「有预算但没接线」。建立时三件事：调用方给片段 → 字符预算 → 端到端可红断言。
- **「模型这一轮实际收到了什么」缺独立可回放证据**：现只有 `ChatOptions.Instructions` 与落库历史两份局部快照，没有一次请求的全量快照。
- **端到端负控**：见上「证据打折」。

**明确不在本文范围的**：历史存储与跨 run 记忆（⑤）、循环与工具执行（② / ④）、模型调用方式（模型层）。

# 附录（要评估框架与选型的人看，改代码不必读）

## A. 框架给了什么

| 需求 | MAF / MEA 有等价物吗 | 本仓怎么做 |
|---|---|---|
| 指令下发 | `ChatOptions.Instructions`，每轮随请求下发、不进历史 | 直接用，只设一次 |
| 多轮历史 | `ChatHistoryProvider` / `InMemoryChatHistoryProvider` | 转交 DI provider；落库版由 ⑤ 覆盖 |
| 历史压缩 | `CompactionProvider` + 六策略 | **不能用**：`AIContextProvider` 子类，撞 F38（见 ⑤ 附录 C） |
| 自动记忆召回 | `ChatHistoryMemoryProvider` | **不能用**：同上 |
| 自定义注入 | `AIContextProviders` | **不用**：会在工具环外包第二层，绕过守卫与轨迹 |
| 片段字符预算 | 无 | 未建立（见第七节） |

## B. 与其它五份的边界

② 讲「怎么从一轮走到下一轮」；③ 讲「允许走几轮、什么时候停」；④ 讲「一轮里的工具怎么执行」；⑤ 讲「跨轮保住什么」；⑥ 讲「走过之后留下什么」。本格只回答「这一轮模型看到什么」。

工具清单是本格与 ② 的交界：`BuildAgent` 把 `_tools.GetTools()`（④ 的目录过滤结果）放进 `ChatOptions.Tools`——清单内容归 ④，挂到请求这个动作归 Harness。
