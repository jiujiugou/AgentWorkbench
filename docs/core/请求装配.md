## 1. 这一格要解决什么问题

指令写在对话消息里，就会变成历史的一部分。框架每轮请求都把历史带上，于是一句「你是客服」在第三轮请求里出现三遍——不是模型记性好，是我们把同一句话塞了三次。

另一种错更隐蔽。框架合并 agent 级与 run 级请求选项时，`Instructions` 是换行拼接而不是覆盖。两处都写同一句，模型收到的不是一句，是 `A\nA`。

两种错都不抛异常。从返回值看，模型正常工作；从账本看，也没有哪一笔能说明模型这一轮究竟看到了什么。本格存在的理由就是：**让「模型这一轮实际看到的东西」成为一件由我们组装、能说清楚的事**——本轮的话以什么形态进请求，指令以什么值进请求，指令走哪条路进请求。

边界也随之定下来。本格只回答这一轮看到什么：上一轮留下什么归 ⑤，怎么走到下一轮归 ②，这一轮工具怎么执行归 ④，模型怎么调归模型层。但要管住「这一轮」，得先看一次装配实际经过哪些点。

## 2. 整体模型：一次装配经过哪些点

一次 run 的上下文只装配一遍。本轮输入整理成一条消息，指令定好形态交给 BuildAgent；之后历史由 provider 追加，本格不再介入。

```text
一次 run 的输入（Input / Instructions）
  │
  ├─ 装配请求
  │     ├─ Input 为空/空白 → 抛 ArgumentException（不静默收口）
  │     ├─ 消息 = [ 一条 user 消息 ]     ← 永远只有一条
  │     └─ 指令 = 启用 && 有内容 ? Trim 后原文 : null
  │
  ├─ BuildAgent(client, instructions)
  │     └─ agent 级请求选项里的指令只设这一次
  │
  └─ 历史由 ChatHistoryProvider 追加（不进装配产物）
        ├─ 内存版：框架自带
        └─ 落库版：⑤ 用 Replace 覆盖
```

图里每个分支都是一项判定权：消息只能有一条，指令的取值只有「原文」和「null」两种，指令经 BuildAgent 进 agent 级选项。三处分工也各自有主——消息与指令形态由本格判，把这些值放进请求选项是 Harness 的装配动作，历史的存取由 provider 负责。本格只产出数据，不包装 `IChatClient`；包装一层就会在工具环外多一层，④ 的守卫和轨迹都会被绕开。

这些判定要成立，还得靠别的部件把东西送到手上：

| 依赖 | 提供什么 | 断了谁兜着 |
|---|---|---|
| DI 注入的历史 provider | 追加、读取历史，把历史挡在装配产物之外 | 缺省退回框架的内存版；落库版由 ⑤ 用 `Replace` 覆盖 |
| Harness 的装配动作 | 把装配产物放进 agent 级请求选项 | 本格只产出数据；没人放，指令不进请求，模型看不到 |
| ③ 的能力位 | 指令是否注入 | 缺省启用；关掉后产物指令恒为 `null`，能力位同步为关 |

图上每一处都已经写成了"应该怎么做"，但为什么不能换一种做法，得逐条说清——否则下次有人改回去，看不出坏在哪。

## 3. 为什么这么定

### 3.1 消息为什么只有一条

历史由 provider 追加，不进装配产物。把历史与本轮输入揉成拼接文本后，回放与轨迹里就分不清「模型看到的上一轮」和「用户这次说的话」——两者在账本上变成同一段字，事后没法还原。所以装配产物里的消息列表永远只有一条，本格也不预留片段字段：没有接通的路，先留字段只会让人以为它能用。

### 3.2 指令为什么是 null，不是空串

请求选项的 `Instructions` 收到空串，等于注入了一条空指令；在模型眼里这和「没有指令」不是一回事。空串会让模型以为有人交代了什么却没说清，`null` 才是「这次不注入」。所以停用、输入为空、全空白三种情形都收口成 `null`——这也是第 4 节那个开关能成为安全边界的前提。

### 3.3 指令走哪条路，设几次

指令走 `ChatOptions.Instructions`，不挂 `AIContextProviders`。框架每轮随请求下发指令，且不进 provider 记录的历史。挂 context provider 会在工具环外包第二层，绕过 ④ 的守卫与轨迹——实测同参重复调用不再判 `loop_detected`，工具异常不再归类 `tool_error`。结构门禁钉住「代码里不出现 `AIContextProviders`」。

选对路还不够，得保证只走一次。框架合并两级请求选项时，`Instructions` 是换行拼接而非覆盖；agent 级和 run 级都写，同一句就重复进每轮请求（实测 `A\nA`）。所以指令只在 agent 级设一次，run 级只带温度。

### 3.4 框架给了一半，另一半明确不用

指令下发与多轮历史框架都有等价物，本格只做「整理成一条消息 + 决定指令形态」，不自建历史队列。历史压缩与自动记忆召回虽然现成，但都是 `AIContextProvider` 子类——接进来就等于换条路做自定义注入，撞上 3.3 那条门禁。不用它们不是因为多余，是因为那条路会拆掉执行控制。

这四条判定都要求同一种状态：指令要么完整注入，要么彻底没有，中间没有模糊地带。落到一个开关上，它就不是性能旋钮，而是安全边界。

## 4. 配置：唯一的开关

### 4.1 关状态是可验证的

实际键名与默认值不抄在这里——值以代码与宿主配置为准，登记位置在 `documents/context.toml` 的 evidence 段。本格只有一个开关：关掉后装配产物里的指令恒为 `null`，能力位同步为关——「一条指令都不注入」是可验证的状态，不靠调用方自觉。

另外两个看似该设的开关，都不该归本格。历史条数由框架的 provider 保管，框架没有统一条数开关；本格再设一个，同一件事就有了两个口径。片段预算现在也不加——片段注入还没接进 run，此时加预算就是死配置，要等片段真正进模型时和片段一起加。

配置和行为都定了，但失败时怎么处理还没说——本格的失败全发生在请求发出之前。

## 5. 失败与恢复语义

本格没有环内失败出口；所有失败都在「请求发出之前」暴露，或干脆不报错地收口成 `null`：

| 形态 | 记在哪 | 回填什么 | 谁能继续 |
|---|---|---|---|
| 本轮输入为空 / 全空白 | 装配异常（无轨迹） | 不装配、不请求 | 调用方修输入重试 |
| 指令为空 / 全空白 | 装配产物（指令字段 `null`） | 不注入，不报错 | 模型按无指令继续 |
| 开关关闭 | 装配产物（指令恒 `null`，能力位同步关） | 不注入 | 同上 |
| 历史 provider 缺失 / 被替换 | 框架默认 provider / ⑤ 的 `Replace` | 本轮照常请求 | 跨 run 记忆的缺口归 ⑤ |

前三种对应第 3 节的三项判定：输入形态、指令取值、注入开关。输入为空要抛异常而不是静默收口，是因为「用户这轮什么都没说」和「系统替用户补了话」在账本上没法区分。指令为空和开关关闭都收口成 `null`，模型照常继续——这正是不报错的「关」状态。片段的失败语义还不存在，那条路没接通。

这些边界凭什么算成立？下一节把每条变成可验的契约。

## 6. 契约验收：从边界推导

本节不是测试清单，是 §1–§5 每条边界的验收推导。判定型用例必须正例能绿、负控能红；能脚本判定的禁止用 AI 判。用例名、变异点与强度细节在 `contracts/context.toml`，本文只留结论。

| 契约 / 小节 | 从哪条边界推导 | 结论 |
|---|---|---|
| `CONTEXT-SHAPE-001`（第 3.1 节） | 本轮输入独立成一条 `user` | 有判据：最小装配，含绿对照 |
| `CONTEXT-SWITCH-001`（第 3.2 / 4 节） | 停用与空指令零注入，能力位同步 | 有判据：最小装配 + 能力位 |
| `CONTEXT-INJECT-001`（第 3.2 / 3.3 节） | 指令每轮进请求、不进历史；两级不重复 | 有判据：最小装配 + 结构门禁两路 |
| `CONTEXT-NOWRAP-001`（第 3.3 节） | 不挂 provider、不包客户端，守卫与轨迹不绕开 | 结构判据：代码行扫描，钉住三个旧形态 |
| `CONTEXT-SNAPSHOT-001`（第 7.1 节） | 模型实际收到的输入可独立回放 | **无判据**：只有请求选项与落库历史两份局部快照 |

证据强度有四处打折，别把「有判据」读成「完全证明」：

- 注入等价判据都跑在独立最小装配上，没走真实装配入口；真实工具环下 ③ 的重复判定、④ 的异常归类仍只有单测证据。
- 「模型这一轮实际收到了什么」缺独立可回放证据——就是上表最后一行，没有一次请求的全量快照。
- 端到端负控还没建立，上面的「可信」只到最小装配这一层。
- 参考片段这条路完全没接通，谈不上验收，单独登记为缺口。

验得出的部分已经验了，剩下的是未定的决定和未关闭的缺口。

## 7. 未决问题

### 7.1 回放证据的缺口

**要不要补一份一次请求的全量快照？** 现在只能从请求选项和落库历史两头拼，拼不出「模型实际收到什么」——`CONTEXT-SNAPSHOT-001` 的 gap 尚未关闭。

### 7.2 其余未决

1. **参考片段注入要不要现在建立？** 装配输入没有片段字段，片段进模型这条路完全不存在，不是「有预算没接线」。建立时要一起定三件事：调用方给片段、字符预算、端到端可红断言。
2. **端到端负控放在哪一层？** 最小装配上的判据已经够用，但真实工具环下 ③ / ④ 的判定仍只有单测。

## 8. 与其他五个部件

本格只回答「这一轮模型看到什么」：② 讲怎么走到下一轮，③ 讲何时停，④ 讲工具怎么执行，⑤ 讲跨轮保住什么，⑥ 讲留下什么。

工具清单是本格与 ② 的交界：清单内容归 ④（按白名单裁剪的结果），把清单挂到请求这个动作归 Harness。本格拥有的是「指令形态 + 消息形态」的判定权，不拥有清单内容，也不拥有循环。
