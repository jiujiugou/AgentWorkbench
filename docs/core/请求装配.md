# 请求装配（Runtime.Context · 六部件之① 请求装配）

- **适用侧**：底座 ｜ **寿命**：现状（就近维护） ｜ **最后校准**：2026-11-13

这个部件只干一件事：**把「本轮输入 + 指令」整理成一次模型请求的输入**——消息形态、注入形态、空指令判定在这里收口。
它不拥有上下文：历史从哪来、参考片段内容对不对、工具环怎么转，都不归它；循环本体在框架里（MEA 的 `FunctionInvokingChatClient`），底座不重写。

**装法**：指令走 MAF 的 `ChatOptions.Instructions`，历史走 `ChatHistoryProvider`，消息用 `ChatMessage` 直接承载。
本仓没有自写 `IChatClient` 装饰器，也没有片段预算——片段注入尚未接进真实 run，见第六节。

## 一、职责五项

| # | 职责 | 说明 |
|---|---|---|
| 1 | **消息形态** | 本轮输入永远单独成一条 `user` 消息；历史由 MAF 的 `ChatHistoryProvider` 追加，不与本轮输入揉成拼接文本——揉了之后回放与轨迹里分不清「模型看到的上一轮」和「用户这次说的话」 |
| 2 | **指令形态** | 指令为空或全空白时返回 `null`；有内容时压掉首尾空白后产出。不做片段合成（片段未接），也不把指令混进消息 |
| 3 | **注入形态** | 产出物交给 MAF 原生的 `ChatOptions.Instructions`：每轮随模型请求下发，且不进 `ChatHistoryProvider` 记录的历史。不自写装饰器，不挂 `AIContextProviders` |
| 4 | **停用与空包** | `Enabled = false` 或没有指令时，`ContextPlan.Instructions` 为 `null`——不往 `ChatOptions` 里塞空串，也不空包一层客户端 |
| 5 | **历史 provider 转交** | `CreateChatHistoryProvider()` 只把 DI 注入的 provider 交给 Agent；不决定存哪（默认内存版，落库版由 `Memory.Persistence` 用 `Replace` 覆盖） |

## 二、不归本格

- 历史从哪来、怎么存、跨 run 记忆 → **⑤ 状态与持久化**（`Runtime.Session` 契约 + `Memory.Persistence` 实现）；本格只转交 provider
- **参考片段的检索、内容、权限过滤、字符预算** → 尚未建立；建立时由调用方给片段，预算落在本格（见第六节）
- 循环本体、回填、批次 → **② 框架**（装配在 `Runtime.Harness`，内核在 `Runtime.Tools` 被 new 出来）
- 单次调用怎么执行、参数绑定、结果回填 → **④ 工具执行**
- 模型怎么调（超时 / 重试 / 用量） → `Runtime.Model`
- 允许循环几次、跑多久、什么时候必须停 → **③ 终止与预算**
- 审批、白名单、幂等 → 边界外的判定内容（「该不该做」，不是「该看到什么」）
- 把 `Instructions` 放进 `ChatOptions` → 装配动作，在 `Runtime.Harness/BuildAgent`；本格只产出数据
- 每次请求带上当前工具清单 → ① + ② 的交界，清单由 `Runtime.Harness/BuildAgent` 组装

## 三、三处分工（组装 / 装配 / 注入点）

| 处 | 位置 | 干什么 |
|---|---|---|
| 组装与判定 | `Runtime.Context`（纯类，只引 `Shared` 与 MAF/MEA 抽象，不读库、不检索） | `IRequestContextComposer` 两口：`Compose` → `ContextPlan(Messages / Instructions)`；`CreateChatHistoryProvider` 转交 DI provider |
| 装配与传递 | `Runtime.Harness` | `PrepareRunAsync` 调 `Compose(new ContextRequest(Input, Instructions))`；`BuildAgent` 把 `plan.Instructions` 放进 `ChatClientAgentOptions.ChatOptions`，并挂 `CreateChatHistoryProvider()` |
| 请求注入点 | MAF 框架 `ChatOptions.Instructions` | 由 `AgentHarnessService.BuildAgent` 设置**一次**；MAF 每轮随请求下发。run 级 options 只带 `Temperature`，不得再带 `Instructions` |

最后一行是硬约束：MAF 合并 agent 级 / run 级 `ChatOptions` 时，两级 `Instructions` 是**换行拼接**而非覆盖；
两处都设会让同一句指令重复进每轮请求（实测 `A\nA`，见 `Runtime/请求装配.cs` 的生产装配形状判据）。
结构门禁 `F38` 把「只设一次」钉住。

## 四、配置（`Harness:Context`）

| 键 | 默认 | 含义 |
|---|---|---|
| `Enabled` | true | 是否启用请求装配；关闭后 `ContextPlan.Instructions` 恒为 `null` |

只有一个键。历史条数归 MAF 的 `ChatHistoryProvider`（框架无统一条数开关）；片段字符预算要等片段注入
真正接进 run 时再加——现在加就是死配置。

## 五、红线

1. **不重写框架已有的东西**：`ChatHistoryProvider`、`ChatOptions`、工具清单都是框架的，动手前先问能不能配出来。
2. **零垂直业务语义**：不出现合同、工业、仓储、单证这类词（AC-02，`F37` 源码门禁）。
3. **职责单向**：只依赖 `Shared` 与 MAF/MEA 抽象，不认识 Harness 流水线、工具 / 模型实现；本格只产出 `ContextPlan`，不包装 `IChatClient`。
4. **注入形态只有一条**：指令走 `ChatOptions.Instructions`，**不挂** `AIContextProviders`、不自写装饰器——后者会让 MEA 在 `FunctionInvokingChatClient` 外面再包一层函数调用环，`ToolExecutionPipeline` 的守卫与轨迹被绕过（实测：同参重复调用不再判 `loop_detected`，工具异常不再归类 `tool_error`）。`F38` 是源码门禁。
5. **指令不进历史**：注入的是模型请求选项而不是 `run.Messages` / 会话历史；`ChatHistoryProvider` 只按输入消息记录。
6. **指令只设一次**：见第三节；run 级 options 再带一份会重复。
7. **加一项上下文能力要做三件事**：配置键 → 判定 / 预算 → 能证明「模型这一轮实际收到了什么」。缺第三步，前两步等于没做。

## 六、怎么算验收通过

判定型用例必须**正例能绿、负控能红**；能脚本判定的禁止用 AI 判。验收以 `dotnet test` 实测为准，本文不列测试文件名与条数（会漂）。

已闭合的：指令每轮进请求且不进历史、本轮输入独立成一条 `user`、工具往返完整留在历史、
`UseProvidedChatClientAsIs` 不另包函数环、run 级 options 只带 `Temperature` 时指令不丢也不重复、
停用与空指令零注入——对应仓根 `agent-parts.toml` 的 `maf-injection-equivalence` 与 `instruction-assigned-once`。

还没建立的：

- **参考片段注入**：`HarnessRunRequest` 没有 `Fragments` 字段，`ContextRequest` 也没有——片段进模型
  这条路**完全不存在**，不是「有预算但没接线」。建立时要做三件事：调用方给片段 → 字符预算 → 端到端可红断言。
- **「模型这一轮实际收到了什么」缺独立可回放证据**：现只有 `ChatOptions.Instructions` 与落库历史两份
  局部快照，没有一次请求的全量快照（通用判据见 `Agent部件全景与查漏清单.md` §一.2）。
- **端到端负控**：`maf-injection-equivalence` 的 6 条都跑在独立最小装配上，没走 `AgentHarnessService.BuildAgent`；
  真实 `ToolExecutionPipeline` 下 ③ `loop_detected` / ④ `tool_error`+轨迹 仍只有单测证据。

当前已登记的决定、证据与状态在仓根 `agent-parts.toml` 的 `[[part]] request-assembly`，本文不复制。
