# 请求装配（Runtime.Context · 六部件之①）

- **适用侧**：底座 ｜ **寿命**：现状（就近维护） ｜ **最后校准**：2026-11-23

> **类型**：Architecture（解释型）。本文解释「一轮模型请求的输入是怎么被组装的、哪些判定只能由本格做」，不是事实源、不是参考手册。
> **范围**：边界归属、装配路径与控制流理由、设计取舍、失败语义、验收判断、未决问题。
> **非范围**：历史存储与跨 run 记忆（⑤）、循环与工具执行（② / ④）、模型调用方式（模型层）。
> **可枚举部分不写在这里**：文件/符号定位、配置实际值、测试规模都在 `docs/kb/documents/context.toml` 的 `evidence` / `fact` 段，由 `scripts/kb_check.py` 对账；本文只写机器判不了的判断。

一句话：**把「本轮输入 + 指令」整理成一次模型请求的输入**——消息形态、注入形态、空指令判定在这里收口。
拿掉它，指令会混进对话历史每轮累积、或两级设置被框架拼成两遍——两种错都不会报错，只会让模型看到不该看到的东西。

## 一、负责什么 / 不负责什么

判据只有一条：**「模型这一轮实际看到的东西」是不是本格组装的？**

| 事 | 归属 |
|---|---|
| 本轮输入单独成一条 `user` 消息 | **本格**（只存在于装配产物里，别处重建不出来） |
| 指令的空判定与首尾空白处理 | **本格**（每次现算，不留副本） |
| 指令走请求选项而非消息 | **本格** |
| 历史 provider 的转交 | **本格（只转交，不决定存哪）** |
| 历史从哪来、怎么存、跨 run 记忆 | ⑤ 状态与记忆 |
| 参考片段的检索 / 内容 / 权限 / 字符预算 | 尚未建立（见第七节） |
| 把指令放进请求选项 | 装配动作（Harness） |
| 每次请求带当前工具清单 | ① + ② 交界 |
| 循环本体、回填、工具执行 | ② / ④ |
| 模型怎么调（超时 / 重试 / 用量） | 模型层 |
| 跑几轮、跑多久、何时停 | ③ 终止与预算 |

本格管四件事：消息形态、指令形态、注入形态、历史 provider 转交。

依赖断了谁兜着：

| 依赖 | 提供什么 | 断了谁兜着 |
|---|---|---|
| DI 注入的历史 provider | 追加、读取历史，把历史挡在装配产物之外 | 缺省退回框架的内存版；落库版由 ⑤ 用 `Replace` 覆盖 |
| Harness 的装配动作 | 把装配产物放进 agent 级请求选项 | 本格只产出数据；没人放，指令不进请求，模型看不到 |
| ③ 的能力位 | 指令是否注入 | 缺省启用；关掉后产物指令恒为 `null`，能力位同步为关 |

## 二、机制形状

一次 run 的上下文只装配一遍，之后历史由 provider 追加，本格不再介入。

```
一次 run 的输入（Input / Instructions）
  │
  ├─ 装配请求
  │     ├─ Input 为空/空白 → 抛 ArgumentException（不静默收口）
  │     ├─ 消息 = [ 一条 user 消息 ]     ← 永远只有一条
  │     └─ 指令 = 启用 && 有内容 ? Trim 后原文 : null
  │
  ├─ BuildAgent(client, instructions)
  │     └─ agent 级请求选项里的指令只设这一次
  │
  └─ 历史由 ChatHistoryProvider 追加（不进装配产物）
        ├─ 内存版：框架自带
        └─ 落库版：⑤ 用 Replace 覆盖
```

装配产物里的消息列表永远只有一条——历史不在其中。历史交给 `ChatHistoryProvider`，本格不包装客户端，也不预留片段字段。

## 三、为什么这么定

**本轮输入永远单独成一条 `user` 消息。** 历史由 provider 追加；揉成拼接文本后，回放与轨迹里分不清「模型看到的上一轮」和「用户这次说的话」。

**指令为空或全空白返回 `null`，不返回空串。** 请求选项的 `Instructions` 收到空串等于注入了一条空指令，和「没有指令」在模型眼里不是一回事；`null` 才是「不注入」。

**注入走 `ChatOptions.Instructions`，不挂 `AIContextProviders`。** 框架每轮随请求下发指令，且不进 `ChatHistoryProvider` 记录的历史。挂 context provider 会让工具环外包第二层，绕过 ④ 的守卫与轨迹——实测同参重复调用不再判 `loop_detected`，工具异常不再归类 `tool_error`。结构门禁 F38 钉住「代码里不出现 `AIContextProviders`」。

**指令只设一次：agent 级，run 级不带。** 框架合并两级请求选项时，两级的 `Instructions` 是**换行拼接**而非覆盖；两处都设，同一句会重复进每轮请求（实测 `A\nA`）。run 级选项只带温度。

**历史 provider 只转交，不决定存哪。** 本格把注入的 provider 交给 Agent；内存版是框架默认，落库版由 ⑤ 用 `Replace` 覆盖。本格写死实现，⑤ 就换不掉了。同样，本格只产出装配结果（数据），不包装 `IChatClient`——把数据放进请求选项是 Harness 的装配动作，本格不做，是为了不给工具环外再套一层。

**框架给的部分不重写，但两类现成能力明确不用。** 指令下发与多轮历史都有等价物（前者每轮随请求下发、不进历史，后者由 `ChatHistoryProvider` 追加），所以本格只做「整理成一条消息 + 决定指令形态」，不自建历史队列。历史压缩与自动记忆召回虽然现成，但都是 `AIContextProvider` 子类——接进来就等于换条路做自定义注入，会撞 F38，因此不用，不是多余。

## 四、配置口径

实际键名与默认值不抄在这里——值以代码与宿主配置为准，登记位置在 `docs/kb/documents/context.toml` 的 evidence 段。

- **只有一个开关，缺省启用。** 它不是性能开关，是安全边界：关掉后装配产物里的指令恒为 `null`，能力位同步为关——「一条指令都不注入」是可验证的状态，不靠调用方自觉。
- **历史条数不归本格。** 历史由框架的 provider 保管，框架没有统一条数开关；本格不另设一个，否则同一件事两个口径。
- **片段预算现在不加。** 片段注入还没接进 run，此时加预算就是死配置；要等片段真正进模型时，和片段一起加。

## 五、失败与恢复语义

本格的失败一律在「请求发出之前」暴露，没有环内失败出口。

| 形态 | 记在哪 | 回填什么 | 谁能继续 |
|---|---|---|---|
| 本轮输入为空 / 全空白 | 装配异常（无轨迹） | 不装配、不请求 | 调用方修输入重试 |
| 指令为空 / 全空白 | 装配产物（指令字段 `null`） | 不注入，不报错 | 模型按无指令继续 |
| 开关关闭 | 装配产物（指令恒 `null`，能力位同步关） | 不注入 | 同上 |
| 历史 provider 缺失 / 被替换 | 框架默认 provider / ⑤ 的 `Replace` | 本轮照常请求 | 跨 run 记忆的缺口归 ⑤ |

片段的失败语义还不存在——这条路没接通，谈不上失败。

## 六、怎么算验收通过

判定型用例必须**正例能绿、负控能红**；能脚本判定的禁止用 AI 判。验收以 `dotnet test` 实测为准。

| 主张 | 守它的那一组 | 强度 |
|---|---|---|
| 指令每轮进请求且不进历史 | 注入等价判据 | 独立最小装配，可信 |
| 本轮输入独立成一条 `user` | 装配产物形态判据 | 独立最小装配，可信 |
| 工具往返完整留在历史、不另包函数环 | 结构门禁 F38 | 代码行扫描，可信 |
| run 级只带温度时指令不丢也不重复 | 注入等价判据 | 独立最小装配，可信 |
| 停用与空指令零注入 | 注入等价判据 + 能力位 | 独立最小装配，可信 |

**证据强度打折的地方：**

- 这组注入等价判据都跑在独立最小装配上，没走真实的装配入口；真实工具执行管道下 ③ 的重复调用判定、④ 的工具异常归类与轨迹仍只有单测证据。
- 「模型这一轮实际收到了什么」缺独立可回放证据：现只有请求选项与落库历史两份局部快照，没有一次请求的全量快照。
- 端到端负控还没建立，上面的「可信」只到最小装配这一层。

## 七、未决问题

1. **参考片段注入要不要现在建立？** 装配输入没有片段字段，片段进模型这条路完全不存在，不是「有预算没接线」。建立时要一起定三件事：调用方给片段、字符预算、端到端可红断言。
2. **要不要补一份一次请求的全量快照？** 现在只能从请求选项和落库历史两头拼，拼不出「模型实际收到什么」。
3. **端到端负控放在哪一层？** 最小装配上的判据已经够用，但真实工具环下 ③ / ④ 的判定仍只有单测。

## 八、与其他五个部件

② 讲「怎么从一轮走到下一轮」；③ 讲「允许走几轮、什么时候停」；④ 讲「一轮里的工具怎么执行」；⑤ 讲「跨轮保住什么」；⑥ 讲「走过之后留下什么」。本格只回答「这一轮模型看到什么」。

工具清单是本格与 ② 的交界：清单内容归 ④（按白名单裁剪的结果），把清单挂到请求这个动作归 Harness。
