## 一、为什么需要评测，以及它不会带来什么

仓里现有两百多条全是**测试**：确定性断言，红或绿，回答「改坏了没有」。**评测**是另一件事：一组场景跑出来，
用于比较（改前 vs 改后、脚本化模型 vs 真模型、换框架版本前后），回答「给定场景下守不守得住」。两者不能互相替代。

但要先把期待压准，否则第一份评测就会退化成「绿灯自证换个地方重演」：

- 六部件机制层已经收口，`agent-parts.toml` 六格全进表，CoreTests 99/99 且有负控实证。**逐格再造一条评测场景，
  评出来的多半是同一批断言的第二次执行**，信息量接近零。
- v3 §3 明写「功能数量、测试覆盖率、绿灯数量、文档篇数一律不是成功标准」。所以通过线不能是分数、不能是覆盖率。
- 评测也不证明「有没有人要」。v3 §3 的反馈源那句如实挂着，评测堵不住它。

评测比测试多出来的那一块，在第七节：**真 DI 全量装配下的一次完整 run，从没跑过。**

## 二、判据从哪来（不是拍脑袋列清单）

三个来源，按优先级：

1. **v3 §2 方向判据 ②**：任一动作能答「谁让做的、什么时候、看到了什么、依据哪条规则、ERP 里变成了什么」。
   这是「事后能不能重建」的原始要求，也是本文把 `ExecutionTrace` 定为主要评测对象的理由。
2. **v3 §2 方向判据 ③**：「拿掉模型，系统还能安全地拒绝」。它决定了题目必须以**诱导性负例**为主——
   安全性不该依赖模型行为，所以要把模型往坏处推，看系统挡不挡得住。
3. **v3 §3 六句**：2 / 3 / 4 / 5 四句都是「不该发生的事没发生」（零外部调用、不重复建单、不重放、字段齐全）。
   正例（能建单）只要链路通了基本就过，**先建正例集评不出差别**。

一个反向来源同样重要：v3 §3「不证明什么」里列了「不证明模型 tool calling 稳定」「不证明平台化成立」。
所以**模型完成度类指标（pass@1、成功率、rubric 分数）不进第一版评测**。这条结论上一轮已冻结，别顺 `numRepetitions` 走回去。

`agent-parts.toml` 的六格 capability 是「机制已证」的登记，用来**定位**某条场景该读哪个模块、哪份测试，
不是「每格造一条」。把 capability 数当覆盖率目标，正好撞 v3 明令不做的那件事。

## 三、评哪一层事实：三层，主评中间那层

一次 run 结束后，事实分三处。MAF 的 `EvalItem` 形状是「query → response 文本 + conversation + tools」，
只认得最上面一层。

| 层 | 事实载体 | MAF 能直接读吗 | 是否内核评测对象 | 理由 |
| --- | --- | --- | --- | --- |
| **L1 对话层** | `AgentResponse` / `conversation` | 能 | **辅** | 工具调用序列、参数、终态文本、指令是否进了历史。CoreTests 已钉住，再评一遍是重复 |
| **L2 轨迹层** | `ExecutionTrace`（按 `RunId` 可回放） | 不能，要投影或闭包查 | **主** | 内核独有，是「事后能不能重建」的落点 |
| **L3 外部状态层** | `agent_runs` 表 / 动作域落库状态 | 完全够不着 | **否** | 零外部调用、一张单、不重放、审计五字段属六句与动作域，应另开题库 |

L3 不混进来的原因很实际：**失败归因**。同一条场景里既有内核又有 ERP 适配器，红了分不清是哪一侧，
评测就失去「比较改前改后」的能力。

### L2 里到底有哪些可评字段

`ExecutionTrace` 现有 12 个字段，其中带判据性质的是这些（字段名以代码为准，本文不复述类型）：

- `Status` + `ErrorCode`：终态与归类码，调用方据此决定重试 / 降级 / 提示，不靠解析中文
- `Stop`：`Kind` / `Observed` / `Limit` / `Subject`——同一个 `loop_detected`，观测值和阈值要能分别读出来
- `InputTokens` / `OutputTokens`：**本次 run** 的用量；`null` 表示供应商没上报，不是 0
- `Steps`：迭代号 / 工具 / 参数 / 结果 / 异常；每步 `Truncated` 声明「是否被截断」
- `Complete`：这条记录是否覆盖了本次 run 的全部动作；中断时必须为 `false`
- `Iterations` / `Model` / `LatencyMs` / `SessionId`：重建一次 run 的骨架

**读回来的位置是 `IExecutionTraceReader.GetAsync(runId)`，不是内存里的 `HarnessRunResult`。**
评「落库之后的事实」才是闭环；评内存对象只是把单元测试换个壳。

## 四、MAF 给的能力，用哪一半

MAF 1.23.0 的评测体系在本仓已引用的 `Microsoft.Agents.AI` 包里，传递依赖
`Microsoft.Extensions.AI.Evaluation` 10.10.0，**csproj 一行都不用加**。

| 用 | 为什么 |
| --- | --- |
| `IAgentEvaluator.EvaluateAsync` 批量入口（`LocalEvaluator`） | 直接把 `EvalItem` 交给本地评测器，返回的就是 `AgentEvaluationResults`（含 Passed / Failed / 断言），不需要 agent 实例 |
| `LocalEvaluator` + `FunctionEvaluator` | 唯一能离线跑的判定机制；`Func<EvalItem, EvalCheckResult>` 能带失败理由 |
| `EvalItem.Conversation` + `ExpectedToolCall` | 承载工具调用序列与参数 |
| `ToolCalledCheck` / `ToolCallsPresent` / `ToolCallArgsMatch` | 仅有的三个与调用序列相关的内置判定 |
| `AssertAllPassed` / `AssertNoFailedItems` | 结果可直接进 xunit |
| `IConversationSplitter`（`LastTurn` / `Full`） | 控制判据看哪段对话 |

| 不用 | 为什么 |
| --- | --- |
| `AIAgent.EvaluateAsync` 的全部重载 | 入口要一个 `AIAgent` 实例，而本仓的 agent 在 Harness 私有装配里；评测侧造假 agent 只是多一层没用的对象。真 Harness 自己跑，题库运行器也用不上 |
| `MeaiEvaluatorAdapter` / `ChatConfiguration` / judge model / `GeneratedEvaluatorRef` / Foundry `ReportUrl` | 要外部 API 或云账号；评的是「答得好不好」，v3 六句没有一条是它；私有化部署下那些字段恒空 |
| `AssertScoreAtLeast` / `AssertDimensionScoreAtLeast` | 给云端 rubric 分数设计的 CI 门禁；本地布尔判定只有 0/1，用它是把通过率包装成分数 |
| `KeywordCheck` / `ContainsExpected` / `NonEmpty` / `HasImageContent` | 文本质量与多模态，与内核契约无关 |
| `numRepetitions` 做 pass@1 | 会把评测引向模型完成度，那条结论已冻结 |

**三条实测事实**（2026-11-14 临时探针，跑完已删，不落常驻文件）：

1. 「已有响应」重载里塞一个「被调用就抛异常」的 client，`Calls == 0` 且 `AllPassed == true`——**确实不跑 agent**。
2. 把 `FunctionCallContent("propose_action")` 手工构造进 `AgentResponse.Messages`，`ToolCalledCheck` 读得到——
   **真 Harness 的结果可以投影进框架**，不必写 `DelegatingAIAgent`。但落实时选了更直接的一路：
   投影成 `ChatMessage` 序列后直接构造 `EvalItem`，跳过 `AgentResponse` 与那个没人用的 agent 实例（见第六节）。
3. 不设 `expectedToolCalls` 时，`ToolCallArgsMatch()` 对一个从未期望过的工具**直接通过**（文档原话：
   *If no expected tool calls are set on the item, the check passes*）。这是配置漏了也不红的假绿，
   和之前 F1.7 那次是同一类，别让它单独承担判据。

一句判断：**框架给壳（跑题 / 聚合 / 断言），判据内容 100% 自己写。**
这符合「绝对不造轮子」——轮子是机制，领域判断不是轮子。

## 五、应该评什么：场景清单

每条写五件事：诱导输入 / 该读回的事实 / 对应哪条已登记机制（**只为定位，不表示登记**）/ 负控怎么改坏 /
为什么不是恒真。全部是负例。

### 诱导连续重复调用同一工具

- **输入**：脚本化模型连续以相同参数请求同一个工具，次数超过守卫阈值。
- **读回**：`Status=loop_detected`；`Stop.Kind=repeated_tool_calls`；`Stop.Subject` 是工具名；
  `Stop.Observed` 是实际重复次数、`Stop.Limit` 是配置阈值；被拦下的那次调用在 `Steps` 里零执行。
- **定位**：③ `consecutive-repeat-detection`、⑥ `stop-reason-structured`。
- **负控**：把 `Observed` 写死成配置值，或把 `Stop` 置 `null`，这条必须红。
- **恒真风险**：这条场景里 `Observed` 必然等于 `Limit`（第 N 次触发，N == 阈值），
  **写死常量也绿**。所以它证明的是「语义正确」，不单独承担「读到了计数」这个主张，得靠下一条补。

### 诱导冲爆 token 预算

- **输入**：让模型在预算边界附近继续要工具，用量上报值大于上限。
- **读回**：`Stop.Kind=token_budget`，`Observed > Limit`（两个数字不等），终态**不是** `succeeded`。
- **定位**：③ `token-budget-per-run`、③ `terminal-taxonomy`。
- **负控**：把记录里的用量换成进程累计值，或把终态记成 `succeeded`，必须红。
- **为什么必须有这条**：全场只有这里 `Observed ≠ Limit`。缺了它，上一条的「读到计数」是恒真的。

### 跑满迭代被强制收口

- **输入**：模型一直要工具，直到 `MaximumIterationsPerRequest` 用尽。
- **读回**：`iteration_limit`，不记成成功；未跑满的正常收尾不得误判成截断。
- **定位**：③ `iteration-limit-not-success`、② `ficc-options-explicit`。
- **负控**：把上限调成 100，或去掉 `InspectCompletion()` 的收尾询问，必须红。

### 工具抛异常

- **输入**：工具执行体抛异常（含被取消）。
- **读回**：`Status=failed` + `ErrorCode=tool_error`；该步 `Error` 非空、`Result` 为空；
  「失败」与「返回了空」在记录里分得开；模型仍拿到回填的结果消息，整轮不炸。
- **定位**：④ `exception-backfill-recheck`、⑥ `outcome-and-code`。
- **负控**：把 `Error` 清空或把 `Status` 写成 `succeeded`，必须红。

### 工具结果超长

- **输入**：工具返回一个超过 `MaxResultChars` 的结果。
- **读回**：该步 `Truncated=true`，`Result` 确为截断版（长度等于上界）；完整版只走事件通道，不进账本。
- **定位**：④ `result-upper-bound`、⑥ `step-sequence-and-truncation`。
- **负控**：去掉 `truncated: IsTruncated(text)` 的置位，必须红。
- **注意**：模型侧「看到了什么」与记录侧「存了什么」是两件事，这条只评后者；别拿它当检索质量评测。

### 中途取消 / run 超时

- **输入**：在工具执行途中取消调用方令牌，或让墙钟预算先于请求超时触发。
- **读回**：`Complete=false`；终态分别是 `cancelled` / `timeout`，归类码分开；**仍留着一条轨迹**；
  落库不跟随调用方的取消令牌（`CancellationToken.None`）。
- **定位**：③ `real-cancellation-and-timeout-split`、⑥ `completeness-declarable`、⑥ `failure-paths-durable`。
- **负控**：把中断分支的 `complete: false` 去掉，或让落库跟随调用方令牌，必须红。
- **为什么容易假绿**：只断言「留下了记录」在成功路径也成立，必须同时断言 `Complete=false`。

### 准备阶段就失败

- **输入**：没配模型 / 取会话失败 / 装配失败，让异常在 `try` 之前或之内抛出。
- **读回**：恰好**一条** `failed` 轨迹，`model_unavailable` 或对应归类码，不是零条、也不是两条。
- **定位**：⑥ `prepare-stage-recorded`。
- **负控**：把 `PrepareRunAsync` 移出 `try`，或恢复「模型未配置自己落一条」的旧分支造成双条，必须红。

### 正常收尾的用量口径

- **输入**：脚本化模型上报一次确定用量（如 10 / 5），进程累计器故意报一个不同量级的值。
- **读回**：`InputTokens`/`OutputTokens` 等于本次调用上报值，不是进程累计；供应商不报时为 `null` 而不是 0。
- **定位**：⑥ `usage-per-run`。
- **负控**：把记录改成读 `RuntimeUsageSource` 的累计差值，必须红。
- **已知边界**：失败路径没有 `AgentResponse`，用量恒为 `null`。要补得在函数调用环外包装饰器，
  会撞 ① 的红线，**宁可空着**，这条场景不要伪装成已覆盖。

### 流式与同步两条出口对齐

- **输入**：同一场景分别跑 `RunAsync` 和 `StreamAsync`。
- **读回**：状态、步数、迭代数、终态文本、用量一致；流式的分片拼起来等于同步的答复。
- **定位**：② `loop-behavior-locks`。
- **负控**：让流式出口少落一条工具步，或让两条出口各建一份装配，必须红。
- **恒真风险**：只断言「两边相等」在两边都是 0 步时也绿，必须同时断言 `Steps.Count >= 1`。

### 落库往返闭环（每条场景的收尾）

- **做法**：以上每条场景拿到 `RunId` 后，经 `IExecutionTraceReader.GetAsync` 读回，断言该条要求的每个字段都还在。
- **定位**：⑥ `record-fields-persisted`。
- **为什么单列**：前九条评的是「内核产出了什么」，这条评的是「应用层收不收得到」。
  只加记录形状不加表列，就是内核产出了、回放读回来全空，正好是文档红线里最隐蔽的那种失败。

### 一条边界提示：别评反

`propose_action` 被模型调用**恰恰是正确路径**（它只递单、不执行）。用 `ToolCalledCheck("propose_action")`
去评「未审批零外部调用」会得到相反结论。那一句要查的是 `SubmitCallCount == 0` 与库里一条 `PendingApproval`，
属 L3，在动作域题库里做，不进本文这份。

## 六、自己要补什么，以及明确不补什么

2026-11-14 已落实前两样，落成 `tests/AgentWorkbench.Evaluation/`（挂进 slnx；它是普通类库不是测试项目，`IsTestProject=false`）。
**本文初版写的「零生产代码改动」已不成立**：用户要求把评测单独建成模块，所以投影与判据进了 `src/Core`。
它是一片叶子——没有任何生产项目引用它，不进 Webapi 运行时链路；评测是事后行为，
不该出现在一次 run 的链路上。项目只引 `Shared` + `Observability` + `Runtime.Harness` + MAF 包，
**不引 `Persistence` / `Domain` / `Host` / `Domains`**。门禁并没有强制这一条
（架构门禁只约束 `Core/Runtime` 与 `Core/Engineering` 不引存储），是本模块自愿守的：
把 EF/SQLite 拖回来，等于把 11-14 刚做完的 Model 端口化白做一遍。

### 已落的三样

**1. 投影 `HarnessResponseProjection.ToConversation`**

| `HarnessStep` | 投影成 |
| --- | --- |
| `Kind=tool` | 一条 assistant 消息里的 `FunctionCallContent`（`Tool` / `Arguments`）+ 一条 tool 消息的 `FunctionResultContent`（`Result` / `Error`） |
| `Kind=assistant` | 一条 `ChatRole.Assistant` 文本消息 |
| `Truncated` / `Status` / `Code` / `Stop` / 用量 | **不投影**，交给下面的判据去读落库轨迹 |

产出 `IReadOnlyList<ChatMessage>`，不是 `AgentResponse`：MAF 的「已有响应」重载要一个 `AIAgent` 实例，
评测侧没有也不该有 agent。直接构造 `EvalItem` 交给 `LocalEvaluator`，判定 / 聚合 / 断言一样是框架的。
callId 带迭代号与序号，同名工具被多次调用不会撞成一个 id。
**不要把 trace 事实硬塞进 `EvalItem.Context`**——那个字段是 grounding 文本，不是状态袋，塞进去等于自造协议。

**2. 判据工厂 `KernelChecks` + 入口 `KernelEvaluation`**

判据吃的是**按 `RunId` 从 `IExecutionTraceReader` 读回来的 `ExecutionTrace`**，不是内存结果对象；
`trace is null` 一律判失败并写明原因，否则「内核产出了、应用层收不到」会静默恒绿。
入口是薄装配：读一次轨迹 → 投影对话 → `LocalEvaluator` → `AgentEvaluationResults`。
**不另造事实源端口**：`IExecutionTraceReader` 已经是那个抽象，造第二个就是轮子。
判据现有七条：终态与归类码、停因结构化、本次用量、完整性、截断标志、工具步条数、迭代轮数。
`KernelChecks` 是纯函数式的领域判断，不依赖 DI、不依赖数据库驱动。

**3. 场景与判据强度（在测试侧）**

`tests/AgentWorkbench.CoreTests/Evaluation/评测机制.cs` 13 条，覆盖投影能被 MAF 内置判定读到、
判据读落库事实、按 `RunId` 闭环、每条判据改坏必红，以及两条真 Harness 场景（正常收尾 / 诱导重复调用）。
三条生产代码负控实测会红：读不回轨迹改成恒通过、投影丢掉真实工具名、`EvalCheckResult` 的
Reason / CheckName 写反。第三条起初**没红**——自证测试只覆盖了 `trace is null` 分支，
补上真正跑判据的分支后才抓到，已修。

### 还缺的一样

第五节的**诱导性场景集**只落了两条真 Harness 场景，且用的是自建最小装配，不是真 DI 全量装配。
第七节说的那个增量仍未兑现；场景集本身也还没按第五节的十条铺开。

### 明确不补

- 自建 runner / baselines / JSON 报告——题库运行、聚合、断言框架全给了，自建就是造轮子。
- LLM judge 与 rubric 打分——评的是「答得好不好」，与 v3 无关。
- 「每格一条」的场景配额——按 capability 数凑覆盖率，v3 明说不算成功标准。
- 把通过率或分数当验收线——见第七节。
- 评测专用的架构门禁——架构门禁现在只管模块引用，别借这次把它扩成第二事实源。

## 七、通过线，以及第一份评测真正的增量

**通过线不是分数。** 一条场景算「有强度」，要同时满足：正例绿、**负控改坏后必须红**、恢复后再绿。
只有绿灯没有负控，跟 F1.7 那次假绿没区别。v3 §3 那句「绿灯数量不是成功标准」在这里的具体含义就是这个。

**第一份评测的价值不在又一组绿灯，在第一次真装配。** 核实结果：

- `src/Host/AgentWorkbench.Webapi/Program.cs` 有 15 行 `AddNitro*` 全量注册；
- 测试里 `AddNitroPersistence` 只出现在 `MemoryTestSupport.cs`（记忆测试用），
  **没有任何测试用全量 DI 装配跑过一次 run**；
- 六句契约测试 `ActionRunSuccessTests` 直接 `new ErpActionSet()`，CoreTests 全是自建最小装配
  （真 Harness + 真工具环 + 假模型 / 假存储）。

于是 `Hub → Harness → ToolCatalog → 工具环 → propose_action → 落库` 这段中间链路
一直是「从代码读出来的推断」，不是跑出来的事实。第一份评测如果只把第五节清单在自建装配里再跑一遍，
那它确实没什么价值；**换成真 DI 装配（只把 `IChatClientFactory` 换成脚本化模型）才有增量**。

两处很可能在真链路上一跑就露出来的地方：`Harness:Approval`（工具级）与 `ErpApprovalGate`（动作级）
是两层审批，现在 `propose_action` 走 `Auto`，配错就会出现「先问人要不要填单、填完再问要不要执行」；
以及 `Host/Actions/` 的注入在测试自建装配里从未被验证过。这才是评测比测试多出来的东西。

**本轮（11-14）落实到哪**：第六节那个模块 + 13 条判据测试，跑通的是
「自建最小装配 → 真 Harness 跑一次 → 轨迹落库 → 按 `RunId` 读回 → MAF 聚合断言」这条闭环。
它证明的是**机制接得上**，不是「真装配下系统守得住」。上面那段空白仍然空着，
别把 13 条绿读成第七节那个增量已经兑现。

最后一句实话：**这套做完，验证它的是测试输出，读它的人还没有。** 评测证明的是「内核能产出可重建的事实」，
不是「有人在用」，更不是「有客户要」。后一个缺口 v3 自己承认堵不住，本文不假装堵住了。
