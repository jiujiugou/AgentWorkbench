## 1. 前置条件

| 项 | 要求 | 说明 |
|---|---|---|
| .NET | 10.0 SDK / Runtime | 目标框架 `net10.0` |
| 数据目录 | 可写，且**在部署时挂载持久卷** | 默认 `src/AgentWorkbench.Webapi/data/` |
| 磁盘 | ≥ 1 GB 可用 | 库 + 上传的 PDF（`data/uploads/`） |
| 端口 | 8080（后端）、5173（前端开发） | 可用 `--urls` 覆盖 |
| 模型服务 | 外部 API 或本地 ollama | 未配置时 `api/health` 报 `modelConfigured: false` |

**数据目录必须持久化。** 库、上传文件、**DataProtection 密钥**三样都在里面或指向里面——丢掉任何一样，要么数据没了，要么所有人被登出。

## 2. 首次部署的顺序（**顺序错了会得到半套结构**）

```
1. 准备数据目录与密钥目录（见 §3）
2. 编译：dotnet build AgentWorkbench.slnx
3. 启动：dotnet run --project src/AgentWorkbench.Webapi  --urls http://localhost:8080
       ↓ 启动时自动执行
   3a. EF Core Migrate()      ← 只建 AspNet* 七张
   3b. FluentMigrator MigrateUp()  ← 只建业务表 + tenants
   3c. 种子（仅当库中零用户且配置允许）
4. 生成首个管理员（见 §4）—— 全新部署必须做，否则无人能建租户
5. 健康检查：curl --noproxy '*' http://localhost:8080/api/health
6. 登录验证：用 §4 得到的账号调 /api/auth/login
```

**3a 与 3b 必须串行且顺序固定（EF 先）。** 两者都拿 SQLite 写锁，并行会 `database is locked`；反过来则违反"身份表先就位"的假设。

**`curl` 打 localhost 必须加 `--noproxy '*'`**——本机存在 `HTTP_PROXY` 时，localhost 请求会被劫持到代理，表现为"服务没起来"。

## 3. DataProtection 密钥（**最容易漏，且不报错**）

### 3.1 为什么必须单独配

Identity 的 cookie 是**加密签名**的，密钥来自 ASP.NET Core 的 DataProtection 密钥环。

当前仓库**零配置**：

```
全仓无 DataProtection / PersistKeysTo / KeysPath
```

含义是密钥环落在默认位置（Windows 用户目录 `%LOCALAPPDATA%\ASP.NET\DataProtection-Keys`，容器内是临时目录）。

**后果很具体，而且不报错**：

| 场景 | 现象 |
|---|---|
| 容器重建 | 密钥丢了 → 所有 cookie 解不开 → **全员被踢下线** |
| 换一台机器部署 | 同上 |
| 多实例负载均衡 | 两台机器密钥不同 → **用户随机掉线，像抽奖** |
| 容器以非 root 运行 | 密钥目录不可写 → 启动直接失败，日志里只有一句 DataProtection 异常 |

### 3.2 配法

```
appsettings.json
{
  "DataProtection": { "KeysPath": "/var/aw/keys" }
}
```

启动时显式持久化：

```csharp
builder.Services.AddDataProtection()
    .PersistKeysToFileSystem(new DirectoryInfo(keysPath))
    .SetApplicationName("AgentWorkbench");   // 多个应用共用目录时必须设，否则密钥串用
```

| 要点 | 理由 |
|---|---|
| `KeysPath` 挂持久卷 | 不挂就是"重建即全员登出" |
| `SetApplicationName` 必须显式设 | 不设则按内容根路径推导，**部署路径一变密钥就换** |
| 备份时连同密钥目录一起备 | 只备份库，恢复后所有人仍被登出 |

## 4. 首个平台管理员（REQ-AUTH-11）

Identity 只会建用户，**它没有"平台管理员"这个概念**。全新部署后必须能产生一个能创建首个租户的账号，否则系统卡在登录页。

三种做法，推荐第一种：

| 方案 | 做法 | 评价 |
|---|---|---|
| **A. 首启动种子（推荐）** | 配置 `Identity:SeedDemo=true` 或 `Identity:Bootstrap:{userName,password}`，启动时若无任何 `platform_admin` 则创建 | 可复现、可写进文档；生产环境强制要求首次登录后改密 |
| B. 命令行工具 | 提供 `dotnet run -- create-admin` | 更干净，但要额外维护一个入口 |
| C. 手工 SQL | 直接往 `AspNetUsers` / `AspNetUserRoles` 插行 | **不推荐**——Identity 的密码哈希格式不是手写能凑对的 |

**无论哪种，都必须满足两条**：空库启动后按文档能在无人协助下得到管理员；该路径不依赖"已存在另一个管理员"。

**安全要求**：种子账号的密码必须是**启动参数或环境变量**，不能硬编码在仓库里；首次登录后强制改密（或至少在建租户的接口上要求改密标记）。

## 5. 配置项

```json
{
  "Identity": {
    "SeedDemo": false,
    "Lockout": { "MaxFailedAccessAttempts": 5, "DefaultLockoutMinutes": 5 },
    "Password": { "RequiredLength": 8, "RequireDigit": false, "RequireNonAlphanumeric": false },
    "Cookie": { "ExpireDays": 7, "ValidationIntervalMinutes": 30 }
  },
  "DataProtection": { "KeysPath": "/var/aw/keys" },
  "Harness": { "Loop": { "TimeoutSeconds": 300, "MaxIterations": 6 } }
}
```

| 配置 | 影响 | 改成别的值会怎样 |
|---|---|---|
| `Lockout.MaxFailedAccessAttempts` | 触发锁定的失败次数 | 太小会误锁正常用户；太大等于没有保护 |
| `Lockout.DefaultLockoutMinutes` | 锁定时长 | 太长会让被误锁的人干等 |
| `Cookie.ExpireDays` | 会话有效期 | 越长，令牌被窃后的窗口越大 |
| **`Cookie.ValidationIntervalMinutes`** | **改密/停用后旧会话的最长存活时间** | 调大会让"停用立即生效"变成"最多 N 分钟后生效" |
| `Harness.Loop.TimeoutSeconds` | 单次 run 超时 | 太小模型必 504；缺失则该键不生效，必 504 |

**`Harness:Loop` 必须显式写在 appsettings 里**——缺了它，真模型调用几乎必然超时（这是踩过的坑）。

## 6. 备份与恢复

### 6.1 备份必须用 backup API，不能用 `cp`

```bash
# 正确：sqlite3 的在线备份
python -c "
import sqlite3
sqlite3.connect('data/agentworkbench.db').backup(sqlite3.connect('backup/app-$(date +%F).db'))
"

# 错误：WAL 模式下直接 cp，会得到一个缺 WAL 的坏库
cp data/agentworkbench.db backup/app.db
```

**WAL 模式下直接拷贝主文件，会丢掉尚未 checkpoint 的事务**——拷出来的库能打开，但数据是旧的，而且不报错。

### 6.2 一次完整备份包含三样

| 内容 | 路径 | 丢了会怎样 |
|---|---|---|
| 数据库 | `data/agentworkbench.db` | 全部业务数据没了 |
| 上传文件 | `data/uploads/` | 检索命中但点开 404 |
| **密钥** | `DataProtection:KeysPath` | 恢复后所有人被登出（数据还在） |

### 6.3 恢复演练（**没演练过的备份等于没有备份**）

```
1. 停服务
2. 恢复库 + uploads + 密钥
3. 启动，观察两套迁移是否报错（版本不匹配会在这里暴露）
4. 登录，查一条历史会话
5. 检索一次，确认 FTS 与向量都还能命中
```

第 5 步最容易被跳过，但它才是关键：**库恢复了、向量集合没恢复**是这套系统的特有故障（向量表由运行时创建，不在迁移里）。

## 7. 回滚边界（写清楚，出事时没时间讨论）

| 回滚什么 | 安全吗 | 说明 |
|---|---|---|
| 代码回滚（库保留新结构） | ✅ 安全 | 旧代码不认新列，但不会崩 |
| 库回滚（跑到旧版本号） | ❌ **危险** | 密码哈希已升级为新格式，旧代码验不过 → **这批用户永久登不上** |
| DataProtection 密钥回滚 | ⚠️ 看情况 | 回到旧密钥 = 其间签发的 cookie 全失效 |

**结论：上线后只能回代码，不能回库。** 需要回库的唯一路径是"整库还原 + 同时还原代码"，两者必须在同一时刻。

## 8. 故障处置

| 现象 | 先查什么 | 常见原因 |
|---|---|---|
| 打开前端**全部 401** | 是否已有登录页与 `/api/auth/login` | 默认拒绝授权已生效，而前端还没有登录入口 |
| 登录页表单提交后**跳到一个不存在的页面** | cookie 的 `OnRedirectToLogin` 是否改成 401 | Identity 默认 302 跳 `/Account/Login` |
| 用户**莫名被登出** | 密钥目录是否被重建 / 是否多实例 | DataProtection 密钥不一致 |
| 端口 8080 起不来 | `netstat -ano \| grep ":8080 "` | 旧进程未退出；**构建失败也可能真因是这个**（dll 被占用，MSB3027） |
| 迁移报错 | `VersionInfo` 与 `__EFMigrationsHistory` 两张账本 | 有人手跑了其中一套工具 |
| 检索命中但打开 404 | `documents` 有行、文件是否在 | 删了文件没删索引（或反过来） |
