# TOML 模板：kb 元数据的编写要求

- **适用侧**：公共 ｜ **寿命**：常驻 ｜ **最后校准**：2026-11-24
- **适用**：`docs/kb/documents/*.toml` 与 `docs/kb/contracts/*.toml` 的新建与修改
- **不适用**：文档正文（见 `docs/文档模板.md`）、`docs/plans/`、`docs/adr/`
- **性质**：协作规范。校验器在 `scripts/kb_check.py`，本文只解释要求与判据

> 本文回答一个问题：一份 TOML 元数据写到什么程度算合格。
>
> 它不记录任何一份 TOML 的当前内容。哪篇文档现在有哪些事实、哪些契约，属于那篇的 TOML 自己的事。

本文为什么存在：TOML 层的错误不会让任何东西报错。写错一个 `cases`，用例其实不存在，检查器能抓到；但写一句看起来像事实、实际无法对账的 `claim`，或者把「测试存在」写成结论——这些不会红，只会慢慢变成一份没人敢信的元数据。

## 1. 两份文件各管什么

| 文件 | 回答什么 | 读者 |
| --- | --- | --- |
| `documents/<同名>.toml` | 这篇文档依赖哪些源码、哪些测试、哪些配置值 | 改代码前想知道「会动到哪篇文档」的人 |
| `contracts/<同名>.toml` | 这篇文档承诺了哪些可核对的行为，各自证到什么程度 | 判断「这格做完没做完」的人 |

一份文档一个文件，两边同名。不同名就无法从文档找到它的契约，也无法从契约找回它的文档。

**两者不能互换。** documents 是「关系与事实」——文件和符号在哪、配置实际是多少；contracts 是「主张与证据」——说了要做到什么、有没有判据。把主张写进 documents，`--impact` 会以为那只是引用；把文件路径写进 contracts，改文件时没人知道要复核契约。

## 2. documents 的结构

```toml
# <部件名>（六部件之<编号>）
# 字段含义见 docs/TOML模板.md；这里只存关系、证据与带 expect 的事实。

[[documents]]
path = "docs/core/<文档名>.md"
watch = [
  "src/<模块前缀>/**",
]

[[documents.evidence]]
type = "source"
path = "src/<模块>/<文件>.cs"
symbols = ["<符号一>", "<符号二>"]

[[documents.evidence]]
type = "test"
path = "tests/<项目>/<文件>.cs"

[[documents.fact]]
claim = "<一句话，说清这条事实具体是什么>"
check = "json"
path = "src/Host/AgentWorkbench.Webapi/appsettings.json"
json_path = "<配置>:<路径>"
expect_count = 0
```

**`watch` 是影响面，不是依赖清单。** 它的用途只有一个：改了这个路径，`--impact` 应该提醒你核对这篇文档。所以它记的是「改这里会让这篇文档的判断失效」，不是「这篇文档提到过这个目录」。判据：改这个路径下的代码，文档里有没有一句话会变成假的。

看某个路径被多篇共用时，`watch` 里可以带一行注释说明为什么这篇也要跟。**没有注释的多路径 watch，半年后没人知道那条是不是复制粘贴来的。**

**`symbols` 防的是改名。** 它要求这些符号真的出现在那个文件里——方法改名后，证据指向失效，检查器立刻报。所以记的应该是「这篇文档的判断依赖这个符号存在」的那些，不是文件里所有公开成员。

**`fact` 必须能机器核对。** 三种 check：

| check | 核对什么 |
| --- | --- |
| `json` | 读 JSON，按冒号路径取值，比对 expect / expect_count / expect_contains |
| `csproj` | 读 PackageReference 的版本 |
| `test-count` | 数测试文件里的 `[Fact]` / `[Theory]` |

`claim` 写的是「声明 + 对账口径」，不是把值抄一遍。抄值会变成第二份副本，改了配置两边不同步，而检查器只对一边。正确形态是让人读完 `claim` 就知道该去核对什么，值交给 `expect_*` 从真实文件里取。

**无法机器核对的事实，不要写进 `fact`。** 把它写进文档正文的判断里，或者登记为契约的 gap。「看起来像事实但校验不了」的条目比没有条目更糟——它让元数据显得完整，实际不可信。

## 3. contracts 的结构

```toml
# 架构契约 · <部件名>（六部件之<编号>）
#
# 一份文档一个契约文件：docs/kb/contracts/<与 documents/ 同名>.toml。
# 字段与禁令见 docs/TOML模板.md。

[[contract]]
id = "<前缀>-<领域>-001"
section = "<文档里的小节号>"
document = "docs/core/<文档名>.md"
statement = "<可核对的行为>"
impl_path = "src/<模块>/<文件>.cs"
impl_symbols = ["<符号>"]
[[contract.evidence]]
kind = "test"
path = "tests/<项目>/<文件>.cs"
cases = ["<用例名片段>"]
strength = "<这段证据能证明到哪一层>"
mutation = "<改坏哪一处，这段证据应当变红>"
[[contract.evidence]]
kind = "gap"
reason = "<为什么没有判据>"
```

**`statement` 写行为，不写评价。** 「不符合准入策略的工具不得进入模型可见清单」是行为，可核对；「准入策略应当合理」不是，无法证伪。凡是不能用「成立 / 不成立」回答的句子，都不是契约。

**`section` 指向主张真正讲在哪。** 不是「这份文档最相关的一节」，是那条主张被论证的那一节。契约堆在文档末尾的验收节、正文里找不到对应论证，读者就无法从结论回到推导。

**`cases` 的每个片段都必须真的出现在测试文件里。** 这是检查器唯一的强约束：写一个不存在的用例名，或者用例被删掉，立刻报。所以宁可写少，不能写猜——写一个大概记得的名字，等于给这条证据注水。

**`strength` 是打折声明，不是优点陈述。** 它要回答「这段证据最多能证明到哪」。同一份用例，跑在 Mock 策略上和跑在真实策略上，证明力差一个量级，`strength` 必须说出来。只写「有测试」等于没说。

**`mutation` 是设计，不是结论。** 写的是「改坏哪一处应当变红」这个设计；是否真跑过、结果如何，不在 TOML 里写，也不因为写了就算验过。

**`gap` 必须写 reason，且 reason 要指向具体缺什么。** 「证据不足」不是 reason；「落库臂从没真跑过，测试项目未引用该实现，两臂对照实为同实现两个实例」才是。前者让人没法接手，后者让人知道下一步干什么。

## 4. 七条纪律

**一、不写 status。** 验证结果每次现算。写死「已通过」就是第二种假绿——测试哪天红了，status 还写着通过。

**二、ID 只给三类主张。** 跨部件的、属于安全默认值的、有已知缺口的。其余主张挂在文档小节号上就够。ID 一多就变成第五套编号，没人维护。

**三、ID 跨仓唯一，且不随实现变。** 方法改名、测试换文件、实现重构，只要主张没变，ID 就不变。ID 编进文档正文，读者靠它把结论和证据对上。

**四、一份契约只属于一份文档。** 两个部件都关心的边界，各写各的那一侧，不要复制同一条。复制会漂移，而漂移后没人知道该信哪份。

**五、evidence 可以多段，一段只说一层。** 真实策略一段、Mock 一段，各自写 `strength`。合成一段写「综合验证」，就把打折信息抹掉了。

**六、TOML 里不写文档正文该说的话。** 不写背景、不写理由、不写「为什么这样设计」。这些属于 `docs/core/` 的正文。TOML 只存可对账的东西——一旦开始写解释，它就会变成第二份正文，然后没人同步。

**七、新增契约先看该节有没有论证。** 契约指向的小节里，必须能找到这条主张为什么成立、不成立会怎样。找不到就先补正文，再发 ID。反过来做，会造出一条有 ID、有测试、但读者无法理解为什么的契约。

## 5. 不合格的样子

**抄值。** `claim` 里直接写「白名单有 7 项」，而不是声明加 `expect_count = 7`。配置一改，claim 变成假话，检查器还对着旧值。

**猜用例名。** `cases` 里写一个大概记得的名字。检查器会抓——但抓不到的情况更糟：名字碰巧对了，实际测的是另一件事。

**结论冒充证据。** `strength` 写「已验证」，实际只跑了内存实现。结论要能在测试变红时跟着变；不变的，写的是存在性。

**契约堆在验收节。** 所有 `section` 都指向最后一节。读者读机制时不知道哪句话是承诺，读验收时不知道承诺从哪来。

**watch 写成目录清单。** 把 `src/` 下所有相关目录都列进去，`--impact` 每次都提醒这篇文档，几次之后就没人看了。watch 的价值在准，不在全。

**fact 塞不可核对的东西。** 「代码风格统一」「模块职责清晰」——这类条目永远不会红，也永远不会有用。

## 6. 自检：七问

1. 每条 `watch` 能不能回答「改这里，文档里哪句话会变假」？
2. 每条 `fact` 的 `claim` 是不是声明加口径，而不是抄了一个值？
3. 每条 `section` 指向的那一节里，能不能找到这条主张的论证？
4. 每个 `cases` 片段，是不是真的在测试文件里？
5. 每段 `strength` 有没有说出「最多能证明到哪」，而不是「有测试」？
6. 每个 `gap` 的 `reason`，能不能让接手的人知道下一步做什么？
7. 有没有一条 `status`、一句解释性正文、或者一个不可核对的 fact 混进来？
