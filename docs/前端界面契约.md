# 前端界面契约（按 S01–S10）

- **适用侧**：应用 ｜ **寿命**：现状 ｜ **最后校准**：2026-11-10
- **回答**：每一步在人眼前呈现成什么、什么状态必须看得见、看不见就是错
- **不回答**：页面布局与组件选型、当前完成度（测试红绿）、未来想做的页面

**这份文件是 [运行期流程.md](运行期流程.md) 的另一半。** 那一份写系统内部走了哪十步，
这一份写同样的十步在人眼前是什么样。**同一套 `Sxx` 编号，两个投影**——翻哪一份都能对上号，
不新增第二套坐标。写的是「必须成立的条件」，不是「现在已经做到」。

判据引用两处，不在此复述：正本 §4.1 六句成功判据（第 1–6 句）、README 的三条方向判据（①②③）。
正本不在工作区时的取法见 [README.md](README.md) §1。

## 每格怎么读

```
承载界面   现在是哪个页面承载它；没有就写「暂无」——「暂无」本身是契约的一部分
承载判据   它为什么必须存在。挂不上任何判据的界面功能不该做
必须可见   缺任何一条，界面就是在骗人
数据来源   哪张表 / 哪个端点（这层能从代码查，写下来省每次翻找）
禁止       明确不许的做法
```

## 跨步约束：界面不承担的三件事

界面是**呈现层**，不是判定层。以下三条在每一格都成立，后面不再重复：

- **不判权限**。按角色隐藏按钮只是提示，真正的拒绝在服务端。界面上「看不见按钮」不等于「做不了」。
- **不判风险**。`RiskLevel` 只展示，不参与「要不要批」的计算，也不替人排序决策。
- **不判幂等**。显示服务端给出的「新执行 / 回放 / 不确定」，界面自己不去推断「这个应该没执行过」。

## 主干十格

### S01 · 你输入一句话

- **承载界面**：`ChatView`
- **承载判据**：判据②（谁 / 何时）；S01 阶段产物「编号必带」
- **必须可见**：
  - 本条输入立刻出现在消息列表里（本地先显，不等服务端回显）。
  - **发送失败在原位标记**，不能静默丢弃——用户必须知道这句没送出去。
  - 生成中状态可见，且此时不接受第二条输入（拒绝要能看出是「正在生成」，不是按钮无反应）。
- **数据来源**：本地状态；Hub 返回的 `code`
- **禁止**：把「输入已被接收」和「run 已开始」显示成同一件事。

### S02 · Hub：验身份、取会话

- **承载界面**：`ChatView`（会话区）、`LoginView`
- **承载判据**：判据①（谁）；判据②（谁）
- **必须可见**：
  - 当前主体与所属租户始终可见（谁是这次操作的责任人）。
  - 会话归属：进入会话时只可能是当前主体的会话，别人的会话不出现、不报错、不泄露存在性。
  - **入口前拒绝的理由要分类显示**：未登录 → 去登录；缺输入编号 / 同连接已有生成 → 明确提示。
  - **断开 → 明确终态**：显示「已停止」并保留已有内容与已发生的单据，不得显示为完成。
- **数据来源**：`/api/auth/me`；Hub 的 `ReceiveStopped` / `Error`
- **禁止**：把「连接中途断开」与「入口前拒绝」显示成同一种失败；撤销已发生的副作用不在界面职责内。

### S03 · Harness 组上下文

- **承载界面**：暂无（**必须可查，不必常驻显示**）
- **承载判据**：判据②（看到什么）
- **必须可见**：本轮实际注入的历史条数、工具/动作能力清单。这是「模型看到了什么」唯一的实证，
  没有它，判据②里的「看到什么」这一项在产品上没有落点。
- **数据来源**：`chat_messages`、`agent_steps`
- **禁止**：把「注入了哪些能力」当成实现细节不暴露——能力清单就是「不越权」的正面清单。

### S04 · 模型决策

- **承载界面**：`ChatView`（工具调用卡片）
- **承载判据**：核心命题「模型想做什么」vs「系统真的做了什么」的前半
- **必须可见**：每次工具调用的工具名、参数、结果摘要、发生顺序与迭代序号。
  实测已出现过「模型声称调用了三个工具、实际只调了两个」而系统判 `succeeded`——
  只有把这层显示出来，人才能当场看出谎报。
- **数据来源**：Hub 的 `ReceiveTool`；`agent_steps`
- **禁止**：只显示模型的自然语言叙述，不显示调用记录。**叙述不是记录。**

### S05 · `propose_action` 填成一张单子

- **承载界面**：暂无
- **承载判据**：判据②（谁 / 何时 / 依据什么）
- **必须可见**：
  - 单据的结构化视图：动作名、发起主体、结构化参数（不是裸 JSON 串）、提交时间、来源消息。
  - 同一句话产生的多张单要能分清，按单据分块，不混成一段文字。
- **数据来源**：`action_requests`、`GET /api/actions/{id}`
- **禁止**：把 `requestId` 当作面向用户的主标识（它是内部去重键）；显示「已提交」却不给任何单号。

### S06 · 四道闸门

- **承载界面**：`ApprovalsView`（部分承载）
- **承载判据**：§4.1 第 2 句「未审批零外部调用」；判据②（依据哪条规则）
- **必须可见**：Schema / Permission / BusinessRule / Audit **逐道**的 allow / deny 与理由文本。
  只显示「通过 / 不通过」等于没给依据。
- **数据来源**：`action_trace`（`stage` / `outcome` / `reason`）
- **禁止**：把四道合成一个总状态；deny 时不说明「外部系统什么都没发生」。

### S07 · 审批：挂起 or 直接放行

- **承载界面**：`ApprovalsView`
- **承载判据**：§4.1 第 2 句；判据②（依据哪条规则 / 会变成什么）
- **必须可见**：
  - 待审批队列：动作名、发起人、提交时间、结构化参数。
  - **四道闸门的判定结果与理由**（S06 的产物在这里被消费）。
  - 风险等级与影响范围——只展示。
  - **「如果批准，外部系统里会变成什么」的预览**。让审批人读 JSON 再点头，等于没审批。
  - 批准 / 拒绝，**拒绝理由**。
  - 超时策略：挂起多久失效、失效后是什么状态。
- **数据来源**：`GET /api/actions/pending`、`GET /api/actions/{id}/audit`
- **禁止**：批准时修改参数（改参数＝换一张单，必须重走 S05–S06）；
  用界面隐藏按钮代替服务端角色判定。

### S08 · 执行：幂等 → 连接器 → 外部

- **承载界面**：暂无
- **承载判据**：§4.1 第 3 句「同 `request_id` 只一张单」、第 4 句「超时只查证不重放」
- **必须可见**：
  - 外部对象标识（单号 + 可点链接）与**外部系统的当前真实状态**，不是我们库里的镜像。
  - **回放标记**：这条是幂等回放，不是新执行。
  - **不确定态**：「结果未知，正在查证」。这是第三种状态，与成功 / 失败并列，
    由第 4 句直接推出——普通前端只有两格，这一格必须专设。
  - 耗时、重试次数。
- **数据来源**：`action_results`、`action_idempotency`、`action_trace`
- **禁止**：把「不确定」渲染成「成功」或「失败」；把回放显示成新执行。

### S09 · 结果回传模型

- **承载界面**：`ChatView`
- **承载判据**：判据③（拿掉模型仍能安全拒绝 → 收口必须可见）
- **必须可见**：迭代次数与上限、重复调用判定、超限收口时的明确状态与归类码。
- **数据来源**：Hub 的 `ReceiveDone`；`agent_runs.iterations` / 状态码
- **禁止**：超限时显示为「完成」；只显示最后一段文本而把 `failed` 藏起来。

### S10 · 流式输出 + 落库

- **承载界面**：`ChatView`、追溯页（**暂无**）
- **承载判据**：§4.1 第 5 句「审计五字段齐全且可反查」
- **必须可见**：
  - 终态 + 归类码，与正文分开显示（正文说成了什么，不等于系统做成了什么）。
  - 三笔落库分别可查：模型历史、模型轨迹、动作审计——三者不合并，界面上也不能糊成一条。
  - 审计写失败 → **不算成功**，界面必须说清「这次没有可靠记录」。
- **数据来源**：`GET /api/runs/{id}/trace`（**当前不存在**）、`chat_messages`、`agent_runs`
- **禁止**：正文成功而审计缺失时仍显示成功态。

## 待定（需要人拍板，不由实现决定）

未定的部分留在这里，不写进上面的「必须可见」——写进去就等于假装已经决定了。

1. **不确定态怎么显示**（S08）：一条独立状态条？标在单据卡上？要不要挡后续操作？
2. **回放要不要显式标**（S08）：标成一个小标签，还是只在展开详情里出现？
3. **审批页给不给「影响预览」**（S07）：给的话，预览由谁算——域提供还是底座推导？
4. **拒绝理由是否必填**（S07）：必填则拒绝路径多一个校验点；不必填则「谁决定的」少一半。
5. **追溯页的入口挂在哪**（S10）：挂在会话里（点一条消息看轨迹），还是独立一级页面？
6. **S01 要不要「重发」按钮**：现在没有，因为重放的前置条件（输入级去重）未成立，见 S01 契约。

## 怎么验

界面契约没法用一条命令证明。可验的两端：

- **数据端**：每格「数据来源」列出的表与端点，能用 `curl` 或 SQL 查到真实内容 —— 这是「看得见」的前提。
- **呈现端**：对着真实 run 逐格走一遍，检查「必须可见」每一条是否真的出现在界面上。
  缺一条就是这一格没做完，不是「以后优化」。

文档自身由 `DocsHygieneTests` 守（状态位、相对链接、不重定义写法），改完跑一次。
