## 1. F2 知识资料管理（3 条）

*把一份 文件 交进去，之后提问能用上；交不进去要说清为什么。* 逐条操作细目见 [阶段1-F2.md](阶段1-F2.md)。

1. **能上传 文件；不支持或处理不了的必须明确反馈**（REQ-05）🟢
   - 判据：传 PDF → 列表出现一行；传 Word / 空文件 / 超限 → 明确拒绝并说原因，**不入库、不排队**。
2. **处理状态可见且带错误信息；只有处理成功的文档才能被标为"可检索"**（REQ-06）🟢
   - 判据：处理中 / 成功 / 失败三态用户都能看见；失败带可读原因；未成功的一律不能标可检索。
3. **删除后不得再被检索引用；删除范围要覆盖索引与派生内容**（REQ-10）🟡
   - 判据：用只在该文档出现过的词检索 → 删除 → 同一问题答"资料里没有"。
   - 现状：删除是"先删索引与向量 → 再删记录 → 再删文件"，**没有 L1 事务**；删记录失败会留下"列表里有、搜不到"的残废记录。

**不做**：PDF 以外的格式、文档版本管理、在线预览编辑、文档级权限、外部来源连接器。

## 2. F3 知识问答（3 条）

*把问题变成带原始出处的答案；没依据时明确说没有。* 功能构成见 [F3-知识问答.md](../设计/阶段1/功能/F3-知识问答.md)，验到哪一步见 [F3-功能验证.md](../设计/阶段1/功能/F3-功能验证.md)。

1. **根据用户问题检索当前可访问的资料**（REQ-07）🟢
   - 判据：问一个只有某份文档能答的问题 → 命中该文档的片段。
2. **结果必须含可核查来源：文档名称 + 相关位置 + 对应原文片段，三者缺一不可**（REQ-08）🟡
   - 判据：答案的每条结论有出处；出处能定位到片段序号与页码；点开能看到原文。
   - 现状：三样都有，但**答案里的出处没有任何程序校验**——模型编一个不存在的出处，不会有东西报错。
3. **检索不到足够证据时必须明确告知，不得把无依据内容伪装成来自文档**（REQ-09）🔴
   - 判据：问一个库里没有的问题 → 只输出"资料不足以回答"，**不掺任何推测**。
   - 现状：拒答只在"零候选"时触发；而全文检索有模糊匹配兜底，中文问句基本都有候选 → **实际靠模型听指令，不可测**。

**不做**：通用问答（不检索直接答）、多轮任务编排、主动推送、改写翻译扩写。

## 3. F4 Agent 执行与可审计（4 条）

*把"答错了"从玄学变成可排查的问题——记录必须真实、完整、无后门。*

1. **每次执行有唯一标识，并记录执行者、所属团队、输入、状态、最终结果**（REQ-11）🟡
   - 判据：每次问答都能查到一个 run，含输入与终态。
   - 现状：`agent_runs` 有 id / session_id / status / error / 耗时 / 模型；**无执行者与团队**（阶段 2 补）。
2. **关键步骤如实记录：检索证据、工具调用及输入输出、状态变化、错误信息；没有发生的步骤不得伪造**（REQ-12）🟢
   - 判据：轨迹里的步骤与真实调用一一对应；失败步骤必须出现，不能只显示成功的。
3. **状态至少区分：运行中 / 成功 / 失败 / 已取消 / 达到执行限制后终止**（REQ-13）🟡
   - 判据：故意停一次 → 状态是"已取消"，**不是"失败"**。
   - 现状：已有 `succeeded / failed / cancelled / timeout`；"达到迭代上限终止"并入失败码，**没有独立状态**。
4. **可请求停止自己有权管理的运行；不得把"收到停止请求"等同于"已经停止"，终态要如实**（REQ-16）🟢
   - 判据：停止后终态反映实际停在哪一步；已发出的模型调用未撤销要能看出来。
5. **（隐含，容易被漏）不存在绕过记录的路径**（REQ-11~16 的合并要求）🔴
   - 判据：所有作答入口都留轨迹。
   - 现状：`POST /api/knowledge/ask` **仍走独立链路、不留 run**——这是审计链上的一个后门。

**不做**：模型输出的确定性重放（只承诺"记录可回放"，不承诺"结果可重现"）、全套 APM、成本计费、执行记录的查询界面与权限（属 F5）。

## 4. F5 会话与执行记录（4 条）

*让上周那次的答案、引用和过程还能被找到，并且能接着聊。*

1. **能列出自己有权访问的会话（按最近更新排序），并且能接着聊；续聊不新开会话**（REQ-04）🟢
   - 判据：列表只出现自己的会话；接着问的追问落在同一条会话里，此前轮次是上下文。
2. **能查看执行轨迹：迭代轮次、工具调用及参数与返回、耗时、结束状态与原因**（REQ-14、REQ-15）🟡
   - 判据：每条回答能展开它那次运行；**失败步骤必须标出**。
   - 现状：`GET /api/harness/runs/{id}` 能查 run；但**查询无归属校验**，且轨迹条只在当次连接推送，重开页面看不到。
3. **重开会话时，当时的答案与当时的引用（文档名 / 位置 / 原文）仍在**（REQ-08 的持久化部分）🔴
   - 判据：关浏览器重开 → 答案原文与引用列表都还在，且与当时一致。
4. **每条回答保存时同时保存引用来源与对应的运行标识**（REQ-21）🔴
   - 判据：能由一条回答定位到唯一一次运行，三样（这句话 / 这些出处 / 那次运行）对得上。
   - 现状：`messages` 只有 id / conversation_id / role / content / created_at——**引用从未落库，消息与运行无关联**。

**不做**：团队级全员审计视图、会话导出、历史全文搜索、自动归档与保留期清理、编辑或删除单条消息、跨会话记忆。

## 5. F6 服务端能力（5 条）

*让系统能被程序使用，而不只是被人点。*

1. **核心业务能力必须能通过服务端接口完成，不依赖浏览器里的临时状态**（REQ-17）🟢
   - 判据：关掉前端，用 `curl` 走完"上传 → 提问 → 拿答案与来源 → 查轨迹"。
2. **可按运行标识查询状态与已保存的结果**（REQ-18）🟢
   - 判据：拿到 runId 就能查它的状态与结果，不必重跑。
3. **客户端断开不得导致已提交任务丢失；重连后可查已保存的状态与结果**（REQ-19）🟡
   - 判据：发完问题立刻断连 → 重连能查到结果。
   - 现状：有连接取消处理，但**未验证过"断连后任务继续跑完"**。
4. **错误反馈明确、稳定；不得泄露其他团队数据、内部凭据或敏感配置**（REQ-20）🔴
   - 判据：4xx/5xx 的错误体结构统一、能被程序判断；错误体里不含异常堆栈、路径、凭据。
   - 现状：全库错误体仍是 `{ message }`，**没有业务码**，调用方只能比对文案。
5. **存在一份平台级模型配置：供应商（端点、凭据）+ 可用模型；同一时刻只有一个激活供应商、每个供应商只有一个默认模型；凭据不得回传**（REQ-22）🟡
   - 判据：改配置后所有调用方下一次问答都走新配置；并发激活两个也只剩一个；任何读接口不返回凭据原文；配置失效时**明确报错，不静默走默认值**。
   - 现状：两张表 + 设置页已实现，凭据只回 `apiKeyConfigured` 布尔；缺口是**库内明文**、`is_active` **无唯一约束**、配置失效行为未验证。

**不做**：每团队自带模型供应商（BYOK）、模型路由与故障自动切换、按团队用量配额、多语言 SDK、GraphQL/gRPC。

## 6. 阶段 1 的总验收（五个域串起来的一句话）

> 打开系统 → 传一份 PDF → 问一个只有它有答案的问题 → 看到引用 → 展开轨迹 → 关浏览器重开，三样都还在 → 同样的事用 `curl` 也能做完。

**另外一条不计入功能验收、但必须做**：干净目录起一遍，全程无手工 SQL。
