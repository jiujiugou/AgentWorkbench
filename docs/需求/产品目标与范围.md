## 1. 产品定义

### 1.1 一句话

> **面向企业私有化部署的受控动作执行底座：把「模型想做什么」变成「系统真的做了什么」，保证不越权、不重复执行、办错了能追回。对外交付的是「底座 + 一个动作域」的完整系统；制造业 ERP 是第一版装进去的那个动作域，不是产品本身。**

方向再收拢成一句，用于所有范围取舍：

> **不做「会聊 ERP 的 AI」（厂商 copilot 已免费提供，做不出生意），做「能让 AI 安全碰 ERP 的那一层」（行业空白：没人交得出「不越权、不重复、能追回」的证明）。**

两层必须同时说清，缺一半都会读错：

- 只说「底座」→ 会读成卖框架、没有可交付的东西；
- 只说「ERP 动作 Agent」→ 会读成一套工单逻辑，把底座降成配角。

**底座不单独交付。** 客户拿到的是装好第一个动作域、能跑通完整动作的系统；「业务无关」是内部结构约束，不是对外售卖形态。

### 1.2 产品由两层组成

|                   | 组成                                                                                 | 认识外部系统吗                               |
| ----------------- | ---------------------------------------------------------------------------------- | ------------------------------------- |
| **底座**（主体，业务无关）   | Agent Runtime / Harness、编排层、知识层、记忆与状态层、工程保障层五层，**加工具层的「管辖」半边**                     | **完全不认识**。只认识工具名、不透明参数、步骤、片段、会话、轨迹、终态 |
| **动作域**（可替换，业务相关） | 企业应用层（身份、唯一 PDP、权限策略、字段映射、业务 API、管理入口）+ 工具层·适配器半边（`ActionSpec` 声明、ERP 具体调用、单据状态翻译） | 认识。所有业务语义集中在这里                        |

**工具层劈两半**：管辖（白名单 / JSON Schema / 参数校验 / 幂等键生成 / 去重表 / 审计落库）属于底座，同样不认识业务；只有适配器半边认识采购单。

底座**问，但不理解**，靠三个注入口（ADR 0017 §三）：

- `PermissionQuery(subject, action_key, scope)` → PDP 返回 allow/deny。底座知道「调用前必须问一次」，不知道「金额上限 5 万」；
- `ActionSpec` 由适配器声明，参数值对底座是**不透明 JSON**，只按 Schema 校验、按名绑定、原样透传；
- `TraceEvent` 结构在底座，**判据、题库、通过线由动作域注入**。

> **换域判据（AC-01）**：把 ERP 换成另一个动作域，底座五层一行代码不改，只换企业应用层的策略与工具层的适配器。这是「底座是主体」唯一可验证的含义。

**第一动作域（ERP）的形状**，属于动作域、不属于底座：

```
自然语言意图 → 结构化参数 → 契约校验 → 权限判定 → （写动作）挂起审批
             → 执行 → 幂等收口 → 轨迹落库 → 结果 / 外部单号
```

- **入口是任务，不是聊天框**：用户要的是「这张单到哪一步」「建一张草稿采购单」，不是一段建议。
- **知识层仍是底座能力，但不是主线**：v1 的知识库问答降为只读工具之一；主数据与文档片段是两套索引，交易数据实时查 ERP，不灌进向量库。
- **两个进程，状态只在一处**：C# 主服务是唯一对外入口、唯一状态持有者、唯一 PDP；Python 侧进程只提供 `/retrieve` `/embed` `/ingest` `/execute` 四个无状态内部端点（ADR 0013）。

### 1.3 这个定义排除了什么

| 排除                 | 含义                                 | 为什么                                             |
| ------------------ | ---------------------------------- | ----------------------------------------------- |
| **不是聊天机器人**        | 不承诺「答得像人」；查询与写动作必须落到真实数据或真实单据      | 一段看似合理的业务建议在 ERP 里没有价值，还可能诱导人照着做                |
| **不是一套写死的 ERP 逻辑** | 底座五层不得出现采购单、供应商、金额阈值、审批人角色等业务概念    | 写死一次，换域时权限、审计、轨迹全部要重做（ADR 0017）                 |
| **不是 Agent 平台**    | 不做可视化编排、插件市场、多租户 agent 实例等**交付形态** | 没有第一个真实动作之前，平台化只会生产「可被自己验收的东西」。**「底座可换域」≠ 平台化** |
| **不是 ERP 本身**      | 不建单据模型、不定义审批层级、不改业务口径              | 单据状态机属于 ERP；本产品只读取状态、按契约发起动作                    |
| **不是 RAG 产品**      | 检索是底座能力；答案质量指标不再是成功目标              | v1 的判据对象换了                                      |
| **不是对外 SaaS**      | 私有化部署、无公开注册、无计费                    | 沿袭 v1                                           |
| **不是 BPM 工作流引擎**   | 工作流只用于挂起 → 人批 → 恢复与断点续跑            | 编排是运行时机制，不是交付给用户的编排能力                           |
| **不是 RPA**         | 不模拟界面点击操作 ERP                      | 模拟点击的审计链路是断的，而审计恰是产品要卖的东西                       |

### 1.4 差异化在哪

> 通用 Agent 框架能给循环与工具协议，通用 AI 能给一段看似合理的业务建议；但都不替企业回答「这次动作在授权范围内吗、只执行了一次吗、办错了能追回吗」，也不保证换一个业务域时这些保证仍然成立。

价值 = **能执行 + 管得住 + 查得清**：「能执行」是入场券；「管得住」= 调用前拦截 + fail-closed 审批 + 动作域注入的权限四维（业务对象 × 操作 × 数据范围 × 金额阈值）；「查得清」= 幂等键、去重表、审计事件、`request_id` 贯穿、外部单号回写。

模型只负责把自然语言翻成参数，**难点全部在模型之外**。

### 1.5 与 v1「ERP 连接器不做」的关系

v1 排除的是「把 ERP 当**外部知识来源**同步进来」，该条款继续有效。第一动作域做的是另一件事：**把 ERP 当动作目标实时调用**——不同步数据、不做增量，但 v1 那三条理由（授权 / 同步 / 权限映射）一条都没躲掉，还要再加事务、幂等、审批、对账。不是改主意了，是换了一个更难的对象。

## 2. 行业依据与方向判据

### 2.1 行业共识（外部依据）

制造业 ERP + AI Agent 的落地已形成可引用的共识：

1. **三级能力分级**：Tier 1 只读（查 ERP、出建议）→ Tier 2 起草（备好 payload **等人批**）→ Tier 3 自主写（直接改 ERP，只用于范围窄、风险低、量大的动作）。**绝大多数生产部署停在 Tier 1/2**。
2. **能力层绝不绕过验证门直达记录系统**：Agent → 动作网关（schema 校验、实体映射、状态审计、fail-safe）→ ERP/MES/WMS。Agent **永不直接调 ERP API**，只调用受控的动作原语。
3. **模型输出一律当不可信数据**：自由文本永不进入执行路径；只有通过 schema 校验的结构体才能到网关——模型被注入操纵，它输出的东西也塞不进一个没有「提升权限」字段的结构体。

### 2.2 三条方向判据（怎么知道没跑偏）

| # | 判据                                                  | 做不到意味着            |
| - | --------------------------------------------------- | ----------------- |
| 1 | 换一个动作域，底座五层 **diff 为空**（AC-01）                      | 做的是 ERP 定制项目，不是产品 |
| 2 | 任取一笔动作，五个问题能答：**谁让做的、什么时候、看到了什么、依据哪条规则、ERP 里变成了什么** | 审计只是日志，不是证据       |
| 3 | **拿掉模型，系统还能安全地拒绝**                                  | 安全性依赖模型行为，等于没有安全性 |

第 3 条最容易被忽略：ERP 场景里 agent 会读到供应商 PDF、客户邮件、质检报告，这些都可能是注入攻击面。这就是 schema 边界比提示词更硬的原因（§2.1 第 3 条）。

### 2.3 四条边界（不做什么）

- **不做平台**：可视化编排、插件市场、多租户 agent 实例（§1.3）。
- **不做 RPA**：审计链一断，产品就不成立。
- **不做第二个真实动作域**：只做一次假动作集演练证明边界（§4.1 第 6 句）。
- **不做通用连接器**：一个 ERP、四个动作，跑通再抽象。

## 3. 目标用户与部署形态

### 3.1 三类用户

| 用户               | 关心什么                              |
| ---------------- | --------------------------------- |
| **业务操作员**        | 查单据状态、发起一个受控动作                    |
| **审批人**          | 确认写动作、拒绝并留理由、超时后接管（**v1 没有这个角色**） |
| **系统管理员 / 部署维护** | 工具白名单、动作域策略与适配器配置、凭据、审计查询、备份恢复    |

同一个人可兼任多职，但职责边界分开写——权限与验收标准不同。

### 3.2 部署形态

私有化、服务端：C# 主服务是唯一对外入口、唯一状态持有者、唯一 PDP；Python 侧为无状态能力进程（四端点），可同机部署。

### 3.3 第一版面向谁（诚实版）

**第一版没有真实客户，验证对象是 ERPNext 自托管实例的默认单据模型 + 一套可替换的适配器。** 它是第一个动作域，不是产品的边界。

选 ERPNext 的理由（已确认，2026-11-07）：REST API 完整、Docker 一条命令起、采购单 → 收货 → 发票 → 付款的状态机与字段校验都是**别人定的**——契约由外部设计、不迁就我们，会暴露自己想破头也想不到的问题。纯 mock 不算验证：契约自己编，验证的是想象。

### 3.4 不面向谁

个人用户、公众、超大规模组织（无组织树）、多租户 SaaS 运营。

## 4. 第一版成功目标

### 4.1 要证明什么

> **在一个由外部设计的单据模型上，系统能可靠执行 1 个只读动作 + 1 个带人工审批的写动作，且不越权、不重复、能追回；同时证明这些保证没有被写死在底座里。**

拆成六句可检验的话（每条都能写出反例）：

1. 用 ERPNext 真实 API 查到单据状态，返回带 ERP 状态码与时间戳；查不到时明确说查不到（不是 mock 返回值）。
2. 建一张草稿采购单，**未审批时零外部调用**；拒绝与超时过期都不执行。
3. 同一 `request_id` 连打两次，ERP 侧只有一张单，第二次返回首次结果。
4. 模拟超时，系统记「执行中」并发起状态查询，**不重放调用**；查不到转人工。
5. 任取一笔执行，五个字段齐全，能回答「谁在什么时候让系统做了什么」。
6. 用一个字段、策略、题库都不同的**假第二动作集**跑通同一套运行时，**底座五层 diff 为空**（AC-01 演练，不实现第二个真实域）。

### 4.2 不证明什么（比 4.1 更重要）

- **不证明有客户要、不证明业务口径对**：物料编码、税码、单位、成本口径每家不同，必须等真实客户。
- **不证明能对接任意 ERP**：只证明适配器接口可替换；每家系统仍要一套字段与权限映射。
- **不证明底座能单独作为产品交付**：对外交付的是「底座 + 动作域」的完整系统。
- **不证明模型 tool calling 稳定**：那是前提，不通过就换模型，不算成果。
- **不证明平台化交付形态成立**，也不证明答案质量（v1 的对象）。
- **功能数量、测试覆盖率、绿灯数量、文档篇数一律不是成功标准。**

> **开源 ERP 跑通 ≠ 真实客户可用。** 差异集中在字段与口径、真实权限模型、异常分支三处。

### 4.3 反馈源

v1 的教训：唯一稳定可得的反馈是绿灯，闭环退化成自己写需求、自己实现、自己验收。v3 把反馈源换成「**外部设计的单据模型不迁就我们**」——不依赖客户，但也不是自己编的。这一步堵得住绿灯自证，堵不住「有没有人要」，后者必须如实挂着。

## 5. 第一版范围

### 5.1 必须实现（按两层分列）

**A. 底座（业务无关，换域不改）**

| 范围项                                             | 归属             | 依据              |
| ----------------------------------------------- | -------------- | --------------- |
| 运行时五条不变量（可停 / 可拦 / 可回放 / 可恢复 / 不自作主张）           | C#（MAF 1.23.0） | ADR 0014 / 0016 |
| 编排 / 知识 / 记忆与状态 / 工程保障四层的底座侧能力                  | C# 为主          | 能力矩阵附录 C        |
| 工具层·管辖半边：白名单、JSON Schema、参数校验、权限前移、幂等键、去重表、审计落库 | C#             | ADR 0017 §二     |
| 三个注入口（端口定义，不含业务实现）+ 五字段错误信封                     | C#             | ADR 0017 §三     |
| Checkpoint 持久底座（MAF `CheckpointManager` + 幂等先行） | C#             | 已实施，2026-11-07  |
| 禁词扫描（AC-02）：扫类型名 / 字段名 / 方法名                    | CI             | ADR 0017 §六     |

**B. 第一动作域（ERP，可替换；换域只换这一组）**

| 范围项                | 说明                                                                                                | 依据         |
| ------------------ | ------------------------------------------------------------------------------------------------- | ---------- |
| 动作契约三类型            | `ActionSpec` / `ActionRequest` / `ActionResult`，含 JSON Schema；`SideEffecting` 标志在类型上分开「可重复」与「必登记」 | §6 依据 1    |
| 动作网关               | 四道校验按序：schema 校验 → 权限四维 → 业务规则 → 审计留痕；**任何一道不过 = fail-closed**，默认实现全部拒绝                           | §2.1 第 2 条 |
| 动作原语四个             | Query / Draft / Submit / Cancel；**Draft 与 Submit 拆开**（草稿可重复无副作用，提交有副作用必幂等）                        | §2.1 第 1 条 |
| 唯一 PDP + 权限四维      | 业务对象 × 操作 × 数据范围 × 金额阈值，策略由动作域注入                                                                  | ADR 0017   |
| 实体映射               | 物料 / 工单 / 供应商编码映射 + 冲突检测；**映射不过校验 fail-closed，不猜**                                                | §2.1       |
| 1 只读 + 1 写（强制人工审批） | 审批走**最小闭环**（已确认）：待办列表 + 单据详情 + 同意/拒绝两个按钮，不做管理后台                                                   | §3.1       |
| 假 ERP（假动作集）        | 内存实现四个原语；同时是网关测试装置与 AC-01 验收手段                                                                    | §4.1 第 6 句 |
| 审计五字段              | 意图、参数、审批人、结果、外部单号                                                                                 | §2.2 判据 2  |

### 5.2 后续版本（带重开条件）

| 范围项                   | 重开条件         |
| --------------------- | ------------ |
| 第二个真实动作域              | 出现第二个真实集成对象  |
| 真实客户的字段映射、权限模型、异常分支   | 有真实环境与业务专家   |
| 长期记忆                  | 能定义「什么算记错」   |
| 完整前端 / 管理后台           | 第一个真实使用者出现之后 |
| Python 侧深度接入（检索接动作链路） | M3 端到端跑通后决定  |

### 5.3 明确不做

| 不做                  | 理由                             | 出处          |
| ------------------- | ------------------------------ | ----------- |
| 把业务概念写进底座五层         | 换域时全要重做                        | AC-02       |
| 第一版实现第二个真实动作域       | 可换域 ≠ 平台化                      | §2.3        |
| 多 agent / 自主规划      | 制造业要确定步骤；两个 agent 争调度权破坏 R1/R3 | ADR 0016 B1 |
| **自动重放带副作用的工具调用**   | 超时后状态未知，可能建两张单；模型请求重试（无副作用）不放弃 | B2 / F9-03  |
| 自动执行写动作             | 写默认 `Ask` + fail-closed        | B6          |
| 可视化编排 / 插件市场 / 通用对话 | 无反馈源                           | §1.3        |
| ERP 数据同步 / 报表 / BI  | 那是 ETL 的活，与「动作可追责」无关           | §1.5        |
| 公开注册、部门树、逐文档 ACL    | 沿袭 v1                          | —           |

> **放弃 ≠ 容忍缺陷**：fail-open 类缺陷（工具重名静默保留、参数留痕丢类型）是必修项，不在放弃清单里（ADR 0016 §七）。

### 5.4 前提（不满足则整条路不成立）

1. `dotnet build` 一条命令全通 —— **已达成**（2026-11-07 restore 破案，环境变量问题）。
2. 一个能真连的 ERPNext 实例（Docker 自托管，自带 demo 数据）。
3. 目标 ERP 有没有幂等能力 / 能否按外部单号查状态——有与没有是两套架构，不能假设。
4. Python 仓 94 处改动落 git（冻结的前提是版本控制先落定）。

## 6. 范围判定的五条依据

1. **动作正确性 > 功能齐全**：1 只读 + 1 写跑通，比十个工具停在 mock 上有信息量。
2. **状态只在一处**：C# 负责「决定」，Python 负责「算」。
3. **业务语义只在一处**：底座只定义端口，动作域实现并注入。
4. **反馈源必须不迁就我们**：外部单据模型 > mock > 绿灯，排序不能倒。
5. **判据跟着对象走**：先定表结构（对象），再定判据（结论）；第一批只 5 条运行时 + 8 条动作 + 2 条边界。
