## 1. 产品定义

### 1.1 一句话

> **AgentWorkbench 是一套面向企业团队、支持私有化部署的多用户 AI 知识工作台。**

### 1.2 展开

企业管理员可以管理团队成员；团队成员可以导入或使用企业文档，通过自然语言查询自己有权访问的知识，并获得附带原始来源引用的答案。

系统需要保留每次 Agent 执行的关键过程记录，包括输入、检索证据、工具调用、执行状态变化和最终结果，使授权用户能够查询和审查执行过程。

### 1.3 这个定义排除了什么

**边界靠"不是什么"才立得住**。以下四条任何一个被违反，产品就变成了别的东西：

| 排除 | 含义 | 为什么排除 |
|---|---|---|
| **不是通用聊天助手** | 答案必须来自企业文档，不允许凭通用知识作答 | 一旦允许自由发挥，权限与引用就都失去意义 |
| **不是对外 SaaS 平台** | 第一版部署在客户自己的环境里，不提供公开注册 | 公开运营要处理计费、滥用、合规、SLA，与"验证产品是否成立"无关 |
| **不是文档管理系统** | 只管理"被问答所需"的文档，不做版本、流程、协同编辑 | 那是另一个产品，做了会拖垮 MVP |
| **不是数据分析工具** | 不做报表、统计、趋势分析 | 那是 BI 的范围，"查知识"和"算指标"是两种问题 |

### 1.4 差异化在哪

市场上已有成熟的知识库产品。本产品的立足点不是"功能更多"，而是：

> **通用 AI 答得再好，也没法向企业证明「这个答案只来自我司内部文档，而且只有该看的人看到了」。**

所以产品的价值 = **能问答 + 管得住 + 查得清**。

- "能问答"已经是通用能力，不构成差异化
- "管得住"（权限）与"查得清"（执行过程可回放）才是

第二条尤其关键：**多数知识库产品能做到"答案有引用"，但做不到"检索证据与执行过程可回放"**——而"答错了为什么错"恰恰是上线后第一个被问到的问题。

## 2. 目标用户

### 2.1 三类用户

| 用户 | 关心什么 |
|---|---|
| **企业管理员** | 负责团队成员管理、知识资料管理和系统日常使用 |
| **企业成员** | 通过自然语言查询企业知识，查看答案及其来源 |
| **系统部署维护人员** | 负责部署、运行、备份和故障恢复 |

> 注意：第一版中"企业管理员"与"系统部署维护人员"**很可能是同一个人**（小团队场景），但两者的职责边界必须分开写——因为它们的权限与验收标准不同。

### 2.2 第一版面向谁

**一个有实际知识查询需求的企业团队。**

不是"所有企业"，也不是"个人用户"。第一版的验证对象是**一个真实团队**，它的规模、行业、文档量都不预设——但必须真实存在，且真的在用。

### 2.3 不面向谁

- **个人用户**：不为单人使用做优化（不做免登录、不做本地模式）
- **公众**：不做公开注册与公开运营
- **超大规模组织**：不做多级组织树、不做跨部门复杂授权（第一版权限只到团队边界）

## 3. 核心价值

| # | 价值 | 具体含义 | 对应需求 |
|---|---|---|---|
| 1 | **知识可用** | 用户能够通过自然语言查询企业文档，而不必逐份查阅原始资料 | REQ-07 / REQ-08 |
| 2 | **答案有据** | 答案应提供能够对应到原始资料的引用，用户可以核查依据 | REQ-08 |
| 3 | **访问受控** | 用户只能访问自己有权查看的知识和执行记录 | REQ-AUTH-02 ~ 06 |
| 4 | **过程可查** | 出现错误答案或执行异常时，可以查看本次执行记录，分析问题发生在哪里 | REQ-11 ~ 15 |
| 5 | **部署可控** | 系统能够部署在企业自行管理的环境中 | NFR-07 / NFR-08 |

**五条价值里，第 2、3、4 条是差异化，第 1 条是入场券，第 5 条是销售前提。**

第 1 条不做到，产品不存在；第 2、3、4 条不做到，产品没有存在理由。

## 4. MVP 成功目标

### 4.1 要证明什么

第一版需要证明：**一个真实团队能够在独立部署的系统中完成文档入库、知识问答、引用核查和执行过程审查，同时满足成员访问控制、数据隔离和基本运行维护要求。**

拆成四句可检验的话：

1. 有人真的把文档传进去了（不是测试数据）
2. 有人真的用它问了问题，并看了引用（不是演示）
3. 有人真的在答错时打开执行记录找原因（不是"知道有这功能"）
4. 这套东西能被别人装起来、备份、恢复（不是只在开发机上跑）

### 4.2 不证明什么

> 产品是否具有足够的市场竞争力，仍需通过真实用户使用进行验证，**不作为仅凭功能实现即可判定的结论**。

同理，以下都不属于 MVP 的成功标准：

- 功能数量达到多少条
- 测试覆盖率达到多少
- 支持了多少种模型、多少种文档格式
- 有没有人愿意付钱

**MVP 只回答一个问题：这条路通不通。** 通不通的标准是"有人真的用起来了"，不是"功能都做完了"。

## 5. 第一版范围

### 5.1 必须实现

| 范围项 | 对应需求 |
|---|---|
| 多用户注册、登录与团队成员管理 | REQ-01 ~ REQ-03 |
| 团队级数据隔离 | REQ-AUTH-02 / NFR-01 |
| PDF 文档上传、处理状态与知识检索 | REQ-05 ~ REQ-07 |
| 带原始来源引用的知识问答 | REQ-08 / REQ-09 |
| Agent 执行记录、步骤查询和过程审查 | REQ-11 ~ REQ-15 |
| 长任务状态查询、停止请求及客户端断连后的状态恢复查询 | REQ-16 / REQ-18 / REQ-19 |
| 独立部署、基本运行监控和备份恢复 | NFR-07 ~ NFR-09 |

### 5.2 后续版本

| 范围项 | 为什么第一版不做 |
|---|---|
| 团队内部的文档级、部门级或岗位级权限 | 权限矩阵是 `团队 × 成员 × 文档` 三维组合，漏一处就漏数据；第一版先锁死"团队边界"，把矩阵留到有真实授权需求时再做 |
| 飞书、Confluence、企业网盘、ERP 等外部知识来源连接器 | 每接一个来源 = 一套授权 + 增量同步 + **来源侧权限映射**，与 AI 能力无关，属于无底洞 |
| 租户配额、用量管理及更完整的管理员界面 | 有真实用户后才谈得上"管理"；此刻管理员界面只需够用 |
| 更完善的审计查询、运维分析与告警 | 先有"能查到"，再谈"查得方便" |
| 经过真实使用验证后增加的行业专用功能 | 没有真实使用之前，任何"行业功能"都是猜的 |

### 5.3 明确不做

| 不做 | 理由 |
|---|---|
| 模型训练与微调平台 | 与产品价值无关；模型能力由供应商负责 |
| 通用 Agent 编排 DSL、可视化拖拽工作流设计器 | 有成熟产品（Dify / Coze 等），自研是重复劳动；本产品的价值在"管得住、查得清"，不在编排 |
| 计费与支付系统 | 第一版不对外运营 |
| 移动端 App | 企业知识查询以桌面为主；做 App 会吃掉大半工期 |
| 第一版面向公众运营的多租户 SaaS 平台 | 与 §1.3 的定位冲突；公开运营要处理合规、滥用、SLA |
| 对 Agent 输出进行确定性重放的承诺 | LLM 输出不确定；**承诺重放等于承诺无法兑现的事**。我们承诺的是"记录可回放"，不是"结果可重现" |

> 最后一条尤其重要：**"可回放"和"可重现"是两回事**。前者是记录历史，后者是保证结果一致——后者在 LLM 场景下做不到，任何声称能做到的产品都在说谎。

## 6. 范围判定的三条依据

范围不是拍脑袋定的，以下三条是取舍的统一理由：

### 依据 1：能用一次 > 功能齐全

只要能跑通一次真实使用，缺的功能都会有人提；跑不通一次，功能再多也没人用。

所以"必须实现"里没有任何一条是"锦上添花"——**七项里少任何一项，一个团队就没法完整走一遍**。

### 依据 2：与 AI 能力无关的复杂度一律后置

第三方连接器、计费、配额、组织树——这些都难在产品工程，不难在 AI 能力。它们可以晚做，且晚做不影响核心验证。

反过来，"权限"和"执行记录"虽然也难，但它们**正是产品的差异化**，所以必须第一版做。

### 依据 3：权限先到边界，不到矩阵

第一版只回答"这个人属不属于这个团队"，不回答"这个人能不能看这份文档"。

理由是复杂度不对称：**租户边界是二维的（属于/不属于），文档授权是三维的（团队 × 成员 × 文档）**。二维能靠一条 SQL 条件守住，三维要靠一个权限服务 + 全量测试，量级差一个数量级。
