## 1. 功能域总览

产品拆为 **6 个功能域、33 条需求**。功能域是"一组必须一起成立的能⼒"，不是"一组代码"。

| 域 | 目标（一句话） | 需求编号 | 能否独立成立 |
|---|---|---|---|
| **F1 身份与访问控制** | 回答"你是谁"和"你能碰什么" | REQ-AUTH-01~11、REQ-01~03 | 是所有域的前提 |
| **F2 知识资料管理** | 把企业的纸变成**可检索、可引用的证据** | REQ-05、REQ-06、REQ-10 | 否，需 F1 |
| **F3 知识问答** | 把问题变成**带原始出处的答案** | REQ-07、REQ-08、REQ-09 | 否，需 F1 + F2 |
| **F4 Agent 执行与可审计** | 把"答错了"从玄学变成**可排查的问题**（写入侧） | REQ-11、REQ-12、REQ-13、REQ-16 | 否，需 F1 + F3 |
| **F5 会话与执行记录** | 让上周那次的答案、引用和过程**还能被找到**（读取侧） | REQ-04、REQ-14、REQ-15、REQ-21 | 否，需 F1 + F3 + F4 |
| **F6 服务端能力** | 让系统能被**程序**使用，而不只是被人点；并提供**全局唯一**的模型配置 | REQ-17~20、REQ-22 | 否，需 F1~F5 |

**33 条需求全覆盖，无遗漏、无重叠。**（REQ-AUTH-07~11 为引入成熟账户框架后补充的 5 条，见 §2.5；REQ-21 为新增的"历史结果持久化"，见 §6；REQ-22 为"平台级模型配置"，见 §7）

**两处归属调整，各有理由：**

| 调整 | 原归属 | 现归属 | 理由 |
|---|---|---|---|
| REQ-04 会话管理 | F1 | **F5** | F1 关心的是"这份会话归谁"（由 REQ-AUTH-03 表达）；"能看到自己的历史会话、能接着聊"是产品能力，不是访问控制 |
| REQ-14 / REQ-15 | F4 | **F5** | F4 的任务是**把记录写对、写全、无后门**；"谁怎么读到它"是另一个问题，混在一起会让 F4 的验收对象变模糊 |

**F4 与 F5 是同一条链的两端，不是两个功能：** F4 负责"记录必须存在且真实"，F5 负责"记录必须能被读到并能接着用"。**只做 F4，数据写了没人看（等于死数据）；只做 F5，看到的是空壳。**

优先级排序不是按上表顺序，而是按 §4 的依赖链——**能独立跑通的最小闭环，从 F1 开始必然经过 F2 到 F3，F4 是"能不能被信任"的分界，F5 是"能不能被集成"的分界。**

## 2. F1 身份与访问控制

### 2.1 这个域为什么存在

没有它，产品就是一个**公开的聊天框**——任何人都能看任何文档，任何答案都没有归属。它是产品差异化的地基（"管得住"）。

### 2.2 核心能力

| # | 能力 | 说明 | 需求 |
|---|---|---|---|
| 1 | **身份识别** | 除健康检查等明确公开的接口外，一切业务操作都必须经过身份验证 | REQ-AUTH-01 |
| 2 | **注册与登录** | 用户可注册、登录、登出；系统能识别当前请求属于谁 | REQ-01 |
| 3 | **团队与成员** | 新用户注册后获得初始团队与管理员身份；管理员可查看成员并通过受控流程邀请他人 | REQ-02、REQ-03 |
| 4 | **团队隔离** | 一个团队的成员不能读取其他团队的任何数据 | REQ-AUTH-02 |
| 5 | **会话归属** | 成员只能读取、续聊、删除自己有权访问的会话；未授权访问**不得修改原数据** | REQ-AUTH-03 |
| 6 | **知识访问控制** | 检索与答案生成必须遵守知识资料的权限；**不得因模型能推断就绕过** | REQ-AUTH-04 |
| 7 | **执行记录访问控制** | 成员只能查看自己有权查看的执行记录，**含其中的输入、证据、工具参数与结果** | REQ-AUTH-05 |
| 8 | **默认拒绝** | 无法确认身份、归属或权限时，**不得默认授予** | REQ-AUTH-06 |

> **本域只管"能不能"，不管"看到什么"。** 会话历史的列表、续聊、轨迹展开属于 F5（§6）；这里只规定"别人的会话你不能动"。这条界限不划清，F1 会一路膨胀成"所有功能都要过一遍权限"，而 F5 则变成没人负责的空壳。

### 2.3 边界（本域不做什么）

| 不做 | 理由 |
|---|---|
| 团队内部的文档级 / 部门级 / 岗位级授权 | 见 [产品目标与范围.md](产品目标与范围.md) §6 依据 3：三维矩阵量级高一个数量级，第一版先锁团队边界 |
| 单点登录（SSO / LDAP / OAuth 对接） | 第一版是企业自己部署、自己管账号，对接外部 IdP 属于后续版本 |
| 多级组织树 | 一个用户属于一个团队，不做"公司—部门—小组"层级 |
| 密码找回 / 邮件验证 | 第一版由管理员重置，不做自助找回（避免引入邮件服务依赖） |

### 2.4 本域的隐含要求

> **"拒绝"必须是可观察的，不是静默失败。**

越权访问返回 404 而不是 403（不泄露资源是否存在），但**同时必须留下可查的拒绝记录**——否则运维无法回答"他到底是没权限，还是系统坏了"。这条不写进 REQ，因为它跨 F1 与 F5，属于两个域的接口约定。

### 2.5 账户行为需求（REQ-AUTH-07~11）

**这 5 条是为"接入成熟的账户框架"补的。** 此前 F1 只定义了"能不能进"和"能看什么"，没定义**账户本身会经历什么状态**——而一个成熟框架一接进来，这些状态就自动存在了。需求不写，它们就会以框架默认值的形式进入产品，没人验收、也没人反对。

| # | 需求 | 判据（可验收） |
|---|---|---|
| **REQ-AUTH-07** | **登录失败限制**：连续失败达到阈值后，该账户在设定时长内拒绝登录；阈值与时长必须可配置 | 连续失败 N 次后登录被拒；等待时长后自动恢复；**提示不得透露剩余时长，也不得透露账户是否存在** |
| **REQ-AUTH-08** | **账户停用与恢复**：管理员可停用成员；停用后新登录被拒，**已签发的会话在约定窗口内失效**；恢复后可重新登录 | 停用后用旧 cookie 访问必须被拒（不只是拦新登录）；恢复后可正常登录。**"停用"与"因失败被锁定"必须是两个独立状态与两个独立操作** |
| **REQ-AUTH-09** | **凭据变更后会话失效**：改密或由管理员重置密码后，其他已签发的会话在约定窗口内失效 | 改密后，用改密前签发的会话访问必须被拒（在窗口到期后立即生效） |
| **REQ-AUTH-10** | **成员管理的权限边界**：只有本团队管理员可管理本团队成员；**不得将成员提升到高于自己的角色**；不得停用或删除自己 | 普通成员调用成员管理接口被拒；管理员无法产出高于自身的角色；对自己执行停用被拒 |
| **REQ-AUTH-11** | **首个管理员的最小可复现路径**：全新部署后，必须存在一条明确、可重复的路径产生一个能创建首个团队的管理员；**该路径不得依赖"已存在另一个管理员"** | 空库启动后，按文档步骤能在无人协助下得到第一个可登录的管理员账号 |

**两条共同约束：**

1. **窗口必须写进配置，不能写死在代码里。** REQ-AUTH-08 / 09 里都出现"约定窗口"——它不是模糊表述，而是要求把窗口长度作为配置项写下来（例如会话校验间隔 30 分钟）。没有具体数字，这两条无法验收。
2. **框架自带、但本节没有列出的能力，第一版一律关闭。** 两因素认证、邮箱确认、外部登录（OAuth/企业微信）、自助找回密码——每开一项，必须先补一条 REQ 和对应验收。**理由不是"用不上"，而是"开了没人验收，就等于扩大了攻击面"。**

## 3. F2 知识资料管理

### 3.1 这个域为什么存在

答案的"依据"全部来自这里。**如果这一步是脏的，后面再好的检索和模型都只是在脏数据上做推理。**

### 3.2 核心能力

| # | 能力 | 说明 | 需求 |
|---|---|---|---|
| 1 | **文档上传** | 团队管理员可上传 PDF；不支持或无法处理的文件必须给出明确反馈 | REQ-05 |
| 2 | **处理状态** | 显示处理状态与必要错误信息；**只有处理成功的文档才能被标记为可检索** | REQ-06 |
| 3 | **删除与索引清理** | 删除后不得通过正常检索被引用；删除范围必须覆盖索引与派生内容 | REQ-10 |

### 3.3 边界（本域不做什么）

| 不做 | 理由 |
|---|---|
| PDF 以外的格式（Word / Excel / 图片 / 网页） | 第一版只做一种格式，把它做透比支持八种都做半吊子强 |
| 文档版本管理（v1 / v2 / 历史回滚） | 属于文档管理系统范畴，见 [产品目标与范围.md](产品目标与范围.md) §1.3 |
| 在线预览与编辑 | 只提供"可核查原文"的只读访问，不做编辑器 |
| 文档级权限 | 同 F1 §2.3 |
| 外部知识来源连接器（飞书 / Confluence / 网盘 / ERP） | 每个连接器 = 授权 + 增量同步 + 来源侧权限映射，与 AI 能力无关 |

### 3.4 本域最关键的一条判断

> **"处理中"和"处理失败"必须对用户可见，不能让失败的文档看起来像"资料里没有"。**

这是 REQ-06 存在的唯一理由。一旦失败被伪装成可用，用户会得到"查不到"的答案，然后怀疑是 AI 不行——**实际是文档根本没入库**。这类问题的排查成本极高，因为症状和"检索不准"一模一样。

## 4. F3 知识问答

### 4.1 这个域为什么存在

产品的门面。用户感知到的全部价值，发生在这一个域里。

### 4.2 核心能力

| # | 能力 | 说明 | 需求 |
|---|---|---|---|
| 1 | **知识检索** | 根据用户问题查询**当前团队可访问**的知识资料 | REQ-07 |
| 2 | **引用展示** | 结果必须包含可核查来源：**文档名称、相关位置、对应原文片段**（三者缺一不可） | REQ-08 |
| 3 | **无证据时明确说明** | 检索不到足够证据时，必须明确告知资料不足，**不得把无依据内容伪装成来自企业文档** | REQ-09 |

### 4.3 边界（本域不做什么）

| 不做 | 理由 |
|---|---|
| 通用知识问答（不检索直接答） | 违反"不是通用聊天助手"定位；一旦允许，权限与引用全失效 |
| 多轮复杂任务编排（"帮我整理一份报告"） | 那属于 Agent 编排，与"查知识"是两种产品 |
| 主动推送 / 定时摘要 | 第一版是"问—答"模型，不做主动式 |
| 生成新内容（改写、翻译、扩写） | 只做"基于已有资料作答"，不做创作，否则引用失去意义 |

### 4.4 本域最关键的一条判断

> **REQ-09（无证据时拒答）比 REQ-08（给出引用）更难，也更重要。**

给出引用只是"有依据"；承认"没依据"才是**可信**。前者做不好会被发现，后者做不好会被信任——**然后在一个关键问题上误导用户**。

这也解释了为什么这个域的真正难点不在模型，而在**判定"够不够"的阈值与可测量性**（见 [非功能需求.md](非功能需求.md)）。

## 5. F4 Agent 执行与可审计

### 5.1 这个域为什么存在

**这是本产品最独特的域。** 一般知识库产品做到"答案有引用"就停了；本产品要做到"**答错了为什么错**"。

它把一次问答从"结果"变成"过程"，从"玄学"变成"可排查"。

**本域只负责"写"这一侧：记录必须被写入、写全、写对、没有绕过通道。** 记录怎么被读到、怎么被读懂，属于 F5（§6）。这个切分不是为了对称——它决定验收对象：本域的验收是"库里有没有这一行、这一行是不是真的"，F5 的验收是"界面上能不能看到、看到的是不是当时那次"。

### 5.2 核心能力

| # | 能力 | 说明 | 需求 |
|---|---|---|---|
| 1 | **执行记录** | 每次执行必须有唯一标识，并记录执行者、所属团队、输入、状态与最终结果 | REQ-11 |
| 2 | **关键步骤记录** | 反映实际发生的步骤：检索证据、工具调用及输入输出、关键状态变化、错误信息；**没有发生的步骤不得伪造** | REQ-12 |
| 3 | **执行状态** | 至少区分：运行中 / 成功完成 / 执行失败 / 已取消 / 达到执行限制后终止 | REQ-13 |
| 4 | **执行停止** | 可请求停止自己有权管理的运行；尽可能终止后续请求；**明确记录最终状态** | REQ-16 |

> **"记录查询"（REQ-14）与"过程审查"（REQ-15）已移入 F5。** 它们描述的是读侧视图与权限，而本域的四条全部回答同一个问题：**这次运行在库里留下了什么、是否真实。**

### 5.3 边界（本域不做什么）

| 不做 | 理由 |
|---|---|
| 对模型输出的确定性重放 | LLM 输出不确定；承诺重放等于承诺无法兑现的事。**本域承诺"记录可回放"，不承诺"结果可重现"** |
| 全链路 APM / 分布式追踪（OpenTelemetry 全套） | 这是内部工具的能力，不是产品承诺；第一版只做"业务级执行记录" |
| 成本核算与计费 | 后续版本 |
| 执行记录的无限期在线查询 | 保留策略见 [待确认决策.md](待确认决策.md)，第一版不做归档 |
| **执行记录的查询界面与权限过滤** | 属于 F5。**放在这里会让"写入是否真实"和"读取是否越权"混成一条验收** |

### 5.4 三条容易犯错的地方

**① "记录"不等于"审计"。**

记录 = 把发生的事写下来。
审计 = 保证**每条路径都留痕**，没有后门。

这两者差一个数量级的工作量。只要存在一条绕过记录的路径，审计链就是断的——**被质疑时无法证明"没被记录的操作不存在"**。

**② "停止"不等于"已经停止"。**

REQ-16 明确要求不得把"收到停止请求"等同于"所有操作已经停止"。已发出的外部请求（模型调用、工具调用）不一定能撤销，所以**终态必须如实反映"实际停在哪一步"**。

**③ 状态机比状态列表重要。**

需求只要求"至少区分五种状态"，但真正的难点是**状态迁移是否合法**：能不能从"已取消"变成"成功完成"？能不能在"失败"之后再写步骤？

没有合法迁移规则的实现，会写出"看起来有状态、实际自相矛盾"的记录——而这比没有记录更糟，因为它会被当成证据。

## 6. F5 会话与执行记录

### 6.1 这个域为什么存在

前面四个域都在回答"**这一次**问得对不对"。这个域回答另一个问题：

> 上周三那次问过什么、当时它答了什么、依据是哪几段、过程长什么样。

没有它，F3 的答案和 F4 的记录都只在当次连接里有效——刷新页面就消失，产品退化成"一次性问答机"。

**本域不产生任何新数据，只负责让已有数据被读到、被读懂、被接着用。**

### 6.2 核心能力

| # | 能力 | 说明 | 需求 |
|---|---|---|---|
| 1 | **查看历史会话** | 列出当前用户有权访问的会话，按最近更新排序，显示标题与时间；**列表不得出现他人会话**（连"存在一条你看不到的会话"都不可推断） | REQ-04 |
| 2 | **继续已有对话** | 选定一条会话后追问，**此前轮次作为上下文**；续聊产生的消息与原会话同属一条会话，不新开会话 | REQ-04 |
| 3 | **查看执行轨迹** | 每条回答可展开其运行记录：迭代轮次、工具调用及参数与返回、耗时、结束状态与原因；**失败步骤必须标出，不得只显示成功步骤** | REQ-14、REQ-15 |
| 4 | **查看历史结果及引用** | 重开会话时，**当时的答案与当时的引用（文档名称、位置、原文片段）仍在**，不依赖浏览器当时的临时状态 | REQ-08、**REQ-21** |

**REQ-21（新增）· 历史结果的持久化与运行关联**

| 项 | 内容 |
|---|---|
| 需求 | 每条助手回答在保存时，必须同时保存**该回答的引用来源**与其**对应的执行记录标识**，使得重开会话后能完整还原"这句话、这些出处、那次运行" |
| 判据 | 提问后关闭浏览器，重新登录打开同一会话：①答案原文可见；②引用列表可见且与当时一致；③能由该条回答定位到唯一一次运行记录 |
| 现状 | `messages` 只有 `role` / `content` / `created_at`；**引用只通过实时推送发过一次，从未落库**；消息与 `agent_runs` 之间没有关联字段 → 重开会话时引用消失，也无法判断"这条回答是哪次运行产生的" |

**为什么它必须是一条独立需求，而不是"顺手加两列"**：它定义了"一条回答由哪些部分组成"。现在一条回答实际是三块（正文、引用、运行），却只保存了一块。**只要有一块没保存，"可回放"这个承诺在用户侧就是不成立的**——用户看不到的地方，等于没有。

### 6.3 边界（本域不做什么）

| 不做 | 理由 |
|---|---|
| 团队级审计视图（管理员浏览全员历史） | REQ-AUTH-05 的边界是"自己有权查看的"；团队级审计是另一个产品面，第一版不做 |
| 会话导出（PDF / Markdown / 批量下载） | 导出把数据带出系统，权限随之失效（转发不受控）；后续版本再说 |
| 历史会话的全文搜索 | 需要独立索引，与知识检索是两套东西；不做不代表不重要，是**第一版不混进知识库索引** |
| 自动归档 / 保留期清理 | 见 [待确认决策.md](待确认决策.md)；第一版不做清理，**但也不得对外承诺"永久保留"** |
| 编辑或删除单条消息 | 会破坏"回答↔运行记录"的对应关系，审计链随之断裂；只允许删除整个会话 |
| 跨会话的上下文记忆（"还记得我上次说的吗"） | 长期记忆是后续版本；第一版只在**同一条会话内**续聊 |

### 6.4 本域最关键的一条判断

> **"能看到历史"不是前端缓存，是服务端契约。**

判据就一句话：**换一台电脑、换一个浏览器，登录同一账号，历史会话、当时的答案、当时的引用、当时的轨迹，必须一模一样。**

如果某样东西只存在于当次连接的推送里（当前**引用**就是这样），它重开就消失。用户会认为"系统没保存"，而事实是**从未保存过**——这两个问题在界面上长得完全一样，排查成本却差得远。

### 6.5 一条容易被忽略的差异：轨迹按"运行"存，历史按"会话"看

一次会话会有多次运行（每问一次一次）。`agent_runs` 以 `session_id` 关联会话，所以按会话能列出全部运行。

缺的是**回答与运行的对应**：`messages` 里没有 run 标识。后果很具体——

> 重开会话时，能看到 3 条回答、也能看到 5 次运行，**但说不清哪条回答来自哪次运行**。

REQ-21 要补的正是这个连接点。没有它，"查看执行轨迹"在历史场景下只能退化成"把这次会话的所有运行堆在一起"，等于没回答"这句话为什么这么答"。

## 7. F6 服务端能力

### 7.1 这个域为什么存在

产品形态是**服务端为主**（见 [产品目标与范围.md](产品目标与范围.md) §1.2）：**把前端整个删掉，核心价值仍完整。**

这个域是那个判断的落地检查表。它包含两类东西，**性质不同**：

| 类型 | 内容 | 验收方式 |
|---|---|---|
| **接口属性** | 能力可只经 HTTP 完成、断连不丢任务、错误稳定 | 调接口，库里查不到 |
| **平台配置** | 模型供应商与可用模型（全局共享） | 查配置、看是否对所有人一致 |

### 7.2 核心能力

| # | 能力 | 说明 | 需求 |
|---|---|---|---|
| 1 | **独立接口使用** | 核心业务能力必须能通过服务端接口完成，**不得依赖浏览器中的临时状态** | REQ-17 |
| 2 | **运行状态查询** | 调用方可按运行标识查询状态与已保存的执行结果 | REQ-18 |
| 3 | **断连容忍** | 客户端断开**不得导致已提交任务丢失**；重连后可查已保存的状态与结果 | REQ-19 |
| 4 | **错误反馈** | 返回明确、稳定的错误信息；**不得泄露其他团队数据、内部凭据或敏感配置** | REQ-20 |
| 5 | **平台级模型配置** | 管理员配置模型供应商（端点、凭据）与可用模型；**配置全局共享，所有团队使用同一套**；凭据**不得回传**给任何客户端 | **REQ-22** |

**REQ-22（新增）· 平台级模型配置**

| 项 | 内容 |
|---|---|
| 需求 | 系统必须存在一份**平台级**的模型配置：供应商（名称、端点、凭据）与可用模型（标识、显示名、默认项），且同一时刻**只有一个激活供应商**、每个供应商**只有一个默认模型** |
| 判据 | ① 修改配置后，所有团队的下一次问答都走新配置（不是只有当前用户）；② 同一时刻只允许一个供应商处于激活态——**并发激活两个时也必须只剩一个**，不允许出现两行 `is_active = 1`；③ 任何读接口返回的配置里**不得包含凭据原文**；④ 未配置或配置失效时，问答返回明确错误，**不得静默用默认值胡答** |
| 现状 | 两张表 + `SettingsController` + 设置页**都已实现**；判据③已满足（只返回 `apiKeyConfigured` 布尔）。缺口：**`api_key` 库内明文**（未加密）；`is_active = 1` **库层无唯一约束**（应用层靠事务"先全清 0 再置 1"，正常路径不会出两个，但并发或直接 SQL 可以）；`provider_models` 缺 `UNIQUE(provider_id, model)`、**判据④未验证**（配置失效时是报错还是静默走默认值，没有测试） |

**为什么它是"服务端能力"而不是"系统设置"**：模型端点是**全系统共用的一个资源**。前端、curl、未来的第三方客户端拿到的必须是同一套——如果它能按用户或按团队分叉，那"同一份答案前提一致"就不成立了。

### 7.3 边界（本域不做什么）

| 不做 | 理由 |
|---|---|
| **每团队自带模型供应商（BYOK）** | 会把"一套部署一个模型来源"变成"每个团队各自一份凭据"，运维与排障成本翻倍；且凭据分散后无法统一审计。**这是刻意选的全局共享，不是没做** |
| 模型路由 / 多供应商负载均衡 / 故障自动切换 | 第一版只认"当前激活的那一个"；切换是人工动作，不是自动策略 |
| 按团队或按用户的用量统计与配额 | 需要用量表（当前没有），属于后续版本 |
| 公开 SDK（各语言客户端） | 有了稳定的 HTTP 契约，SDK 是包装工作；第一版不做 |
| GraphQL / gRPC | REST 够用；多一套协议 = 多一套要维护的契约 |
| 对外 API 的版本化承诺（v1 冻结） | 第一版客户就是自己人，契约可以动；**但一旦有外部调用方，必须立刻做版本** |
| 第三方应用市场 / 插件体系 | 后续版本，需先有稳定契约 |

### 7.4 本域最关键的一条判断

> **F6 是"服务端为主"的验收单。任何一条不成立，产品就退化成了"只能在浏览器里用的网站"。**

特别提醒 REQ-19：**断连容忍是"服务端状态"的证明。** 如果任务会随连接消失，说明状态其实在前端——那整个 F4 的可审计承诺也就无从谈起。

**REQ-22 是这五条里唯一"配置错了会让所有答案都错"的一条。** 其余四条的失败是"某个功能不可用"，它是"整个产品在用一个错的模型回答所有人"——而且不会报错。所以它的判据里特意加了第 ④ 条：**配置失效时必须明确失败，不得静默降级**。

## 8. 域之间的依赖与实现顺序

```
F1 身份与访问控制
   │  （所有域的入口，没有它其余都是裸奔）
   ▼
F2 知识资料管理
   │  （没有它，F3 检索的是空集）
   ▼
F3 知识问答
   │  （这是最小可用闭环：能问、能答、有引用）
   ▼
F4 Agent 执行与可审计 ──（写：记录必须真实、完整、无后门）
   │
   ▼
F5 会话与执行记录 ─────（读：记录必须能被找到、被读懂、被接着用）
   │  （没有它，F3 的答案和 F4 的记录都只在当次连接里有效）
   ▼
F6 服务端能力
       （有了它，才从"人点"变成"可集成"）
```

**F4 与 F5 是同一条链的两端**：F4 保证"库里有这一行且它是真的"，F5 保证"这一行能被看到、能和产生它的那句回答对上"。**先做 F4 再做 F5 是可行的；反过来不成立**——没有记录，读侧只能显示空。

**但实现顺序不是严格串行**，理由：

| 阶段 | 做什么 | 能验证什么 |
|---|---|---|
| 第一段 | F1 + F2 + F3 的最小链路 | 一条真实问答跑通（含引用） |
| 第二段 | F4 + **F5 的会话部分**（历史会话、续聊） | 答错时能定位到具体步骤；关掉浏览器再打开，会话还在 |
| 第三段 | F5 的引用与运行关联（REQ-21） | 重开会话时引用不消失，且能对上唯一一次运行 |
| 第四段 | F6 + F1 的隔离补全 | 换一个客户端也能用；两个团队互不可见 |

**第三段单独列出来的原因**：它最容易被当成"顺手加两列"而漏掉，而它恰恰是"可回放"这个卖点在用户侧成立与否的唯一判据。**库里有记录但界面上看不到，用户不认为你保存了。**

**关键约束（v1.3 修正）：隔离排在阶段 2，不在 F2/F3 之前。**

原版写的是"F1 的隔离必须在 F2/F3 做完之前就补上，否则要面对历史数据归谁的迁移"。这条**已作废**——产品策略改为**先完成单用户闭环，再补多用户隔离**（分界理由见 [REMADE.md](../REMADE.md) §4.0）。

作废的依据是可实测的：存量数据共 **983 行**（文档 64 / 页 390 / 片段 438 / 消息 34 / 会话 10 / run 15 / step 23 / session 9），**全部属于同一个种子账号**，`ALTER TABLE ADD COLUMN ... NOT NULL DEFAULT '<种子租户>'` 一次迁移即可补齐。原警告假设的是"多人数据混在一起后再拆"，在单人场景里不成立。

**仍然有效的一条**：阶段 1 写查询时必须继续带 `tenantId` / `userId` 参数（值恒为种子账号），**不许删签名**。`ConversationRepository` 的五个方法已经是强制 owner 签名，退回去等于两次白改，中间还会丢掉已写好的越权校验。

## 9. 当前实现与需求的差距

只记录"已确认的差距"，不做进度评估。

| 功能域 | 已具备 | 明确缺口 |
|---|---|---|
| F1 | 注册/登录/登出的后端、默认拒绝授权、会话归属校验 | **前端无登录页**（当前整体 401）；隔离 **0 条测试**；团队邀请流程未做 |
| F2 | PDF 上传、解析、切分、状态 | 文档**无团队归属**；删除的索引清理未验证 |
| F3 | 检索、RAG、引用展示 | 检索**无团队过滤**（跨团队会串）；无相关性下限（拒答分支不触发） |
| F4 | 执行记录、步骤、状态、停止 | 记录**无归属**；`POST /api/knowledge/ask` **绕过记录**（审计有后门） |
| F5 | 会话列表与历史消息接口、续聊、轨迹条与回放界面 | **引用从未落库**（重开会话即消失）；**消息与运行无关联**（说不清哪条回答来自哪次运行）；轨迹条只在当次连接推送 |
| F6 | 核心能力有同步 REST 入口；`providers`/`provider_models` + 设置页可配模型 | 流式只有 SignalR、无 SSE；错误响应不统一；接口无版本；**凭据明文入库**；**`is_active` 无唯一约束**（可同时激活两个） |

> 这张表的意义：**除 F5 外，每个缺口都对应一条已有 REQ**——说明需求没有超出现有架构能力，缺的是补全而不是重设计。
>
> **F5 是唯一一处例外，且这个例外有价值**：它的两个缺口（引用未落库、消息与运行无关联）不是因为"没实现"，而是因为**需求定义里从来没要求保存这两样东西**——`REQ-08` 只说"结果必须包含引用"，说的是展示，不是持久化。查到这里才发现"可回放"这个承诺在用户侧是不成立的，因此补了 `REQ-21`。**这是从需求审查里挖出的缺失，不是从代码里挖出的 bug。**

## 10. 编号与维护约定

**编号规则**

| 前缀 | 含义 | 示例 |
|---|---|---|
| `REQ-AUTH-xx` | 访问控制类需求（横切，被所有域引用） | REQ-AUTH-02 成员隔离 |
| `REQ-xx` | 功能需求（按编号顺序，**不复用已删编号**） | REQ-07 知识检索 |
| `NFR-xx` | 非功能需求（见 [非功能需求.md](非功能需求.md)） | NFR-01 数据隔离 |
| `AC-xx` | 验收条件（见 [验收条件.md](验收条件.md)） | AC-11 会话越权 |

**编号与功能域是两件事。** 功能域可重组（如本次把 REQ-04 从 F1 移到 F5、REQ-14/15 从 F4 移到 F5），但 **REQ 编号永不迁移、永不重排**——它被验收用例、测试名和历史记录引用着。域改了只改本文件 §1 与各域能力表，需求编号保持原样。

**维护约定**

1. **新增需求必须落进某个功能域**，不允许出现"游离需求"。若确实无域可归，说明功能域划分需要调整——先改本文档 §1，再谈需求。
2. **删除需求时保留编号空位**，不重排。重排会让所有验收用例和历史记录指向错误的条目。
3. **每条需求必须有对应验收条件**。没有 AC 的 REQ 视为"未完成定义"，不计入完成度。
4. 本域划分若调整，[验收条件.md](验收条件.md) 与 [产品目标与范围.md](产品目标与范围.md) 必须同版复核。
