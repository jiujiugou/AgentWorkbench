# 阶段 2 · 审批轴正交化

> **状态：已完成**（2026-10-13）
> **依赖：阶段 1 已完成**（Hub 已是 harness 流）
> **本阶段目标**：补上 Codex 正交两维里的**第二维** —— 工具审批（`Auto` / `Ask` / `Deny`）。

## 目标

能力边界（能不能用）× 审批级别（什么时候问人）**必须是两个独立维度**，官方明确说这两层不能混。
本阶段的落地判据就是：两维各有各的契约、各有各的配置节、各有各的测试文件，**任何一个文件同时提到两者即为越界**。

## 实际落地清单

### 1. Safety：审批契约与配置（新增 `ToolApproval.cs`）

| 类型 | 作用 |
| --- | --- |
| `ToolApprovalMode` | `Auto`(0) / `Ask`(1) / `Deny`(2) |
| `IToolApprovalPolicy` | `Decision(toolName)`；与 `IToolPolicy` **并列不合并** |
| `ToolApprovalPolicy` | 持 `IOptionsMonitor<ToolApprovalOptions>`，改配置即热重载 |
| `ToolApprovalOptions` | 配置节 `Harness:Approval`：`Default`（默认 `Auto`）+ `Overrides`（工具名 → 级别） |
| `AutoToolApprovalPolicy` | 显式「全部放行」的具名实现（单例），供测试与不关心审批的组合点使用 |

`AddNitroSafety` 现在绑两条配置节并注册两个单例：`IToolPolicy` / `IToolApprovalPolicy`。
`appsettings.json` 新增：

```json
"Harness": {
  "Approval": { "Default": "Auto", "Overrides": {} }
}
```

### 2. ToolExecution：审批闸门（新增 `ToolApproval.cs` + 改 `ToolExecutionPipeline.cs`）

- `ToolApprovalRequest(ToolName, Arguments)`、`IToolApprover.RequestAsync`、
  `ToolApprovalCodes`（`approval_policy_denied` / `approval_user_denied` / `approval_unavailable`）。
- `ToolExecutionLimits` 增第三项 `IToolApprover? Approver`（run 级，由调用方提供）。
- `ToolExecutionPipeline` 构造增 `IToolApprovalPolicy`（DI 注入）；
  在**守卫判定之后、工具真正执行之前**过闸门：

| 级别 | 行为 |
| --- | --- |
| `Auto` | 直行；**不触碰审批者**（不打扰、不引入通道故障面） |
| `Deny` | 工具**绝不执行**；回填结构化拒绝载荷，归类码 `approval_policy_denied` |
| `Ask` | 问 `limits.Approver`；批准则执行，否则归类码 `approval_user_denied` |

- **fail-closed 三处兜底**：未提供 approver / 审批超时（`Task.WaitAsync`） / 审批通道抛异常，
  一律按 `approval_unavailable` 拒绝。**两侧都倒向「不放行」**，任何一侧失灵都不会退化成「没批准也执行」。
- 顺序说明：守卫（循环 / 预算）在前 —— 它判的是「整轮要不要停」，是更上层的止损，已决定要停的调用不必再走审批。
- 超时值 `ToolExecutionOptions.ApprovalTimeoutSeconds`（默认 120）。

### 3. AgentHarness：只做透传

- `HarnessRunRequest` 增 `IToolApprover? Approver = null`；
  `PrepareRunAsync` 把它塞进 `ToolExecutionLimits`。
- **Harness 构造依赖保持 13**（阶段 0 冻的预算没有回退）：级别来自 DI 的策略，通道来自 run 请求，
  两者都不需要进 harness 构造。

## 与计划的偏差（如实记录）

1. **没有 `ApprovalOptions.Enabled` 短路开关**。计划里写「审批分支用开关短路回现状」，
   实际用 `Default = Auto` 表达同一件事 —— 默认全放行就等于现状。少一个旋钮，少一处将来会烂的配置。
2. **用具名 `AutoToolApprovalPolicy` 而不是容忍 `null` 策略**。`IToolApprovalPolicy` 是安全维度，
   「没有策略」用 `null` 静默表达会埋雷；改成必须显式写 `AutoToolApprovalPolicy.Instance`。
3. **超时放在 `ToolExecutionOptions` 而不是 `ToolApprovalOptions`**。它是「管道愿意等多久」，
   属于执行层的等待预算；放在审批配置里会让「策略」变成配置袋。
4. **没有为「被拒」新增轨迹字段**。拒绝写在既有 `ToolCallTrace.Error` 里（归类码）+
   `Result` 里（结构化载荷）—— 新增字段会一路波及 `HarnessStep` / `ExecutionStep` / 持久化 schema，
   收益不抵成本。代价是 `Error` 语义扩成「这次调用没有正常完成」，已在其文档注释里说明。

## 未落地（后置，与前端对话框**成对**）

`AgentHub` 的 `ApprovalRequested` / `ApprovalResponse` 事件与前端确认框**一起后置**，原因是一个实测得出的硬约束：

> ASP.NET Core SignalR 的 `HubOptions.MaximumParallelInvocationsPerClient` **默认为 1** ——
> 同一连接上的 Hub 方法调用是**串行**的。若在 `Send`/`Ask` 里 await 一个由 `RespondToApproval`
> 完成的 `TaskCompletionSource`，两个调用会互相等待，**直到审批超时才解开**（表现：每次 Ask 都必超时被拒）。
> 要么把并行度调大（会改变 Hub 现有的「一连接一生成」假设，`Generations` 字典与 `Stop` 语义都要重审），
> 要么把流式搬运挪到后台任务（改动面更大）。两条路都必须和对话框一起设计，不能先把事件发出去。

因此当前状态：**配置成 `Ask` 且不提供 approver 时，行为是 fail-closed 的拒绝**（安全，但功能未接通）。
接通步骤（待做，非本阶段）：

1. `ChatRequest`/前端增加审批应答通道，`AgentHub` 实现 `IToolApprover` 并传入 `HarnessRunRequest.Approver`；
2. 解决上面的并行度问题（推荐：把审批应答改走**独立的 `IHubContext` 广播 + 每连接独立 CTS**，
   或明确把 `MaximumParallelInvocationsPerClient` 提到 2 并补 Hub 并发测试）；
3. 前端确认对话框；服务端在 `Ask` 时还应发一个 `ApprovalRequested` 事件（当前没有专门事件，
   拒绝会以 `ToolCompleted`（带归类码）的形式到达前端）。

## 设计红线

- **绝不**把审批塞进 `ToolPolicy` 或 `AgentRunGuard` —— 那是把刚拆开的两个维度又粘回去。
- **绝不**默认 `Ask`。默认 `Auto`，逐个工具显式提升。否则用户第一次用就被弹窗淹没。
- **绝不** fail-open。审批通道的任何异常都必须倒向「拒绝」。
