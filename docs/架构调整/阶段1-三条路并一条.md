## 目标

所有入口汇成一条路：**用户在用的聊天页（`AgentHub`）与 `HarnessController` 走同一个 harness**，
共享同一个 loop、同一个 guard、同一个 trace 落库。

一句话判据：**用户实际发起的每一次对话，都在轨迹表里有一条记录。**

## 为什么这一步最陡

它动的是用户每天在用的聊天页，但也是唯一能让「评测覆盖真实路径」成为可能的一刀。

**阶段 1 之前，tau2 / MAF 评测考的都只是 `HarnessController` 那条没人用的路。**

## 关键约束（踩过的坑，别重复踩）

- MEA `ChatClientAgent.Instructions` **是只读属性**，写不了。
- 用**字符串构造函数**传指令会关掉 `UseProvidedChatClientAsIs` → **工具双执行**。
- **指令不能用 `Agent.AIContextProviders` 注入**（曾以为是正解，实测被证伪）：
  挂上 provider 后 MEA 会在我们自己装配的 `FunctionInvokingChatClient` **外面**再包一层函数调用环，
  `ToolExecutionPipeline` 的守卫与轨迹采集全被绕过 —— 连续同参调用不再判 `loop_detected`、
  工具异常不再归类 `tool_error`，全部退化成 `succeeded`（19 个既有用例同时变红）。
  **正解**：`RunInstructionsChatClient` —— 装饰在工具环外，转发前只往消息前插一条 system。
  进模型请求但不进会话历史（`ChatHistoryProvider` 在装饰器上游，只记 `run.Messages`）。
  回归闸：`tests/AgentWorkbench.EvaluationTests/HarnessInstructions/`。
- `ToolExecutionOptions.MaxResultChars = 400` —— **轨迹里的工具结果是截断的**，
  所以 UI 来源面板不能读轨迹，必须用 `ToolCompleted` 事件带的完整结果。
- `IAgentLoop.ExecuteAsync` 只有泛式重载；流式 drain 也要包进 run 级墙钟预算。

dotnet test  AgentWorkbench.slnx            → 182/182 绿
  EvaluationTests  39（含本步新增 9）
  UnitTests       133

自动化判据（`HarnessStreaming` / `HarnessInstructions` 两个域）：

- 增量分片拼接 = 完整答复；工具完成事件带工具名；终态唯一、在末尾、带 `RunId`；账本留下工具步与答复步。
- **同源对齐**：同一脚本走两条出口，账本的终态 / 迭代数 / 工具序列 / 工具调用次数逐项相同。
- **刻意不对称**：工具事件带完整结果，账本存截断结果——两侧同时锁，改单边即红。
- **负控**：模型崩溃时事件流不允许出现 `Completed`；不带指令时不允许凭空出现 system 消息；
  判据自身有负控（缺终态 / 终态不在末尾 / 终态重复三种坏形状必须抛）。
- **回归闸**：带指令时 `loop_detected` 与 `tool_error` 仍必须成立（防指令通道绕过执行控制）。

**手工冒烟未执行**（需要真实模型与前端在跑）：`cd web; npm run dev` → 聊天页问一个需要工具的问题，
应看到流式回答 + 来源面板有内容 + 轨迹面板有本次 run。这条留给用户在有 key 的环境执行。
