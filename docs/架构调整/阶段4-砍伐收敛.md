## 砍伐清单（按顺序执行）

### 0. 先跑端到端冒烟切片（唯一裁判，必须先做）

```
灌中性 PDF → 提问 → 断言轨迹里有 search_knowledge 调用 + 结果
```

- 这是**整场调整里唯一的裁判**，其他动作都是运动员。
- 它的结论直接决定第 1 条（`Knowledge.Local` 935 行去留）。

### 1. `Knowledge.Local` 去留裁决

- 若冒烟切片证明检索链路可用 → 保留，并补「检索质量」的客观判据（负控不能被误命中，**当前误命中率 1.0 FAIL 未修**）。
- 若证明不可用 → 砍。这是本阶段最大的单项瘦身。

### 2. `Workflow` 大砍（约 300 行 + 托管服务）

- 前置验证：**确认前端没有工作流页面在真实使用**（查 `web/src` 路由与调用）。
- 砍法：`WorkflowWorker` / `WorkflowRunQueue` 降级为**同步单步执行**，删掉整个后台执行模型
  （连带检查点语义、托管服务）。
- `AgentStepExecutor` 的 `BuildInput` 自检索并入 `ContextBuilder` 或直接删（与阶段 0 已拆的双重检索收尾）。
- `WorkflowSeeder` 的提示词种子：提示词要提为**一等公民**（`IPromptStore`），
  不能继续活在种子代码里（这是 Codex「指令层与执行层分离」的落点）。

### 3. `Memory` 瘦身

- 进程内实现若**只有测试在用** → 移进 `tests/` 做 test double，`Memory` 项目只留契约。
- 省 1 个项目、1 个 `AddNitro` 注册、约 392 行。

### 4. `Context` 删除 / 合并

- `ContextBuilder` 在阶段 0 后**已零 src 消费者**（README 已标记）。
- 并入 `AgentHarness` 或 `Knowledge`：纯函数留着，**项目和注册删掉**。

### 5. `Safety` 合并

- 策略变成 `ToolPipeline` 的构造参数（审批契约见阶段 2）。
- 契约留着，项目删掉。

### 6. 死代码清理

- `ChatService` / `RagService`（若阶段 1 重接后零消费者）、`AgentWorkbench.Conversation` 项目去留。

## 设计红线

- **不要**为了「架构好看」砍掉有真实消费者的模块——本阶段的判据是测试，不是美观。
- **不要**在本阶段引入任何新项目 / 新框架。新能力只准以**工具**形式进入已有 loop。
- **保留差异化**：`Safety` 的审批与 `ToolPolicy` 是简历上的加分项（多数 Dify 工程师没有），
  合并的是**项目边界**，不是能力本身。
