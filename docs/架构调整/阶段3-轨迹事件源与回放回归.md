# 阶段 3 · 轨迹事件源与回放回归

> **状态：未开始**
> **依赖：阶段 1 完成**（流式路径也要被回放覆盖）

## 目标

把 `IExecutionTraceStore` 从「只写不读的死数据」变成**回归源**：
测试读历史轨迹 → 回放 → 判分。这是治「验收假绿」的根因手术。

一句话判据：**每次 run 的轨迹，都有一条测试会因它被篡改而变红。**

## 为什么排在这里

- 阶段 0 造门禁，阶段 1 并路并产出流式回归，阶段 3 把两者接到轨迹上。
- **阶段 4 的每一次砍伐，都由本阶段的回放回归兜底**——所以本阶段必须先于砍伐完成。
- 这是 Codex「rollout」/ OpenCode「session」的对应物：trace 是一等公民，可回放、可分支。

## 现状证据（结构性根因）

- `IExecutionTraceStore` 全仓**只有一个写入方**：`src/AgentWorkbench.AgentHarness/AgentHarnessService.cs`。
- `GetRunAsync` **只被前端回放面板消费，测试零消费**。
- 结论：轨迹是**死数据**——写了没人读，于是「测试全绿」与「真实效果」之间没有连线。
- 这是「机制完备、效果空白」在测试层的直接体现，也是「我出题我作答」自循环的一个侧面。

## 改动清单

### 1. `tests/AgentWorkbench.EvaluationTests`（新增回放用例族）

复用现有夹具，**零产品代码改动即可起步**：

```
Fixtures/HarnessUnderTest.cs   —— 已有批量判分 / 失败路径捕获 / 账本→对话
Fixtures/ModelFakes.cs         —— 已有脚本化模型（先调工具再回答）
Fixtures/TestTools.cs          —— 已有正例/负例工具
Checks/LedgerChecks.cs         —— 已自建判定原语（StatusIs / ErrorCodeIs / WasPersisted）
```

用例形态：
1. 跑一次 run（真实 harness，MockLlm 驱动）→ 落轨迹。
2. 从轨迹重建：工具调用序列、迭代次数、终态 status。
3. 断言以上三者与预期一致。
4. **负控**：篡改轨迹里的工具序列 / 迭代次数 / status → 必须变红。

### 2. `src/AgentWorkbench.Observability`（补查询面）

- 轨迹查询 API 按 `sessionId` / 时间 / `status` 过滤，**测试与前端共用同一份**。
- 现有落库字段若不够（缺迭代次数、缺 tool 序列的结构化形态），补齐——**只补字段，不动写入语义**。

### 3. 流式事件与轨迹的关系（阶段 1 的收口）

- 阶段 1 的 `ToolCompleted` 事件带**未截断结果**，轨迹存**截断版**（`MaxResultChars=400`）。
- 本阶段需明确：**回放以轨迹为准**（截断版），未截断结果只是 UI 通道，不入回归判据。
  否则回放会因截断与否产生假红。

## 验证判据

| 项 | 正例 | 负控 |
|---|---|---|
| 工具序列回放 | 与轨迹一致 | 篡改序列 → 红 |
| 迭代次数 | 与轨迹一致 | 篡改次数 → 红 |
| 终态 status | 与轨迹一致 | 篡改 status → 红 |
| 失败路径 | `Failed` 轨迹可回放（异常被归类后仍留痕） | 丢轨迹 → 红 |

## 回退方式

- 全部为新增测试 + 新增查询 API，删掉即回退，产品运行时行为不变。

## 预算收紧（阶段收尾时执行）

  （防止这条回归链日后被静默移除）。

## 设计红线

- **不要**为了回放去调真实模型——回放必须确定性（MockLlm）。
- **不要**把回放做成「重新跑一遍」——它是「读历史 + 断言」，不是重算。
