# 阶段 3 · 轨迹事件源与回放回归

> **状态：已完成**
> **依赖：阶段 1 完成**（流式路径已并入同一收尾，回放覆盖到它）

## 目标

把 `IExecutionTraceStore` 从「只写不读的死数据」变成**回归源**：
测试读历史轨迹 → 回放 → 判分。这是治「验收假绿」的根因手术。

一句话判据：**每次 run 的轨迹，都有一条测试会因它被篡改而变红。**

## 为什么排在这里

- 阶段 0 造门禁，阶段 1 并路并产出流式回归，阶段 3 把两者接到轨迹上。
- **阶段 4 的每一次砍伐，都由本阶段的回放回归兜底**——所以本阶段必须先于砍伐完成。
- 这是 Codex「rollout」/ OpenCode「session」的对应物：trace 是一等公民，可回放、可分支。

## 现状证据（开工前的结构性根因）

- `IExecutionTraceStore` 全仓**只有一个写入方**：`AgentHarnessService`。
- `GetRunAsync` 只被前端回放面板消费，**测试零消费**。
- 更糟：已有的「轨迹可回放」用例里，**负控是占位假绿**——
  `Domain6_Ledger/LedgerInvariants.cs` 的 `GetRunAsync_MissingErrorCode_NegativeControl` 写成
  `Assert.True(true, "…")`，`Domain3_AgentLoop/TerminationInvariants.cs` 有两处同样写法。
  它们以「正例已验证」为由跳过，实际什么都没验。

## 实际改动

### 1. 查询面补齐（`src/AgentWorkbench.Observability` + `Persistence`）

- `IExecutionTraceStore` 增 `QueryAsync(ExecutionTraceQuery)`；`ExecutionTraceQuery` 支持
  **SessionId / Status / Limit**（最近优先）。读取语义与 `GetAsync` 共用同一份私有 `Map`，避免两处漂移。
- `IAgentRunRepository` 增 `QueryRunsAsync(sessionId, status, limit)`，SQL 用
  `(@p IS NULL OR col = @p)` 做可选过滤。
- **不做字段/表结构变更**：现有 `Iterations` 与 `Steps` 已够回放，守住「只补读取面、不动写入语义」。
- **判断（主动砍）**：原文档写的「按**时间**过滤」没有真实消费者，属投机参数，**未实现**。
  真需要时再加——先有消费者，再有 API。

### 2. 回放回归测试族（新增 `tests/AgentWorkbench.EvaluationTests/HarnessReplay/`）

- `ReplayFacts.cs`：`ReplayFacts`（工具序列 / 迭代次数 / 终态 / 归类码）+ `TraceReplay` 读取器与判据。
  回放读不到轨迹一律抛——「回放不到」绝不能被当成「一切都对」。
- `HarnessReplayTests.cs`：正例 4 条 + 回放不重跑 1 条 + 负控 5 条 + 判据自证 1 条 + 查询面 2 条。
- `TraceTruncationTests.cs`：流式事件带完整答复、轨迹存截断版、回放只看到截断版。

**判据的分工**（避免「我出题我作答」）：
- **独立预期**：来自脚本 + 选项 + 可观测计数器（如「2 轮 = 工具轮 + 收口轮」），不看轨迹。
- **一致性**：回放事实 == 原 run 事实（两者来源不同：一个是落库轨迹，一个是内存结果）。

### 3. 流式事件与轨迹的关系（阶段 1 的收口）

- `Completed` 事件带**完整**答复（界面要给用户看全文），轨迹存**截断版**（`MaxAssistantChars = 400`）。
- **定死：回放以轨迹为准（截断版）**。未截断结果只是 UI 通道，不入回归判据。
  否则同一段答复会在「截断 / 未截断」之间产生假红。

| 项 | 正例 | 负控 | 结果 |

| 迭代次数 | 与预期一致 | 篡改次数 → 红 | 通过 |

## ⚠️ 开工中发现、但**未处理**（需你拍板）

**成功路径下落库失败会让整个 run 抛错。**
`FinishSucceededAsync` 调 `_traces.SaveAsync(...)` 是**不吞异常**的；所以当 run 本身正常收尾
（含迭代上限 / 循环收口）而账本写不进去时，冒泡出去的是账本异常 → 前端把「已答完」显示成失败。
两种立场都成立：
- 现状（失败）：轨迹写不下去 = 这次 run 不可信，宁可报错。
- 备选（降级）：答复照给，只标记 `WasPersisted=false`。

**我没有改它**——这属于产品语义决策，超出「只补读取面、不动写入语义」的本阶段边界。
注意 3.10 的原始用例正是踩在这条暧昧线上：它用「工具失败一次 + 账本写失败」，但工具异常在环内被容忍、
run 其实正常收尾，于是真正冒泡的是账本异常——旧断言只查异常类型（两者同为 `InvalidOperationException`），
**假绿就是这么来的**。

## 设计红线

- **不要**为了回放去调真实模型——回放必须确定性（MockLlm）。
- **不要**把回放做成「重新跑一遍」——它是「读历史 + 断言」，不是重算（已用「回放不重跑」用例锁死）。
