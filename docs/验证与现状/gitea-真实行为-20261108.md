# Gitea 真实行为采集（证据，非测试）

> 采集时间：2026-11-08 18:27 (UTC+8)
> 采集对象：`https://gitea.com`，`GET /api/v1/version` → `{"version":"29.0.0+dev-160-g55186ca39b"}`
> 身份：`jiujiugou`（id 266563，`is_admin: false`），仓库 `jiujiugou/test`（`private: false`）
> 凭据：token scope = `read:organization, read:repository, read:user, write:issue`（不含 `write:repository`，刻意留缺口）
> 采集方式：真实 HTTPS 请求，未使用任何 mock。探测产生的 issue #1/#2/#3 已全部删除（均返回 204）。

**用途**：替代 ERPNext 实例，作为 M2/M3 的「真实外部系统」。理由见 §4。

---

## 1. 状态码与错误体（原文）

| 场景 | 请求 | HTTP | 响应体（节选原文） |
|---|---|---|---|
| 身份自述 | `GET /api/v1/user` | **200** | `{"login":"jiujiugou","id":266563,"is_admin":false,"email":"…"}` |
| 存在的仓库 | `GET /api/v1/repos/{o}/{r}` | **200** | 65 字段，含 `permissions:{"admin":true,"push":true,"pull":true}` |
| **不存在的仓库** | `GET /api/v1/repos/{o}/not-exist` | **404** | `{"message":"not found"}` |
| **私有仓库（匿名）** | `GET /api/v1/repos/gitea/private-…` | **404** | **与上一条字节级相同**，无法区分 |
| 无 token 写 | `POST /api/v1/user/repos` | **401** | `{"message":"token is required"}` |
| 伪造 token | `GET /api/v1/user` | **401** | `{"message":"invalid username, password or token"}` |
| **scope 不足（写）** | `POST .../issues`（无 `write:issue`） | **403** | `{"message":"token does not have at least one of required scope(s), required=[write:issue], token scope=write:activitypub,read:organization,read:repository,read:user"}` |
| **scope 不足（改仓库）** | `PATCH /api/v1/repos/{o}/{r}` | **403** | `required=[write:repository]` |
| **scope 不足（删仓库）** | `DELETE /api/v1/repos/{o}/{r}` | **403** | `required=[write:repository]` |

**401 / 403 / 404 三者语义分工清晰，不重叠**：

- 401 = 没凭据，或凭据无效
- 403 = 凭据有效但 **scope 不足**
- 404 = 资源不存在，**或无权看到其存在**

## 2. 写动作与幂等（M3 核心证据）

同一 payload 连续发三次：

| 次 | 请求 | HTTP | 外部单号 |
|---|---|---|---|
| 1 | `POST .../issues` | 201 | **#1** |
| 2 | 同上 + `Idempotency-Key: aw-fixed-key-001` | 201 | **#2** |
| 3 | 同上，无任何头 | 201 | **#3** |

```
>>> 三次请求共产生 issue: [1, 2, 3]
```

**结论：Gitea 完全忽略 `Idempotency-Key`，同一业务意图重放 N 次就产生 N 张单。**

这是「同 `request_id` 只生成一张单」这条判据的第一份真实证据——证明**幂等只能在我们侧做**，外部系统不给。也直接印证 `InMemoryActionRunStore.TryClaimIdempotencyAsync` 存在的必要性。

## 3. 三个会静默出错的真实坑

### 3.1 更新返回 201，不是 200

`PATCH .../issues/1`（`{"state":"closed"}`）→ **HTTP 201**，body 是完整 issue 对象。

若适配器写 `if (status == 200) success;`，**关闭动作会被判为失败，而 ERP 里其实已经关掉了**。这是最坏的一类错误：状态已变、系统认为没变。

### 3.2 删除返回 204 且无 body

`DELETE .../issues/{n}` → **204，空 body**。

若解析器无条件 `JsonDocument.Parse(body)`，此处抛异常。判成功必须以状态码为准，不能以 body 为准。

### 3.3 时间是 UTC，不是站点本地时间

```
created_at: 2026-11-08T10:27:43Z      ← API 返回
本地实际:   2026-11-08 18:27 (UTC+8)
```

**与 Frappe 恰好相反**：Frappe 返回 naive 串（`2019-06-03 14:19:00.281026`，无时区，站点时区），Gitea 返回 RFC3339 + `Z`。

若把「按站点时区补偏移」的逻辑套到 Gitea 上，会把 UTC 当本地时间，**差 8 小时且不报错**。

结论：时间解释策略必须由**适配器逐域声明**，不能放进底座。

## 4. 为什么它能替代 ERPNext 做考官

| 属性 | 要求 | Gitea 是否满足 |
|---|---|---|
| 契约由别人定义 | 字段名不能我们自己改 | ✅ `number` / `state` / `created_at` |
| 真实权限模型 | 能真的返回 403，且与 404 分得开 | ✅ scope → 403；不存在 → 404 |
| 真实状态机 | 状态值我们改不了 | ✅ `open` / `closed` |
| 真实失败模式 | 超时、字段漂移、非标准状态码 | ✅ 201 on PATCH、204 空 body、静默忽略幂等头 |
| 零部署成本 | 不占本机资源 | ✅ 公开实例，无需安装 |

**缺的一条**：它没有「金额档位」这种业务语义。这恰好印证四维权限里第四维属于动作域（`IBusinessRule`），不属于底座——见 `docs/参考` 权限模型对照。

## 5. 三条对契约的直接修正

1. **`not_found` 与 `forbidden` 不能一概合并**。scope 不足是 403、资源不存在是 404，可区分；但「私有资源存在而你看不到」是 404，与不存在不可区分。错误码需保留两码，并在语义上注明「404 可能是无权限」。
2. **403 的错误体泄露权限结构**（`token scope=…, required=[…]`）。这是反面教材：我们的拒绝理由**内部审计可详、对外只能给一个码**。
3. **响应原文不得整体入审计**。`GET /user` 返回 `email`，属个人信息。审计只存白名单字段（外部单号、状态、变更时间）。
