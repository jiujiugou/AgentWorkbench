## 1 被测契约

上传是「先判定、后产生副作用」的同步动作，成功与拒收的边界如下。

| 动作 | HTTP | 响应 | 副作用 |
|---|---|---|---|
| 接收成功 | 202 | `{ id, fileName, status: "pending", sha256, sizeBytes, ... }` | 落盘 `{sha256}{ext}`、插一条 `pending` 记录、入解析队列 |
| 拒收 | 400 | `{ code, message }` | **无**：磁盘不变、库记录不变、队列不变 |

判定顺序是契约的一部分：**有没有 file → 内容是否为空 → 扩展名是否支持 → 是否超过业务上限**。空文件同时扩展名不支持时，返回 `FILE_EMPTY`；超限文件同时扩展名不支持时，返回 `FILE_TYPE_UNSUPPORTED`。

支持扩展名：`.pdf` / `.txt` / `.md` / `.json`，大小写不敏感。业务上限由 `StorageOptions.MaxFileBytes` 决定（默认 30 MB），判定条件是 `file.Length > MaxFileBytes`，**恰好等于上限应当接收**。

## 7 功能 2：看它处理到哪了

> 对应 [阶段1-F2](../../设计/阶段1/阶段1-F2.md) §1 第 2 件（REQ-06）。
> **现状：S01–S11 已实现并全绿**（2026-10-31）。
> 契约入口：`GET /api/documents` 与 `GET /api/documents/{id}` 的 `status` / `error` / `indexState` 字段。

### 7.1 被测契约

状态机由 `DocumentParseWorker` 推进：

| `status` | 用户看到 | 可检索 | 说明 |
|---|---|---|---|
| `pending` | 处理中 | 否 | 已接收 / 已重排队，等待 Worker |
| `parsing` | 处理中 | 否 | 正在抽取、清洗、切块、写页与片段、建索引 |
| `parsed` | 可检索（按 `indexState` 细分） | 条件 | 解析成功；是否真正可检索由 `indexState` 判定 |
| `failed` | 失败 + 原因 | 否 | 解析失败或索引永久失败；`error` 必有文字 |

可检索判据取自 `IndexStates.Describe`（两个 Controller 共用），**不是文档状态列**：

| `indexState` | 产生条件 | 可检索 |
|---|---|---|
| `full` | `parsed` 且 chunks > 0 且 vectors ≥ chunks | 是（全文 + 语义） |
| `text_only` | `parsed` 且 chunks > 0 且 vectors = 0 | 是（仅全文） |
| `partial` | `parsed` 且 0 < vectors < chunks | 是（部分语义） |
| `empty` | `parsed` 且 chunks = 0 | 否 |
| `pending` | `status ∈ {pending, parsing}` | 否 |
| `failed` | `status = failed` | 否 |

两条硬约束：

1. `pending` / `parsing` / `failed` 永远不得出现 `full` / `text_only` / `partial`。
2. `failed` 行的 `error` 必须是非空文字；非 `failed` 行的 `error` 为 `null`。

> `text_only` / `partial` 仍算「可检索」是刻意的：解析成功但向量暂缺时，全文检索仍能命中；若判成失败，用户会误以为文档没入库。这与「只有成功的才能标可检索」不冲突——`status` 仍是 `parsed`。

| AC | 判据 | 对应用例 |
|---|---|---|
| AC-7 | 六个 `indexState` 的映射与 §7.1 表一致 | S01 |
| AC-8 | 可检索集合恰好是 `full` / `text_only` / `partial` | S02 |
| AC-9 | 列表与详情每行都带 `status` / `error` / `indexState`；失败行有可读原因 | S03、S04 |
| AC-10 | `pending` / `parsing` / `failed` 不得被标成可检索 | S05 |
| AC-11 | Worker 正常完成 → `parsed`，页/块落库，`error` 为空 | S06 |
| AC-12 | 解析失败 → `failed` + 原因，不得留 `parsed` | S07、S10、S11 |
| AC-13 | 索引永久失败 → `failed` + 原因；暂时失败 → `parsed`，`error` 为空，`indexState` 为 `text_only` 或 `partial` | S08、S09 |

## 8 功能 3：看它的原文和片段

> 对应 [阶段1-F2](../../设计/阶段1/阶段1-F2.md) §1 第 3 件；原文可核查是 REQ-08「引用三要素」的前置。
> **现状：P01–P08 已实现**（2026-10-31）；P01、P02、P05–P08 绿，P03 / P04 红。
> **已知缺口（P03 / P04 变红的原因）**：两个端点当前都不判文档是否存在，任意 id 都返回 `200 []`。
> 这与 F2 §4 第 4 条「`pages` / `chunks` 不判存在」是同一件事；在 Controller 补存在性判定前，这两条应当保持红。
> 契约入口：`GET /api/documents/{id}/pages`、`GET /api/documents/{id}/chunks`。

### 8.1 被测契约

| 动作 | HTTP | 响应 | 说明 |
|---|---|---|---|
| 读页 | 200 | `[{ pageNo, rawText, cleanedText }]`，按 `pageNo` 升序 | 文档存在但还没有页（`pending` / `parsing`）→ `[]` |
| 读片段 | 200 | `[{ seq, pageFrom, pageTo, heading, content, charCount }]`，按 `seq` 升序 | 文档存在但还没有块 → `[]` |
| 文档不存在 | 404 | 无业务体 | **必须与「还没解析完」的 `200 []` 分开** |

三条硬约束：

1. **404 只由「文档记录不存在」触发**。记录存在就返回数组，即使状态是 `pending` / `parsing` / `failed`；`failed` 后已落库的页与块仍然可读（索引永久失败时全文仍可用，见 §7.1）。
2. **顺序稳定**：页按 `pageNo` 升序且从 1 开始；片段按 `seq` 升序且从 0 开始、连续无洞。
3. **字段自洽**：`charCount == content.Length`；有页时 `1 ≤ pageFrom ≤ pageTo ≤ pageCount`；`cleanedText` 是 `rawText` 清洗后的文本，不是另一页的内容。

> `rawText` 是抽取器的原始产物（保留原始空白/页码行），`cleanedText` 是去页眉页脚、合并断行、规范化空白后的结果。两者都为必填字符串，允许相等（输入本来就很干净时）。

|---|---|---|

| AC-15 | 片段端点字段完整、按 `seq` 升序，`charCount` 与 `content` 一致 | P02 |
| AC-16 | 不存在的 id 返回 404，而不是 `200 []` | P03、P04 |
| AC-17 | 文档存在但尚未解析完时返回 `200 []`，与 404 可区分 | P05 |
| AC-18 | 索引永久失败但页/块已落库时，原文与片段仍可读 | P06 |
| AC-19 | 多页 PDF 的页序、页内容与片段页范围一致 | P07 |
| AC-20 | 长文本被切成多块时，`seq` / `charCount` / 页范围自洽 | P08 |

## 9 功能 4：失败了再试一次

> 对应 [阶段1-F2](../../设计/阶段1/阶段1-F2.md) §1 第 4 件。
> **现状：R01–R06 已实现并全绿**（2026-10-31）。
> 契约入口：`POST /api/documents/{id}/reparse`。

### 9.1 被测契约

| 动作 | HTTP | 响应 | 副作用 |
|---|---|---|---|
| 重新排队 | 202 | `{ id, status: "pending" }` | 记录置 `pending`、`error = null`、解析队列 +1；页/块不立即删除 |
| 文档不存在 | 404 | 无业务体 | 无：状态、队列、页/块均不变 |

四条约束：

1. **任意状态都可重试**。`DocumentStatus` 明确「重处理：任意状态」；`parsing` 中调用会发生什么**尚未决定**，本组不锁定（见 §9.5）。
2. **重试只负责排队**，不负责解析；`pending → parsed|failed` 由 Worker 推进（功能 2）。
3. **响应后立即可见**：返回 202 后读 `GET /{id}`，状态必须是 `pending`、`error` 为 `null`。
4. **不提前删内容**：重试不删除已有页/块；旧内容保留到 Worker 成功替换。这样重试失败也不会把上一版正文弄丢。

> **现状（已知不一致）**：`Reparse` 只把 `status` 置 `pending`、`error` 置 `null`；`pageCount` / `parsedAt` 因 `UpdateStatusAsync` 的「`null` = 不动」语义保留旧值。于是 `pending` 行可能仍带旧 `parsedAt`。本组不把「清不清」写成承诺，见 §9.5。

### 9.2 验收判据（AC）

| AC | 判据 | 对应用例 |
|---|---|---|
| AC-21 | `failed` 文档重试 → 202、`pending`、`error = null`、队列 +1 | R01 |
| AC-22 | `parsed` 文档重试 → 202、`pending`、`error = null`、队列 +1 | R02 |
| AC-23 | 不存在的 id → 404，且状态/队列/页块均不变 | R03 |
| AC-24 | 连续重试两次 → 202×2、队列 +2、最终 `pending` 且 `error = null` | R04 |
| AC-25 | 重试后列表可见 `pending` / `error = null` / `indexState = pending` | R05 |
| AC-26 | 重试不提前删除旧页/块，旧内容保留到 Worker 替换 | R06 |

### 9.3 用例清单

| ID | 层级 | 场景 | 输入 | 期望 |
|---|---|---|---|---|
| R01 | 契约 | 失败后重试 | 预置 `failed` + `error`，调用 reparse | 202；响应 `id` 正确、`status=pending`；库中 `pending`、`error=null`；队列 +1 |
| R02 | 契约 | 成功后重试 | 预置 `parsed`（`pageCount=1`、`parsedAt` 非空），调用 reparse | 202；库中 `pending`、`error=null`；队列 +1 |

## 10 功能 5：删掉它

> 对应 [阶段1-F2](../../设计/阶段1/阶段1-F2.md) §1 第 5 件。
> **现状：D01–D07 已实现并全绿**（2026-10-31）。
> 契约入口：`DELETE /api/documents/{id}`。

### 10.1 被测契约

| 动作 | HTTP | 响应 | 副作用 |
|---|---|---|---|
| 删除成功 | 204 | 无体 | 索引清干净 → 记录删（级联页/块）→ 文件尽力删；列表不再出现 |
| 文档不存在 | 404 | 无体 | 无：记录、文件、队列、知识引擎均不动 |
| 索引清不干净 | 409 | `{ message, code, ftsRemaining, vectorsRemaining }` | **保留记录、页/块、文件**，允许重试删除 |
| 文件删不掉 | 204 | 无体 | 记录与索引已清；文件残留（磁盘垃圾，不影响检索） |

五条约束：

1. **索引没清干净就不能删记录**。`chunks_fts` / 向量表没有外键，删了记录就再没有入口清残留，会留下「列表看不见、检索却命中」的幽灵。
2. **只有 `RemoveResult.Cleaned == true` 才删记录**；`FtsRemaining > 0` 或 `Failure != null` 都走 409。
3. **删除成功后列表消失**：`GET /api/documents` 不再有该行；仓储里页/块为空。页/块端点是否 404 属功能 3 的 P03/P04，本组不重复断言。
4. **文件删除是 L3，best-effort**：失败只留磁盘垃圾，不改变 204，也不影响「搜不到」。
5. **删除不负责停止正在跑的解析**：并发语义未定（见 §10.5）。

> **现状（设计缺口）**：Controller 已是「先 `RemoveDocumentAsync` → `Cleaned` 才 `DeleteAsync` → 删文件」，但 L1 没有事务；`DeleteAsync` 失败时可能留下「列表可见、索引已空」的记录。本组不模拟这一失败，见 §10.5。

### 10.2 验收判据（AC）

| AC | 判据 | 对应用例 |
|---|---|---|
| AC-27 | 删除已解析文档 → 204；记录/页/块/文件消失；`RemoveDocumentAsync` 恰好一次；队列不变 | D01 |
| AC-28 | 不存在的 id → 404；记录/文件/队列不变；`RemoveDocumentAsync` 不调用 | D02 |
| AC-29 | FTS 残留 → 409；记录/页/块/文件全部保留 | D03 |
| AC-30 | 向量删除失败 → 409；记录/页/块/文件全部保留 | D04 |
| AC-31 | 失败文档也能删 → 204；三层清理完成 | D05 |
| AC-32 | 重复删除 → 第一次 204，第二次 404；知识引擎仍只调用一次 | D06 |
| AC-33 | 真实 FTS 索引删除后，同一查询不再命中 | D07 |
