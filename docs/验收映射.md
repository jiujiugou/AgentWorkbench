## 1. 真实 API 查状态

- **查哪里**：被接入系统自己的记录，按业务键读回（当前载体 ERPNext：采购单 `name` → `docstatus` / `status` / `supplier` / `grand_total`）
- **算过**：状态码与状态值是对方 API 自己返回的；查不到时系统明确说查不到
- **算失败**：返回的是 mock、假件、或我们自己格式的时间串
- **现在**：**有实证（2026-11-20 首次，11-22 复验）**。`POST /api/actions` → `erp.query` → `McpActionExecutor` → `frappe_get_doc`，HTTP 200 / `status=succeeded` / `code=mcp_ok` / `externalId=PUR-ORD-2026-00001`，返回真单据全字段（11-22 读到 `docstatus=1` / 供应商 AW Test Supplier / grand_total 51）。边界：只读，且走 HTTP 入口——模型聊天入口未验（当时 `glm-4-flash` 把 tool call 写成文本，`tools=0`，未进闸）。11-08 Gitea 的 PATCH 201 / DELETE 204 / RFC3339+Z 仍是探针事实，不是完整 run。

## 2. 未审批零外部调用

- **查哪里**：对方系统的记录数 / 访问日志——不是我们自己的调用计数
- **算过**：未点同意时对方记录数不变；拒绝与超时过期都不执行
- **算失败**：审批没点，对方那边多了一条
- **现在**：**实证成立（2026-11-22，`erp.cancel`）**。提交写动作得 HTTP 202 / `status=pending` / `approval_required`，此时独立 `erp.query` 回查单据仍 `docstatus=1`——未审批，对方一行没动。审批是**真闸**（`spec.RequiresApproval=true` 即挂起），不是早先以为的「`Approved=true` 桩直接放行」；审批人取登录用户（王工）。边界：审批人仍是操作者本人、非独立真人，「真人拒绝」状态未验；`erp.draft` 真跑被 Frappe 以 `MandatoryError: supplier, items` 拒绝（绑定只写 `remarks`，缺必填字段），故建单动作没有作用对象。S07 拒批后未 Resume 的缺口仍挂着。

## 3. 同 request_id 只有一条

- **查哪里**：对方系统按业务键查到的记录条数（ERPNext 为 `name`，Gitea 为 issue number）
- **算过**：只有一条，第二次返回首次结果
- **算失败**：两条以上——11-08 实测 Gitea 完全忽略 `Idempotency-Key`，同 payload 连发三次得三张单
- **现在**：**实证成立（2026-11-22，`PUR-ORD-2026-00002`）**。同一 request_id（`f1da53e8...`，由 userId + clientMessageId + actionKey + 参数确定性派生）连发两次 cancel：第一次挂起→审批→`docstatus=2`；第二次相同请求体返回 `replayed_from_idempotency`，审计里 execute 段**只有 1 个**，对方 `modified` 只变一次。证据来自对方状态+审计，不是我方绿灯。边界：Gitea 侧按业务键的读取口仍缺失。

## 4. 超时只查证不重放

- **查哪里**：超时之后，对方侧有没有第二次写
- **算过**：记「执行中」、发起状态查询、不重放；查不到转人工
- **算失败**：对方侧出现第二次写
- **现在**：**三层缺口都已修、判据全绿；真站点超时闭环仍未跑**。11-22 挖出并修掉三层：① frappe_mcp 把网络故障与拒绝都压成 `isError` 文本 → `ToolFailureClassifier` 按异常类型+关键字区分；② `McpActionExecutor` 无 Unknown 路径 → `Unavailable→Unknown`；③ **工具调用根本没有超时**（会无限等）→ `McpOptions.ToolCallTimeoutSeconds`（默认 30s，可配）+ `ToolCallTimeout.RunAsync` 严格区分内部超时与外部取消。共 20 条判据（含端到端：写 1 次 / 查证 1 次 / `verified_by_query` / 明确拒绝零查证 / 超时 vs 取消分流），两处负控变异自证。**真站点闭环仍未跑**：注入 sleep 的实验暴露 frappe_mcp 用同步 httpx + 同步 sleep 会堵死 asyncio 事件循环，查证被排队饿死——这是造出来的故障、不是产品真实链路，已清理。判定权仍在对方系统。

## 5. 审计五字段

- **查哪里**：任取一笔执行，五字段（意图 / 参数 / 审批人 / 结果 / 外部单号）是否齐全，且「在对方系统里变成什么」能回对方核对
- **算过**：字段齐全，最后一项与对方记录一致
- **算失败**：缺字段，或「变成什么」对不上
- **现在**：**写动作路径有实证（2026-11-22，`request_id=68a540b793932e63725a4ddeea77b8a0`）**。七条轨迹：schema / permission / business_rule / audit(written) / approval(pending→allow) / execute(succeeded)；`approver=王工` 出现在 approval 与 execute 两段，execute 带 `externalId=PUR-ORD-2026-00001`。「变成什么」独立回查确认：`docstatus=2` / `status=Cancelled` / `modified=2026-11-22 10:12:24`，与对方记录一致。11-20 只读那次（`f4e7faf9858fe41608ddf9b74bd42d03`）五条轨迹仍作对照。判定权在对方系统。

## 6. 换第二个体系，底座 diff 为空

- **查哪里**：`git diff src/Core/`，以及第二个体系自己的记录
- **算过**：第二体系跑通同一套运行时，底座 diff 为空，且对方一行没改
- **算失败**：底座出现业务名词 / 引用方向变了，或改了对方
- **现在**：**结构层实证成立，结果层未验（2026-11-22）**。只改环境变量 `Actions:ActionSet=GiteaActionSet` 切域，不改任何文件，`git diff src/Core/` 切前切后都为 0；能力目录真换了（`erp.query` → `spec_not_found`，`repo.query` → 被识别并打到 GiteaAdapter）。gitea.com 公开实例可达（版本/仓库匿名读 200），但 `GiteaOptions.IsConfigured` 要 Token 非空，环境里没有只读 token，真查证返回对方 `401 not_authenticated`。**缺一个 gitea.com 只读 token**，第六句作为「任何」的唯一证据仍是空的。
