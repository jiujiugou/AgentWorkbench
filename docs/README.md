## 2. 两条线，各自维护

| 线 | 现状文档 | 什么时候改 |
| --- | --- | --- |
| **底座**（`src/Core`） | `core/*.md`（部件文档：请求装配 / 终止与预算 / 状态与记忆） | 底座机制变了才改 |
| **应用**（`src/Domains` + `src/Host` + 企业应用层） | `AGENTS.md` 的域清单；`core/tools.md` 的「换域」节（`应用.md` 待补） | 换动作域 / 方向变就改 |
| **公共** | 正本 + 本页 + `运行期流程.md` | 判据或边界变了就改 |

> **AC-01-doc**：换动作域、或应用方向改变时，`core/runtime.md` 与 `core/tools.md` 的 **diff 必须为空**。
> 不为零就说明业务语义漏进了底座文档——与 AC-01「底座五层 diff 为空」是同一条判据在文档层的对应物。

分线维护的意义：方向变过三次以上，变的几乎都是**应用线**；底座线（端口、网关、工具环、上下文、不变量）基本继承。
分线之后转向一次只动一条线，不会再出现「全部文档一起过期、一起重写、最后一把清空」。

## 3. 三类寿命，处理方式不同

| 寿命 | 文件 | 转向时 |
| --- | --- | --- |
| **常驻**（每次会话读） | `AGENTS.md`、本页 | 只改几句定位、命令、禁区 |
| **现状**（当前有效） | `core/*.md`、正本 | **允许改**，同一次提交里改完；旧值交给 git，不堆历史 |
| **只追加**（过程） | `plans/` | **永不改旧段**；带日期，允许写「不知道」；做完归档不删 |

10-29 清空 21 份文档且未提交 git、不可恢复，是这仓最贵的一课。**旧文档不删**；要清先提交成回滚点。

## 4. 读的顺序

1. 正本 `docs/需求/产品目标与范围.md`（唯一正本；冲突时以它 + ADR 0013–0018 为准）
2. [运行期流程.md](运行期流程.md) + [前端界面契约.md](前端界面契约.md)（同一套 `Sxx` 的两个投影：
   系统内部怎么走 / 人眼前看到什么）
3. `core/*.md` 部件文档（请求装配 / 终止与预算 / 状态与记忆）——按你当前要动的那一格读
4. 代码 —— 与文档冲突时**以代码为准并回来修文档**，不替代码圆话
5. `AGENTS.md`（给 agent 的工作规则与实测命令，不是需求）

## 5. 状态位纪律

每份正式文档头部写**三要素**：适用侧 / 寿命 / 时间（现状类写「最后校准」，只追加类写「建立」）。
**状态位说假话比没有状态位更糟**：代码已落地却写 `draft`、方向已换却写「当前」，都比空白有害。
这条不是自觉，[门禁](#7-门禁查什么)会查。

## 6. 模块文档写法（**唯一一处定义**）

1. **短**：只写地图与跨模块信息，不复述模块 README。
2. **路由优先**：开头给「先读哪三个」，避免 agent 全仓 grep。
3. **只收代码推不出的**：坑、非显然约定、已定不许争的决策；目录结构、类名清单、行号、完成度数字一律不写。
4. **每条坑给「去哪核」的指针**，不复制代码注释——注释才是源头，抄一份就多一份会烂的事实源。
5. **带状态位与日期**，允许写「我不知道 / 未复测」；改代码时同一次改这里。

> **只在这里定义一次。** `core/` 下各文件不复述这套规矩，只遵守；`AGENTS.md` 只放三条硬规矩 + 指向本节。

## 7. 门禁查什么

`DocsHygieneTests`（测试项目 `Docs/`）三条，改文档后跑一次测试即可：

| 编号 | 查什么 | 为什么 |
| --- | --- | --- |
| **D1 状态位** | 正式文档头部 15 行内必须有「适用侧」「寿命」「最后校准 / 建立」 | 状态位说假话比空白更糟 |
| **D2 链接** | 文档内相对 `*.md` 链接的目标必须存在 | 指向已删文件=把人带沟里；工作区没有但 HEAD 有的，写纯文本 |
| **D3 不重定义** | `core/*.md` 不得出现「本文件的写法」这类定义 | 同一套规矩只写一处，否则两份会分叉 |

排除：`adr/`（自带生命周期，写完不改）、`plans/`（自带模板）、根目录 `产品目标与范围.md`（未跟踪的旧副本）。

