## 判据

**「需要？」判的是这个功能要不要在产品里生效，不是「要不要写代码」。** 拿掉它，六句成功判据里哪一句会破；或者更底一层，单次工具调用链还成不成立。答不出 → 不需要。

**状态列**：已用 = 本仓显式用；默认 = 框架默认生效、未改；未用 = 框架有但没接；自写 = 项目另写了一套。

## 结论

1. **28 行里真正要动手的只有 3 行**：11、16（H1 / H2，已补实现）、19（H3，已补复验测试）。这三项在 H 组展开，**H 不计入 28 行**；**本方向待办已清零**，三条测试全绿。
2. **H 组只有 3 条**：H1 / H2 是框架不给、本仓补的两格实现（2026-11-12 落地）；H3 是框架已有机制、本仓替换执行委托后的复验（只写测试，不新写实现）。H1/H2 均做过负控变异：分别关掉实现，对应测试按原红因变红。已补完的那半段（白名单、审批三态、结果否决、环内控制、留痕）不属「需要增补」，见同目录 `README.md` 第二节。
3. **其余 13 行「需要」全部由框架默认或已装配覆盖**，不写代码也不写测试 —— 与「框架给的机制不重写、不测试」是同一句话。
4. **12 行「不需要」不用接**，也不用因为清单全就觉得缺。
5. **第 20 行口径**：上一轮曾按「框架有、没接上、值不值得顺手定」列进「值得动」，本表按「产品需不需要」判成「不需要」。两把尺子不同，不是改结论。
6. **第 26 行的条件**：如果 M3 的「审批挂起与恢复」要跨进程 / 跨重启，它会变成「需要」，框架挂起恢复正是现成形态；但那属于动作链方向，不在这张 ④ 的表里判。
