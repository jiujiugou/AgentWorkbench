## 一、框架给的，不重写也不测试

框架（严格说是 `Microsoft.Extensions.AI`，不是 MAF 本体）已经提供：

- 把一段代码登记成模型看得见的能力：名字、说明、参数结构；随每次请求把当前清单带上。
- 模型给回来的 JSON 按声明结构转成参数；执行完把返回值变成模型能读的一条消息。
- 工具报错不炸整轮，把失败回填给模型，让它自己改参数或换路。
- 本地函数、MCP 工具、远程托管工具走同一套登记与回填，模型分不出差别。

**为什么分清楚**：这些是机制，按「不造轮子」一律不重写。框架保证的是默认装法成立，不保证我们替换过执行委托、夹过观察层之后还成立——改装配后要复验，而不是补写一套实现。

## 二、我们自己补的后半段

框架在执行前只留了一个「可以插入判断」的位置，判断内容全在外面。本模块填的是：

- **谁能被看到**：白名单裁剪与匹配语法（精确名 / 尾部通配 / 单星号 / 空规则）；重名只留一个。
- **执行前要不要问人**：自动放行 / 直接拒 / 挂起问人三态；拿不到批准（超时、无审批者、通道故障）一律拒绝，拒绝作为结构化载荷回填，不与工具失败混在一起。
- **结果能不能进下一轮**：依据不足时本轮直接收口，但那份结果仍留在轨迹里，事后能查「它看到了什么才拒的」。
- **环内怎么控**：同工具同参数连着调、token 用量到顶时，在真正执行前停掉，用干净收口而不是抛异常（异常会被框架当成工具失败喂回模型）。
- **留什么痕**：每轮第几次、工具名、参数、结果、失败原因；框架对「模型点了清单外的工具」只回填错误、不留痕，所以单独补了一层观察把它记下来。

判定内容归我们，机制归框架 —— 这是这一格唯一的划分标准。

### 曾列在「还没处理」、其实已经解决

- 工具抛异常分不清「炸了」和「返回空」→ 轨迹已记异常类型与消息，并与拒绝区分。
- 工具卡死、取消不生效 → 取消能穿透到执行体（旧文档记录已实测，本轮未复测）。
- 危险工具误调用 → 审批闸门 + fail-closed 已落地。旧表格把这三条与正文「已挡住」并列，自相矛盾，故划掉。

### 不属于本方向，别在这儿等

- 同名工具静默去重、不报警 —— 仍是待裁决，但属工具注册，不是框架之外要补的后半格。
- 模型看不到真实失败原因 —— 待定取舍（细节回模型 vs 结构化错误回传）；现在异常原样交给框架决定。
- 重跑产生两次副作用 —— 动作判重方向，已由动作网关的 `requestId` 去重表承担，不是本模块该补的。
- 并发多任务、沙箱、自动重试与降级 —— 会话 / 编排 / 执行环境方向，尚未定。
- 「结果或参数特别大」这条拆两半：轨迹截断已做；给模型的上界就是本方向第 1 条。
