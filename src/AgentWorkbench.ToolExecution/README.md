# 工具调用模块

这个模块只干一件事：**把模型说的「我要调某个工具」变成真实代码真的被执行了一次，
并且留下事后能回放的记录**。

它不做执行循环本身。执行函数、把结果回填给模型、循环往复直到模型给出答案 —— 这套东西框架里已经有了，
底座不重写一遍。这个模块只管环外面的三件事：**工具从哪来、哪些工具能被模型看到、一次调用留下什么痕迹**。

---

## 一、现在已经具备的能力

### 工具怎么接进来

- 一个工具一个类。新增工具 = 加一个类 + 注册一行，老代码一行不用改。
- 工具的说明书（叫什么、干什么用、要哪些参数）跟着参数签名自动生成，不用手写。
- 工具按能力归属：谁的能力谁实现。看时间、算数这类通用工具放在工具模块；查知识库的工具放在知识库模块；
  看文档的工具放在文档模块。工具平台不替别人做数据访问。

### 哪些工具能被模型看到

- 白名单说了算。不在白名单里的工具，模型既看不到也调不动；对话和编排两条入口共用同一份名单，不会两边对不上。
- 重名的工具只暴露一个。目前是静默保留第一个 —— 真冲突了不报警，这是要改的地方。

### 一次调用怎么落地

- 模型说要调工具 → 真的调用 → 结果回填 → 再问模型，循环到出答案或者触顶。
- 一次请求最多循环几轮（默认 6 轮）由执行控制决定。
- 每次调用**发出之前**先问一句执行控制守卫（`IAgentRunGuard.InspectToolCall`）：判「同工具 + 同参数」连续重复、
  以及本 run 的 token 用量。要停就不执行这次调用，把原因记进轨迹、让框架干净收口
  （`FunctionInvocationContext.Terminate`，不是抛异常 —— 抛异常会被框架当成「工具失败」喂回模型）。
- 这件事只能在这一层做：重复指纹和用量增量只有到环内、调用发出时才有。
- 每一次真实调用都留痕：第几轮、调的什么工具、传的什么参数、拿到什么结果、失败的话为什么失败。
- 留痕里的参数文本按参数名排过序（键序稳定），所以它同时就是重复调用判定用的指纹。

### 参数这一关

- 按名字把模型给的参数绑到工具上；少了必填参数或类型对不上，当场报错，这个错误同样记进痕迹。
  （实测过：模型漏传参数，轨迹里能看到「缺少必填参数」。）
- 参数留痕是「转成文本」后存的，会丢类型和嵌套结构：存下来是 {"failTimes":"0"}，不是 {"failTimes":0}。
- 取值范围、路径合法这类业务校验由每个工具自己写，底座不替它兜底。

### 权限与审批

两层正交，各管各的，不合并：

- **能力白名单**（`IToolPolicy`，目录层）：决定「有哪些工具」——名单外的模型根本看不到。
- **审批级别**（`IToolApprovalPolicy`，执行层）：决定可见的工具「执行前要不要先问人」。
  每次调用**发出之后、真正执行之前**过闸门：`Auto` 直行、`Deny` 拒绝、`Ask` 挂起等人工确认。
- **fail-closed**：`Ask` 拿不到批准（超时 / 未提供审批者 / 通道故障）一律按拒绝处理 ——
  等不到答复不等于默认同意。审批者由调用方按 run 提供（`IToolApprover`），本模块只依赖契约、不依赖通道。
- 被拒的工具**绝不执行**；轨迹里记结构化拒绝载荷 + 归类码（`approval_policy_denied` /
  `approval_user_denied` / `approval_unavailable`），回放时「被拒」与「工具失败」分得开。
- 被拒不阻断整轮：模型看到「被拒」，可以换路或收口 —— 而不是反复重试同一个被拒调用。

还差：单次任务再收窄到子集；执行沙箱（能碰哪些路径、多久超时、输出多大）。

### 超时与取消

- 整轮跑太久会停（默认 30 秒）。
- 取消能真的打断工具正在做的事，而不是等它跑完再由外层判超时。这一点已经用探针实测过。
- 还差：单个工具自己的时间上限；以及工具收到取消也不理（第三方阻塞调用）时怎么强制隔离。

### 失败怎么算

- 工具炸了，痕迹里记下异常类型和消息，跟「返回了空」区分得开。
- 一次失败不致命：记一笔，让模型看到失败后继续走；**连续失败到上限（框架默认 3 次）整轮算失败**，
  落库状态是 failed，每一步都带着失败原因。端到端已经实测过。
- 归类码已落地：本模块如实记下每一步的异常，冒泡出环的失败由编排层归类成 `tool_error`（不是 `unhandled_error`），
  连同终态落进 `agent_runs.error_code`（见 `AgentLoop` / `AgentHarness` 的 README）。
- 还差：工具侧自动重试；降级（重试 → 换等价工具 → 给占位结果 → 终止）；幂等键（重跑一遍不产生第二次副作用）。

### 结果怎么处理

- 存痕迹时结果超长就截断（当前上限 400 字符），避免轨迹表被大结果撑爆。
- 还差：图片、结构化结果原样回传；超大结果存到外部只回一个引用。

### 现在有哪些工具

- 全是只读、无副作用的：看当前时间、四则运算、查知识库、列文档。
- 文件、数据库、网络请求、执行命令这类工具一个都没有。它们属于各自模块，但底座得先把规矩定下来，
  否则每个模块各写一套：**只读优先；要写就得带幂等键、要审批、要有沙箱**（能碰哪些路径、多久超时、输出多大）。
  审批那一格已经有了（`Harness:Approval` 里把工具提升到 `Ask` / `Deny` 即可）；幂等键与沙箱还没有。

## 二、还没处理的问题（接下来要干的活）

| 问题 | 不处理的后果 | 现在什么状态 | 做好的标准 |
| --- | --- | --- | --- |
| 模型调一个不存在的工具 | 整轮报 500 | 已挡住：白名单外不可见 | 未知工具名得到一条错误结果，模型还能继续走 |
| 两个地方注册了同名工具 | 静默取第一个，真冲突被掩盖 | 只去重，不报警 | 启动时就告警或直接失败 |
| 漏传参数、参数类型不对 | 工具内部崩，或执行了错东西 | 已挡住：失败原因进痕迹，整轮不崩 | 和工具自己的业务异常能区分开 |
| 工具抛异常 | 事后分不清「炸了」还是「返回空」 | 已挡住：每步带失败原因 | 连续失败到上限 → 整轮 failed |
| 工具卡死 | 整轮挂住，取消不生效 | 已挡住：取消能穿透进去 | 取消后立刻返回，实测远快于工具声明的耗时 |
| 模型看不到真实失败原因 | 模型没法自我修正，只会重复同样的错调用 | 只回一句泛化的错误文本，真实原因只在服务端 | 明确取舍：是把细节回给模型，还是自己搞结构化错误回传 |
| 恢复后重跑，副作用做两遍 | 重复写入 | 没做 | 幂等键命中时第二次调用不产生副作用 |
| 结果或参数特别大 | 撑爆上下文、撑爆轨迹表 | 只做了截断 | 有上限、有外部化引用，回放时还能还原 |
| 并发跑多个任务 | 工具状态串、轨迹张冠李戴 | 没做 | 并发任务各自轨迹互不干扰，共享状态有明确归属 |
| 危险工具 | 一次误调用就是真实破坏 | 已挡住：审批闸门（Auto/Ask/Deny）+ fail-closed | 没批准就不执行；超时/无应答也拒绝 |

## 三、加一个工具要做三件事

1. **写一个工具**：一个工具一个类。参数名字、类型、说明写清楚 —— 这些就是给模型看的说明书，写不清模型就调不对。
2. **注册**：加到它所属模块的注册里。通用工具进工具模块，知识库工具进知识库模块，文档工具进文档模块。
3. **放行**：把工具名加进白名单，否则模型看不到它。

放哪个模块的判断标准很简单：**这个工具依赖谁的能力，就住在谁那里**。

---

## 四、红线

1. **不重写框架已有的东西**。执行循环、回填结果是框架的，这里只加策略和痕迹。动手前先问：框架能不能配出来？能就别写。
2. **零垂直业务语义**。底座代码里不出现合同、工业、仓储、单证这类词。
3. **依赖单向**：工具调用依赖安全策略和公共部分，不许反过来。
4. **模型生成的一切都不可信**。工具名、参数、调用次数都当外部输入校验，绝不直接拼成命令或路径。
5. 工具需要落库时，按既有的数据库迁移规矩来。

---

## 五、怎么算验收通过

判定型的用例必须**正例能绿、负控能红**；能靠脚本判定的，禁止用 AI 来判。

目前覆盖到的（都在测试项目里）：

- 白名单裁剪：名单外的工具不暴露；空白名单等于什么都不暴露。
- 内置工具的名字和默认白名单对得上。
- 工具抛异常 → 痕迹里留下失败原因；工具成功 → 不留。
- 连续失败到上限 → 整轮失败且每一步都带原因；单次失败不阻断；取消能穿透进工具内部。
  （负控只拧一个故障旋钮，结果必须跟着变。）
- 环内提前终止：连续同工具同参数 → 停在阈值（`loop_detected`）；**负控**：关掉检测 → 同一场景跑满 `MaxIterations`。
  （见 `tests/AgentWorkbench.UnitTests/Harness/AgentHarnessExecutionControlTests.cs`。）
- 审批闸门五行（`tests/AgentWorkbench.UnitTests/Tools/ToolApprovalGateTests.cs`）：Auto 执行 / Deny 不执行 /
  Ask+批准执行 / Ask+拒绝不执行 / Ask+无应答超时按拒绝。**负控**：每条「未执行」断言就是它自己 ——
  闸门失效则探针计数变 1，用例当场红。策略层另见 `ToolApprovalPolicyTests`（含配置热重载负控）。
- 审批真的接在 harness 那条路上：请求里的 `IToolApprover` 走到管道、拒绝归类码落进**账本**
  （`tests/AgentWorkbench.Evaluation.AgentTask/HarnessApproval/`）—— 防「代码写好了没人调用」。
- 端到端到落库那层：连续失败落成 failed 且每步带原因；健康工具落成成功且没有失败原因。

专门用来「故意搞坏」的探针工具**刻意放在测试项目里，不进生产工具目录** ——
生产工具里不该出现一个会炸的工具。
