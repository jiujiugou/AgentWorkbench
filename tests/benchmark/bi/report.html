结论

这条评测链可信。 把标准答案当预测喂进去得满分 1.0000； 把恒空查询喂进去、剔除空结果后得零分 0.0000。 正例绿、负控红 —— 它不是恒绿的自欺工具。

怎么复算

cd tests/benchmark/bi

数据集只给 db_schema.json + db_content.json，不含数据库文件，必须先建库。 官方评测脚本没有公开直链（千言是线上提交制），所以评测为自建，指标采用学术界通用的 Execution Accuracy（执行结果集一致性）。

发现 1：gold SQL 是 MySQL 方言，裸跑 SQLite 失败率 90%

这是本轮最大的坑。DuSQL 的标准答案按 MySQL 书写，直接在 SQLite 上执行，2482 条里 只有约 10% 能跑通。写了 sql_dialect.py 做纯语法层适配（对 gold 与 pred 施加同一套规则， 不改变二者可比性）：

适配项影响条数示例
TIME_NOW 自定义函数100where TIME_NOW - 成立时间 != 18
复合查询不允许括号包裹72( select ... ) union ( select ... )
标识符需引号22T2.2018年营业额、GDP总计(亿)
起别名后仍用原表名限定列大量from 比赛记录 as T1 ... on 比赛记录.球员id
limit 缺空格（数据集笔误）2limit3

修完失败率 90% → 1.65%。

发现 2：28.2% 的 gold 查询返回空，恒空 SQL 能白拿 28 分

负控第一次跑出 0.2819，远超阈值。根因不是 bug：688 条 gold 查询本身结果就是空的， 而 Execution Accuracy 对「什么都查不出来」根本不设防 —— 一条恒空 SQL 能白拿 28 分。 这是评测设计层面的真缺陷。

处理方式：报告同时给出 execution_accuracy_nonempty（只在 gold 非空的样本上计算）。 该口径下负控为 0.0000，正确变红。没有改数据让它变绿。

已知边界

  • 指标是 Execution Accuracy（执行结果一致），不是 SQL 字符串匹配 —— 不同写法但结果相同算对。
  • 201 个库中只有 17 个有标注问题，dev 集 2482 条全部落在这 17 个库上。
  • 本轮只做了 oracle 与负控，还没有跑真实模型的预测（需要 API key）。
